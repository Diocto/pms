# feature 스펙 작성

구현을 시작하기 전에 스펙을 쓴다. 스펙 없이 코드를 쓰지 않는다.

## 왜 스펙을 먼저 쓰는가

이 프로젝트에서 비싼 실수는 코드 오타가 아니라 **동시성 설계를 잘못 잡는 것**이다. 그건 다 만든 뒤에 발견하면 갈아엎어야 한다. 스펙 단계에서 경합 지점을 그려보면 30분에 잡을 수 있는 문제다.

## 절차

### 1. 기존 문서를 읽는다

- `docs/spec/00-problem-and-scope.md` (문제 정의와 전체 범위)
- 이미 승인된 다른 feature 스펙 (겹치는 도메인이 있는지)
- `docs/architecture/ddd.md`, `docs/architecture/coding-rules.md`
- `docs/decisions/INDEX.md` (이미 내려진 결정을 뒤집지 않기 위해)

### 2. 소유 범위를 먼저 정한다

`docs/architecture/parallel-work.md`를 읽고 아래를 정한다.

- 소유 패키지
- 읽기만 하는 패키지
- Flyway 번호 대역
- 수정이 필요한 공유 파일

**다른 feature가 소유한 도메인 패키지를 수정해야 한다면 여기서 멈추고 관리자에게 알린다.** 스펙을 다 쓴 뒤에 발견하면 낭비다.

### 3. 도메인 모델을 그린다

애그리거트 경계를 먼저 잡는다. 판단 기준은 **함께 지켜져야 하는 불변식**이다. 기능 단위로 나누지 않는다.

애그리거트마다 불변식을 문장으로 적는다. "잔여 재고는 음수가 될 수 없다"처럼 명확해야 한다. 불변식을 못 쓰겠으면 경계가 잘못 잡힌 것이다.

상태가 있는 애그리거트는 전이 표를 채운다. **표의 모든 칸을 채운다.** 금지된 조합도 금지라고 명시한다. 빈칸을 남기면 구현자가 알아서 판단하게 되고, 그게 버그가 된다.

### 4. 유스케이스별로 도메인 모델의 변화를 쓴다

이 부분을 성의 없이 쓰면 스펙의 의미가 없다.

"예약을 생성한다"가 아니라 이렇게 쓴다.

| 순서 | 대상 | 변화 |
|---|---|---|
| 1 | RoomDailyInventory (3일치 행) | remaining이 각각 1 감소 |
| 2 | Reservation | PENDING 상태로 새로 생성 |
| 3 | IdempotencyRecord | 결과와 함께 저장 |

**무엇이 새로 생기고, 무엇의 어떤 필드가 바뀌고, 무엇이 사라지는지**가 다 나와야 한다.

### 5. 경합 지점을 찾는다

각 유스케이스에 대해 물어본다. **두 요청이 정확히 같은 시각에 이걸 실행하면 무슨 일이 생기는가.**

찾는 방법은 단순하다. 읽고 판단하고 쓰는 패턴을 찾는다. 그 사이에 다른 요청이 끼어들면 무엇이 깨지는지 그려본다.

경합 지점마다 방어 수단을 정한다. `coding-rules.md`의 동시성 제어 절에 있는 표를 기준으로 고른다. **가장 먼저 조건부 UPDATE로 풀 수 있는지 검토한다.** 락은 그다음이다.

방어를 3층으로 설계하고, **1차가 뚫렸을 때 2차가 막는다는 걸 어떻게 증명할지**까지 쓴다.

### 6. DB를 설계한다

테이블, 컬럼, 타입, 제약을 쓴다.

**불변식을 지키는 제약을 반드시 하나 이상 둔다.** 애플리케이션 로직이 전부 뚫려도 DB가 막는 방어선이다.

인덱스마다 어떤 쿼리를 위한 것인지 쓴다. 근거 없는 인덱스는 넣지 않는다.

### 7. 멱등성을 정한다

어떤 연산이 멱등해야 하는지, 키 형식은 무엇인지, 재요청에 뭘 돌려줄지 정한다.

**Redis가 죽었을 때도 중복이 막히는지** 확인한다. 안 막히면 DB 제약을 추가한다.

### 8. 테스트 계획을 쓴다

동시성 테스트 시나리오는 구체적으로 쓴다. 스레드 수, 재고 수, 기대 결과를 숫자로 적는다.

### 9. 결정 검토란을 채운다

스펙을 쓰면서 **작성자가 내린 결정을 전부** 검토란(D1, D2, ...)에 모은다. 범위를 자른 것, 모델링 방식을 고른 것, 유스케이스를 묶은 것이 다 결정이다. 결정마다 이유, 트레이드오프(포기한 것), 대안, 확인 질문을 쓴다.

본문에만 결정을 묻어두면 관리자가 무엇을 검토해야 하는지 안 보인다. **관리자의 동의는 문서 전체가 아니라 D 항목 단위로 받는다.**

### 10. 열린 질문을 비운다

결정하지 못한 것이 남아 있으면 승인을 요청하지 않는다. 관리자에게 물어서 결정하고 채운다.

## 산출물

`docs/spec/F00-<이름>.md`에 `docs/spec/TEMPLATE.md` 형식으로 쓴다.

## 흔한 실패

| 증상 | 무엇이 문제인가 |
|---|---|
| 도메인 모델 절이 클래스 목록뿐 | 불변식이 없다. 경계 근거가 없다 |
| 유스케이스가 "~를 처리한다" 한 줄 | 모델 변화가 안 보인다. 구현자가 알아서 판단하게 된다 |
| 동시성 절에 "락을 건다"만 있음 | 어떤 락을 어느 행에 어떤 순서로 거는지 없다 |
| 전이 표에 빈칸 | 금지인지 미정인지 알 수 없다 |
| DB 제약이 PK뿐 | 최후 방어선이 없다 |
