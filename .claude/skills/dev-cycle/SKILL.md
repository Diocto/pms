# 개발 사이클

승인된 스펙 하나를 구현이 끝날 때까지 돈다.

**시작하면 알아서 진행한다.** 매 단계 승인을 받지 않고 진행 상황을 보고하지도 않는다. 스펙과 Task 목록이 무엇을 만들지 이미 정해뒀으니 그대로 간다. 다음 승인 게이트는 사이클이 끝난 뒤다.

**결정이 필요한 것이 나오면 되돌리는 비용으로 가른다.** 나중에 고쳐도 코드 몇 줄이면 **정하고 진행하되 스펙의 결정 검토란에 기록한다.** 스키마나 계약이 바뀌어야 하면 **관리자에게 바로 묻는다.** 둘 다 PM을 거치지 않는다.

**다른 세션의 코드가 궁금하면 그 세션에 직접 묻는다.** 이미 병합됐거나 푸시된 것만 묻고, 답은 `git show`로 실물 확인한다.

```
TDD 구현 → 테스트 실행 → 리뷰어 3명 병렬 → 피드백 반영 → (심각·중요가 남았으면 다시)
```

## 시작 전 확인

- [ ] 스펙이 **승인되었는가.** 승인 전이면 여기서 멈춘다
- [ ] 스펙의 열린 질문이 비어 있는가
- [ ] **`docs/tasks/F00.md`를 만들었는가** (아래 0단계)
- [ ] `docs/architecture/coding-rules.md`를 읽었는가
- [ ] `docs/architecture/tdd.md`를 읽었는가
- [ ] 내 worktree에서 작업하고 있는가
- [ ] Docker가 떠 있는가 (`docker compose up -d`)

## 0단계: Task 목록을 먼저 만든다

**코드를 쓰기 전에 `docs/tasks/F00.md`를 만든다.** 형식은 `docs/tasks/TEMPLATE.md`다.

### 왜 먼저인가

**스펙은 "무엇을 만드는가"이고 Task 목록은 "어떤 순서로 끝내는가"다.** 둘은 다른 문서다.

먼저 만드는 이유가 셋이다.

**끝을 정의하게 된다.** "재고 도메인 구현"은 언제 끝났는지 알 수 없다. 쪼개면서 **완료 기준을 쓰지 못하는 덩어리가 드러나고**, 그건 아직 설계가 덜 됐다는 신호다. 코드를 쓰기 시작한 뒤에 알면 늦다.

**순서의 이유를 묻게 된다.** 앞의 것이 뒤의 것의 전제인지, 아니면 그냥 나열인지가 갈린다. 전제라면 그 순서를 어겨선 안 되고, 아니라면 급한 것부터 해도 된다.

**중간에 잘릴 때 무엇이 남는지 알 수 있다.** 이 프로젝트는 절단 순서가 정해져 있다. Task로 쪼개져 있으면 **"여기까지는 쓸 수 있다"**를 말할 수 있지만, 한 덩어리면 잘리는 순간 전부 사라진다.

### 쪼개는 기준

| 좋은 Task | 나쁜 Task |
|---|---|
| 재고 조건부 UPDATE와 그 동시성 테스트 | 재고 도메인 구현 |
| 전이 표 49칸 전수 테스트 통과 | 상태머신 만들기 |
| 락 어댑터 + 데드락 테스트 K8 | 동시성 처리 |

**완료 기준을 관찰 가능한 것으로 쓴다.** "잘 동작한다"가 아니라 **"T27a~T27d가 초록"**처럼 확인할 수 있는 문장이다.

**하나가 반나절을 넘지 않게 한다.** 넘으면 그 안에서 무엇이 먼저 끝나는지 다시 묻는다.

### 상태를 갱신한다

상태는 넷뿐이다 — **대기 · 진행 · 완료 · 보류.**

**`진행`은 한 번에 하나만 둔다.** 둘이면 둘 다 안 끝나고 있는 것이다.

**상태 변경을 커밋에 함께 담는다.** 별도 커밋으로 미루면 갱신을 잊는다. 현황판(`tools/dashboard.py`)이 이 파일을 읽어 **지금 어느 Task를 하고 있는지** 보여주므로, 낡은 상태는 곧 틀린 보고다.

### 리뷰 단위와 맞춘다

**Task 여러 개를 묶어 한 리뷰 회차를 만든다.** 회차마다 리뷰어 3명을 부른다.

한 번에 전부 만들고 한 번 리뷰받으면 **1회차에서 지적받을 것이 2~4회차에 그대로 복제된 뒤에 발견된다.** 회차 경계를 Task 목록에 표시해두면 언제 멈춰 리뷰를 받을지가 분명해진다.

## 1단계: TDD 구현

### 순서를 지킨다

실패하는 테스트를 먼저 쓴다. **실패를 눈으로 확인한다.** 확인 없이 넘어가면 그 테스트는 아무것도 검증하지 않을 수 있다.

### 안쪽부터 만든다

도메인부터 시작해 바깥으로 나간다. 컨트롤러부터 만들면 도메인이 API 모양에 끌려간다.

```
1. VO와 상태머신 (순수 단위 테스트)
2. 애그리거트와 불변식 (순수 단위 테스트)
3. 유스케이스 (포트를 가짜 구현으로)
4. 영속성 어댑터와 마이그레이션 (Testcontainers)
5. 동시성 (Testcontainers)
6. 컨트롤러 (Testcontainers)
```

### 상태머신은 전수 검증한다

전이 표의 모든 `(상태, 이벤트)` 조합을 순회하는 테스트를 쓴다. 허용된 것은 전이되고 금지된 것은 예외가 나야 한다. **스펙의 표와 코드의 표가 같은지도 확인한다.**

### 동시성 코드에는 반드시 동시성 테스트를 붙인다

`docs/architecture/tdd.md`의 동시성 테스트 절을 따른다. `threading.Barrier`로 동시에 출발시키고, 결과 카운트가 아니라 **최종 DB 상태**를 검증한다.

**1차 방어선을 끈 테스트도 쓴다.** 분산락 없이도 불변식이 지켜지는지 확인하는 테스트다. 이게 없으면 Redis 장애 시 데이터가 깨진다.

### 커밋

작은 단위로 자주 커밋한다. 커밋 메시지는 한국어로 쓴다.

## 2단계: 테스트 실행

전체를 돌린다. 자기 feature 것만 돌리지 않는다.

```bash
docker compose up -d    # Testcontainers가 쓸 Docker가 떠 있어야 한다
pytest
```

**결과를 그대로 기록한다.** 통과 개수와 실패 내용을 다음 단계에서 쓴다.

실패가 있으면 리뷰로 넘어가지 않는다. 고치고 다시 돌린다.

## 3단계: 리뷰어 3명 병렬 호출

**세 명을 한 번에 호출한다.** 한 메시지에서 Agent 툴을 세 번 부른다. 순차로 부르면 시간이 세 배로 든다.

| 리뷰어 | 관점 |
|---|---|
| `concurrency-reviewer` | 동시성 제어, 멱등성, 트랜잭션 경계 |
| `domain-reviewer` | 도메인 모델, 상태머신, 유스케이스 시퀀스 |
| `architecture-reviewer` | 레이어 구조, DB 설계, 코딩 규칙 |

각 리뷰어에게 아래를 전달한다.

- feature 번호와 스펙 파일 경로
- 리뷰 대상 커밋 범위 또는 변경 파일 목록
- 테스트 실행 결과
- 이전 라운드가 있었다면 그 결과와 조치 내용

리뷰 결과를 `docs/reviews/F00-round<N>.md`에 `docs/reviews/TEMPLATE.md` 형식으로 정리한다.

### 리뷰어가 무엇을 봤는지 확인한다

**"지적 없음"을 그대로 받지 않는다.** 리뷰어가 파일을 하나도 못 읽었을 때와 정말 깨끗할 때의 출력이 같을 수 있다. 경로가 틀렸거나, 검색 명령이 에러로 죽었거나, 아직 없는 디렉터리를 봤을 수 있다.

리뷰 결과에 **몇 개 파일을 봤는지**가 없으면 되묻는다. 모집단이 0인 검사는 통과가 아니라 **검사 안 된 것**이다.

이건 이 프로젝트가 잡으려는 실패 유형 그 자체다 — **통과했는데 아무것도 증명하지 못한 것.** 리뷰가 그 함정에 빠지면 그 뒤의 모든 초록이 무의미해진다.

## 4단계: 피드백 반영

### 판단부터 한다

지적을 받았다고 무조건 고치지 않는다. **틀린 지적이면 반박한다.** 리뷰 문서의 반박 절에 근거를 남긴다. 조용히 무시하는 것만 금지다.

리뷰어는 코드만 보고 판단한다. 스펙에 이미 근거가 있는 결정을 "문제"로 지적할 수 있다. 그럴 땐 스펙을 인용해 반박한다.

### 고칠 때도 TDD로

지적받은 문제를 **재현하는 테스트를 먼저 쓴다.** 테스트 없이 고치면 같은 문제가 다시 생겨도 모른다.

### 다시 돌지 말지 판단한다

| 결과 | 조치 |
|---|---|
| 심각이 하나라도 있음 | 반드시 다시 돈다 |
| 중요가 있음 | 고치고 다시 돈다. 미룬다면 이유를 문서에 남긴다 |
| 제안만 있음 | 반영하거나 미룬다. 다시 돌 필요 없다 |
| 지적 없음 | 다음 단계로 |

**같은 지적이 두 라운드 연속 나오면 멈추고 관리자에게 보고한다.** 접근 자체가 잘못됐을 수 있다.

## 5단계: 완료 판정

아래를 모두 만족하면 사이클을 끝낸다.

- [ ] 전체 테스트 통과
- [ ] 리뷰 심각 0건
- [ ] 중요 지적이 모두 처리되었거나 미룬 이유가 문서에 있음
- [ ] 스펙의 모든 유스케이스가 구현됨
- [ ] 스펙의 전이 표와 코드의 전이 테이블이 일치
- [ ] 동시성 테스트가 있고 통과함
- [ ] 1차 방어선을 끈 테스트가 있고 통과함
- [ ] 커밋이 정리되어 있음

## 다음 단계

`approval-report` 스킬로 개발 완료 승인 보고서를 만든다.

개발 중 내린 결정이 있으면 `decision-log`로 ADR을 남긴다.

## 금지

- 스펙 승인 전에 코드를 쓰는 것
- 테스트 없이 구현하는 것
- 동시성 코드에 동시성 테스트 없이 리뷰로 넘어가는 것
- 리뷰 지적을 근거 없이 무시하는 것
- 리뷰어 셋 중 일부만 부르는 것
- 소유하지 않은 도메인 패키지를 수정하는 것
