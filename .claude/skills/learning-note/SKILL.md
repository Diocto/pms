# 학습 노트

개발하면서 나온 개념을 나중에 읽으려고 모아둔다. **이 프로젝트를 몰라도 읽히게** 쓴다. 다음 프로젝트에서 다시 찾아볼 수 있어야 한다.

의사결정 이력과 다른 물건이다.

| | 의사결정 이력 (ADR) | 학습 노트 |
|---|---|---|
| 묻는 것 | 이 과제에서 왜 MySQL을 골랐나 | 갭락이 무엇이고 언제 걸리나 |
| 수명 | 프로젝트와 함께 | 계속 쓰인다 |
| 제출 | 대상 | 대상 아님 |

## 두 가지 모드

### 제목 쌓기 (개발 중 기본)

개발 중에는 흐름을 끊지 않는다. 새 개념이 나오면 `docs/learning/INDEX.md`의 대기 목록에 **한 줄만 추가한다.**

```markdown
- [ ] InnoDB 갭락과 넥스트키 락 — 재고 행 잠글 때 나온 개념
```

제목과 어떤 맥락에서 나왔는지만 쓴다. 30초를 넘기지 않는다.

**언제 쌓는가**

- 처음 보는 개념이 나왔을 때
- 알고는 있었지만 정확히 설명은 못 하겠는 개념이 나왔을 때
- 예상과 다르게 동작해서 알아본 것
- 리뷰어가 지적한 개념

### 본문 작성 (요청 시)

관리자가 요청하거나 feature가 끝났을 때 본문을 쓴다.

`docs/learning/<제목>.md`에 `docs/learning/TEMPLATE.md` 형식으로 쓴다.

작성 후 INDEX의 대기 목록에서 지우고 작성된 노트 표에 추가한다.

## 본문을 쓸 때

**한 줄 정의부터 쓴다.** 한 문장으로 설명하지 못하면 아직 이해한 게 아니다. 그 상태에서 긴 글을 쓰면 자기도 모르게 남의 설명을 옮기게 된다.

**해결하려는 문제부터 쓴다.** "낙관락은 버전 컬럼을 두고..."로 시작하지 않는다. "여러 요청이 같은 행을 고칠 때 나중 것이 앞의 것을 덮어쓰는 문제가 있다"로 시작한다.

**코드 예시는 최소로 만든다.** 프로젝트 코드를 그대로 붙이지 않는다. 개념만 남긴 짧은 형태로 다시 쓴다. 프로젝트 맥락이 섞이면 나중에 다른 데서 못 쓴다.

**틀리게 알고 있던 것을 쓴다.** 이게 가장 값진 부분이다. "나는 이렇게 알고 있었는데 실제로는 이랬다"를 남긴다.

**언제 쓰지 않는지도 쓴다.** 적용 조건을 모르면 아는 게 아니다.

## 다루면 좋은 주제

이 프로젝트에서 나올 만한 것들이다. 참고용이고 여기 없는 것도 쌓는다.

- 트랜잭션 격리 수준과 각 수준에서 생기는 현상
- InnoDB 락 종류 (레코드락, 갭락, 넥스트키락)와 걸리는 조건
- 비관락과 낙관락의 선택 기준
- 분산락이 안전하려면 무엇이 필요한가
- 멱등성을 보장하는 방법들
- 상태머신을 코드로 표현하는 방식들
- Flyway가 스키마를 관리하는 방식
- Testcontainers가 하는 일
- 커넥션 풀 크기가 성능에 미치는 영향
- k6의 부하 모델

## 금지

- 개발 중에 본문까지 쓰느라 흐름을 끊는 것
- 이해하지 못한 채 설명을 옮겨 적는 것
- 프로젝트 맥락 없이는 못 읽는 노트를 쓰는 것
