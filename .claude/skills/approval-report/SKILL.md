# 승인 보고서

관리자가 읽고 판단할 수 있는 보고서를 만든다. 질문 몇 개를 던지는 게 아니다.

## 언제 쓰는가

| 시점 | 보고서 종류 |
|---|---|
| 스펙 작성 완료 | 스펙 승인 |
| 개발 사이클 완료 | 개발 완료 승인 |

## 절차

### 1. 보고서 파일을 쓴다

`docs/reports/F00-<단계>.md`에 `docs/reports/TEMPLATE.md` 형식으로 쓴다.

### 2. 근거는 실제 결과를 붙인다

테스트 결과를 요약만 쓰지 않는다. **실행 출력을 그대로 붙인다.** "테스트 통과"는 근거가 아니다.

동시성 테스트는 시나리오별로 스레드 수, 기대값, 실제값을 표로 쓴다.

### 3. 불리한 것을 먼저 쓴다

레이어 규칙을 어긴 곳, 미룬 지적, 구현하지 못한 것을 **숨기지 않고 먼저 밝힌다.** 나중에 발견되면 보고서 전체의 신뢰가 무너진다.

### 4. 판단이 필요한 지점을 정리한다

관리자가 결정해야 하는 것을 질문으로 만든다. **각 질문에 내 추천과 근거를 붙인다.** 질문만 던지면 관리자가 처음부터 조사해야 한다.

### 5. 터미널 요약을 만든다

관리자가 폰으로 확인할 수 있어야 한다. **3~5줄로 압축한다.**

```
[F01 개발 완료 승인 요청]
예약 생성·취소 구현. 테스트 47개 전부 통과 (동시성 6개 포함).
분산락을 끈 상태에서도 재고 초과 판매 0건 확인.
리뷰 2라운드, 심각 0 / 중요 1건은 다음 feature로 미룸.
판단 필요: 취소 마감 시각을 체크인 당일 자정으로 할지 24시간 전으로 할지.
보고서: docs/reports/F01-dev-approval.md
```

### 6. 승인을 기다린다

**승인 없이 다음 단계로 넘어가지 않는다.** 관리자가 자리에 없으면 기다린다.

조건부 승인을 받으면 조건을 문서에 기록하고 진행한다.

재작업 판정을 받으면 사유를 스펙이나 리뷰 문서에 반영하고 개발 사이클로 돌아간다.

## 좋은 보고서와 나쁜 보고서

| 나쁨 | 좋음 |
|---|---|
| "동시성 처리를 구현했습니다" | "재고 차감을 조건부 UPDATE로 바꿔 락 없이 원자성을 확보했습니다. 100 스레드 경합에서 재고 10개가 정확히 10건만 팔렸습니다" |
| "테스트를 통과했습니다" | 실행 출력 + 계층별 개수 표 |
| "몇 가지 개선점이 있습니다" | "중요 지적 1건을 미뤘습니다. 이유는 ...이고 F02에서 처리합니다" |
| "어떻게 할까요?" | "A안을 추천합니다. 이유는 ...입니다. B안은 ... 때문에 뺐습니다" |

## 금지

- 실행하지 않은 테스트 결과를 쓰는 것
- 통과하지 않은 것을 통과했다고 쓰는 것
- 미룬 지적을 빼놓는 것
- 승인 없이 진행하는 것
