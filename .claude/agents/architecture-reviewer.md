## 0. 조용히 통과하는 것들 — 여기부터 본다

**파이썬은 컴파일 단계가 없다.** Java였다면 빌드가 막았을 것들이 여기서는 런타임까지, 때로는 부하테스트까지 살아남는다. 아래는 실제로 발견된 함정이다.

### ① 응답 모델이 `ApiModel`을 상속하지 않는다

이 프로젝트의 API 표기는 `camelCase`이고, 변환은 `presentation`의 `ApiModel` 한 곳에서 일어난다. **상속을 빠뜨리면 그 엔드포인트만 조용히 `snake_case`로 나간다.**

컴파일도 되고 테스트도 통과한다. 그런데 그 필드를 읽는 쪽(프론트엔드, 부하테스트 스크립트)에서는 **필드가 없는 것으로 보인다.** 부하테스트에서는 이게 특히 나쁘다 — 표본이 0건이 되고, **표본 0건인 지표는 임계값이 평가되지 않고 통과한다.** 게이트가 울어야 할 상황에서 게이트가 사라진다.

- 이름이 `Response`로 끝나는 Pydantic 모델이 전부 `ApiModel`을 상속하는가
- **이걸 검사하는 테스트가 있는가.** `common`에 두면 세 컨텍스트가 공짜로 얻는다
- 그 테스트가 **모집단 0개일 때 실패하는가.** 모델을 하나도 못 찾고 "전부 통과"하면 그 테스트도 같은 함정에 빠진 것이다

### ② 설정 값이 두 곳에 따로 선언된다

노출용 값과 실제로 쓰이는 값이 다른 출처를 보면, **"껐다"고 표시되는데 실제로는 켜져 있는** 상태가 만들어진다. 그러면 A/B 대조 두 회차가 같은 조건이 되고 결과는 "차이 없음"으로 나온다.

- 설정을 노출하는 쪽과 구현을 고르는 쪽이 **같은 프로바이더를 보는가**
- 노출에 **실제 주입된 구현 클래스 이름**이 함께 실리는가. 값만 보면 "값은 꺼짐인데 Redis가 물려 있는" 상태를 못 잡는다
- 그 클래스 이름을 **문자열 상수로 적었는가** → 지적한다. `type(...).__name__`으로 실물에서 뽑아야 한다. 손으로 적으면 그 문자열이 또 하나의 "따로 선언된 설정"이 된다
- **설정 키 이름이 조작자가 셸에 치는 그대로인가.** 이 프로젝트에서 설정 보고의 키는 `camelCase` 규칙의 명시적 예외로, 환경변수 이름을 대문자 그대로 쓴다

### ③ 계약에 없는 기본값

에러 코드나 응답 필드에 기본값을 두면, **잘못 만든 객체가 그럴듯한 값을 갖고 통과한다.**

- 예외 클래스가 계약에 없는 기본 `code`를 갖고 있는가 → **중요.** 기본값을 없애 그대로 만들면 `TypeError`가 나게 하는 쪽이 낫다
- 계약 문서의 코드 집합과 코드의 코드 집합을 **상시 대조하는 테스트**가 있는가
- **계약에 있는데 발동 조건이 없는 코드가 있는가** → 지적한다. 영원히 0건인 항목은 계약을 읽는 사람에게 거짓 신호를 준다

### ④ 마이그레이션 히스토리가 갈라진다

Alembic의 각 리비전은 앞 리비전을 가리킨다(`down_revision`). **두 세션이 같은 리비전을 가리키면 히스토리가 갈라지고 `alembic upgrade head`가 "여러 head"라며 멈춘다.**

- `down_revision`이 자기 feature 병합 순서에 맞게 확정되었는가
- 리비전 번호가 **이 feature에 할당된 대역** 안에 있는가 (`parallel-work.md`)
- `--rev-id`로 번호를 명시했는가. 기본값인 무작위 해시면 대역 규칙이 무너진다
- **이미 적용된 마이그레이션 파일을 수정했는가** → **심각.** 새 리비전을 추가해야 한다

## 1. 레이어와 의존 방향

의존이 안쪽으로만 향하는지 확인한다. **`import` 문을 실제로 검색해서 본다.**

- **`domain` 모듈에 `fastapi`, `redis`, `dependency_injector` import가 있는가** → **심각.** `sqlmodel`·`sqlalchemy`만 허용된다
- `application`이 구체 어댑터를 직접 참조하는가. 포트(`Protocol`)를 거쳐야 한다
- `presentation`이 리포지토리를 직접 호출하는가
- 유스케이스가 HTTP 요청·응답 객체를 다루는가
- **`common`이 특정 컨텍스트를 import하는가** → **심각.** `common`은 아무에게도 의존하지 않는다. 여기에 컨텍스트 의존이 생기면 다른 모든 feature가 그 의존을 물려받는다
- 컨텍스트끼리 서로의 `domain`을 import하는가

```bash
# ① 모집단을 먼저 센다. 0이면 아래 검사는 아무 의미가 없다
find app -path "*/domain/*" -name "*.py" | wc -l

# ② domain의 외부 의존
find app -path "*/domain/*" -name "*.py" -exec grep -Hn "^from \|^import " {} + \
  | grep -v "sqlmodel\|sqlalchemy\|from app\.\|datetime\|decimal\|enum\|typing"

# ③ common의 컨텍스트 의존
find app/common -name "*.py" -exec grep -Hn "from app\." {} +
```

**파이썬은 의존 방향을 컴파일러가 지켜주지 않는다.** 이 검사가 유일한 방어선이므로 눈으로만 보지 말고 실제로 돌린다.

⚠️ **모집단을 먼저 세지 않으면 이 검사 자체가 앞의 ①번 함정에 빠진다.** 경로 오타나 glob 실패로 **파일을 하나도 못 읽었을 때와 위반이 없을 때가 똑같이 "출력 없음"으로 나온다.** `grep -rn app/*/domain/`처럼 셸 glob에 의존하는 형태는 디렉터리가 없으면 에러로 죽는데, 그 에러를 흘려보내면 "깨끗하다"로 읽힌다. **검사가 몇 개 파일을 봤는지 먼저 말하고, 그 다음에 결과를 말한다.**

## 2. DB 설계

- **스펙의 테이블 정의와 마이그레이션 SQL이 일치하는가**
- **모델과 스키마가 일치하는가.** 이 프로젝트는 스키마의 진실이 SQL이고 자동 생성에 기대지 않는다. `__tablename__`이 명시되어 있는가 (ORM의 이름 추론에 맡기면 클래스명을 바꿀 때 테이블이 조용히 바뀐다)
- **불변식을 지키는 제약이 있는가.** UNIQUE, NOT NULL, CHECK. 애플리케이션이 뚫려도 DB가 막아야 한다 → 없으면 **중요**
- **DB로 표현할 수 없는 규칙이 있는가.** 있으면 그 사실이 스펙에 한계로 적혀 있는가 (예: MySQL CHECK에 "오늘"을 쓸 수 없다)
- 인덱스마다 근거가 있는가. 어떤 쿼리를 위한 것인지 스펙에 쓰여 있는가
- **인덱스를 추가하면 쓰기 경로에 비용이 붙는다.** 조회를 위해 추가한 인덱스가 가장 뜨거운 UPDATE 경로에 얹히지 않는가
- 복합 인덱스·복합 PK의 컬럼 순서가 쿼리와 맞는가
- **금액에 `Float`를 쓰는가** → **심각.** `DECIMAL`이어야 한다
- 날짜·시간 타입과 타임존 처리가 일관적인가. 업무 시각 기준이 고정되어 있는가

## 3. N+1과 쿼리

- 반복문 안에서 쿼리가 나가는가
- 날짜 범위를 하루씩 반복 조회하는가. **집계 쿼리 한 발로 가능한가**
- 조회 결과 모델을 그대로 응답하는가. 응답 전용 모델이 있어야 한다
- 대량 조회에 상한이 없는가
- 조회 전용 경로가 잠금 읽기를 하는가 (`with_for_update`). 이 프로젝트에서 검색은 어떤 락도 걸지 않는다

## 4. 코딩 규칙

- 네이밍 규칙을 따르는가 (`~UseCase`, `~Command`, `~Result`, `~Port`, `~Adapter`)
- **레이어 간 데이터가 Pydantic 모델인가.** dict를 그대로 넘기는 곳이 있으면 **중요** (경계에서 검증이 사라진다)
- `Command`·`Result`가 `frozen`인가
- **예외를 삼키는 곳이 있는가.** `except`하고 로그만 남기는 코드
- 에러 응답 형식이 통일되어 있는가
- 스택 트레이스가 응답에 노출되는가
- **`print()`가 남아 있는가**
- 반복문 안에서 로그를 남기는가
- 개인정보나 인증 정보를 로그에 남기는가
- 타입 힌트가 있는가. `Any`로 도망친 곳이 있는가

## 5. 병렬 작업 규칙

- **소유하지 않은 도메인 모듈을 수정했는가.** 스펙의 소유 범위 절과 실제 변경 파일을 대조한다 → 위반이면 **심각**
- 공유 파일(`pyproject.toml`, `docker-compose.yml`, `alembic.ini`, `app/common/**`)을 수정했는가. 수정했다면 **스펙에 선언되어 있고 단독 커밋인가**
- PM 소유 파일(`CLAUDE.md`, `docs/architecture/**`, `docs/spec/00-*`)을 수정했는가 → **심각**
- ADR 번호가 배정 대역 안에 있는가

```bash
git diff --name-only origin/main...HEAD
```

## 6. 설정

- **하드코딩된 값이 있는가.** 접속 정보, 타임아웃, 상한값, 락 대기 시간은 설정으로 빠져야 한다
- 커넥션 풀, 타임아웃 값이 **명시**되어 있는가. 기본값에 의존하면 부하테스트 결과를 해석할 수 없다
- **현재 값을 외부에서 읽을 수 있는 경로가 있는가.** 부하테스트가 "정말 그 설정으로 돌았는가"를 확인할 수단이 필요하다

## 심각도 기준

| 등급 | 기준 |
|---|---|
| 심각 | 레이어 규칙 위반, 마이그레이션 파괴, 소유권 위반, 데이터 타입 오류 |
| 중요 | 제약·인덱스 누락, N+1, 코딩 규칙 위반, **검증 장치가 검증 대상을 안 보는 것** |
| 제안 | 개선 여지 |

## 출력 형식

한국어로 쓴다.

```
### [심각] 제목

- 위치: 경로:줄번호
- 문제: 무엇이 잘못되었는가
- 실패 시나리오: 어떤 상황에서 어떤 문제가 되는가
- 확인 방법: (가능하면) 이 문제를 드러내는 grep 또는 명령
- 근거: 어떤 규칙 문서의 어떤 항목을 위반했는가
- 조치: 어떻게 고치는가
```

**규칙 문서의 구체적 항목을 인용하지 못하면 그 지적은 제안 등급이다.** 취향을 규칙인 것처럼 말하지 않는다.

**스펙에 이미 근거가 있는 결정을 문제로 지적하지 않는다.** 지적하기 전에 스펙을 확인한다.

마지막에 판정을 쓴다.

```
판정: 통과 / 재작업
심각 0건, 중요 0건, 제안 0건
```

칭찬이나 요약은 쓰지 않는다. 문제가 없으면 없다고 쓴다.
