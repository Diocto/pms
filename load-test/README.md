# load-test — k6 부하테스트 스크립트

설계 문서는 `docs/load-test/scenarios.md`다. **이 디렉터리는 그 설계의 구현이며, 판정 기준의 진실은 설계 문서에 있다.**

## 구조

```
load-test/
├── config.js              모든 상수. API 계약이 바뀌면 여기만 고친다
├── lib/
│   ├── api.js             API 호출 래퍼. URL을 직접 만드는 곳은 여기뿐이다
│   └── metrics.js         공통 지표와 응답 분류
├── reset.sh               실행 전 초기화. 매번 돌린다
├── verify/*.sql           실행 후 DB 검증. k6 결과만으로 끝내지 않는다
└── s*.js                  시나리오별 부하 스크립트
```

## 왜 config.js에 전부 몰아넣었는가

시나리오 스크립트는 URL을 직접 만들지 않고 `pathFor()`만 쓴다. 그래서 계약이 바뀌어도 고칠 곳이 한 파일이다.

승인 전이던 F01의 결정 셋을 기각 대비 플래그로 격리해뒀었고, **2026-08-15에 셋 다 판단이 끝나 플래그를 전부 지웠다.**

| 결정 | 결과 | 우리가 고친 것 |
|---|---|---|
| D7 `confirmationCode` | **채택.** 형식은 `260901-H1R3-K7M2XQ4R` (20자) | 없음 — 파싱도 길이 가정도 없었다 |
| D1 `guestCount` | **채택** | 없음 — 항상 싣는다 |
| D4 `NO_SHOW` | **유예(추후 작업)** | 전이 표 36칸으로 축소 |

**대비책은 값을 냈지만, 확정된 뒤의 플래그는 부채다.** D4가 빠질 때 플래그로 격리해둔 덕에 반영이 표 정의 한 곳 수정으로 끝났다. 그래도 다시 뒤집힐 일 없는 스위치를 남기면 읽는 사람이 "언젠가 켜지는 기능"으로 오해한다. 전이 표는 이제 **36칸(상태 6 × 이벤트 6) = 허용 7 + 멱등 6 + 거부 23**이다.

**확인번호를 파싱하지 않는다.** 형식에 날짜와 객실타입이 들어 있어 뽑아 쓰고 싶어지지만, 관리자 제약이 "키를 무작위 키처럼 대하라"이고 F01도 읽는 함수를 두지 않았다. 응답에서 받은 문자열을 그대로 경로에 넣기만 한다. **문자열을 문자열로만 다루면 형식이 바뀌어도 안 깨진다.**

## 실행 순서

```bash
docker compose up -d

# 워커 수 N 은 회차마다 같아야 한다. 로그는 파일로 받는다 (LockNotOwnedError 관찰용)
uvicorn app.main:app --workers N > docs/load-test/results/app-s1.log 2>&1 &

cd load-test
./reset.sh s1
k6 run s1-inventory-burst.js --summary-export=../docs/load-test/results/s1-summary.json
./verify/run.sh s1          # 전제 단언 -> common.sql -> s1.sql
```

**세 단계가 다 끝나야 한 시나리오가 끝난 것이다.** `reset.sh`를 빼먹으면 이전 실행 데이터가 섞여 판정이 무의미해지고, 검증을 빼먹으면 k6가 받은 응답만 보고 DB 실제 상태를 안 본 것이 된다.

**`verify/run.sh`로 돌린다. `mysql < verify/x.sql`을 직접 치지 않는다.** SQL만 돌리면 검증 결과가 "비어 있음"으로 보이는데 그게 **통과인지 미검사인지 구분되지 않기 때문**이다. `run.sh`는 위반을 세기 전에 **검사 대상이 0이 아닌지 먼저 단언하고**, 0이면 종료 코드 1로 중단한다.

특히 값 필터가 위험하다. `WHERE event IN ('CANCEL', ...)`은 저장된 표기가 `cancel`이면 아무것도 못 잡고, **"이중 복원 0건"이 초록불로 뜬다.** 이건 파이썬 전환으로 실제로 커진 위험이라(Enum을 이름이 아니라 값으로 저장하는 일이 흔하다) 사람 눈이 아니라 종료 코드로 막는다.

`common.sql`은 비용이 거의 없으니 매번 돌아간다. 그중 **(3)번이 특히 값지다** — 이력에 남은 전이 조합이 허용 7행의 부분집합인지 보는 쿼리로, **"부하 중 발생한 N건의 전이가 전부 표 안에 있었다"**를 운영 데이터로 증명한다. 전수 테스트가 "코드가 거부하도록 짜여 있다"를 보인다면 이건 "실제로 한 건도 새지 않았다"를 보인다.

## 검증기를 먼저 검증한다

```bash
./verify/selftest.sh
```

일부러 깨진 상태를 만들어 검증 쿼리가 실제로 잡는지 확인한다. **재고와 이력 양쪽을 본다.**

**두 번 돌린다.** 병합 직후 한 번(재고 쪽만 검증됨 — 이력이 비어 있다), 그리고 **S4나 S6를 돌린 뒤 한 번 더**(이력 쪽까지 검증됨). 이력 행이 없으면 스크립트가 건너뛰면서 그 사실을 크게 찍는다 — 조용히 넘어가면 "검증기를 검증했다"가 절반만 참인 채로 리포트에 들어간다.

## 부하 프로파일에서 조절하는 설정

| 키 | 기본 | 부하테스트 | 쓰는 곳 |
|---|---|---|---|
| `PMS_LOCK_ENABLED` | true | ON/OFF 두 회차 | S5 |
| `PMS_RESERVATION_HOLD_MINUTES` | 10 | **S4-B만 1** | S4-B |
| `PMS_PAYMENT_DECLINE_RATE` | 0.0 | 경합 0.0 / 결제 분기 1.0 | S4 |
| `PMS_SEARCH_CACHE_ENABLED` | true | ON/OFF 두 회차 | S8 (F03) |

**기본값과 다르게 둔 값은 전부 리포트에 적는다.** 재현하려는 사람이 같은 조건을 만들 수 없으면 그 수치는 근거가 못 된다. `decline-rate`는 0.0과 1.0만 결정적이고 그 사이는 확률적이니, 경합 시나리오에 확률적 거절을 섞지 않는다 — 테스트가 가끔 깨지고 그때 원인이 경합인지 결제인지 구분되지 않는다.

**손대지 않지만 리포트에 적는 값 셋.**

| 키 | 기본 | 왜 적는가 |
|---|---|---|
| `PMS_LOCK_WAIT_MILLIS` | 200 | **S5의 락 실패 건수를 사실상 이 값이 정한다.** "락의 가격은 N건"이라는 문장은 이 숫자 없이는 근거가 아니다 |
| `PMS_LOCK_TTL_SECONDS` | 3 | 트랜잭션이 이보다 길면 `LockNotOwnedError`가 난다 — 임계 구역에 둘이 들어갔다는 뜻 |
| `PMS_RESERVATION_EXPIRE_SCAN_SECONDS` | 30 | 만료가 언제 일어나는지를 정한다 |

**보류 시간은 S4-B 말고는 절대 줄이지 않는다.** 배경 만료 스캐너가 부하 도중에 예약을 만료시키면 재고가 돌아오고, **"재고 100에 성공 정확히 100"이 100을 넘는다.** 그걸 동시성 버그로 오진하게 된다. 기본 10분이 가장 긴 시나리오(S6, 5분)보다 긴 것은 우연이 아니라 지켜야 하는 조건이다.

## 필수 시나리오 (F01만 병합되면 전부 실행 가능)

| 스크립트 | 증명하는 것 |

| `s2-inventory-sustained.js` | 지속 부하에서 재고 100 → 성공 정확히 100 |

## 밟기 쉬운 함정 셋

**1. 같은 예약은 같은 `X-User-Id`로.** 취소가 소유자를 검증하는데 남의 예약이면 403이 아니라 **404**를 준다. VU 번호가 요청마다 바뀌면 전이 요청이 전부 404로 떨어지는데, 404는 "예약이 없다"로 읽혀서 원인을 찾는 데 한참 걸린다. `not_found` 지표를 하드 게이트로 둔 이유다.

**2. 멱등 키는 `(userId, key)` 조합이다.** 같은 키 문자열이라도 사용자가 다르면 별개 요청으로 취급된다. 재시도마다 VU가 바뀌면 키가 충돌하지 않아 전부 성공하고, "중복 0건"이라는 결론이 나온다. 멱등성이 작동해서가 아니라 **애초에 중복 요청을 안 보내서**다. `s3`는 키마다 전용 사용자를 묶는다.

**3. 결제 거절은 200이다.** `confirm`은 결제가 거절돼도 HTTP 200을 주고 본문 `status`가 `CANCELLED`가 된다. HTTP 코드만 보고 성공을 세면 확정 성공률이 부풀려진다. `classifyTransition`이 본문까지 읽는 이유다.

## 응답 코드를 세는 규칙

거절은 에러가 아니다. 재고 소진·중복·금지 전이로 인한 거절은 시스템이 옳게 동작한 증거이므로 에러율에서 뺀다. 반면 **락 획득 실패**는 재고가 남았는데도 예약을 못 해준 것이라 실패로 센다. 이건 **락 설계의 가격**이고, S5에서 락 없는 쪽과 비교할 대상이 바로 이 값이다.

**락 실패는 상태 코드가 아니라 본문 `code`로 판정한다.** 원래는 "503이면 락 실패"로 짰는데, 병합 직후의 예외→상태 표(`app/common/error_handlers.py`)에 503 자리가 없어서 락 실패가 400으로 나갈 상태였다. 그러면 락 실패가 "잘못된 요청"으로 집계돼 `bad_request` 게이트가 잘못 울고, **락의 가격은 ON·OFF 양쪽 0으로 나온다.** F01이 같은 구멍을 독립적으로 잡아 지금은 503이 맞다(`ServiceUnavailableError`, main `d9124f5`). **그래도 판정은 계속 `code`로 한다** — 상태 코드는 변환 계층이 한 번 삐끗하면 바뀌는 값이고(실제로 바뀔 뻔했다), `code`는 계약의 기계 검증본(`app/common/error_codes.py`)이 지키는 값이다.

하드 게이트는 다섯이다. 0이 아니면 성능 미달이 아니라 **무효 실행**이므로 결과를 폐기하고 원인을 고쳐 다시 돌린다.

| 지표 | 뜻 |
|---|---|
| `server_error` | 앱 장애 |
| `bad_request` | 내 요청이 틀렸다 |
| `not_found` | 예약 소유자를 잘못 물려 보냈다 |
| `forbidden_transition_passed` | 금지 전이가 통과했다 (명제 (다) 반증) |
| `unknown_rejection` | **우리가 모르는 거절 코드가 왔다** |

마지막 항목은 성능과 무관하다. 예전 분류기는 모르는 코드를 "전이 거절"이나 "중복"으로 흘려보냈고, 그 바구니는 에러율에서 빠진다. **모르는 것을 아는 것으로 취급하는 순간 리포트가 거짓말을 시작한다.**

## 응답에 안 나오는 신호

`LockNotOwnedError`는 로그에만 나온다. **내가 쥔 락이 TTL(기본 3초)을 넘겨 자동으로 풀렸고 그 사이 남이 가져갔다**는 뜻이다 — 그 순간 임계 구역에 둘이 있었다. 정상 동작에서는 한 건도 안 나와야 한다.

```bash
grep -c LockNotOwnedError docs/load-test/results/app-s5off.log
```

그래서 앱을 띄울 때 표준 출력을 파일로 돌려둔다. 나오면 성능 문제가 아니라 **1차 방어선이 그 순간 작동하지 않았다는 증거**이므로 TTL을 늘리고 그 회차를 다시 돌린다.
