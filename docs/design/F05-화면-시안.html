실패가 정상으로 보이는 예약 화면 세 개

검색 결과는 캐시 때문에 최대 10초 낡을 수 있고, 그래서 "예약 가능"이라고 떠 있는데 누르면 실패하는 일이 설계상 정상으로 일어난다. 이 시안은 화면 세 개(검색 → 예약 → 예약 상세)의 정상 흐름과 함께, 그 실패들을 화면이 어떻게 다루는지를 상태 단위로 전부 그린 것이다. API는 F01·F03 계약 문서에 있는 것만 쓴다.

작성일 2026-08-15 상태 승인됨 · 구현 중 화면 3개 · 상태 14종 스택 Next.js (확정) + 제안 4건

이 시안을 읽는 법

회색 브라우저 틀 안쪽이 제품 화면이고, 틀 바깥(이 배경)은 검토용 설명이다. 제품 화면은 라이트 단일 테마로 고정했고, 이 문서 자체는 보는 사람의 화면 설정(밝게/어둡게)을 따른다.

화면마다 정상 상태 하나가 아니라 상태 여러 개를 그렸다. 로딩·비어 있음·실패가 이 프로젝트에서는 본편이기 때문이다. 각 상태의 오른쪽 위 회색 코드는 그 상태를 만드는 서버 응답이다.

데이터는 전부 시드 계약(F01 스펙 1.9절) 값이다 — 서울 그랜드 호텔 / 부산 오션뷰 호텔, 객실타입 5종, 판매 기간 2026-08-01 ~ 10-29. 시안 속 스위트(10실)가 경합 시연용 객실이다.

화면 이동 지도

화면은 셋뿐이고 목록 화면은 없다(F01에 목록 API가 없다 — D7). 예약 직후에는 응답을 들고 상세로 이동하고, 나중에 다시 찾을 때는 상단의 확인번호 입력으로 진입한다.

상태 3

재고 부족 — 이 화면의 핵심

409 INSUFFICIENT_INVENTORY

검색 결과가 낡아 있었던 것뿐, 사용자도 시스템도 잘못한 게 없다. 그래서 오류 화면이 아니라 진행 화면으로 그린다. 브리핑의 권장 흐름을 그대로 따른다: 사실을 말하고 → 최신 재고를 자동 조회하고(fresh=true) → 남아 있으면 사용자가 다시 누르지 않아도 한 번 더 시도하고 → 두 번 실패하면 대안으로 보낸다. 자동 재시도는 최대 2회.

1단계 · 409 수신
"방금 마감됐습니다"

오류 아이콘 없이 사실만. "결제는 진행되지 않았습니다"를 반드시 함께 쓴다.

2단계 · 자동
최신 재고 다시 확인

fresh=true로 캐시를 우회해 재검색. "최신 재고를 확인하고 있습니다…" 진행 표시.

3단계 · 자동
남아 있으면 재시도

잔여가 있으면 같은 멱등성 키로 한 번 더 예약 요청. 사용자는 기다리기만 한다.

4단계 · 2회 실패
대안으로 보낸다

"이 조건은 마감되었습니다." 재시도 버튼을 주지 않고 다른 날짜·객실 검색으로 돌려보낸다.

  • 만드는 때: 주문서 화면에 들어올 때 1회 (UUID)
  • 같은 키로 나가는 경우: 버튼 연타, 네트워크 타임아웃 후 재시도, REQUEST_IN_PROGRESS 후 재요청, 409 후 자동 재시도
  • 새 키로 바뀌는 때: 예약 성공, 또는 사용자가 날짜·객실·인원을 바꿨을 때 — 그건 다른 예약 시도다
  • 400을 받으면: 서버가 키를 지웠으므로 입력 수정 후 새 키로 제출
  • 보관은 화면 상태(메모리)에만 한다. 새로고침하면 새 키다 — 근거와 한계는 D6

  • 멱등 재요청은 200 + 기존 예약으로 온다. 201과 똑같이 S3로 이동하면 된다
  • 503(LOCK_ACQUISITION_FAILED)은 혼잡 — "지금 예약이 몰리고 있습니다" + 잠시 후 재시도 안내 (응답→문구 매핑 표 참조)

기술 스택 제안

Next.js는 확정 · 나머지는 D1~D4

선택 기준은 브리핑의 한 줄이다 — "화면 세 개에 그게 정말 필요한가." 그래서 이 표의 절반은 "안 쓴다"는 결정이다. 각 항목의 근거·트레이드오프는 결정 검토란의 해당 D 항목에 있다.

X-User-Id에 대해 — 알고 뺐다

상단의 사용자 선택값이 그대로 X-User-Id 헤더로 나간다. 이 헤더는 클라이언트가 마음대로 정할 수 있으므로 인증이 아니다. 아무나 아무 값이나 넣을 수 있고, 남이 예약할 때 쓴 값을 알면 그 예약을 조회·취소할 수 있다. 이것은 과제가 의도적으로 범위에서 뺀 것이며(ADR-0006 — 인증은 이 과제의 관심사가 아니다), F05가 고칠 문제가 아니다. 서버 쪽 완화 장치는 하나 있다: 소유자가 다르면 403이 아니라 404를 주어 예약의 존재 자체를 숨긴다. 같은 내용을 구현 코드의 API 모듈 주석에도 남긴다.

같은 이유로 그럴듯한 로그인 화면을 만들지 않았다. 상단의 "사용자(과제용 식별값)" 선택은 없는 기능을 있는 것처럼 보이지 않게 하려는 표기다.

D2스타일링은 전역 CSS 한 벌 + CSS 변수, 라이브러리 0. 화면 셋·컴포넌트 소수에 도구가 해결할 규모 문제가 없고, 교육 노트 6(CSS 레이아웃)이 유틸리티 클래스 뒤에 숨지 않은 실제 CSS를 예제로 써야 한다. 트레이드오프: 클래스 이름 관리가 수동이고, 화면이 늘어나면 충돌 위험이 커진다. 대안: Tailwind(의존성·학습 대상 추가, 노트 소재가 사라짐), CSS Modules(파일 수만 늘고 셋 규모에선 이득 없음). 두 번 반복되는 스타일이 생기면 그때 공통 클래스로 뽑는다.스타일링 라이브러리 없이 가도 괜찮습니까?
D3데이터 페칭은 fetch 직접 + lib/api.ts 한 곳. 응답 검증은 손수 쓴 함수. TanStack Query·zod 안 씀. 호출이 4종뿐이라 캐시·중복 제거 계층이 할 일이 없고, 재시도 정책(409 2회·REQUEST_IN_PROGRESS 3회)은 이 화면 고유 규칙이라 어차피 직접 쓴다. 검증도 응답 4종 형태 확인이 전부라 라이브러리 값을 못 한다. 트레이드오프: 검증 함수를 손으로 유지해야 하고 계약 변경 시 수동으로 따라가야 한다. 대안: TanStack Query(번들 +12KB, 학습 대상 추가), zod(선언은 깔끔하나 의존성 추가). 응답 종류가 늘면 그때 재검토.페칭·검증 라이브러리 없이 가도 괜찮습니까?
D4상태 관리 라이브러리 안 씀. 화면 간 공유가 필요한 상태는 검색 조건·확인번호 둘뿐이고 둘 다 URL에 실린다(새로고침·공유 무료). 나머지는 화면 안 useState로 끝난다. 트레이드오프: 화면을 넘나드는 공유 상태가 늘어나면 그때 도입 비용을 다시 치른다. 대안: Zustand — 지금 넣으면 "왜 있는지 모르는 의존성"이 된다.상태 관리 없이 URL + useState로 가도 괜찮습니까?
D5세 화면의 본체는 클라이언트 컴포넌트, 서버 컴포넌트는 뼈대만. 세 화면 모두 상호작용(검색 실행, 제출·재시도, 카운트다운)이 본질이라 브라우저에서 돌아야 한다. 서버 컴포넌트로 미리 그릴 수 있는 것은 레이아웃과 정적 안내뿐이다. 트레이드오프: Next.js의 서버 렌더링 이점을 얕게만 쓴다 — 첫 페인트에 데이터가 실리지 않는다. 대안: 검색 결과를 서버 컴포넌트로 렌더 — 10초 낡는 데이터를 서버에서 미리 그리면 하이드레이션 직후 재검증이 필요해 오히려 복잡해져 기각. 이 판단 과정이 교육 노트 1의 본문이다.클라이언트 컴포넌트 중심 구성으로 가도 괜찮습니까?
D6멱등성 키는 화면 상태(메모리)에만 둔다. 새로고침하면 새 키다. 키의 수명("같은 예약 시도")을 폼의 수명과 일치시키는 가장 단순한 구현이다. 트레이드오프: 제출 직후 응답을 못 받은 채 새로고침하면, 재제출이 새 키로 나가 중복 예약이 될 수 있다. 그 확률과, sessionStorage에 입력값과 키를 함께 보관·비교하는 복잡도를 저울질해 단순한 쪽을 골랐다 — 이중 예약은 사용자가 상세 화면에서 취소로 회복할 수 있다. 대안: sessionStorage 보관(입력 동일성 비교 로직 필요), 서버 발급(재시도 시 키가 바뀌어 멱등성 자체가 무너짐 — 계약 위반).새로고침 시 키가 바뀌는 한계를 받아들입니까?
D7목록 화면 없음, 호텔 2곳은 상수. F01에 예약 목록 API가 없고 호텔 목록 API도 없다. 백엔드에 추가를 요구하지 않는다(브리핑 원칙). 재방문 진입은 상단 확인번호 입력으로 해결한다. 트레이드오프: 확인번호를 잃으면 예약을 다시 찾을 수 없다 — 실제 서비스라면 안 되는 UX지만 이 과제의 증명 대상과 무관하다. 대안: localStorage에 내 예약 번호 목록 보관 — 편의는 늘지만 "서버에 없는 목록"이라는 거짓 화면이 된다.목록 없이 확인번호 진입으로 가도 괜찮습니까?
D8체크인·체크아웃 버튼을 화면에 두지 않는다. 브리핑의 화면 셋은 고객 여정(검색→예약→확인)이고, 체크인·체크아웃은 프런트 직원 액션이다(F01 2.1절). 시연이 필요하면 API 직접 호출로 충분하다. 트레이드오프: 상태 머신의 마지막 두 전이(CHECKED_IN·OUT)를 화면에서 일으킬 수 없다 — 상세 화면은 그 상태를 표시만 한다. 대안: 상세 화면에 개발자용 버튼 노출 — 고객 화면에 직원 행동이 섞여 기각.체크인·체크아웃은 표시만 하고 버튼은 빼도 괜찮습니까?
D9교육 노트는 위 6편으로 확정하고, 본문은 구현 단계에서 판단이 실제로 생긴 시점에 쓴다. 시안 단계에서 본문까지 쓰면 아직 안 내린 구현 판단을 지어내게 된다 — "실제로 판단한 것만 쓴다"는 요구와 어긋난다. 트레이드오프: 완료 승인 시점에 노트 6편 검토가 몰린다. 대안: 지금 일반론으로 써두고 나중에 고치기 — 튜토리얼 요약 금지 원칙에 걸려 기각.노트 6편 구성과 "구현 중 작성" 방식에 동의합니까?

이 시안이 전제하는 것 (승인 전 확인)

F01·F03 스펙은 현재 재승인·승인 대기 상태다. 이 시안은 그 계약(에러 코드 표, emptyReason·salesOpenUntil·source 필드, 시드 값)이 그대로 확정된다고 전제했다. 특히 F03의 D9(emptyReason)가 부결되면 S1의 빈 결과 3분할이 무너지므로, 그 경우 PM을 통해 알려주시면 시안을 고친다. 열린 질문은 없다.
