# AI 활용

## 요약

이 프로젝트는 Claude Code로 만들었다. 다만 "AI에게 코드를 시켰다"가 아니라, **AI가 스스로를 검증하도록 구조를 짜는 것**을 과제의 일부로 다뤘다.

핵심 판단은 하나다. **AI의 가장 위험한 실패는 틀린 답이 아니라 그럴듯한 답이다.** 틀린 코드는 컴파일이 막아준다. 그런데 "동시성을 제어했습니다"라는 문장은 아무도 막아주지 않는다. 그래서 이 프로젝트의 AI 활용은 대부분 **그럴듯한 것을 걸러내는 장치**를 만드는 데 쓰였다.

---

## 1. 무엇을 만들었는가

작업을 시키기 전에 작업 환경부터 만들었다. 저장소의 `CLAUDE.md`와 `.claude/`, `docs/architecture/`가 그것이다.

### 규칙 문서 — 매번 설명하지 않기 위해

| 문서 | 담은 것 |
|---|---|
| `coding-rules.md` | 코드를 쓰기 전에 읽는 규칙. 다층 방어 원칙 포함 |
| `clean-architecture.md` | 패키지와 레이어 배치 |
| `ddd.md` | 도메인 모델을 만들 때의 규칙 |
| `tdd.md` | 실패하는 테스트를 먼저 쓴다 |
| `diagram-rules.md` | 다이어그램 표기 표준형과 한국어 해설 의무 |
| `parallel-work.md` | 여러 세션이 동시에 돌 때의 충돌 방지 |

이 문서들이 없으면 같은 지시를 세션마다 반복하게 되고, 반복하다 보면 **세션마다 조금씩 다른 규칙이 적용된다.** 문서로 고정하면 지시가 아니라 참조가 된다.

### 스킬 — 절차를 매번 다시 정하지 않기 위해

`feature-spec`, `approval-report`, `dev-cycle`, `decision-log`, `learning-note`, `load-test` 여섯 개를 만들었다. 각각 "스펙을 쓸 때 무엇을 어떤 순서로 하는가"를 담고 있다.

### 리뷰어 에이전트 — 관점을 나누기 위해

`concurrency-reviewer`, `domain-reviewer`, `architecture-reviewer` 셋을 만들어 개발 사이클마다 **병렬로** 호출한다.

셋으로 나눈 이유가 있다. 한 리뷰어에게 "전부 봐줘"라고 하면 **눈에 띄는 것부터 보고 나머지는 흐려진다.** 관점을 강제로 나누면 각자 자기 렌즈로만 보게 되고, 동시성 리뷰어는 예쁘지 않은 코드를 그냥 넘기는 대신 락 순서를 끝까지 본다.

### 승인 게이트 — 사람이 판단할 자리

스펙을 다 썼을 때와 개발 사이클을 마쳤을 때, 두 번 멈추고 사람의 승인을 받는다.

**승인 문서에는 결정 검토란을 반드시 둔다.** AI가 내린 판단을 D 항목으로 전부 모으고, 각각에 **결정·이유·트레이드오프·대안·확인 질문** 다섯 가지를 적는다. 동의는 문서 전체가 아니라 **항목 단위로** 받는다.

이 장치가 이 프로젝트에서 가장 큰 값을 냈다. 이유는 이렇다.

> AI는 결정을 본문 안에 자연스럽게 녹여 쓴다. 읽으면 매끄럽고, 읽는 사람은 그게 결정인 줄 모르고 지나간다. **D 항목으로 뽑아내면 "이건 내가 정한 것이고 이렇게 정한 이유는 이렇다"가 강제로 드러난다.** 그리고 트레이드오프 칸이 비어 있으면 그 결정은 검토되지 않은 것이다.

실제로 이 프로젝트에서 나온 D 항목은 **51개**다(F01 22 · F02 15 · F03 14). 이걸 본문에 묻어뒀다면 사람이 검토할 수 없었다.

## 2. 어떻게 일을 나눴는가

### 세션 구조

작업을 다섯 개의 독립된 세션으로 나눴다.

```
PM 세션 ─┬─ F01 예약 코어      (동시성·멱등성·상태 전이)
         ├─ F02 선착순 프로모션
         ├─ F03 가용 객실 검색
         └─ F04 부하테스트
```

**PM 세션은 코드를 쓰지 않는다.** 규칙 문서와 전체 범위를 소유하고, 세션 사이를 중계하고, 승인 게이트에서 사람을 돕는다. feature 세션은 자기 스펙부터 구현까지 전 과정을 담당한다.

**세션끼리 직접 말하지 않는다.** 모든 질문은 PM을 거친다. 이게 번거로워 보이지만 두 가지를 얻는다 — 결정이 한 곳에 모여 기록되고, 한 세션의 착각이 다른 세션으로 바로 번지지 않는다.

### 충돌을 막은 방법

네 세션이 같은 저장소에서 동시에 돌았다. 텍스트 충돌은 git이 잡아주지만 **의미 충돌은 못 잡는다.** A가 상태를 하나 추가하고 B가 같은 클래스의 다른 메서드를 고치면, git은 조용히 병합하고 상태 전이 표만 깨진다.

그래서 **도메인만 강하게 잠그고 나머지는 병합으로 풀었다.**

| 대상 | 정책 |
|---|---|
| 도메인 모델 | Hard. 소유 세션만 수정 |
| Flyway 마이그레이션 | Hard. 번호 대역 예약 (F01 V001~, F02 V201~, F03 V301~) |
| ADR 번호 | Hard. 대역 배정 (F01 0007~, F02 0020~, F03 0030~, F04 0040~) |
| 공유 파일 | PM 전용 / 절차 필요 / 자동 병합의 3등급 |
| 애플리케이션·테스트·문서 | Soft. 충돌하면 병합 |

각 세션은 자기 git worktree에서 작업한다. 폴더가 같아도 작업 공간이 분리되므로 서로 덮어쓰지 않는다.

**ADR 번호 대역은 처음엔 없었다.** 네 세션이 동시에 결정을 남기면 전부 다음 번호를 집어 같은 번호의 ADR이 네 개 생긴다는 걸 실행 중에 발견하고 규칙을 추가했다.

## 3. 실제로 무엇이 걸러졌는가

구조를 설명하는 것보다 **그 구조가 실제로 잡아낸 것**을 보이는 편이 낫다. 아래는 전부 실제로 일어난 일이다.

### 세션이 다른 세션의 오류를 잡은 사례

**시드 날짜가 실행일에 묶여 있었다.** F01이 재고 데이터를 `CURDATE()` 기준 90일로 만들려 했다. F02가 자기 특가 날짜를 정하다 "그 범위가 언제인가"를 물었고, 그때 드러났다. 마이그레이션은 한 번만 실행되므로 90일이 지나면 재고 없는 날짜가 생기고, 재시드할 때마다 범위가 움직여 부하 스크립트가 어느 날 갑자기 깨진다. **그리고 그 실패는 "재고 부족"으로 보여서 정상 동작처럼 읽힌다.** 고정 날짜로 바꿨다.

**측정 대상이 조용히 바뀔 뻔했다.** F02가 20실 한정 특가를 여는데, F04의 부하 시나리오가 그 특가를 때린다. F02가 "특가 대상 객실타입의 그날 일반 재고가 넉넉하지 않으면, F04가 재는 게 특가 경합이 아니라 일반 재고 고갈"이라는 걸 짚었다. 성공 20건이 나와도 그게 특가 제약 때문인지 재고 때문인지 구분되지 않는다.

**문서가 코드보다 먼저 낡았다.** F02가 설계를 바꾸면서 결정 항목과 인터페이스는 갱신했는데 API 절이 따라오지 않았다. F04가 스크립트를 짜려고 그 문서에서 엔드포인트를 찾다가 발견했다. **다른 세션이 내 문서를 실제로 쓰는 순간이 문서 오류가 드러나는 시점**이다.

**규칙이 층위로 정리됐다.** F03은 검색에서 과거 날짜를 막고, F01은 예약에서 과거 날짜를 열어뒀다. F03이 이걸 "감수해야 할 비일관"으로 올렸는데, 실은 비일관이 아니라 책임이 다른 것이었다. 검색은 고를 수 있는 것을 보여주고 예약은 만들 수 있는 것을 받는다. F01의 규칙도 `checkIn` 기준에서 `checkOut` 기준으로 바뀌면서 더 정확해졌다.

### AI가 자기 테스트의 무의미함을 발견한 사례

가장 값진 사례다. F04가 멱등성 부하 시나리오를 다 짜놓고 계약 문서를 다시 읽다가 이렇게 보고했다.

> 멱등 키가 `(사용자, 키)` 조합이라, 재시도마다 다른 가상 사용자 번호를 쓰면 같은 키 문자열이어도 전부 다른 요청이 된다. **1000건이 다 성공하고 "중복 예약 0건"이 나오는데, 멱등성이 작동해서가 아니라 애초에 중복 요청을 안 보낸 것이다. 실패했으면 차라리 나았을 통과다.**

리포트에는 "멱등성 검증 통과"로 적혔을 것이고, 읽는 사람은 검증됐다고 믿었을 것이다.

이 발견 뒤 **"각 시나리오마다 이 테스트가 통과했는데도 시스템이 망가져 있을 수 있는 경우를 한 줄씩 적어보라"**고 지시했고, 다섯 건이 더 나왔다. 그중 하나는 검증 체계 전체를 무력화하는 종류였다 — **불변식 검증이 전부 "결과가 비면 통과" 형태라, 검증 SQL이 컬럼명 오타 하나로 0행을 반환하면 모든 것이 초록이 된다.**

그래서 **검증기를 검증하는 스크립트**를 따로 만들었다. 일부러 불변식을 깨뜨려 두고 검증 쿼리가 실제로 잡아내는지 확인한 뒤 되돌린다.

### 자기 결정을 뒤집은 사례

**F01: "문서로 덮는다"를 기각.** 특가로 판 예약에 정가를 기록하고 금액 불일치를 문서로 설명하자는 안이 있었다. F01이 거부했다 — 단가를 저장하는 이유가 "사후 복구가 불가능해서"인데, 거기에 정가를 박으면 **틀린 값을 되돌릴 수 없게 일부러 저장하는 것**이 된다.

**F01: 안 만들기로 한 필드를 만듦.** 쿠폰 확장용 필드를 "항상 비어 있는 필드는 문서가 아니라 잡음"이라며 만들지 않기로 했었다. 나중에 특가가 실제 사용자가 되자 뒤집으면서 이렇게 적었다 — *"원래 판단이 틀렸던 게 아니라 전제가 바뀐 것이다."*

**F02: 결함을 안고 가던 설계를 폐기.** 승인된 예외 범위를 넓히지 않으려고 2단계 방식을 쓰고 있었는데, 그 대가로 "예약은 남았는데 특가만 반납되는 틈"을 안고 있었다. 대안이 생기자 뒤집으면서 **"예외를 확대하지 않으려고 실제 결함을 안고 가는 건 본말이 뒤집힌 선택"**이라고 적었다.

**F01: 자기 문서에서 자기모순 3건 발견.** 제출 문서 초안을 다시 훑으라고 했더니, 문장을 다듬는 대신 스펙과 어긋난 곳을 찾았다. 상태를 하나 추가하면서 갱신하지 못한 숫자, 문제 사례로 부적절한 예시, 표준 문구를 무심코 붙여 사실이 아니게 된 다이어그램 라벨. **"읽기 좋아지는 것보다 사실이 틀린 게 더 위험하다"**는 판단이었다.

### 두 세션이 따로 같은 답에 닿은 사례

F01과 F02가 서로 모르는 상태에서 **노쇼 시 재고를 복원하지 않는다**는 같은 결론에 도달했다. 근거도 같았다 — 방이 그 손님 앞으로 잡혀 있었고 재판매되지 않았으므로 소진된 것이다. (노쇼 기능 자체는 이후 관리자 판단으로 이번 범위에서 유예됐다. 두 판단이 일치했다는 사실은 그대로 기록해 둔다.)

F02와 F04는 각자 다른 작업을 하다 **"특가로 팔린 방도 실제 객실을 차지하는가"**라는 같은 질문에 막혔다. 한쪽은 설계 경계 때문에, 한쪽은 부하 판정식 때문에.

**독립적으로 같은 곳에 닿았다는 건 그 지점이 설계의 급소라는 신호**로 읽었다.

## 4. 사람이 한 일

AI가 많은 일을 했지만 **결정은 사람이 했다.**

- 무엇을 만들고 무엇을 뺄 것인가 (범위 문서의 D1~D6)
- 각 feature 스펙의 D 항목 승인
- 일정이 밀릴 때 무엇부터 자를 것인가
- 세션을 언제 열고 어떤 순서로 병합할 것인가

그리고 AI가 만든 규칙 자체도 사람이 승인했다. 다이어그램 표기법은 시안 4종을 만들어 고르게 했고, 병렬 작업 정책은 ADR로 남겨 동의를 받았다.

**AI에게 넘기지 않은 판단의 공통점은 "트레이드오프가 있는 선택"이었다.** 답이 하나인 문제는 맡기고, 무엇을 포기할지 정하는 문제는 사람이 했다.

---

## 5. 한계와 주의

**AI는 자기가 만든 테스트의 무의미함을 잘 발견하지 못한다.** 위 멱등성 사례는 자동으로 나온 것이 아니라 "통과했는데도 망가져 있을 수 있는 경우를 적어보라"는 명시적 지시 뒤에 나왔다. **질문하지 않으면 나오지 않는다.**

**AI는 문서를 부분적으로만 갱신한다.** 결정을 바꾸면 그 결정을 적은 절은 고치지만 그 결정에 딸린 API 절, 다이어그램, 예시는 따라오지 않는 일이 반복됐다. 설계를 바꿀 때마다 **"이 변경의 흔적이 남았을 만한 곳을 전부 훑어라"**는 별도 지시가 필요했다.

**AI는 자기 결정을 무겁게 보이려는 경향이 있다.** 승인 항목의 등급을 스스로 내린 사례는 51개 중 한 번뿐이었다.

**병렬 세션의 진짜 병목은 충돌이 아니라 승인이었다.** 네 세션이 한 시간 만에 스펙 네 벌과 부하 스크립트를 냈고, 그 뒤로는 전부 사람의 판단을 기다렸다. 도구를 늘리면 만드는 속도는 늘지만 **검토하는 속도는 늘지 않는다.** 그래서 승인 보고서를 압축하는 것(24KB → 12KB), 결정에 등급을 매기는 것, 하위 영향을 표시하는 것이 실제로 일정을 좌우했다.
