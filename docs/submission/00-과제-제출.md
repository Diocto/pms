## 1. 무엇을 풀었나

### 1.1 같은 방을 동시에 예약하면 무슨 일이 벌어지는가

숙박 예약에서 진짜 어려운 것은 화면도 결제도 아니고 **한 개 남은 방을 두 사람이 같은 순간에 누르는 상황**입니다. 재고를 읽고 → 남았는지 판단하고 → 깎는 세 단계 사이에 다른 요청이 끼어들면 둘 다 "남아 있다"고 읽고 둘 다 예약에 성공합니다. 방은 하나인데 예약은 둘입니다.

이것이 초과 판매(오버부킹)입니다. 손님이 도착해서야 발견되고, 그 시점에는 소프트웨어로 해결할 수 없습니다.

### 1.2 더 어려운 쪽은 되돌리는 경로다

막는 것보다 어려운 것이 **되돌리는 것**입니다.

하나의 예약에 취소, 결제 실패, 시간 만료가 동시에 도착할 수 있습니다. 셋 다 "재고를 돌려놓아라"는 뜻인데, 실제로 돌려놓아야 하는 횟수는 **한 번**입니다. 두 번 돌려놓으면 있지도 않은 방이 재고에 생깁니다.

**그리고 이 오류는 아무도 발견하지 못합니다.** 초과 판매는 손님이 항의해서 알려지지만, 재고를 한 번 더 돌려놓은 것은 항의할 사람이 없습니다. 다음 손님이 그 유령 재고를 예약하고, 그때 다시 초과 판매가 됩니다.

### 1.3 후보가 셋이었고, 그중 이것을 골랐다

처음에 놓고 고민한 후보는 셋이었습니다.

| # | 후보 | 무엇이 어려운가 |
|---|---|---|
| ① | 프로모션 때 예약이 폭주하는 경우 | 짧은 시간에 수천 건이 한 자원에 몰린다 |
| ② | **숙박 예약에서 초과 판매를 막는 경우** | 같은 방을 여러 사람이 같은 순간에 예약한다 |
| ③ | 숙박 일자별로 예약 금액을 다르게 하는 경우 | 성수기·주말에 따라 하루하루 값이 다르다 |

셋 다 예약이라는 같은 도메인에 있고 셋 다 만들면 볼거리가 있습니다. 남은 시간에 셋을 다 할 수 없다는 것이 문제였습니다.

**②를 고른 이유는 셋이 나란한 후보가 아니라 하나가 나머지의 토대였기 때문입니다.**

②를 풀려면 재고를 `(객실타입, 날짜)` 한 줄로 쪼개야 합니다. 기간을 통째로 들고 있으면 어느 날짜에서 부딪혔는지 알 수 없으니까요. **그런데 ③이 필요로 하는 것도 정확히 그 줄입니다.** "8월 20일은 12만원, 21일은 18만원"을 말하려면 20일과 21일이 각각 행으로 있어야 합니다.

순서를 뒤집으면 ③이 성립하지 않습니다. 날짜 슬롯 없이 가격만 만들면 그것은 **"객실타입마다 값이 다르다"이지 "날짜마다 값이 다르다"가 아닙니다.** 그래서 **날짜별 재고 슬롯을 먼저 만들고 그 위에 가격을 입히는 순서**로 정했습니다.

**①은 실제로 만들어 보고 접었습니다.** 후보로만 두고 지나친 것이 아니라 별도 feature로 착수했는데, 폭주를 막는 코드가 예약 생성과 **똑같은 조건부 UPDATE 한 문장**이었습니다. 같은 증명을 두 번 하는 셈이라 폐기하고 그 시간을 부하테스트에 썼습니다 ([ADR-0058](../decisions/ADR-0058-선착순-특가-폐기.md)).

**②만 고유하게 가진 어려움이 하나 더 있습니다** — 1.2의 되돌리는 경로입니다. ①에도 ③에도 이 문제는 없습니다.

#### 이 순서가 맞았는지는 지금 코드에서 보입니다

③을 얹을 자리가 실제로 열려 있는지 확인했습니다.

- **슬롯은 이미 있습니다.** `room_daily_inventory`가 `(객실타입, 날짜)`를 기본키로 갖고 하루치 잔여를 듭니다. 5박 예약은 이미 5개 행을 건드립니다
- **가격만 아직 평평합니다.** 단가가 객실타입에 하나 붙어 있고 날짜와 무관합니다
- **그래서 ③은 컬럼을 더하는 일이 됩니다.** 테이블을 새로 만들 필요가 없습니다

다만 **공짜는 아닙니다.** 지금 총액이 `단가 × 박수`라는 곱셈 한 번인데, 날짜별 가격은 이 전제를 깨서 **박별 단가의 합**으로 바꿔야 합니다. 예약 생성과 검색 양쪽을 고쳐야 합니다.

값을 붙들어 두는 구조는 이미 서 있습니다. 예약 행이 단가와 총액을 **스냅샷으로** 갖고 있어서, 나중에 가격표가 바뀌어도 이미 잡힌 예약의 금액은 흔들리지 않습니다.

판단의 전문은 [ADR-0063](../decisions/ADR-0063-과제-문제-선정.md)에 있습니다. **셋을 다 조금씩 만드는 대안도 검토했고 왜 접었는지도 거기 적었습니다.**

그래서 이 프로젝트는 **동시성 제어 · 멱등성 · 상태 전이** 셋에만 깊게 들어가고, 나머지는 의도적으로 얕게 두거나 잘랐습니다. 무엇을 잘랐는지는 2.3에 전부 있습니다.

## 3. 구현하면서 고려한 것들

### 3.1 재고를 날짜 단위 행으로 쪼갠 것

기간을 통째로 다루지 않고 `(객실타입, 날짜)` 하나에 잔여 수량 한 줄을 둡니다. 8/20~8/23 예약이면 3개 행을 건드립니다.

이 선택 하나가 뒤의 모든 것을 정합니다. **경합의 대상이 이 행이고, 잠금의 단위도 이 행이고, 초과 판매를 막는 제약이 붙는 곳도 이 행**입니다. 기간을 통짜로 들고 있었다면 어디서 부딪혔는지 알 수 없었을 것입니다.

### 3.2 세 겹으로 막는다

```
1층. Redis 분산락       — 경합을 DB까지 내려보내지 않는다 (비용을 줄인다)
2층. 조건부 UPDATE      — WHERE remaining >= ? 로 갱신하고 rowcount를 본다 (실제 판단)
3층. DB CHECK / UNIQUE  — remaining >= 0 을 DB가 거부한다 (마지막 방어)
```

여기서 중요한 것은 **1층이 정확성을 담당하지 않는다**는 점입니다. 분산락을 완전히 꺼도 결과는 같아야 하고, 실제로 같았습니다(3.7).

`UPDATE ... WHERE remaining >= 요청수량`의 `rowcount`가 0이면 재고가 없는 것입니다. 읽고 판단하고 쓰는 것이 아니라 **한 문장 안에서 판단과 갱신이 같이 일어나기 때문에** 그 사이에 끼어들 틈이 없습니다.

> **한 문장으로 줄이면: 정합성은 DB가 지키고, 락은 비용을 줄이는 장치다.**

### 3.3 상태는 표가 정한다 — 36칸

`(현재 상태, 이벤트) → 다음 상태` 표를 만들고 그 표로만 전이합니다. `setStatus` 같은 세터는 만들지 않았습니다. 외부는 이벤트만 던집니다.

상태 6개 × 이벤트 6개 = **36칸을 전부 채웠습니다.**

| 종류 | 칸 수 | 뜻 |
|---|---|---|
| 허용 | 7 | 상태가 실제로 바뀝니다 |
| **멱등 흡수** | 6 | 이미 그 상태입니다. 성공으로 응답하되 **아무것도 바꾸지 않습니다** |
| 거부 | 23 | 잘못된 요청입니다 |

**멱등 흡수 6칸이 이 표의 핵심입니다.** 이미 취소된 예약에 취소가 또 오면 성공으로 응답하지만 `restores_inventory=False`로 표시돼 있어 **재고를 두 번 돌려놓지 않습니다.** 1.2에서 말한 "아무도 발견하지 못하는 오류"를 여기서 막습니다.

if-else로 분기했다면 23개 거부 칸 중 몇 개는 빠졌을 것입니다. 표로 만들면 빈 칸이 눈에 보입니다.

### 3.4 멱등성 키는 예약 생성에만 요구한다

`Idempotency-Key` 헤더는 **`POST /api/reservations` 하나에만** 필수입니다.

확정·취소·체크인·체크아웃에는 요구하지 않습니다. 이 요청들은 **전이 표의 멱등 흡수 칸이 이미 흡수하기 때문**입니다. 같은 취소 요청이 열 번 와도 첫 번째만 상태를 바꾸고 나머지 아홉은 흡수됩니다. 키를 따로 받으면 같은 일을 두 군데서 하게 됩니다.

예약 생성만 다른 이유는, **생성은 "이미 그 상태"라는 것이 없기 때문**입니다. 재시도가 새 예약을 만들어버립니다. 그래서 여기만 Redis에 키를 남깁니다.

### 3.5 외부 호출은 트랜잭션 밖에서

결제는 트랜잭션을 열어둔 채로 부르지 않습니다. 상대가 느리면 **DB 커넥션을 쥔 채로 기다리게 되고**, 그동안 다른 요청들이 커넥션을 못 받습니다.

대신 승인과 커밋 사이에 틈이 생깁니다. 그 틈에서 프로세스가 죽으면 돈은 나갔는데 예약은 확정되지 않습니다.

**이 틈을 알면서 남겼습니다.** 관리자 판단으로 고객 문의를 받아 사람이 처리하는 쪽을 택했습니다. 다만 "사람이 처리한다"고 적으려면 사람이 찾을 수 있어야 하므로 코드로 확인했습니다 — **우리 DB만 봐서는 못 찾고**(만료된 예약과 겉모습이 같습니다), 결제 호출에 예약 id와 멱등성 키를 함께 넘기므로 **결제사 원장과 대조하면 찾습니다.** 이 한계까지 [ADR-0062](../decisions/ADR-0062-결제-예약-불일치는-사람이-처리한다.md)에 적었습니다.

**그리고 이 판단은 짐작이 아니라 실측에 기댑니다.** "커넥션을 오래 쥐면 옆 기능이 대가를 치른다"는 것을 이 시스템에서 두 번 측정했습니다(3.7의 S5, S8).

### 3.6 검색은 잠그지 않고 읽는다

검색은 재고에 잠금을 걸지 않습니다. 검색 결과가 살짝 낡는 것은 받아들이고, **예약 시점에 다시 확인해서 막습니다.** 검색이 잠금을 걸면 검색량이 예약을 밀어냅니다 ([ADR-0030](../decisions/ADR-0030-검색은-잠금-없이-읽는다.md)).

캐시 무효화는 자리만 만들고 연결하지 않았습니다. 짧은 TTL로 낡음을 처리합니다 ([ADR-0031](../decisions/ADR-0031-캐시-무효화는-자리만-만든다.md)).

### 3.7 부하로 확인한 것

숫자는 전부 실측이고, **판정 기준은 측정 전에 못 박았습니다.**

**(가) 초과 판매는 일어나지 않았다.** 100실짜리 재고에 20초 동안 6,000건을 밀어넣었습니다. 성공은 정확히 100건입니다.

**(나) 분산락을 꺼도 결과가 같았다 (S5).** 락을 끄고 3회, 켜고 3회 돌렸습니다. **여섯 번 모두 성공 건수가 정확히 같았습니다.** 다른 것은 비용이었습니다 — 락을 켜면 DB 행 잠금 대기가 **0건**, 끄면 **434건**. 락은 정확성이 아니라 비용을 위한 장치라는 3.2의 문장이 여기서 증명됩니다.

**(다) 캐시의 값어치는 검색이 아니라 예약에서 나왔다 (S8).** 검색을 초당 500건 흘리면서 캐시를 껐다 켰습니다.

| | 검색 p95 | 예약 p95 |
|---|---|---|
| 캐시 켬 | 8.6ms | 24.7ms |
| 캐시 끔 | 11.0ms | 385.3ms |
| 차이 | **1.3배** | **15.6배** |

검색 자체는 1.3배밖에 안 빨라졌는데 같은 시간 예약이 15.6배 빨라졌습니다. **캐시가 산 것은 검색 속도가 아니라 예약이 쓸 DB 커넥션입니다.**

다만 이 회차에서 커넥션 수를 직접 세지는 않았습니다. 위 문장은 예약 p95 15.6배에서 끌어낸 **해석**이고, 커넥션을 실제로 센 것은 (나)의 락 대조 회차입니다 — 거기서 경합이 DB로 내려가자 커넥션 점유가 4배로 늘었습니다. 리포트에도 이 구분을 적어 뒀습니다.

**(라) 만료가 몰려도 DB를 때리지 않는다 (L5).** 만료 한 건당 DB 조회 약 3.2회. 방어가 없을 때의 최악은 9회, 완벽한 방어는 1회입니다.

**(마) 고쳤고, 고쳤다는 것을 다시 측정했다 (S4-B).** 커넥션 풀 초기화가 스레드 안전하지 않아 워커별 커넥션이 44/44/44/5로 튀고 5xx가 21건 났습니다. `ThreadSafeSingleton`으로 고친 뒤 예열 없이 다시 돌렸더니 **5xx 0건, 워커별 커넥션 1~2개**였습니다.

전체 시나리오와 원자료는 [04-부하테스트.md](04-부하테스트.md)와 `docs/load-test/`에 있습니다.

### 3.8 알면서 남긴 한계

**모르고 빠뜨린 것과 알고 남긴 것을 구분해서 적었습니다.**

- 물리적 방 배정이 없습니다. "3개 남음"까지만 압니다.
- **일자별 가격이 없습니다.** 1.3의 후보 ③입니다. 얹을 자리는 열려 있지만 지금은 객실타입마다 값 하나입니다.
- 결제-예약 불일치의 자동 감지가 없습니다. 손님이 문의하지 않으면 모릅니다.
- 캐시 무효화가 연결돼 있지 않습니다. TTL이 지나야 갱신됩니다.
- 모의 결제라 결제사 원장이 없어, 3.5의 대응 절차를 지금 환경에서는 시연할 수 없습니다.
- 인증이 없습니다. `X-User-Id`를 헤더로 그냥 믿습니다.

## 4. AI를 어떻게 일하게 만들었나 — 하네스

이 프로젝트는 코드를 AI가 썼습니다. 그래서 **"어떻게 시켰나"가 산출물의 일부**입니다.

### 4.1 문서가 곧 하네스다

`CLAUDE.md`에 "어떤 작업을 할 때 어떤 문서를 반드시 먼저 읽어야 하는가"를 표로 박았습니다. 코드를 쓰기 전엔 코딩 규칙, 도메인을 만들 땐 DDD 문서, 테스트를 쓸 땐 TDD 문서. **읽지 않고 쓴 코드는 리뷰에서 반려됩니다.**

규칙은 `docs/architecture/` 아래에 여섯 편으로 나눠 뒀습니다 — 코딩 규칙, 클린 아키텍처, DDD, TDD, 다이어그램 표기, 병렬 작업.

### 4.2 워크플로우를 스킬로 고정했다

단계마다 대응하는 스킬을 만들어 절차가 매번 달라지지 않게 했습니다.

```
스펙 작성(feature-spec) → [승인] → 개발 사이클(dev-cycle) → [승인] → 완료
                                    TDD → 구현 → 리뷰어 3명 → 반영 → 반복
```

결정이 정해지면 `decision-log`로 ADR을, 새 개념이 나오면 `learning-note`로 학습 노트를 남깁니다. 부하테스트는 `load-test` 스킬이 절차를 잡습니다.

### 4.3 승인 게이트

스펙이 나오면 멈추고, 구현이 끝나면 또 멈춥니다. 사람이 승인해야 다음으로 갑니다. 승인 문서에는 **결정 검토란**을 반드시 둡니다 — 작성자가 내린 결정을 항목마다 (결정 · 이유 · 트레이드오프 · 대안 · 확인 질문)으로 모아서, 사람이 항목 단위로 동의하거나 뒤집습니다. 결정을 본문에 묻어두면 사람이 못 봅니다.

`docs/reports/`에 보고서 17건이 남아 있고, 그중 7건이 승인 게이트를 통과시킨 보고서입니다. 나머지는 기획·조사·확인 요청입니다.

### 4.4 병렬 세션과 격리 규칙

feature마다 별도 세션을 띄우고 각자 git worktree에 격리했습니다. 충돌을 막는 규칙은 세 가지입니다.

- **패키지 소유** — 다른 feature가 소유한 패키지는 건드리지 않는다
- **번호 대역** — 마이그레이션 번호와 ADR 번호를 feature별로 나눠 갖는다
- **막혔을 때 어디로 가는가** — 범위 질문은 사람에게, 계약 질문은 **그 세션에 직접**, 구현 방법은 **스스로 정한다**

세 번째가 가장 많이 고쳐진 규칙입니다(5.1).

### 4.5 리뷰어 서브에이전트 3종

구현이 끝나면 관점이 다른 리뷰어 셋을 붙입니다.

| 리뷰어 | 보는 것 |
|---|---|
| 동시성 리뷰어 | 경합 지점, 잠금, 트랜잭션 경계, 멱등성 |
| 도메인 리뷰어 | 도메인 모델, 상태머신, 유스케이스 흐름 |
| 아키텍처 리뷰어 | 레이어 경계, DB 설계, 코딩 규칙 위반 |

같은 코드를 세 번 읽되 **다른 것을 찾도록** 나눴습니다. 리뷰 기록 11건이 남아 있고, F01은 4회차까지 돌았습니다.

### 4.6 결정을 ADR로 남긴다 — 22건

결정이 하나 정해질 때마다 문서 한 장을 남깁니다. 여기에 **안 만든 것의 이유**가 들어 있습니다.

**누가 정했는지를 구분해서 적었습니다.** AI가 정한 것과 사람이 정한 것은 다르게 읽혀야 하기 때문입니다. 사람이 정한 것은 지시 원문을 그대로 인용해 뒀습니다.

**늦게 쓴 것은 늦게 썼다고 적었습니다.** 8월 16일에 "대화로만 정하고 저장소에 안 남은 결정"이 여섯 개 있는 것을 발견해 소급 기록했고, 소급이라는 사실 자체를 [INDEX](../decisions/INDEX.md)에 적었습니다. 결정 이력의 값은 완결성이 아니라 정확성입니다.

### 4.7 학습 노트

작업 중 처음 나온 개념은 제목만 먼저 쌓아두고 나중에 채웁니다. 7편이 있습니다 — 하이드레이션, 번들, 수량 재고와 호수 배정, 낡음을 다루는 두 층 등. **제출 대상이 아니라고 명시**해서, 학습이 산출물 압박을 받지 않게 했습니다.

### 4.8 사람이 한 일

AI가 하지 않은 것을 적는 쪽이 정직합니다.

- **무엇을 만들지 정하기** — 문제 선정, 범위 절단, 무엇을 뺄지
- **결정 뒤집기** — 승인 게이트에서 항목 단위로 (5.5에 목록)
- **일하는 방식 고치기** — 병렬을 접고 순차로 바꾼 것, PM 역할을 줄인 것
- **기준 정하기** — 부하테스트 판정 기준을 측정 전에 못 박게 한 것

상세는 [05-AI-활용.md](05-AI-활용.md)에 있습니다.

## 5. 하면서 실제로 나온 문제와 고친 것

**여기 적은 것은 전부 실제로 일어난 일입니다.**

### 5.1 일하는 방식에서 나온 문제

**병렬 다섯 세션이 구현 대신 협의만 했다.** 계약을 서로 물고 있는 세션을 동시에 붙였더니, 각자 남의 답을 기다리느라 아무도 코드를 못 썼습니다. 하루 만에 접고 순차로 바꿨습니다 ([ADR-0052](../decisions/ADR-0052-병렬에서-순차로.md)).
→ **배운 것:** 착수 전에 "남의 답 없이 오늘 끝낼 일이 있는가"를 먼저 묻습니다.

**PM이 기술 질문에 답하다가 틀렸다.** PM 세션이 구현 조언을 하기 시작했는데, PM은 코드를 안 보므로 **조언 일곱 건이 세션 반박으로 철회**됐습니다. PM 역할을 "무엇을 만드는가"까지로 잘랐습니다 ([ADR-0053](../decisions/ADR-0053-PM-역할-축소.md), 기록은 `docs/reports/낭비-정리.md`).
→ **배운 것:** 답을 아는 사람이 답합니다. 중개하면 왕복만 늘고 오답이 섞입니다.

**"수정 완료"가 무슨 뜻인지 몰라 사고가 났다.** 세션이 "고쳤다"고 알렸는데 그게 커밋인지 푸시인지 병합인지 구분이 안 됐습니다. 실제로 5.4의 사고가 여기서 났습니다.
→ **고친 것:** 세션 간 통지에 **상태 낱말을 반드시 넣게** 규칙을 바꿨습니다 — `푸시함 (PR 없음)` / `PR #N 열림` / `PR #N 병합됨`. 받는 쪽은 실물로 확인할 의무도 같이 넣었습니다.

### 5.2 검증이 스스로 거짓말할 뻔한 것

**이 항목이 이번 작업에서 가장 위험했던 문제입니다.**

**부하테스트 보고서가 존재하지 않는 수정을 근거로 들었다.** 커넥션 풀 문제를 고쳤다는 보고서(S4-B)가 있었는데, 그 수정 코드가 **보고서 안에만 있고 실제 코드에는 없었습니다.** 커밋은 됐지만 PR이 열리지 않아 병합되지 않은 상태였습니다.
→ **고친 것:** 병합하고 다시 측정했습니다. 그리고 5.1의 상태 낱말 규칙을 만들었습니다.

**측정 결과를 보고 기준을 정하려 했다.** 부하테스트에서 값을 먼저 본 뒤 "이 정도면 통과"라고 판정하면, 결과에 맞춰 기준을 고르게 됩니다.
→ **고친 것:** 판정 기준을 **측정 전에** 문서에 못 박게 했습니다. 그리고 기준을 상수가 아니라 환경의 함수(워커 수 등)로 적게 했습니다.

**예열이 결과를 좋게 만들고 있었다.** S4-B 재측정 때 예열 요청을 넣으면 문제가 안 보입니다. 예열 없이 다시 돌려서 5xx 0건을 확인했습니다.

### 5.3 코드에서 나온 문제

**같은 제약이 세 군데 흩어져 있었다.** "최대 30박" 제한이 예약 API, 검색 API, 화면 세 곳에 각각 박혀 있었습니다. 제약을 없애기로 했더니 세 번 고쳐야 했고, 세 번째를 놓칠 뻔했습니다.
→ 세 곳 모두 제거하고 `MAX_NIGHTS` 검색이 0건인 것을 확인했습니다. 애초에 그 제한의 근거가 잘못됐다는 것도 그 과정에서 드러났습니다 — 재고 테이블에는 존재하는 날짜의 행만 있어서, 긴 기간을 막을 이유가 없었습니다.

**결정 번호를 잘못 인용했다.** 스레드 안전 수정의 근거로 D34를 적었는데 D34는 다른 결정(예약 목록 API)이었습니다. 코드 주석 3곳, 문서 4곳에서 같은 오류가 복사돼 있었습니다.
→ 일곱 곳 모두 D37로 고쳤습니다.

**같은 산출물을 두 세션이 만들었다.** 격리 규칙이 있어도 "이건 공용이겠지" 하는 파일에서 겹쳤습니다.
→ 소유자를 명시하는 쪽으로 규칙을 보강했습니다.

### 5.4 제출물이 사실과 어긋날 뻔한 것

**커밋했는데 병합되지 않은 것을 아무도 못 봤다.** 한 세션이 5개 커밋을 푸시해두고 PR을 열지 않았습니다. 그 안에 **관리자 지시로 없애기로 한 제한이 그대로 남아 있었고**, 5.2의 스레드 안전 수정도 여기 묶여 있었습니다. 현황판은 "완료"였습니다.
→ 병합 전에 **`main`에 실제로 있는지 grep으로 확인**하는 절차를 넣었습니다.

**테스트 개수를 옛날 숫자로 적어뒀다.** 제출 문서에 "215개 통과"라고 적혀 있었는데 그 시점 실제는 308개였습니다(최종 312개).
→ 문서의 수치는 쓰는 시점에 다시 세게 했습니다.

**화면의 평점이 진짜처럼 보였다.** 시연용으로 넣은 평점·리뷰 데이터가 실제 투숙 기록처럼 보일 수 있었습니다.
→ 화면에 "**평점과 리뷰는 시연용 예시 데이터**"를 표시하고, 실제 값(검색 결과·잔여 수량)과 구분했습니다.

### 5.5 사람이 뒤집은 결정들

승인 게이트가 실제로 작동한 사례입니다.

| 뒤집힌 것 | 어떻게 바뀌었나 |
|---|---|
| 기술 스택 (Java/Spring) | Python/FastAPI로 전환. 구현 0줄 시점이라 되돌리는 비용이 쌌습니다 |
| 병렬 5세션 | 순차로. 하루 만에 |
| PM이 기술 조언을 한다 | 스펙 층까지만. 조언 7건 철회 |
| 최대 30박 제한 | 제거. 제한의 근거 자체가 틀렸습니다 |
| 선착순 특가 구현 | 폐기. 같은 증명의 반복이었습니다 |
| 결제 순서를 바꾸자는 제안 | 유지 쪽으로. 바꾸면 커넥션을 쥔 채 외부를 기다리게 되는데, 그 비용이 이 시스템에서 실측된 병목과 같은 종류였습니다 |

### 5.6 문제 → 규칙 매핑

**문제가 날 때마다 규칙을 한 줄 고쳤습니다.** 사람이 매번 감시하는 대신 다음번에 자동으로 걸리게 하는 쪽입니다.

| 실제로 난 문제 | 만들어진 규칙 |
|---|---|
| 세션들이 서로를 기다리기만 함 | 착수 전 "남의 답 없이 오늘 끝낼 일이 있는가" 확인 |
| PM 조언이 틀림 | PM은 스펙 층에서 멈춘다. 기술 질문은 소유 세션이 답한다 |
| "수정 완료"의 뜻이 모호함 | 통지에 상태 낱말 필수 (푸시함 / PR 열림 / 병합됨) |
| 보고서가 없는 수정을 인용함 | 받는 쪽이 실물로 대조할 의무 |
| 측정 후 기준을 정하려 함 | 판정 기준은 측정 전에 문서에 못 박는다 |
| 결정이 대화에만 남음 | 결정마다 ADR. 늦게 쓴 것은 늦었다고 적는다 |
| 결정이 본문에 묻힘 | 승인 문서에 결정 검토란 필수 |

## 6. 계획한 것과 실제로 된 것

### 6.1 처음 계획 대비

| 계획했던 것 | 결과 |
|---|---|
| 하네스 구성 (규칙 문서 · 스킬 · 게이트) | **했다.** 규칙 6편, 스킬 6개, 보고서 17건 |
| 프로젝트 구조와 워크플로우 정의 | **했다.** `CLAUDE.md`가 진입점, 작업별 필독 문서 표 |
| 스펙 하네스 (템플릿에 포함 항목 고정) | **했다.** `docs/spec/TEMPLATE.md`, 결정 검토란 필수 |
| 문제 정의와 해결 과정 기록 | **했다.** ADR 22건 + 리뷰 11건 + 보고서 17건 |
| 아키텍처 설계 하네스 | **했다.** 레이어 경계 셋을 규칙으로 ([ADR-0055](../decisions/ADR-0055-레이어-경계-세-가지.md)) |
| 다중 에이전트 리뷰 | **했다.** 다만 외부 모델 대신 관점을 나눈 서브에이전트 3종으로 |
| 병렬 다중 에이전트 | **줄였다.** 5세션 동시 → 순차 + 부분 병렬. 이유는 5.1 |
| 간단한 프론트엔드 | **했다.** Next.js. 검색 → 예약 → 확정/취소가 실제로 돕니다 |
| CI/CD | **했다.** GitHub Actions + Railway. Terraform은 쓰지 않았습니다 |
| 검토자용 문서 한 장 | **했다.** 이 문서입니다 |
| AI 활용 로깅 하네스 | **안 했다.** 6.2 |

### 6.2 안 한 것 — AI 활용 로깅 하네스

**프롬프트에 ID를 붙여 어떤 프롬프트가 어떤 산출물을 만들었는지 기계적으로 추적하는 장치**를 계획했는데 만들지 않았습니다. 저장소에 흔적이 없습니다.

**대신 남은 것은 결정 단위의 기록입니다** — ADR 22건에 "누가 정했는가"가 적혀 있고, 사람이 정한 것은 지시 원문이 인용돼 있습니다. 프롬프트 단위보다 거칠지만, 되짚을 때 필요한 것은 대개 "이 결정을 누가 왜 내렸나"였습니다.

**만들었어야 했나.** 이 규모에서는 결정 단위 기록으로 충분했다고 봅니다. 다만 5.2의 사고(보고서가 없는 수정을 인용한 것)는 산출물과 근거를 기계적으로 잇는 장치가 있었으면 더 빨리 잡혔을 것입니다.

### 6.3 계획을 크게 바꾼 결정 셋

| 결정 | 시점 | 왜 |
|---|---|---|
| 언어를 Java에서 Python으로 | 8/15 | 구현 0줄 시점. 남은 시간에 구현과 검증을 다 하려면 익숙한 도구가 필요했습니다 |
| 병렬을 접고 순차로 | 8/15 | 계약을 서로 무는 세션은 구현 대신 협의만 합니다 |
| 기능을 넓히는 대신 부하로 파고들기 | 8/16 | 선착순 특가는 예약 생성과 같은 증명이었습니다. 그 시간을 시나리오 10개에 썼습니다 |

**셋 다 "넓히지 말고 파라"는 같은 방향입니다.** 이 과제가 보고 싶어 하는 것이 기능 개수가 아니라고 판단했습니다.

**그리고 이 방향은 1.3의 문제 선정에서 이미 정해져 있었습니다.** 후보 셋 중 토대가 되는 하나를 골라 그것만 깊게 판다는 판단이 먼저였고, 위의 셋은 그 판단을 도중에 다시 확인한 것에 가깝습니다.
