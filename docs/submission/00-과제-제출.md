# 숙박 예약 시스템 — 과제 제출 문서

> **이 문서 하나로 과제 전체를 볼 수 있게 썼습니다.** 근거가 궁금한 항목은 각 절의 상세 문서 링크로 들어가시면 됩니다.
>
> - 배포된 화면: https://pms-web-production-3832.up.railway.app
> - 배포된 API: https://pms-api-production-a037.up.railway.app/health
> - 첫 요청은 컨테이너가 깨어나느라 한 번 실패할 수 있습니다. 새로고침하면 정상입니다.

## 1. 풀고자 하는 문제

### 1.1 호텔 - 객실의 오버부킹 문제

숙박 예약에서 가장 기본적으로 해결되어야 하는 것은 **한 개 남은 방을 두 사람이 같은 순간에 예약하려는 상황**입니다. 재고를 읽고 → 남았는지 판단하고 → 재고를 차감하는 세 단계 사이에 다른 요청이 끼어들면 둘 다 "남아 있다"고 읽고 둘 다 예약에 성공할 수 있습니다.

이것이 초과 판매(오버부킹)입니다. 이런 문제가 발생하면 체크인 시점에 손님이 도착해서야 발견되거나, 사전에 예방한다 하더라도 손님의 예약을 뒤늦게 취소해야 하는 문제가 발생할 수 있습니다.

### 1.2 예약시 취소에 대한 재고 증가 문제

하나의 예약이 취소/결제 실패/결제시간 만료 등의 이벤트가 동시에 발생할 수도 있는데, 하나의 예약에 대해서는 하나의 재고만 회복되어야 합니다.

### 1.3 해당 문제를 고른 이유

프로모션 혜택 발생시의 트래픽 증가, 날짜마다 예약금액이 다른 다이나믹 프라이싱 등의 문제도 있었으나 가장 기본기로 지켜져야 하는 날짜별 재고와 오버부킹 문제를 해결하는 시스템이 구축되어야 다이나믹 프라이싱이나 프로모션 혜택의 순간 트래픽 증가 등을 해결할 수 있다고 생각했습니다. 후보 비교와 검토한 대안은 [ADR-0063](../decisions/ADR-0063-과제-문제-선정.md)에 있습니다.

### 2.2 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어·프레임워크 | Python 3.12 · FastAPI (동기) | 남은 시간에 익숙한 도구가 필요했습니다 ([ADR-0050](../decisions/ADR-0050-기술-스택-전환.md)) |
| ORM · DB | SQLModel · MySQL 8.4 | 조건부 UPDATE와 CHECK 제약이 방어의 마지막 층입니다 |
| 캐시·락 | Redis 7.4 | 멱등성 키, 분산락, 검색 캐시 |
| 스키마 | Alembic (9개) | 스키마의 진실은 SQL로 두고 자동 생성에 기대지 않았습니다 |
| 테스트 | pytest + Testcontainers | SQLite 금지 — 실제 MySQL·Redis를 띄워서 돌립니다 |
| 부하 · 화면 | k6 · Next.js 15 | 시나리오 10개 · 런타임 라이브러리 0개 |

SQLite를 금지한 이유가 이 표에서 가장 중요합니다. 증명하려는 것이 전부 DB 엔진의 잠금 동작에 달려 있어, SQLite로 통과하는 동시성 테스트는 아무것도 증명하지 못합니다. 언어는 8월 15일에 Java/Spring에서 Python/FastAPI로 전환하였습니다 — 구현 코드 0줄 시점이라 되돌리는 비용이 없었습니다.

### 2.3 뺀 것과 이유

뺀 것에는 전부 이유를 기록했습니다. 인증은 과제의 관심사가 아니라 `X-User-Id` 헤더 식별로 대체하고 화면에 상시 안내합니다([ADR-0006](../decisions/ADR-0006-인증-제외.md)). 선착순 특가는 착수 후 막는 방법이 예약 생성과 같은 조건부 UPDATE임을 확인하고 폐기했습니다([ADR-0058](../decisions/ADR-0058-선착순-특가-폐기.md)). 다이나믹 프라이싱은 1.3의 순서에 따라 미뤘습니다. 물리적 방 배정은 수량 재고와 다른 문제라 한계로 기록했고([ADR-0057](../decisions/ADR-0057-방-배정은-범위-밖.md)), 결제-예약 불일치의 자동 보상은 이 규모에 과해 사람이 처리하는 것으로 정했습니다([ADR-0062](../decisions/ADR-0062-결제-예약-불일치는-사람이-처리한다.md)).

## 3. 구현하면서 고려한 것들

### 3.1 재고는 날짜 단위 행

기간을 통째로 다루지 않고 `(객실타입, 날짜)` 하나에 잔여 수량 한 줄을 둡니다. 3박 예약이면 3개 행을 건드립니다. 경합의 대상, 잠금의 단위, 초과 판매를 막는 제약이 붙는 곳이 전부 이 행입니다.

### 3.2 세 겹으로 막는다

```
1층. Redis 분산락       — 경합을 DB까지 내려보내지 않는다 (비용을 줄인다)
2층. 조건부 UPDATE      — WHERE remaining >= ? 로 갱신하고 rowcount를 본다 (실제 판단)
3층. DB CHECK / UNIQUE  — remaining >= 0 을 DB가 거부한다 (마지막 방어)
```

`UPDATE ... WHERE remaining >= 수량`은 판단과 갱신이 한 문장이라 사이에 끼어들 틈이 없습니다. 1층은 정확성을 담당하지 않습니다 — 분산락을 완전히 꺼도 결과가 같아야 하고, 실제로 같았습니다(3.5). **정합성은 DB가 지키고, 락은 비용을 줄이는 장치입니다.**

### 3.3 상태는 표가 정한다

`(현재 상태, 이벤트) → 다음 상태` 표로만 전이하고 상태를 직접 바꾸는 세터는 만들지 않았습니다. 상태 6 × 이벤트 6 = 36칸을 전부 채웠습니다 — 허용 7, 멱등 흡수 6, 거부 23. 멱등 흡수가 1.2 문제의 답입니다: 이미 취소된 예약에 취소가 또 오면 성공으로 응답하되 재고는 다시 돌려놓지 않습니다.

멱등성 키(`Idempotency-Key` 헤더)는 예약 생성에만 요구합니다. 확정·취소·체크인·체크아웃의 재시도는 전이 표의 멱등 흡수가 이미 처리하고, 생성만 "이미 그 상태"가 없어 재시도가 새 예약을 만들 수 있으므로 Redis에 키를 남깁니다.

### 3.4 외부 호출은 트랜잭션 밖에서

결제를 트랜잭션 안에서 부르면 상대가 느릴 때 DB 커넥션을 쥔 채 기다리게 됩니다. 그래서 밖에서 부르고, 대신 승인과 커밋 사이에 틈이 생깁니다. 이 틈은 알면서 남겼습니다 — 이 규모에서는 고객 문의를 받아 사람이 되돌리는 쪽을 택했고, 찾는 방법과 한계까지 [ADR-0062](../decisions/ADR-0062-결제-예약-불일치는-사람이-처리한다.md)에 기록했습니다.

### 3.5 부하로 확인한 것

판정 기준은 측정 전에 확정했고, 숫자는 전부 실측입니다.

| 실측 | 결과 |
|---|---|
| 100실에 6,000건을 20초에 밀어넣음 | 성공 정확히 100건 — 초과 판매 0 |
| 분산락 끄고 3회 · 켜고 3회 (S5) | 여섯 번 모두 성공 건수 동일. 차이는 비용 — DB 행 잠금 대기 0회 ↔ 434회 |
| 검색 캐시 껐다 켬 (S8) | 검색 p95는 1.3배 차이인데 예약 p95는 15.6배 — 캐시가 산 것은 예약이 쓸 DB 커넥션이었습니다 |
| 커넥션 풀 버그 수정 후 재측정 (S4-B) | 5xx 21건 → 0건 — 고쳤다는 것도 측정으로 확인 |

전체 시나리오와 원자료는 [04-부하테스트.md](04-부하테스트.md)에 있습니다.

### 3.6 알면서 남긴 한계

물리적 방 배정 없음(잔여 수량까지만 압니다), 다이나믹 프라이싱 없음(날짜 슬롯이 있어 얹을 자리는 열려 있습니다), 결제-예약 불일치의 자동 감지 없음, 캐시는 짧은 TTL로만 갱신. 각각의 이유는 [03-설계.md](03-설계.md) 9장에 있습니다.

## 4. AI를 어떻게 일하게 만들었나

이 프로젝트는 코드를 AI가 썼습니다. 그래서 "어떻게 시켰나"가 산출물의 일부입니다.

- **문서가 곧 하네스** — 어떤 작업 전에 어떤 문서를 반드시 읽는지 표로 정했고, 읽지 않고 쓴 코드는 리뷰에서 반려됩니다. 규칙 문서 6편이 `docs/architecture/`에 있습니다.
- **워크플로우는 스킬로 고정** — 스펙 작성 → [승인] → 개발 사이클(TDD·리뷰 반복) → [승인]. 단계마다 대응하는 스킬이 있어 절차가 매번 달라지지 않습니다.
- **승인 게이트** — 스펙과 구현 완료마다 멈춥니다. 승인 문서의 결정 검토란에서 사람이 결정을 항목 단위로 동의하거나 뒤집습니다.
- **리뷰어 3종** — 동시성·도메인·아키텍처 관점의 서브에이전트가 같은 코드를 다르게 읽습니다. 리뷰 기록 11건이 남아 있습니다.
- **결정은 ADR로** — 25건이며 안 만든 것의 이유가 여기 있습니다. 누가 정했는지를 구분해 사람이 정한 것은 지시 원문을 인용했고, 늦게 쓴 기록은 늦게 썼다고 적었습니다 ([INDEX](../decisions/INDEX.md)).
- **사람이 한 일** — 문제 선정과 범위 절단, 게이트에서 결정 뒤집기, 일하는 방식 교정, 판정 기준을 측정 전에 정하게 한 것. 상세는 [05-AI-활용.md](05-AI-활용.md)에 있습니다.

## 5. 하면서 나온 문제와 고친 것

**병렬 세션이 구현 대신 협의만 했습니다.** 계약을 서로 무는 세션 다섯을 동시에 붙였더니 각자 남의 답을 기다리느라 코드가 나오지 않았고, 하루 만에 접고 순차로 바꿨습니다 ([ADR-0052](../decisions/ADR-0052-병렬에서-순차로.md)).

**PM이 기술 질문에 답하다 틀렸습니다.** PM은 코드를 보지 않으므로 조언 일곱 건이 세션 반박으로 철회되었고, PM 역할을 "무엇을 만드는가"까지로 줄였습니다 ([ADR-0053](../decisions/ADR-0053-PM-역할-축소.md)).

**검증이 스스로 거짓말할 뻔했습니다 — 가장 위험했던 문제입니다.** 부하테스트 보고서가 근거로 인용한 수정 코드가 보고서 안에만 있고 실제 main에는 없었습니다(커밋만 되고 병합 안 됨). 병합 후 다시 측정했고, 세션 간 통지에 상태 낱말(푸시함/PR 열림/병합됨)을 강제하는 규칙을 만들었습니다.

**측정 결과를 보고 기준을 정하려 했습니다.** 값을 본 뒤 기준을 고르면 결과에 맞추게 되므로, 판정 기준을 측정 전에 문서로 확정하게 했습니다.

문제가 날 때마다 규칙을 한 줄씩 고쳤고, 전체 목록은 [05-AI-활용.md](05-AI-활용.md)에 있습니다.

## 6. 계획한 것과 실제로 된 것

| 계획 | 결과 |
|---|---|
| 하네스(규칙 문서·스킬·승인 게이트)와 스펙 템플릿 | 했다 |
| 문제 해결 과정 기록 (ADR·리뷰·보고서) | 했다 — 합쳐서 52건 |
| 다중 에이전트 리뷰 | 했다 — 외부 모델 대신 관점을 나눈 서브에이전트 3종으로 |
| 병렬 다중 에이전트 | 줄였다 — 5세션 동시 → 순차 + 부분 병렬 (5장) |
| 프론트엔드 · CI/CD | 했다 — Next.js · GitHub Actions + Railway |
| AI 활용 로깅 하네스 (프롬프트 ID 추적) | 안 했다 |

안 한 것은 하나입니다. 프롬프트 단위 추적 대신 결정 단위 기록(ADR)이 남았고, 되짚을 때 필요한 것은 대개 "이 결정을 누가 왜 내렸나"여서 이 규모에서는 충분했다고 봅니다. 다만 5장의 보고서 사고는 산출물과 근거를 기계적으로 잇는 장치가 있었으면 더 빨리 잡혔을 것입니다.

계획을 크게 바꾼 결정 셋(언어 전환, 병렬→순차, 기능 확장 대신 부하 검증)은 전부 "넓히지 말고 파라"는 같은 방향이었습니다.
