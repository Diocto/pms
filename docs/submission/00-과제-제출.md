# 숙박 예약 시스템 — 과제 제출 문서

> - 배포된 화면: https://pms-web-production-3832.up.railway.app
> - 배포된 API: https://pms-api-production-a037.up.railway.app/health
> - 첫 요청은 컨테이너가 깨어나느라 한 번 실패할 수 있습니다. 새로고침하면 정상입니다.

## 1. 풀고자 하는 문제

### 1.1 호텔 객실의 오버부킹 문제

숙박 예약에서 가장 기본적으로 해결되어야 하는 것은 **한 개 남은 방을 두 사람이 같은 순간에 예약하려는 상황**입니다. 재고를 읽고 → 남았는지 판단하고 → 재고를 차감하는 세 단계 사이에 다른 요청이 끼어들면 둘 다 "남아 있다"고 읽고 둘 다 예약에 성공할 수 있습니다.

이것이 초과 판매(오버부킹)입니다. 이 문제가 발생하면 체크인 시점에 손님이 도착해서야 발견되거나, 사전에 발견하더라도 손님의 예약을 뒤늦게 취소해야 하는 상황이 생깁니다.

또 객실은 보통 연박으로 잡히기 때문에 기간에 걸친 날짜별 재고를 모두 고려해야 합니다. 예약 요청 간의 기간 겹침과 오버부킹이 숙박 예약 서비스의 가장 큰 문제라고 판단했습니다.

### 1.2 예약 취소 시의 재고 이중 복원 문제

하나의 예약에 취소 / 결제 실패 / 결제시간 만료 같은 이벤트가 동시에 도착할 수 있는데, 하나의 예약에 대해 재고는 정확히 한 번만 회복되어야 합니다. 두 번 돌려놓으면 있지도 않은 방이 재고에 생기고, 이 오류는 손님이 항의해서 발견되는 오버부킹과 달리 아무도 발견하지 못합니다.

### 1.3 이 문제를 고른 이유

이 외에도 ① 프로모션 이벤트 때의 순간 트래픽 폭증, ② 날짜마다 예약 금액이 다른 다이나믹 프라이싱, ③ 호텔 프론트에서 쓰는 체크인·체크아웃 시스템과 실제 객실의 연동 같은 후보 문제들도 있었습니다. 하지만 가장 기본기로 지켜져야 하는 날짜별 재고와 오버부킹 문제를 해결하는 시스템이 먼저 구축되어야, 다이나믹 프라이싱도 프로모션의 순간 트래픽도 그 위에서 해결할 수 있다고 판단했습니다. 후보 비교와 검토한 대안은 [ADR-0063](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0063-과제-문제-선정.md)에 있습니다.

### 2.3 프로젝트 구조 — 클린 아키텍처 · DDD · TDD

패키지는 재고(inventory)와 예약(reservation) 두 구역으로 나누고, 각 구역 안을 클린 아키텍처의 4개 레이어로 구성하였습니다. 의존은 presentation → application → domain의 안쪽 방향으로만 흐르고, infrastructure는 application이 정의한 포트(Protocol)를 구현해 DB·Redis 같은 바깥 기술을 감춥니다. 판단 기준은 "이 코드를 DB와 웹 없이 테스트할 수 있는가"였습니다. 다만 Python은 의존 방향을 컴파일러가 지켜주지 않기 때문에, 리뷰에서 import를 직접 확인하는 것을 규칙으로 두었습니다 (규칙 문서는 `docs/architecture/`, 레이어 경계는 [ADR-0055](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0055-레이어-경계-세-가지.md)).

도메인 모델은 DDD를 따르되 ORM 모델과 통합하였습니다. 도메인 객체를 SQLModel 테이블 클래스로 직접 만들고, 대신 domain 모듈은 sqlmodel·sqlalchemy 외의 프레임워크에 의존하지 않도록 했습니다 ([ADR-0002](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0002-도메인과-JPA-엔티티-통합.md)). 금액이나 숙박 기간 같은 값은 원시 타입으로 흘리지 않고 값 객체(Money, StayPeriod)로 다루며, 상태 전이 규칙(3.3의 전이 표)도 도메인 안에 있습니다.

구현은 TDD로 진행하였습니다. 실패하는 테스트를 먼저 쓰고 구현했으며, 동시성 관련 코드는 반드시 동시성 테스트를 동반하도록 강제했습니다. 테스트 코드(6,421줄)가 앱 코드(3,819줄)의 1.7배인 것은 이 규칙의 결과입니다.

- **CI** — main 푸시와 PR마다 마이그레이션 head가 하나인지 검사한 뒤, 실제 MySQL·Redis를 띄워 전체 pytest를 돌립니다. 프론트엔드는 테스트·타입 검사·빌드까지 확인합니다.

- **인증·인가** — 서비스에서 가장 중요한 기능이지만, 이 과제가 풀려는 숙박 예약 문제에 집중하기 위해 의도적으로 제외했습니다. 현재는 `X-User-Id` 헤더로 사용자를 식별하고, 화면에 인증이 아니라는 안내를 상시 표시합니다 ([ADR-0006](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0006-인증-제외.md)).

## 3. 구현하면서 고려한 것들

### 3.1 재고는 날짜 단위 행으로 관리

객실별로 기간을 통째로 다루지 않고 `(객실타입, 날짜)` 하나에 잔여 수량 한 줄을 둡니다. 3박 예약이면 3개 행을 건드립니다. 경합의 대상, 잠금의 단위, 초과 판매를 막는 제약이 붙는 곳이 전부 이 행입니다.

### 3.2 정합성을 지키기 위한 3중 방어

```
1층. Redis 분산락            — 경합을 DB까지 내려보내지 않습니다 (DB 잠금 비용의 사전 절감)
2층. 조건부 UPDATE (행 잠금) — WHERE remaining >= ? 로 갱신하고 갱신 행 수를 봅니다 (실제 판단)
3층. DB CHECK / UNIQUE       — remaining >= 0 을 DB가 거부합니다 (마지막 방어)
```

`UPDATE ... WHERE remaining >= 수량`은 판단과 갱신이 한 문장이라 사이에 끼어들 틈이 없습니다.

**비관적 락(SELECT FOR UPDATE)을 별도 층으로 두지 않은 것은 의도된 선택입니다.** 조건부 UPDATE가 실행되는 순간 그 행에 배타 잠금이 걸리므로, 2층이 이미 DB 행 잠금 층입니다. "먼저 잠그고 읽은 뒤 판단해서 갱신"하는 방식과 정확성은 같지만, 잠금을 쥐는 구간이 읽기부터 커밋까지 전체에서 UPDATE 한 문장으로 줄어들고, 잠금이 걸리는 지점이 재고 행 갱신 한 곳뿐이라 데드락이 생길 조합도 줄어듭니다. 여러 날짜의 행을 잡을 때는 날짜 오름차순으로 정렬해 잠금 순서를 통제합니다.

Redis 분산락은 정확성을 담당하지 않습니다 — 분산락을 완전히 꺼도 결과가 같아야 하고, 실제로 같았습니다(3.5의 S5). **정합성은 DB가 지키고, 락은 비용을 줄이는 장치입니다.**

### 3.3 멱등성 키와 상태 전이 표

단순 if/else 분기가 아니라 `(현재 상태, 이벤트) → 다음 상태` **전이 표**로만 상태를 바꾸고, 상태를 직접 바꾸는 세터는 만들지 않았습니다.

클라이언트의 반복 요청을 막는 **멱등성 키**(`Idempotency-Key` 헤더)는 예약 생성에만 요구합니다. 확정·취소·체크인·체크아웃의 재시도는 전이 표의 멱등 흡수가 이미 처리하고, 생성의 경우에는 이미 존재하는 상태가 없어 재시도가 새 예약을 만들 수 있으므로 Redis에 키를 남겨 중복 생성을 방어합니다.

### 3.4 외부 호출과 DB 트랜잭션의 분리

결제 처리를 트랜잭션 안에서 호출하면, 결제사 서버가 느리거나 장애일 때 DB 커넥션을 쥔 채 기다리게 됩니다. 다른 서비스의 장애가 커넥션 고갈로 번져 자사 서비스 전반의 장애가 되는 쪽이 더 큰 영향이라고 판단해, 의도적으로 트랜잭션 밖에서 호출합니다.

대신 승인과 커밋 사이에 틈이 생깁니다 — 그 틈에 서버가 죽으면 실제 결제는 됐는데 예약이 확정되지 않을 수 있습니다. 이 틈은 알면서 남겼고, 이 규모에서는 운영(고객 문의)으로 대응하는 쪽을 택했습니다. 찾는 방법과 한계까지 [ADR-0062](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0062-결제-예약-불일치는-사람이-처리한다.md)에 기록했습니다.

### 3.5 부하 테스트로 정합성을 실측

판정 기준은 측정 전에 확정했고, 숫자는 전부 실측입니다.

| 실측 | 결과 |
|---|---|
| 100실에 6,000건을 20초에 밀어넣음 | 성공 정확히 100건 — 초과 판매 0 |
| 분산락 끄고 3회 · 켜고 3회 (S5) | 여섯 번 모두 성공 건수 동일. 차이는 비용 — DB 행 잠금 대기 0회 ↔ 434회 |
| 검색 캐시 켬/끔 대조 (S8) | 검색 p95는 1.3배 차이인데 같은 시간 예약 p95는 15.6배 (24.7ms ↔ 385.3ms) — 캐시가 산 것은 검색 속도가 아니라 예약이 쓸 DB 커넥션이었습니다 |
| 커넥션 풀 버그 수정 후 재측정 (S4-B) | 5xx 21건 → 0건 — 고쳤다는 것도 측정으로 확인했습니다 |

**S8**은 검색 캐시 스위치(`PMS_SEARCH_CACHE_ENABLED`) 하나만 바꿔 같은 부하를 두 번 돌린 실험입니다. 검색을 초당 500건씩 60초 흘리면서 예약을 섞었고, 캐시를 켠 회차는 히트율 99.8%, 끈 회차는 0%로 대조가 성립합니다. 검색 자체는 캐시가 없어도 인덱스 조회 한 번이라 크게 느려지지 않는데, 초당 500건이 DB 커넥션을 잡는 동안 같은 풀을 쓰는 예약이 밀렸습니다.

**S4-B**는 미결제 만료와 결제 확정이 경합하는 회차인데, 실행 중에 버그를 하나 찾았습니다 — 커넥션 풀 초기화가 스레드 안전하지 않아, 재기동 직후 첫 DB 접근이 몰리면 워커마다 엔진이 수십 개 생겨 MySQL 연결 한도 초과(5xx 21건)가 났습니다. ThreadSafeSingleton으로 수정한 뒤 우회책(워밍업) 없이 같은 부하를 다시 넣어 5xx 0건, 워커당 연결 1개를 확인했습니다.

전체 시나리오와 원자료는 [04-부하테스트.md](https://github.com/Diocto/pms/blob/main/docs/submission/04-부하테스트.md)에 있습니다.

## 4. Agentic Engineering — AI를 어떻게 사용하였는지

이 프로젝트는 설계부터 코드 구현, 테스트, 인프라 배포까지 Anthropic의 Claude Code를 활용해 만들었습니다. 이 항목에서는 AI에게 시킨 것과 개발자가 직접 통제한 영역을 서술하였습니다.

### 4.1 AI에게 의도적으로 시킨 것

- **아키텍처 하네스** — 어떤 작업 전에 어떤 문서를 반드시 읽어야 하는지 정했고, 지켜지지 않은 경우 리뷰에서 한 번 더 검토해 반려됩니다. 규칙 문서 6편이 `docs/architecture/`에 있습니다.
- **멀티에이전트 워크플로우** — 전체 범위를 관리하는 PM 에이전트와, 코드가 겹치지 않는 단위로 기능을 나눠 맡는 구현 에이전트를 두고, 서로 소통하며 구현하게 했습니다.
- **워크플로우를 스킬로 고정** — 스펙 작성 → [승인] → 개발 사이클(TDD·리뷰 반복) → [승인]. 단계마다 대응하는 스킬이 있어 절차가 매번 달라지지 않고, [승인]은 개발자가 직접 합니다.
- **승인 게이트** — 스펙 결정과 구현 완료마다 사람의 개입을 강제합니다. AI 활용의 병목이 될 수 있지만, 멀티에이전트로 여러 기능을 나란히 진행시켜 병목을 줄였습니다.
- **리뷰어 3종** — 동시성·도메인·아키텍처 관점의 서브에이전트가 같은 코드를 다르게 읽습니다. 리뷰 기록 11건이 남아 있습니다.
- **결정은 ADR로** — 결정 사항을 문서로 남기도록 하였습니다. 누가 정했는지를 구분해 사람이 정한 것은 지시 원문을 인용하였습니다.
- **모든 이력의 기록** — 결정 사항, 리뷰 결과, 테스트 결과, 사람이 관여한 부분, 학습용 자료까지 과정을 전부 남기도록 강제했습니다.

### 4.2 개발자가 직접 확인하고 한 일

- 문제 선정과 구현 범위 정의
- 하네스 구축
- 구현하지 않을 것을 정의하고, AI가 제안한 구조나 결정을 보고 채택·반려 판단
- AI가 일하는 방식을 중간에 교정하고, 하네스를 잘 지키고 있는지 검토
- 코드 리뷰 진행과 수정 요청
- 프론트엔드 디자인 시안을 요청해 받아 보고, 화면 구성과 디자인 개선 방향을 직접 지시
- 프론트엔드 + 백엔드 통합 테스트

## 5. 마주한 문제와 대응

### 병렬 세션의 무한 대화

병렬 세션을 구축하고 구현을 명령했는데, 토큰만 소비하고 실제 구현 결과가 0인 현상이 있었습니다. 모든 세션의 의존이 첫 세션(F01 숙박·예약 코어)에 걸려 있었고, 구현 세션 - PM - 구현 세션으로 오가는 의견 조율만 무한히 반복됐습니다.

**해결** — 후속 세션보다 예약 코어를 직접 감독하며 먼저 완성시키는 것이 우선이라고 판단해 예약 코어 구현을 최우선으로 두고, 후속 세션들은 이미 구현된 도메인과 코드 위에서 수정·추가를 진행하게 바꿨습니다 ([ADR-0052](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0052-병렬에서-순차로.md)).

### PM 세션의 과도한 기술 관여

코드를 직접 보지 않는 PM 세션이 구현 세션과 기술 논의를 벌였는데, 구현 세션의 반박으로 철회되는 건이 여러 번(7건) 관측됐습니다.

**해결** — PM 역할을 "무엇을 만드는가"까지로 제한하고, 기술적 구현은 코드를 소유한 구현 세션에게 위임하도록 강제했습니다 ([ADR-0053](https://github.com/Diocto/pms/blob/main/docs/decisions/ADR-0053-PM-역할-축소.md)).

### 세션 간 진행 상황 확인의 어려움

세션을 나눈 것은 좋았으나, 각 세션이 어느 단계를 진행 중인지 보이지 않아 조율 자체가 어려웠고, 그때마다 PM에게 현재 상황을 물어야 했습니다.

**해결** — PM 세션에게 각 세션의 작업 진척도와 남은 Task를 한눈에 보여주는 현황판(JIRA식 대시보드)을 만들게 해서, 물어보지 않고 보게 했습니다.

### 보고서가 존재하지 않는 수정을 근거로 들 뻔함

부하테스트 보고서가 "고쳤다"고 인용한 수정 코드가 보고서 안에만 있고 실제 main에는 없었습니다 — 커밋만 되고 병합되지 않은 상태였습니다. 검증이 스스로 거짓말할 뻔한, 이번 작업에서 가장 위험했던 문제입니다.

**해결** — 병합 후 다시 측정했습니다. 그리고 세션 간 통지에 상태 낱말(푸시함 / PR 열림 / 병합됨)을 반드시 넣고, 받는 쪽은 실물로 대조하는 규칙을 만들었습니다.
