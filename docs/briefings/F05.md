# F05 프론트엔드 · 착수 브리핑

이 문서는 F05 세션의 시작점이다. 이 저장소의 문서 밖에 있는 맥락은 전제하지 않는다.

## 네 임무

예약 흐름을 눈으로 볼 수 있는 **최소한의 화면 세 개**를 만든다. 검색 → 예약 → 예약 상세다.

**너는 다른 feature와 성격이 다르다.** F01~F04는 이 과제가 증명하려는 것(동시성·멱등성·상태 전이)을 직접 다루지만, **프론트엔드는 그 증명에 기여하지 않는다.** 대신 다른 것을 한다 — **설계가 만든 결과를 사람이 확인할 수 있게 한다.**

특히 이것 하나는 프론트가 아니면 보여줄 수 없다.

> 검색 결과가 조금 낡아서 예약이 실패하는 것은 **장애가 아니라 설계다.** 화면이 그 실패를 어떻게 다루는지가 그 주장의 증거다.

## 읽는 순서

1. `CLAUDE.md` (자동 로드됨)
2. `docs/spec/00-problem-and-scope.md` — 승인된 전체 범위
3. **`docs/spec/F01-예약-코어.md`의 2장** — 유스케이스별 API 계약. 네가 소비할 계약이다
4. **`docs/spec/F03-검색-API-계약.md`** — 검색 API와 `emptyReason`·`source` 필드
5. `docs/architecture/parallel-work.md` — 소유 범위 규칙
6. `docs/spec/TEMPLATE.md` — 결정 검토란 형식

**백엔드 규칙 문서(`coding-rules.md`·`ddd.md` 등)는 안 읽어도 된다.** 파이썬 백엔드 규칙이고 너와 무관하다.

## 소유 범위

- **소유 디렉터리:** `frontend/` — 이 아래만 만든다
- **읽기만 하는 것:** `docs/spec/**` (API 계약)
- **절대 건드리지 않는 것:** `app/**`, `migrations/**`, `tests/**`, `load-test/**`, `pyproject.toml`
- **마이그레이션 대역:** 없다. DB를 건드리지 않는다
- **ADR 번호 대역:** `ADR-0060` ~ `0069`

**백엔드 API가 마음에 안 들어도 직접 고치지 않는다.** 필요하면 PM에게 알린다. API 계약은 F01·F03 소유다.

## 기술 스택

**확정된 것은 Next.js 하나다.** 나머지는 네가 제안하고 관리자 확인을 받는다.

| 항목 | 상태 |
|---|---|
| 프레임워크 | **Next.js** (확정) |
| 언어 | 제안 — TypeScript를 권한다 |
| 스타일링 | 제안 |
| 데이터 페칭 | 제안 |
| 상태 관리 | 제안 — **필요 없으면 안 쓰는 것도 제안이다** |

**제안은 결정 검토란에 D 항목으로 올린다.** 이유·트레이드오프·대안을 적는다. 라이브러리를 고를 때 기준은 하나다 — **화면 세 개에 그게 정말 필요한가.**

## 진행 순서 — 다른 feature와 다르다

관리자가 지정한 순서다.

```
디자인 시안 작성  →  [관리자 검토]  →  확정되면 구현
```

**스펙을 먼저 쓰지 않는다.** 화면이 어떻게 생겼는지가 먼저 정해져야 나머지가 따라온다.

### 1단계: 디자인 시안

**시안은 그림이 아니라 화면의 설계다.** 아래를 담는다.

- **화면 세 개의 레이아웃** — 무엇이 어디에 있는가
- **각 화면의 상태들** — 로딩, 비어 있음, 오류, 정상. **비어 있음과 오류를 빠뜨리지 마라**
- **실패를 어떻게 보여주는가** — 아래 「반드시 다뤄야 할 화면 상태」 참고
- **화면 간 이동** — 어떤 동작이 어디로 데려가는가

시안은 **HTML 아티팩트로 만들어 관리자가 브라우저에서 보게 한다.** 실제 프레임워크로 만들 필요 없다. 정적 HTML이면 충분하고, 오히려 그게 빠르다.

**결정 검토란을 붙인다.** 스택 선택과 화면 구성에서 네가 내린 판단을 D 항목으로 모은다.

### 2단계: 관리자 검토

`approval-report` 스킬로 승인을 요청한다. **승인 없이 구현하지 않는다.**

### 3단계: 구현

승인된 시안대로 만든다. 시안과 다르게 만들어야 할 이유가 생기면 멈추고 PM에게 알린다.

## 반드시 다뤄야 할 화면 상태

**이 프로젝트가 증명하는 것이 화면에서 보여야 한다.** 정상 흐름만 만들면 프론트를 만든 값이 없다.

| 상황 | 백엔드 응답 | 화면이 해야 할 일 |
|---|---|---|
| 검색했는데 매진 | `emptyReason: SOLD_OUT` | "매진"이라고 말한다 |
| 검색 범위 밖 날짜 | `emptyReason: NOT_YET_OPEN` | **"판매 전"이라고 구분해 말한다.** 매진과 다른 정보다 |
| 인원에 맞는 방 없음 | `emptyReason: NO_FITTING_ROOM_TYPE` | 인원을 줄이라고 안내 |
| **예약하려는데 재고 부족** | **409** | **가장 중요하다.** 아래 참고 |
| 예약 처리 중 재요청 | 409 `REQUEST_IN_PROGRESS` | 중복 클릭. 버튼을 잠그고 기다린다 |
| 결제 거절 | **200** + `status: CANCELLED` | **성공 응답이지만 예약은 취소됐다.** 200이라고 성공으로 다루면 틀린다 |
| 서버 혼잡 | 503 | 잠시 후 다시 시도하라고 안내 |

### 409를 어떻게 다루는가 — 이게 이 화면의 핵심이다

검색 결과는 캐시 때문에 최대 10초까지 낡을 수 있다. 그래서 **화면에 "예약 가능"이라고 떠 있는데 누르면 실패하는 일이 정상적으로 일어난다.**

이걸 "오류가 발생했습니다"로 처리하면 안 된다. **의도된 흐름이므로 그렇게 보여야 한다.**

권장 흐름이다. 다르게 하고 싶으면 D 항목으로 근거를 대라.

1. 409를 받으면 **"방금 마감됐습니다"**라고 말한다. 오류가 아니라 사실이다
2. **자동으로 최신 재고를 다시 조회한다** (`fresh=true`)
3. 아직 남아 있으면 **한 번 더 시도한다.** 사용자가 다시 누르지 않아도 된다
4. 두 번 실패하면 다른 날짜·객실을 권한다

**최대 2회까지만 재시도한다.** 무한 재시도는 서버에 부하를 얹는다.

### 멱등성 키는 프론트가 만든다

예약 생성 요청에 `Idempotency-Key` 헤더가 **필수**다. 클라이언트가 만든다.

**같은 예약 시도에는 같은 키를 쓴다.** 사용자가 버튼을 두 번 눌러도, 네트워크가 끊겨 재시도해도 같은 키여야 한다. **키를 매번 새로 만들면 멱등성이 무의미해진다** — 서버는 서로 다른 요청으로 본다.

키는 **예약 폼을 열 때 한 번 만들고, 성공하거나 사용자가 입력을 바꿀 때까지 유지한다.**

## 사용자 식별

`X-User-Id` 헤더로 식별한다. 로그인은 이 과제의 범위 밖이다(ADR-0006).

화면에서는 **사용자를 고르거나 입력하는 자리**를 두면 된다. 그럴듯한 로그인 화면을 만들지 마라 — 없는 기능을 있는 것처럼 보이게 하는 것이다.

**같은 예약을 다루는 요청은 같은 값을 써야 한다.** 취소가 소유자를 검증하고, 남의 예약이면 403이 아니라 **404**를 준다.

## 시드 데이터

백엔드에 미리 들어가는 데이터다. 시안과 구현에서 이 값을 쓴다.

- **호텔 2곳:** 서울 그랜드 호텔, 부산 오션뷰 호텔
- **객실타입 5종:** 스탠다드(정원 2·100실) / 디럭스(3·50) / 스위트(4·10) / 오션뷰 스탠다드(2·80) / 오션뷰 스위트(4·20)
- **예약 가능 날짜:** 2026-08-01 ~ 2026-10-29 (고정). 그 밖은 `NOT_YET_OPEN`

정확한 값은 `F01-예약-코어.md` 1.9절이 진실이다.

## 절단 순서에서 네 자리

**네가 첫 번째 절단 대상이다.** 일정이 밀리면 F05부터 자른다.

이유는 명확하다. 이 과제의 평가 대상은 동시성·멱등성·상태 전이를 **수치로 증명하는 것**이고, 프론트엔드는 그 증명에 기여하지 않는다. 백엔드 구현과 부하테스트가 밀리는 상황에서 화면을 만드는 것은 순서가 틀렸다.

**그래서 두 가지를 지켜라.**

- **백엔드에 아무것도 요구하지 마라.** API를 바꿔달라고 하면 그만큼 임계 경로가 밀린다. 있는 계약으로 만든다
- **네가 없어도 나머지가 완결되게 둬라.** `frontend/` 밖을 건드리지 않으면 저절로 그렇게 된다

## 백엔드가 아직 없을 때

**API가 구현되기 전에도 시안과 화면은 만들 수 있다.** 계약이 문서에 확정돼 있기 때문이다.

가짜 응답으로 개발하되, **가짜를 만들 때 실패 응답도 함께 만들어라.** 정상 응답만 흉내 내면 위의 화면 상태들을 실제로 못 만들어 본다.

## 작업 절차

1. **디자인 시안** — HTML 아티팩트. 결정 검토란 포함
2. `approval-report` 스킬로 승인 요청
3. 승인 후 `frontend/`에 구현
4. 완료 승인

스킬이 슬래시 명령으로 없으면 `.claude/skills/<이름>/SKILL.md`를 직접 읽고 그 절차를 따른다.

## 막히면

API 계약이 모호하거나 문서와 어긋나면 **임의 해석하지 말고 PM에게 물어라.** 다른 세션에 직접 말하지 않는다. 답은 대화로 끝내지 않고 해당 문서에 반영된다.
