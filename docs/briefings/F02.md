# F02 선착순 프로모션 · 착수 브리핑

이 문서는 F02 feature 세션의 시작점이다. 이 저장소의 문서 밖에 있는 맥락은 전제하지 않는다.

## 네 임무

특정 날짜·객실타입에 열리는 **한정 수량 특가**를 만든다. 오픈 순간 수백 요청이 재고 행 하나로 몰리는 상황에서, 한정 수량을 정확히 그만큼만 파는 것이 이 feature의 전부다. 유스케이스는 **UC-7 선착순 특가 예약** 하나다.

F01(예약 코어)이 여러 날짜에 걸친 재고를 다룬다면, F02는 **한 점에 몰리는 트래픽**을 다룬다. 경합의 성격이 다르고, 그래서 방어 설계도 달라진다. 이 차이를 스펙에서 설명하지 못하면 F02는 F01의 복사본이 된다.

**스펙 작성부터 시작한다.** 승인 없이 코드를 쓰지 않는다.

5. `docs/spec/TEMPLATE.md` — 스펙 형식 (결정 검토란 필수)

8. `docs/reviews/F01-spec-review-업계정합성.md` — 업계 정합성 검토. 6번 항목(1박 단가 스냅샷)이 F02를 직접 지목한다

## 소유 범위 (선언 완료, 스펙에 그대로 기재)

- **소유 패키지:** `com.pms.promotion.**`
- **읽기만 하는 패키지:** `com.pms.inventory.domain`, `com.pms.reservation.domain`
  - **다른 feature가 소유한 도메인은 절대 수정하지 않는다.** 수정이 필요하다고 판단되면 손대지 말고 관리자에게 알린다 (parallel-work의 "몰래 고치지 않는다")
  - 애플리케이션 계층(`*/application/**`)은 soft 소유다. 그래도 F01의 유스케이스 시그니처를 바꿔야 한다면 그것도 조율 대상이다
- **Flyway 번호 대역:** V201 ~ V299
- **수정이 필요한 공유 파일:** `com.pms.common.exception.ErrorCode`에 프로모션용 코드 추가가 예상된다. 필요하면 parallel-work의 공유 파일 절차(작은 커밋을 main에 먼저)를 따른다
- **ADR 번호 대역:** ADR-0020 ~ ADR-0029. `docs/decisions/INDEX.md`에는 **네가 추가한 줄만** 넣고 기존 줄은 손대지 않는다
- **수정 금지 (PM 세션 소유):** `docs/spec/00-problem-and-scope.md`, `CLAUDE.md`, `docs/architecture/**`, `docs/learning/INDEX.md`. 고쳐야 한다고 판단되면 멈추고 PM에게 보고한다
- **절차 없이 수정 금지:** `build.gradle`, `application.yml`, `docker-compose.yml`, `src/main/java/com/pms/common/**`
- **학습 노트:** `docs/learning/INDEX.md`에 직접 넣지 않고, 스펙 끝에 "학습 노트 후보" 목록으로만 쌓는다

## 00 문서에서 이미 확정된 제약 (스펙에서 뒤집을 수 없음, 뒤집으려면 관리자 승인)

- **프로모션은 "특정 날짜·객실타입에 한정 수량 특가"로만 구현한다. 쿠폰 발급·사용은 범위 밖이다** (00 D5). 다만 나중에 쿠폰을 붙일 수 있도록 **확장에 열린 구조로 자리를 남긴다.** 예약 생성 입력이 주문서 형태라는 F01의 설계가 그 확장 지점이다 (00 D5 검토 결과의 조건)
- **불변식: `PromotionInventory`의 `remaining >= 0`** (00 §4). 이 불변식을 지키는 DB 제약을 최소 하나 둔다
- 재고는 객실타입 × 날짜 수량 행 (00 D3). 특가도 이 모델 위에 얹는다
- 상태 전이는 전이 테이블 방식 (ADR-0003). if-else 분기 금지
- 다층 방어: 1차 → 2차 → 3차 (`docs/architecture/coding-rules.md`의 다층 방어 절). **1차를 껐을 때도 불변식이 지켜지는 것을 테스트로 증명한다**
- 관리자 기능은 만들지 않는다. 프로모션 데이터도 Flyway 시드로 넣는다 (00 D1)

## 미결 사항 (네 스펙에서 결정하고 승인받을 것)

**세 구역 분리 안.** 00 D6의 "대안이었던 것"에 이렇게 적혀 있다 — *"셋으로 나누기(프로모션까지 별도 구역, F02 스펙 때 재검토)"*. 즉 프로모션을 재고·예약과 나란한 **별도 구역(바운디드 컨텍스트)**으로 둘 것인가는 **아직 정해지지 않았고, 네 스펙의 결정 검토란에서 관리자 확인을 받아야 한다.**

판단할 때 참고할 것:

- 00 §4의 도메인 개요는 `PromotionInventory`를 `inventory` 구역 안에 그려두었다. 반면 00 §5의 feature 분할 표는 F02의 소유 패키지를 `promotion.**`로 배정했다. **두 절이 서로 다른 그림을 그리고 있다.** 이 어긋남을 해소하는 것이 이 결정의 내용이다
- 구역을 나누면 00 D6이 허용한 예외("예약 생성만 두 구역을 한 트랜잭션으로")가 세 구역으로 확대된다. 확대하는 것이라면 그 근거를 써야 한다
- 결정 검토란 형식(결정·이유·트레이드오프·대안·확인 질문)을 그대로 지킨다

## 반드시 스펙에서 답해야 하는 질문

아래는 이 브리핑이 답을 주지 않는다. 임의로 넘기지 말고 스펙에서 명시적으로 결정하고 D 항목으로 올린다.

| # | 질문 | 왜 중요한가 |
|---|---|---|
| Q1 | 특가 재고와 일반 재고(`room_daily_inventory`)는 별개인가, 특가를 팔면 일반 재고도 줄어야 하는가 | 별개로 두면 물리적 객실 수를 넘겨 파는 구멍이 생긴다 |
| Q2 | 특가 예약도 `Reservation` 애그리거트를 쓰는가, 아니면 F02가 자기 예약을 만드는가 | 후자면 예약 애그리거트가 둘이 되어 상태머신이 갈라진다 |
| Q3 | 특가 예약이 취소·만료되면 특가 재고를 되돌리는가, 되돌린다면 누가 되돌리는가 | 되돌리는 주체가 F01이면 F01 → F02 역방향 의존이 생긴다. F02는 F01을 수정할 수 없다 |
| Q4 | 1차 방어를 F01과 같은 분산락으로 둘 것인가, 선착순에 맞는 다른 수단을 둘 것인가 | 단일 행에 몰리는 트래픽에서 직렬화 락은 방어가 아니라 병목이다 |
| Q5 | 특가 가격을 어디에 기록하는가 | F01 `reservation`에 기록하려면 F01이 소유한 스키마를 건드려야 한다 |

**F01의 재고 모델·상태 전이 표·예약 생성 API는 아직 확정 전이다(F01 세션이 지금 그 스펙을 쓰는 중). 추정해서 확정하지 마라.** 의존하는 서술마다 "F01 스펙 승인 후 재확인" 표시를 달고, 그 목록을 스펙 끝에 따로 모은다. 목록의 각 항목에는 **F01 결정이 반대로 나왔을 때 설계가 얼마나 바뀌는지**를 한 줄로 함께 적는다. 나중에 되돌리는 비용이 크다.

**F01 스펙에 의존하는 항목은 스펙에 "F01에 요구하는 계약"으로도 따로 모은다.** 관리자가 PM 세션을 거쳐 F01과 조율할 수 있도록, 항목별로 "이게 없으면 F02는 무엇으로 대체하는가"까지 쓴다.

## 작업 절차

스킬이 슬래시 명령으로 등록되어 있지 않다면 `.claude/skills/<이름>/SKILL.md`를 직접 읽고 그 절차를 그대로 따른다.

1. `feature-spec` 스킬 실행 → `docs/spec/F02-선착순-프로모션.md` 작성
2. `approval-report` 스킬로 승인 요청 (가능한 환경이면 `open -a Bear <파일>`로 열고 SendUserFile로도 전송. 두 도구가 없으면 파일 경로와 GitHub 링크 안내. 터미널 요약 3~5줄)
3. **여기서 멈춘다.** 아래 "일정상 제약" 참조
4. 구현 착수 지시를 받으면 `dev-cycle` 스킬로 TDD 개발. 리뷰어 3명(`concurrency-reviewer`, `domain-reviewer`, `architecture-reviewer`) 병렬 호출
5. 완료 승인 후 main 병합은 관리자(PM 경유) 지시를 따른다

## 일정상 제약

- **구현 코드는 F01이 main에 병합된 뒤에 시작한다.** F02는 F01의 `Reservation`과 `room_daily_inventory` 위에 얹히므로, 병합 전에 코드를 쓰면 F01의 확정 결과와 어긋난다
- 문서(브리핑·스펙)까지는 F01과 병렬로 진행해도 된다. 다만 F01 스펙이 확정되면 그 내용과 대조해 스펙을 갱신한다
- **F02는 일정 지연 시 절단 후보 4순위다** (00 D4: F05 프론트엔드 → F03 캐시 → UC-6 체크인아웃 → F02 프로모션. 2026-08-15 F05 신설로 한 칸 밀렸다). 잘릴 수 있다는 전제에서, F01 쪽 코드에 F02가 없으면 동작하지 않는 변경을 심지 않는다. F02를 통째로 들어내도 F01이 그대로 도는 상태를 유지한다

## 환경

- 빌드: `./gradlew test` (Testcontainers가 MySQL 8.4·Redis 7.4를 띄움. Docker 필요)
- 로컬 실행: `docker compose up -d` 후 `./gradlew bootRun`
- 작업 위치: `.claude/worktrees/f02-promotion/` (브랜치 `worktree-f02-promotion`). worktree는 세션과 함께 사라질 수 있으니 **반드시 커밋한다**
- 통합 전에 **전체 테스트**를 돌린다. 자기 feature 테스트만 통과하는 것은 의미가 없다 (parallel-work 통합 절차)

## 막히면

스펙이 모호하거나 이 브리핑과 문서가 어긋나면 임의 해석하지 말고 관리자에게 질문한다. 답을 받으면 대화로 끝내지 말고 해당 문서에 반영한다.

특히 아래는 **즉시 보고 대상**이다.

- `com.pms.reservation.**` 또는 `com.pms.inventory.**`를 수정해야 한다고 판단될 때
- 공유 파일(`ErrorCode`, `application.yml`, `build.gradle`)을 수정해야 할 때
- F01 스펙과 모순되는 요구를 발견했을 때
