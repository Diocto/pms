# F01 예약 코어 · 착수 브리핑

이 문서는 F01 feature 세션의 시작점이다. 이 저장소의 문서 밖에 있는 맥락은 전제하지 않는다.

## 네 임무

예약의 전체 생명주기(생성·확정·취소·만료·체크인·체크아웃)와 일별 재고 차감·복원을 만든다. 과제의 증명 대상인 동시성·멱등성·상태 전이가 전부 이 feature에 있다. **스펙 작성부터 시작한다.** 승인 없이 코드를 쓰지 않는다.

## 읽는 순서

1. `CLAUDE.md` (자동 로드됨. 규칙과 세션 역할)
2. `docs/spec/00-problem-and-scope.md` — 승인된 전체 범위. F01의 유스케이스는 UC-2~6
3. `docs/architecture/ddd.md`, `docs/architecture/coding-rules.md` — 도메인·코딩 규칙
4. `docs/spec/TEMPLATE.md` — 스펙 형식 (결정 검토란 필수)
5. `docs/architecture/diagram-rules.md` — 다이어그램 필수 조항
6. `docs/reviews/F01-spec-review-업계정합성.md` — **아래 참고** 반드시 읽을 것
7. `docs/architecture/parallel-work.md` — 소유 범위 규칙

## 소유 범위 (선언 완료, 스펙에 그대로 기재)

- 소유 패키지: `com.pms.reservation.**`, `com.pms.inventory.**` — **단 `com.pms.inventory.query.**`는 F03(가용 객실 검색) 소유이므로 만들지 않는다**
- Flyway 번호 대역: V001 ~ V099 (공통 스키마 포함. 시드 데이터도 네 몫)
- 시드 데이터 규모는 스펙에서 정하고 결정 검토란에 올려라. 참고값(폐기 초안 기준): 호텔 2곳, 객실타입 5종, 오늘부터 90일치 재고
- 공유 파일 수정: 원칙적으로 없음. `ErrorCode`는 F01에 필요한 코드가 이미 등록돼 있다. 추가 필요 시 parallel-work의 공유 파일 절차

## 이전 이력 (중요)

PM 세션이 작성했던 F01 스펙 초안이 있었고 **2026-08-15에 폐기됐다** (git 이력의 spec-problem-and-scope 브랜치에 남아 있음). 폐기된 초안을 그대로 복사하지 말 것. 다만 그 초안에 대한 업계 정합성 검토(`docs/reviews/F01-spec-review-업계정합성.md`)는 유효한 입력 자료다.

검토가 남긴 것:

- **반영 후보 7개** (인원수 필드, 타임존 고정, CHECK 제약 3종, NO_SHOW·체크인 상한, UC-3 크래시 틈 명시, 단가 스냅샷, confirmation_code). **관리자가 아직 채택 여부를 결정하지 않았다.** 스펙을 쓸 때 각 후보를 네 판단으로 채택/기각하고, 그 판단을 결정 검토란(D 항목)에 올려 관리자 확인을 받아라.
- **문서화 후보 4개** (요금제·다타입 묶음·세금 통화·확정 후 변경 제외)는 00 문서의 제외 표에 추가할 것을 제안하고 승인받아라.

## 00 문서에서 이미 확정된 제약 (스펙에서 뒤집을 수 없음, 뒤집으려면 관리자 승인)

- 재고는 객실타입 × 날짜 수량 행 (00 D3)
- 상태 전이는 전이 테이블 방식 (ADR-0003)
- 예약 생성 입력은 주문서 형태로, 쿠폰 확장 지점을 남길 것 (00 D5 조건)
- 재고·예약 구역 분리, 예약 생성만 한 트랜잭션 예외 (00 D6)
- 다층 방어: Redis 분산락 → 조건부 UPDATE → DB 제약 (`docs/architecture/coding-rules.md`의 다층 방어 절)

## 작업 절차

스킬이 슬래시 명령으로 등록되어 있지 않다면 `.claude/skills/<이름>/SKILL.md`를 직접 읽고 그 절차를 그대로 따른다.

1. `feature-spec` 스킬 실행 → `docs/spec/F01-예약-코어.md` 작성
2. `approval-report` 스킬로 승인 요청 (Bear로 열고 SendUserFile로도 전송, 터미널 요약 3~5줄)
3. 승인 후 `dev-cycle` 스킬로 TDD 개발. 리뷰어 3명(`concurrency-reviewer`, `domain-reviewer`, `architecture-reviewer`) 병렬 호출
4. 완료 승인 후 main 병합은 관리자(PM 경유) 지시를 따른다

## 환경

- 빌드: `./gradlew test` (Testcontainers가 MySQL 8.4·Redis 7.4를 띄움. Docker 필요)
- 로컬 실행: `docker compose up -d` 후 `./gradlew bootRun`
- 스모크 테스트 2건이 이미 통과 상태다. 깨뜨렸다면 네 변경이 원인이다

## 막히면

스펙이 모호하거나 이 브리핑과 문서가 어긋나면 임의 해석하지 말고 관리자에게 질문한다. 답을 받으면 해당 문서에 반영한다.
