# F03 가용 객실 검색 · 착수 브리핑

이 문서는 F03 feature 세션의 시작점이다. 이 저장소의 문서 밖에 있는 맥락은 전제하지 않는다.

## 네 임무

고객이 호텔·날짜 범위·인원으로 **지금 예약할 수 있는 객실타입**을 찾는 검색을 만든다. 00 문서의 UC-1 하나가 전부다.

이 feature의 증명 대상은 동시성 제어가 아니라 **조회 성능과 정합성**이다. 재고를 깎는 쪽(F01)이 진실의 원본이고, 너는 그 진실을 빠르게 보여주되 **얼마나 낡을 수 있는지, 낡았을 때 사용자에게 무엇을 보장하는지**를 문서로 증명해야 한다. **스펙 작성부터 시작한다.** 승인 없이 코드를 쓰지 않는다.

## 읽는 순서

1. `CLAUDE.md` (자동 로드됨. 규칙과 세션 역할)
2. `docs/spec/00-problem-and-scope.md` — 승인된 전체 범위. F03의 유스케이스는 **UC-1 하나**
3. `docs/architecture/clean-architecture.md`, `docs/architecture/coding-rules.md` — 레이어·트랜잭션·캐시 규칙
4. `docs/architecture/parallel-work.md` — 소유 범위 규칙 (F03은 F01과 같은 테이블을 읽는다. 여기가 가장 민감하다)
5. `docs/spec/TEMPLATE.md`, `docs/architecture/diagram-rules.md` — 스펙 형식과 다이어그램 필수 조항
6. `docs/briefings/F01.md` — **F01이 만드는 재고 테이블 구조를 알아야 조회를 설계할 수 있다.** 형식 참고용이기도 하다
7. `docs/reviews/F01-spec-review-업계정합성.md` — 재고 모델의 업계 정합성 검토. "명시적 보류" 절의 *90일 시드 밖 날짜의 판매 전 / 매진 구분*은 검색이 직접 마주치는 문제다

## 소유 범위 (선언 완료, 스펙에 그대로 기재)

- **소유 패키지:** `com.pms.inventory.query.**` — **조회 전용이다**
- **읽기만 하는 패키지:** `com.pms.inventory.domain` (F01 소유). **절대 수정하지 않는다.** 수정이 필요하다고 판단되면 거기서 멈추고 관리자에게 보고한다. 몰래 고치지 않는다
- **Flyway 번호 대역:** V301 ~ V399. **스키마 변경 없이 인덱스 추가 정도만 필요할 가능성이 크다.** 테이블을 새로 만들거나 F01의 컬럼을 바꾸려는 판단이 서면 그것도 관리자에게 먼저 보고한다
- **쓰기 금지:** 재고를 차감하거나 복원하지 않는다. 그건 F01의 일이다. F03의 코드 경로에는 재고 테이블에 대한 `INSERT`/`UPDATE`/`DELETE`가 단 한 줄도 없어야 한다
- **수정이 필요한 공유 파일:** 현재 없음. 에러 코드 추가가 필요하면 `docs/architecture/parallel-work.md`의 공유 파일 절차(작은 커밋을 main에 먼저)를 따른다

## 반드시 스펙에서 답할 것

아래 두 질문에 답하지 못한 스펙은 승인 요청을 하지 않는다.

1. **재고가 바뀌었을 때 캐시를 언제 어떻게 무효화하는가.** F03은 F01의 재고 차감 코드에 손댈 수 없다는 제약 아래에서 답해야 한다. 무효화 신호를 누가 만들고 누가 받는지, 그 신호가 없을 때는 무엇이 캐시를 걷어내는지 쓴다.
2. **캐시가 조금 낡았을 때 사용자에게 무엇을 보장하는가.** 낡음의 방향(팔린 방이 남아 보이는 쪽 / 남은 방이 안 보이는 쪽) 각각에 대해 최악의 결과가 무엇인지 쓴다.

그리고 이것이 이 feature의 핵심 서사다.

> **검색 결과가 낙관적으로 낡으면 예약 단계에서 실패한다. 그 실패는 버그가 아니라 설계된 정상 흐름이다.**

검색은 후보를 제시할 뿐이고 재고의 진실은 예약 시점의 조건부 UPDATE가 정한다. 이 실패가 어떤 응답으로 나가고, 클라이언트가 무엇을 하며, 그 경로에서 초과 판매가 왜 일어날 수 없는지를 **시퀀스 다이어그램과 실패 시나리오 표로** 보여라. "재검색하세요"라고 한 줄 쓰고 넘어가면 반려 대상이다.

## 00 문서에서 이미 확정된 제약 (스펙에서 뒤집을 수 없음, 뒤집으려면 관리자 승인)

- 재고는 **객실타입 × 날짜 수량 행**이다 (00 D3). 검색은 이 행들을 기간만큼 훑는 문제로 귀결된다
- 호텔·객실타입·재고는 **시드 데이터 고정**이다 (00 D1). 관리자 CRUD가 없으므로 검색이 다뤄야 할 데이터 변경은 예약으로 인한 재고 증감뿐이다
- 재고와 예약은 **별도 구역**이다 (00 D6). `inventory.query`는 예약(`reservation.**`)을 참조하지 않는다
- 인증은 `X-User-Id` 헤더 (ADR-0006). 검색은 사용자 식별이 필요 없다면 요구하지 않아도 된다. 어느 쪽이든 스펙에 명시한다
- 다이어그램은 표준형 Mermaid (ADR-0005). 장식·커스텀 HTML 금지

## 일정 제약 (두 가지, 둘 다 강제다)

**1. 구현 코드는 F01이 main에 병합된 뒤에 시작한다.**

F03이 읽을 테이블을 F01이 만들기 때문이다. 이번 세션에서는 **브리핑과 스펙, 즉 문서까지만** 진행한다. 스펙 승인을 받았더라도 F01 병합 전에는 `dev-cycle`에 들어가지 않는다.

이 때문에 스펙을 쓰는 시점에 F01의 확정 스키마가 아직 없다. **F01 브리핑과 위 검토 문서에서 읽어낸 컬럼을 "가정한 계약"으로 스펙에 명시하고, 그 가정 자체를 결정 검토란에 올려 관리자 확인을 받아라.** 가정을 본문에 조용히 묻어두면 F01 병합 시점에 어긋난 것을 아무도 못 찾는다.

> **2026-08-15 갱신:** 스펙 작성 중 PM을 통해 F01의 확정 스키마를 전달받았다. `room_daily_inventory`는 자연키 복합 PK `(room_type_id, stay_date)`이고, 단가는 `room_type.base_price`다. 가정 계약표(스펙 5절 A1~A8) 중 A1~A7이 확정으로 닫혔고 A8(타임존·`Clock`)만 남았다. 그 결과 **F03은 Flyway 마이그레이션을 한 개도 만들지 않는다** — 클러스터드 PK가 검색 쿼리를 그대로 커버하므로 추가할 인덱스가 없다.

**2. F03의 Redis 캐시는 일정 지연 시 가장 먼저 잘리는 항목이다 (00 D4).**

절단 순서는 `F03 캐시 → UC-6 체크인아웃 → F02 프로모션`이며 이미 승인된 결정이다. 따라서 설계 요구가 하나 더 붙는다.

- **캐시 없이 DB 직행으로도 완전히 동작해야 한다.** 캐시는 성능 장치이지 기능의 일부가 아니다
- **캐시를 껐다 켤 수 있는 구조로 만든다.** 절단이 결정돼도 코드를 뜯어내지 않고 설정으로 끌 수 있어야 한다
- 두 모드(켬/끔)에서 **검색 결과가 같다는 것을 테스트로 증명한다.** 다른 점은 낡음의 창(window)뿐이어야 한다

## 동시성 규칙은 F03에도 적용된다

CLAUDE.md의 절대 규칙 — "동시성 관련 코드는 반드시 동시성 테스트를 동반한다" — 은 조회에도 적용된다. F03이 쓰기를 하지 않는다는 사실이 면제 사유가 아니다. 최소한 아래를 스펙의 테스트 계획에 넣는다.

- 재고가 바뀌는 도중에 검색이 도는 상황에서 **응답이 깨지지 않는다**(예외·부분 결과 없음)는 것
- 캐시를 켠 상태에서 **낡음이 정해진 시간 안에 사라진다**는 것. 낡음이 존재한다는 사실 자체도 테스트로 드러낸다. 숨기지 않는다
- Redis가 죽었을 때 **검색이 계속 동작한다**는 것

스레드 수, 재고 수, 기대 결과를 숫자로 적는다.

## 작업 절차

스킬이 슬래시 명령으로 등록되어 있지 않다면 `.claude/skills/<이름>/SKILL.md`를 직접 읽고 그 절차를 그대로 따른다.

1. `feature-spec` 스킬 실행 → `docs/spec/F03-가용-객실-검색.md` 작성 (결정 검토란 D 항목 필수, 열린 질문은 비운다)
2. `approval-report` 스킬로 승인 요청 (가능하면 Bear로 열고 SendUserFile로도 전송, 터미널 요약 3~5줄)
3. **승인을 받아도 F01 병합 전에는 여기서 멈춘다.** F01 병합 후 `dev-cycle` 스킬로 TDD 개발. 리뷰어 3명(`concurrency-reviewer`, `domain-reviewer`, `architecture-reviewer`) 병렬 호출
4. 완료 승인 후 main 병합은 관리자(PM 경유) 지시를 따른다

결정이 정해질 때마다 `decision-log`로 ADR을 남긴다. **F03에 배정된 ADR 번호 대역은 ADR-0030 ~ ADR-0039이며, `docs/decisions/INDEX.md`에는 자기가 추가한 줄만 넣고 기존 줄은 손대지 않는다.**

학습 노트는 `docs/learning/INDEX.md`가 PM 소유이므로 직접 넣지 않는다. **스펙 끝에 "학습 노트 후보" 목록으로만 남기고**, 관리자가 채택하면 그때 `learning-note` 스킬로 등록한다.

### 수정 금지 문서 (PM 소유)

`docs/spec/00-problem-and-scope.md`, `CLAUDE.md`, `docs/architecture/**`, `docs/learning/INDEX.md`는 고치지 않는다. 고쳐야 한다고 판단되면 멈추고 PM에게 보고한다.

절차 없이 고치지 않는 파일: `build.gradle`, `application.yml`, `docker-compose.yml`, `src/main/java/com/pms/common/**`.

## 환경

- 빌드: `./gradlew test` (Testcontainers가 MySQL 8.4·Redis 7.4를 띄움. Docker 필요)
- 로컬 실행: `docker compose up -d` 후 `./gradlew bootRun`
- 스모크 테스트 2건이 이미 통과 상태다. 깨뜨렸다면 네 변경이 원인이다
- worktree: `.claude/worktrees/F03/`, 브랜치 `worktree-F03`. **작업이 끝나면 반드시 커밋한다.** 커밋하지 않은 작업은 없어진다고 생각한다

## 막히면

스펙이 모호하거나 이 브리핑과 문서가 어긋나면 임의 해석하지 말고 관리자에게 질문한다. 답을 받으면 대화로 끝내지 말고 해당 문서에 반영한다.

특히 아래는 즉시 보고 대상이다.

- `com.pms.inventory.domain`을 수정해야 한다고 판단될 때
- F01의 테이블에 컬럼·제약 변경이 필요하다고 판단될 때 (인덱스 추가는 V301 대역 안에서 가능하나, 그 판단도 스펙의 결정 검토란에 올린다)
- F01 병합 후 실제 스키마가 스펙의 가정 계약과 어긋났을 때
