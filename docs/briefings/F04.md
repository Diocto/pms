# F04 부하테스트 · 착수 브리핑

이 문서는 F04 feature 세션의 시작점이다. 이 저장소의 문서 밖에 있는 맥락은 전제하지 않는다.

## 네 임무

k6 부하테스트 시나리오를 **설계하고, 실행하고, 리포트를 쓴다.**

이 과제의 목표는 동시성·멱등성·상태 전이를 **말이 아니라 수치로 증명하는 것**이다(`docs/spec/00-problem-and-scope.md` 1절). 그 증명을 담당하는 것이 바로 F04다. 다른 feature가 "우리 설계는 안전하다"고 문서에 쓰면, 그 문장이 부하 아래에서도 참인지 확인해 숫자를 붙이는 것이 네 일이다.

**큰 숫자를 만드는 것이 목적이 아니다.** 초당 몇 건을 찍었는지보다, 잔여 10실에 1,000건을 꽂았을 때 성공이 정확히 10건이었는지가 이 리포트의 본문이다.

## 읽는 순서

1. `CLAUDE.md` (자동 로드됨. 규칙과 세션 역할)
2. `docs/spec/00-problem-and-scope.md` — 승인된 전체 범위. 특히 1절(증명 대상), 5절(feature 분할과 일정), D4(절단 순서)
3. `.claude/skills/load-test/SKILL.md` — 네 작업 절차. 이 브리핑보다 이쪽이 절차의 진실이다
4. `docs/architecture/parallel-work.md` — 소유 범위 규칙
5. `docs/architecture/coding-rules.md`의 **다층 방어**·**멱등성** 절 — 무엇을 검증해야 하는지가 여기 있다. 특히 "1차 방어선(분산락)을 껐을 때도 불변식이 지켜지는지 증명한다"는 조항은 네 대조군 시나리오의 근거다
6. `docs/briefings/F01.md` — 형식 참고용. F01이 무엇을 만드는지 알아야 무엇을 때릴지 정할 수 있다
7. F01·F02·F03 스펙(`docs/spec/` 아래, 각 세션이 작성 중) — **API 계약과 에러 코드의 진실은 스펙이다.** 병합된 뒤 읽는다

## 소유 범위 (선언 완료, 시나리오 설계 문서에 그대로 기재)

- **소유 디렉터리:** `load-test/` (k6 스크립트·초기화 스크립트), `docs/load-test/` (시나리오 설계·결과·리포트)
- **읽기만 하는 것:** `src/**` 전부, 각 feature 스펙, `docker-compose.yml`, `src/main/resources/application.yml`
- **Flyway 번호 대역:** 없음. **마이그레이션 파일을 만들지 않는다.** 부하테스트용 데이터가 필요하면 F01 시드를 쓰거나, `load-test/` 안의 SQL 스크립트로 넣는다
- **Java 소스는 건드리지 않는다.** 부하테스트를 위해 애플리케이션 코드 변경이 필요하면(예: 분산락 on/off 스위치, 캐시 on/off 스위치) 직접 고치지 말고 관리자를 통해 해당 feature 세션에 요청한다
- **수정이 필요한 공유 파일:** 없음

## 도구

**k6로 확정돼 있다** (`CLAUDE.md` 기술 스택 표). 이 세션에서 바꾸지 않는다. 바꾸려면 ADR이 필요하다.

로컬에 이미 설치되어 있다 (k6 v0.57.0).

## 우선순위 — 이 항목은 잘리지 않는다

00 문서 D4에서 확정된 절단 순서는 **F03 캐시 → UC-6 체크인·체크아웃 → F02 프로모션**이며, **F01 코어와 F04 부하테스트는 자르지 않는다.**

즉 일정이 밀려도 부하테스트는 축소 대상이 아니다. 다만 앞 feature가 잘리면 **때릴 대상이 사라지는** 형태로 영향을 받는다. 그래서 시나리오는 아래처럼 등급을 나눠 설계한다.

| 등급 | 대상 | 의존 |
|---|---|---|
| 필수 | 재고 경합, 멱등성, 상태 전이 경합, 락 유무 대조 | F01만 있으면 된다 |
| 조건부 | 프로모션 스파이크 | F02가 살아남으면 |
| 조건부 | 조회 폭주 속 예약, 캐시 유무 대조 | F03 캐시가 살아남으면 |

**필수 등급은 F01 하나만 병합되면 전부 실행 가능해야 한다.** 조건부 시나리오가 못 돌아도 리포트의 핵심 명제 (가)(나)(다)와 (라)의 절반(락 유무)은 증명된다.

## 증명해야 할 명제

리포트가 참으로 만들어야 하는 문장은 아래 넷이다. 시나리오는 전부 이 넷 중 하나에 매달려야 하고, 어느 명제에도 안 걸리는 시나리오는 만들지 않는다.

### (가) 초과 판매가 일어나지 않는다

> 잔여 N실에 N보다 훨씬 많은 동시 요청이 몰려도, **성공 건수는 정확히 N이고 재고는 절대 음수가 되지 않는다.**

- 검증은 k6가 받은 201 응답 수만으로 끝내지 않는다. **DB를 직접 조회해** `성공 응답 수 = 예약 행 수 = 초기 재고 수` 등식을 확인한다
- `remaining < 0`인 행이 **한 건이라도** 있으면 실패다
- 초과분 요청은 5xx가 아니라 **409 INSUFFICIENT_INVENTORY로 정중히 거절**되어야 한다. 거절은 에러가 아니라 설계대로 동작한 것이므로 에러율 계산에서 분리해 센다

### (나) 같은 요청을 여러 번 보내도 예약은 한 건이다

> **같은 멱등성 키로 같은 요청을 여러 번 보내도 예약은 한 건만 생긴다.**

- 클라이언트 재시도·더블클릭·타임아웃 후 재전송을 그대로 재현한다
- 재요청은 저장된 이전 결과를 그대로 받거나(같은 예약 ID) 409로 거절되어야 하고, **두 번째 예약 행이 생기면 실패다**
- 재고도 한 번만 차감되어야 한다. 예약은 한 건인데 재고가 두 번 빠졌으면 그것도 실패다

### (다) 전이 표 밖의 전이는 동시 상황에서도 통과하지 않는다

> **전이 표에 없는 상태 전이는 동시 요청 상황에서도 통과하지 않는다.**

- 대표 경합: 같은 예약에 **취소와 확정이 같은 순간에** 들어오는 경우. 둘 중 하나만 성공해야 하고, 실패한 쪽은 409 INVALID_STATE_TRANSITION이어야 한다
- **CANCELLED·EXPIRED·CHECKED_OUT은 종료 상태다.** 종료 상태에 도달한 예약이 그 뒤 다른 상태로 움직였다면 실패다
- 취소가 성공했는데 재고가 복원되지 않았거나, 확정이 실패했는데 재고가 한 번 더 빠졌다면 그것도 실패다. **상태와 재고는 항상 짝이 맞아야 한다**

### (라) 상대 비교로 서사를 만든다

> **락 있음/없음, 캐시 있음/없음의 처리량과 정확성 차이를 같은 부하로 나란히 측정한다.**

이 항목이 리포트의 이야기 구조다. 절대 수치("초당 320건")는 이 머신에서만 참이지만, **같은 머신·같은 부하에서 잰 두 값의 차이**는 설계 판단의 근거가 된다.

측정할 대조쌍:

| 대조쌍 | 기대하는 그림 |
|---|---|
| 분산락 있음 vs 없음 | **정확성은 양쪽 다 지켜져야 한다.** 락을 꺼도 2차 방어선(조건부 UPDATE)이 초과 판매를 막는다는 것이 coding-rules의 설계 주장이고, 이걸 수치로 확인하는 것이 목적이다. 차이는 정확성이 아니라 **처리량과 지연, DB 쪽 경합 비용**에서 난다 |
| 캐시 있음 vs 없음 | 조회 처리량과 p95의 차이. 대신 캐시가 재고 변화를 얼마나 늦게 반영하는지(정합성 비용)를 함께 잰다 |

**락을 껐는데 초과 판매가 나온다면, 그것은 F04의 실패가 아니라 발견이다.** 리포트의 하이라이트로 쓰고 관리자에게 즉시 보고한다.

## 리포트에 반드시 들어가는 것 — 실행 환경의 한계

**측정 환경의 한계를 정직하게 쓴다.** 이건 선택이 아니라 필수 조항이다.

- 앱, MySQL, Redis, k6가 **전부 같은 노트북 한 대에서** 돈다. 부하 생성기가 피시험 대상과 CPU·메모리를 나눠 쓴다
- 그래서 여기서 나온 처리량·지연 **절대값은 이 시스템의 성능 한계가 아니다.** k6가 CPU를 뺏어 앱이 못 낸 성능일 수도 있고, 반대일 수도 있다
- **근거로 쓸 수 있는 것은 상대 비교다.** 같은 머신·같은 부하·같은 시각대에 조건 하나만 바꿔 잰 두 값의 차이만이 설계 판단의 근거가 된다
- **정확성(불변식) 검증은 환경 한계와 무관하게 유효하다.** "재고 10에 성공 10건"은 머신이 느리든 빠르든 참이거나 거짓이다. 리포트는 이 구분을 분명히 해야 한다 — *성능 수치는 참고, 불변식 검증은 결론*

리포트에 기록할 환경 항목: 머신 사양(Apple M2 8코어 / 16GB), 앱·DB·k6 동시 구동 여부, HikariCP 최대 커넥션(현재 20), MySQL 격리 수준(REPEATABLE-READ), 실행 시각, k6 버전.

## 작업 절차

스킬이 슬래시 명령으로 등록되어 있지 않다면 `.claude/skills/<이름>/SKILL.md`를 직접 읽고 그 절차를 그대로 따른다.

1. **경합 지점 선정 → 시나리오 설계** → `docs/load-test/scenarios.md`. 시나리오마다 부하 모델·지속 시간·불변식·성공 기준(임계값 + 불변식 검증 쿼리)을 **숫자로** 확정한다
2. **관리자 확인** — 시나리오 설계가 끝나면 확인을 받는다. 결정 검토란(D 항목)을 반드시 둔다
3. **스크립트 작성** → `load-test/*.js` + 초기화 스크립트. F01 API 계약이 확정된 뒤 실제 엔드포인트를 채운다
4. **실행** — F01이 main에 병합된 뒤. `docker compose up -d` → 앱 기동 → `k6 run`
5. **DB 실측 검증** — k6 결과만으로 끝내지 않는다. 부하 후 DB를 직접 조회해 불변식을 확인한다
6. **리포트** → `docs/load-test/report.md`. 숫자 나열이 아니라 **해석**을 쓴다
7. 완료 승인(`approval-report` 스킬)

## 진행 조건과 타이밍

- **지금 바로 시작할 수 있다.** F01·F02·F03과 파일이 전혀 겹치지 않는다 (Java 소스 0줄, Flyway 0건)
- **설계 단계는 API가 없어도 진행된다.** 지금 확정하는 것은 "무엇을 어떤 부하로 때리고, 무엇을 참으로 판정할 것인가"이지 URL이 아니다
- **실제 실행은 F01이 main에 병합된 뒤에 한다.** 일정상 8/16 저녁부터가 실행 구간이다 (00 문서 5절)
- 00 문서 일정 기준: 8/16 시나리오 작성 + 저녁 실행 착수, 8/17 리포트 작성

## 막히면

- **API 계약이 필요하면 추정하지 않는다.** 엔드포인트 경로, 요청 본문 필드, 응답 형식, 에러 코드는 전부 F01 스펙이 진실이다. 스펙이 아직 없으면 **관리자를 통해 F01 세션에 질문한다.** 임의로 가정하고 스크립트를 쓴 뒤 나중에 고치는 것보다, 지금 판정 기준을 확정하고 URL만 비워두는 편이 낫다
- **애플리케이션 코드 변경이 필요하면** (락 스위치, 캐시 스위치, 테스트용 초기화 훅 등) 직접 고치지 말고 관리자에게 요청 사항으로 올린다. 특히 (라) 대조군은 **on/off를 설정으로 바꿀 수 있어야** 성립하므로, 이 요구를 시나리오 설계 단계에서 미리 올려두는 것이 중요하다
- 스펙과 이 브리핑이 어긋나면 스펙이 이긴다. 어긋난 사실을 관리자에게 보고한다

## 환경

- k6: v0.57.0 (설치 완료)
- 인프라: `docker compose up -d` (MySQL 8.4 / Redis 7.4, 포트 3306·6379)
- 앱: `./gradlew bootRun` 또는 `./gradlew bootJar` 후 `java -jar`
- 측정 머신: Apple M2, 8코어, 16GB
- 앱에 `management.endpoints`로 `health,info,metrics,prometheus`가 열려 있다. 병목 분석에 쓴다
- HikariCP 최대 커넥션 20 (`application.yml`). 병목이 커넥션 풀인지 판단하는 기준값이므로 리포트에 기록한다
