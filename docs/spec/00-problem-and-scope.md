# 문제 정의와 구현 범위

- 상태: 승인 대기
- 작성일: 2026-08-14

## 1. 어떤 문제를 푸는가

숙박 예약 플랫폼에서 **같은 객실을 여러 사람이 동시에 예약하려 할 때 무슨 일이 벌어지는가**를 다룬다.

예약 시스템의 진짜 어려움은 CRUD가 아니다. 다음 세 가지가 겹치는 지점에 있다.

**동시성.** 잔여 1실을 두 사람이 같은 순간에 예약하면, 순진한 구현(조회 → 판단 → 저장)은 둘 다 성공시킨다. 초과 판매다. 인기 날짜, 프로모션 오픈 순간에는 수백 요청이 같은 재고 행을 두드린다.

**멱등성.** 결제 버튼을 두 번 누르거나, 타임아웃 후 클라이언트가 재시도하면 같은 요청이 두 번 도착한다. 이걸 두 건의 예약으로 만들면 안 된다. "안 일어나겠지"가 아니라 정상 상황으로 설계해야 한다.

**상태 전이.** 예약은 생성 → 확정 → 체크인 → 체크아웃으로 흐르고, 중간에 취소·결제 실패·미결제 만료로 빠진다. 이 규칙이 if-else로 흩어져 있으면 상태 추가마다 버그가 생기고, 규칙을 문서로 증명할 수 없다.

이 셋을 **말이 아니라 수치로 증명하는 것**(동시성 테스트, k6 부하테스트)까지가 이 과제의 목표다.

### 왜 이 문제를 골랐는가 (자유 주제 선정 이유)

- 정답이 코드 스타일이 아니라 **설계 판단**에 있는 문제다. 락 선택, 트랜잭션 경계, 방어선 설계가 그대로 평가 대상이 된다.
- 검증이 객관적이다. "재고 10개에 100명이 몰렸을 때 정확히 10건만 성공"은 참·거짓이 갈리는 명제다.
- 실무 대표성이 있다. 예약·재고·결제는 어느 도메인에나 있는 구조라 면접에서 깊게 논의할 수 있다.

## 2. 서비스 서사

멀티 호텔 예약 플랫폼이다.

- 플랫폼에 **호텔**이 여러 개 있다.
- 호텔마다 **객실타입**(스탠다드, 디럭스 등)이 있고, 객실타입마다 **총 객실 수**가 있다.
- 고객은 날짜 범위와 인원으로 가용 객실을 검색하고, 객실타입 단위로 예약한다.
- 재고는 개별 객실 호수가 아니라 **객실타입 × 날짜 단위 잔여 수량**으로 관리한다. (실제 OTA들의 모델과 같다)
- 특정 날짜·객실타입에 한정 수량 **특가(프로모션)**가 열리면 트래픽이 한 점으로 몰린다.

## 3. 구현 범위

### 포함

| # | 유스케이스 | 핵심 관심사 |
|---|---|---|
| UC-1 | 가용 객실 검색 (호텔·날짜 범위·잔여 기준) | 조회 성능, Redis 캐시, 캐시-재고 정합성 |
| UC-2 | 예약 생성 | 멱등성 키, 재고 차감 원자성, 분산락, PENDING 생성 |
| UC-3 | 예약 확정 (내부 모의 결제) | 상태 전이, 결제 실패 분기, 외부 호출은 트랜잭션 밖 |
| UC-4 | 예약 취소 | 상태 전이, 재고 복원, 취소-확정 경합 |
| UC-5 | 미결제 만료 (EXPIRE) | 시간 기반 전이, 만료-확정 경합, 재고 복원 |
| UC-6 | 체크인·체크아웃 | 상태 전이 표 완성 |
| UC-7 | 선착순 특가 예약 | 한정 수량 원자적 차감, 스파이크 트래픽 |

여기에 전 구간 공통으로 **k6 부하테스트와 리포트**가 붙는다.

### 제외 (이유와 함께)

| 제외 항목 | 이유 |
|---|---|
| 호텔·객실타입 관리자 CRUD | 관리 기능은 동시성 주제와 무관하다. 호텔·객실타입·재고는 시드 데이터(Flyway 마이그레이션)로 넣는다 |
| 실제 PG 연동 | 외부 의존은 모의 결제 모듈로 대체한다. 설계 포인트(트랜잭션 밖 호출, 실패 분기)는 모의로도 다 보여진다 |
| 회원가입·인증 | `X-User-Id` 헤더로 식별한다. 이 과제의 관심사가 아니다 (ADR 예정) |
| 개별 객실 호수 배정 | 체크인 시 호수 배정은 재고 문제와 다른 문제다. 객실타입 수량 모델로 충분하다 |
| 쿠폰 발급·사용 | 프로모션은 특가 재고 선착순으로 한정한다. 쿠폰은 애그리거트가 하나 더 늘어 3일 반에 부담이다 |
| 알림, 리뷰, 정산 | 주제와 무관하다 |

## 4. 도메인 개요

바운디드 컨텍스트는 둘로 본다.

```
inventory (재고)                     reservation (예약)
├── Hotel / RoomType (읽기 전용 참조)  ├── Reservation (애그리거트 루트)
├── RoomDailyInventory (애그리거트)    │     상태머신: 전이 테이블
│     불변식: remaining >= 0          │     불변식: 전이 표 밖 전이 금지
└── PromotionInventory (애그리거트)    └── (Reservation은 roomTypeId만 보유)
      불변식: remaining >= 0
```

상태 전이 표 초안. 상세는 F01 스펙에서 확정한다.

| 현재 | 이벤트 | 다음 |
|---|---|---|
| PENDING | CONFIRM (결제 성공) | CONFIRMED |
| PENDING | PAYMENT_FAILED | CANCELLED |
| PENDING | CANCEL | CANCELLED |
| PENDING | EXPIRE | EXPIRED |
| CONFIRMED | CANCEL | CANCELLED |
| CONFIRMED | CHECK_IN | CHECKED_IN |
| CHECKED_IN | CHECK_OUT | CHECKED_OUT |

표에 없는 조합은 전부 거부. CANCELLED·EXPIRED·CHECKED_OUT은 종료 상태.

ADR-0004(코어 순차, 확장 병렬)에 따라 나눈다.

|---|---|---|---|---|
| F01 예약 코어 | UC-2~6 전부. Reservation 애그리거트, 상태머신, 재고 차감·복원, 멱등성, 분산락 | `reservation.**`, `inventory.domain` | V001~V099 (공통 스키마 포함) | **단일 세션 순차** |

## 7. 결정 검토란

이 문서를 쓰면서 작성자가 내린 결정입니다. 항목 번호로 동의 여부를 알려주세요. 전부 동의해야 승인입니다.

### D1. 관리자 기능 제외, 호텔·객실·재고는 시드 데이터 고정

- **결정:** 호텔·객실타입 CRUD API를 만들지 않고, 데이터는 Flyway 마이그레이션으로 미리 넣는다.
- **이유:** 멀티 호텔 서사를 유지하면서 범위 폭발을 막기 위해서다. 관리 기능은 동시성 주제와 무관한 CRUD다.
- **트레이드오프:** "플랫폼"이라면서 공급자 쪽 그림이 없다. 검토관이 완결성 부족으로 볼 여지가 있다.
- **대안이었던 것:** 관리자 API 포함(액터 추가, 최소 반나절 소요), 단일 호텔로 서사 축소.
- **확인 질문:** 공급자 기능 없이 시드 데이터로 고정해도 괜찮습니까?

### D2. 확정·취소·만료·체크인아웃(UC-3~6)을 전부 F01 하나에 통합

- **결정:** 예약의 모든 상태 전이 유스케이스를 F01 한 세션이 만든다.
- **이유:** 전부 `Reservation` 애그리거트의 전이라서, 쪼개면 병렬 세션 간 의미 충돌(전이 표 불일치)이 난다. ADR-0004의 도메인 hard 소유 원칙 적용이다.
- **트레이드오프:** F01이 커져서 하루 안에 끝내야 하는 부담이 크다. F01이 밀리면 전체 일정이 민다.
- **대안이었던 것:** UC-6(체크인아웃)을 별도 feature로 분리. 전이 표 소유권이 갈라져 기각했다.
- **확인 질문:** F01 비대화를 감수하고 애그리거트 단위 통합을 유지해도 괜찮습니까?

### D3. 재고 모델을 "객실타입 × 날짜 잔여 수량"으로 고정

- **결정:** 개별 객실 호수는 다루지 않고, 수량으로만 재고를 관리한다.
- **이유:** 동시성 제어 대상이 명확한 행(잔여 수량)이 되고, 실제 OTA 모델과 같다.
- **트레이드오프:** "체크인 때 몇 호실?"에 답이 없다. 호수 배정은 별도 문제로 선언하고 뺐다.
- **대안이었던 것:** 객실 호수 엔티티를 두고 예약-호수 매핑. 배정 알고리즘이 추가돼 기각했다.
- **확인 질문:** 호수 배정 없는 수량 모델로 가도 괜찮습니까?

### D4. 지연 시 절단 순서: F03 캐시 → UC-6 체크인아웃 → F02 프로모션

- **결정:** 일정이 밀리면 이 순서로 자른다. F01 코어와 F04 부하테스트는 자르지 않는다.
- **이유:** 과제의 증명 대상(동시성·멱등성·수치 증명)에서 먼 것부터 자르는 순서다.
- **트레이드오프:** 최악의 경우 프로모션 없는 제출이 되고, 스파이크 시나리오는 "예약 오픈 집중"으로 격이 낮아진다.
- **대안이었던 것:** 프로모션을 사수하고 EXPIRE를 자르는 순서. 상태머신 완결성이 깨져 기각했다.
- **확인 질문:** 이 절단 우선순위에 동의합니까?

### D5. 프로모션은 "특가 재고 선착순"으로 한정, 쿠폰 제외

- **결정:** 특정 날짜·객실타입에 한정 수량 특가를 여는 형태만 구현한다.
- **이유:** 기존 재고 모델을 재사용해 추가 비용이 작고, 스파이크 시나리오 소재로 충분하다.
- **트레이드오프:** 쿠폰 발급·사용이라는 더 흔한 프로모션 형태를 못 보여준다.
- **대안이었던 것:** 선착순 쿠폰(발급 애그리거트 추가 필요, 3일 반에 부담).
- **확인 질문:** 쿠폰 없이 특가 재고 방식으로 가도 괜찮습니까?

### D6. 바운디드 컨텍스트를 inventory / reservation 둘로 분할

- **결정:** 재고와 예약을 다른 컨텍스트로 두고, 예약은 재고를 ID로만 참조한다.
- **이유:** 불변식이 다르다(재고: 잔여 ≥ 0, 예약: 전이 표 준수). 병렬 작업의 소유 경계로도 쓰인다.
- **트레이드오프:** 예약 생성이 두 컨텍스트를 한 트랜잭션에서 건드린다. "한 트랜잭션 한 애그리거트" 원칙의 예외가 되고, 이 예외는 F01 스펙에서 근거를 명시해야 한다.
- **대안이었던 것:** 단일 컨텍스트(경계 없음, 소유 분리 불가), 3분할(promotion 별도 — F02 스펙에서 재검토).
- **확인 질문:** 2분할과 트랜잭션 예외 방침에 동의합니까?

## 8. 열린 질문

없음. (승인 시점 기준)
