# [F03] 검색 API 계약 (F04 부하테스트용)

- 날짜: 2026-08-15
- 상태: **잠정.** `docs/spec/F03-가용-객실-검색.md`가 승인되면 확정된다
- 대상: F04 부하테스트 세션 (PM 경유 전달)
- 원본: `docs/spec/F03-가용-객실-검색.md` 8절. **두 문서가 어긋나면 원본이 진실이다**

이 문서는 F04가 검색→예약 시나리오를 짤 수 있도록 요청·응답 형태와 합격선 숫자만 뽑은 것이다. 설계 근거는 원본 스펙에 있다.

## 1. 엔드포인트

```
GET /api/availability
```

인증 헤더는 요구하지 않는다. `X-User-Id` 없이 호출한다 (스펙 D11).

## 2. 요청 파라미터

| 파라미터 | 타입 | 필수 | 범위 | 비고 |
|---|---|---|---|---|
| `hotelId` | long | 필수 | 양수 | 시드는 1(서울 그랜드), 2(부산 오션뷰). **3 이상은 404** |
| `checkIn` | `yyyy-MM-dd` | 필수 | **오늘(2026-08-15) 이상** | 서버 `Clock` 기준. **예약 API와 달리 검색은 과거를 400으로 막는다** |
| `checkOut` | `yyyy-MM-dd` | 필수 | `checkIn` 초과, `checkIn + 30일` 이하 | 체크아웃 당일은 점유하지 않는다 |
| `guestCount` | int | 필수 | 1 ~ 20 | 시드 `capacity` 최대가 4다. 아래 경계 표 참고 |
| `roomCount` | int | 선택 | 1 ~ 10 (기본 1) | |
| `fresh` | boolean | 선택 | 기본 false | **true면 캐시를 우회하고 DB에서 읽은 뒤 캐시를 다시 채운다** |

범위를 벗어나면 400이다. **400이 대량 발생하면 측정이 오염되므로, 파라미터 생성 로직이 아래 세 경계를 지키는지 먼저 확인하기 바란다.**

### 시드 기준 경계값 (F01 스펙 5.5)

| 경계 | 값 | 지키지 않으면 |
|---|---|---|
| 재고 날짜 범위 | **2026-08-01 ~ 2026-10-29** (고정 날짜. `CURDATE()` 아님) | — |
| **검색 가능한 `checkIn`** | **2026-08-15(오늘) 이상** | 그 앞은 **400**. 시드 범위 안이어도 검색으로 도달할 수 없다 |
| **검색 가능한 `checkOut`** | **2026-10-30 이하** | 그 뒤는 200 + `emptyReason: NOT_YET_OPEN`. **이게 대량 나오면 시나리오가 범위 밖을 찍고 있다는 신호다** |
| 호텔 | 1, 2 | 3 이상은 404 |

즉 부하 시나리오의 안전 구간은 **`checkIn ∈ [2026-08-15, 2026-10-29]`, `checkOut ≤ 2026-10-30`**이다.

### 인원 필터 경계 — 필터 식은 `capacity × roomCount >= guestCount`

시드 `capacity`는 id 1~5에 대해 2 / 3 / 4 / 2 / 4다.

| 요청 | 결과 |
|---|---|
| `hotelId=1, guestCount=2, roomCount=1` | id 1·2·3 (3종) |
| `hotelId=1, guestCount=4, roomCount=1` | id 3만 (스위트) |
| `guestCount=5, roomCount=1` | **항상 빈 결과 + `NO_FITTING_ROOM_TYPE`** (어떤 타입도 capacity 4를 넘지 않는다) |
| `guestCount=5, roomCount=2` | capacity 3 이상 (id 2·3·5) |

### 경합을 만들려면

시드의 초기 `remaining`은 전부 `total_quantity`와 같고 줄여둔 날짜가 없다. **검색 결과의 `minRemaining`이 눈에 띄게 줄어드는 것을 보려면 재고가 적은 객실타입을 써야 한다.**

| 객실타입 | 수량 | 쓰임 |
|---|---|---|
| id 3 스위트 (hotelId 1) | **10실** | 주 경합 대상. 검색+예약 혼합 시나리오에서 `minRemaining`이 10 → 0으로 가는 것을 관찰할 수 있다 |
| id 5 오션뷰 스위트 (hotelId 2) | 20실 | 보조 |
| id 1 스탠다드 | 100실 | 경합이 거의 안 난다. 순수 조회 성능 측정용 |

## 3. 응답

### 200 (가용 있음)

```json
{
  "hotelId": 1,
  "checkIn": "2026-09-01",
  "checkOut": "2026-09-04",
  "nights": 3,
  "guestCount": 2,
  "roomCount": 1,
  "searchedAt": "2026-09-01T14:03:22+09:00",
  "source": "CACHE",
  "staleToleranceSeconds": 10,
  "items": [
    {
      "roomTypeId": 11,
      "roomTypeName": "스탠다드",
      "capacity": 2,
      "minRemaining": 5,
      "pricePerNight": 90000,
      "totalPrice": 270000
    }
  ]
}
```

### 200 (가용 없음)

`items`가 빈 배열이고 `emptyReason`이 붙는다. `NOT_YET_OPEN`이면 `salesOpenUntil`도 붙는다.

```json
{
  "...": "위와 동일",
  "items": [],
  "emptyReason": "SOLD_OUT"
}
```

### 부하테스트에서 쓸 만한 필드

| 필드 | 값 | F04가 쓰는 법 |
|---|---|---|
| `source` | `CACHE` \| `DB` | **캐시 히트율을 응답에서 직접 셀 수 있다.** 별도 계측 없이 `source=CACHE` 비율이 곧 히트율이다 |
| `searchedAt` | ISO-8601 | 응답 시각과의 차이가 곧 **그 응답이 실제로 얼마나 낡았는지**다. 캐시 히트면 0이 아니다 |
| `staleToleranceSeconds` | 정수 (캐시 끄면 `0`) | 낡음의 상한. 아래 합격선의 기준값 |
| `minRemaining` | 정수 | 기간 중 가장 잔여가 적은 날의 잔여. 예약 시나리오에서 이 값이 0이 되는 순간을 관찰할 수 있다 |
| `emptyReason` | 3종 | 빈 응답이 매진인지 판매 전인지 구분. **시나리오가 90일 밖 날짜를 찍고 있으면 `NOT_YET_OPEN`이 대량 나온다 — 그건 측정 오류 신호다** |

### 에러

| 상태 | `code` | 언제 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 파라미터 범위 위반 |
| 404 | `RESOURCE_NOT_FOUND` | 존재하지 않는 `hotelId` |
| 500 | `INTERNAL_ERROR` | DB 장애 |

**Redis 장애는 에러가 아니다.** 200 + `source: DB`로 나간다. 부하 중 Redis를 죽여도 실패율은 오르지 않고 `source` 분포와 응답 시간만 바뀐다.

## 4. 캐시 동작 (F04가 알아야 하는 것)

| 항목 | 값 | 비고 |
|---|---|---|
| 캐시 켜고 끄기 | `pms.search.cache.enabled` (기본 `true`) | **설정 한 줄로 전환된다.** 캐시 유무 비교 측정이 재배포 없이 가능하다 |
| TTL | `pms.search.cache.ttl-seconds` (**잠정 10초**) | 승인 시 확정. 값이 바뀌면 PM 경유로 알린다 |
| 캐시 키 | `avail:{hotelId}:{checkIn}:{checkOut}:{guestCount}:{roomCount}` | `fresh`는 키에 없다 |
| 캐시되는 것 | 빈 결과 포함 응답 전체 | 매진 날짜도 캐시된다 |
| 무효화 | TTL 만료 + `fresh=true` 재적재만 | 재고 변경 이벤트 연동 없음 (스펙 D6) |
| 스탬피드 방어 | **없음** (스펙 D10) | **F04가 이걸 측정해 주기를 기대하고 있다.** 아래 참고 |

부하 시나리오에서 키가 얼마나 흩어지는지에 따라 히트율이 크게 달라진다. 날짜 조합을 완전 무작위로 뽑으면 히트율이 0에 가깝고, 인기 날짜 소수에 몰면 90%를 넘는다. **둘 다 재보는 것이 이 캐시의 값어치를 보여주는 방법이다.**

## 5. 합격선 숫자 (F04 Q6에 대한 답)

TTL 잠정값 10초 기준이다.

| # | 무엇을 재나 | 합격선 | 근거 |
|---|---|---|---|
| S1 | **낡음의 상한 (stale window)** | 재고를 바꾼 시점부터 **TTL + 2초(= 12초)** 안에 모든 검색 응답이 새 값을 반영한다 | TTL이 낡음의 상한이다(스펙 G2). 2초는 요청 왕복과 측정 여유 |
| S2 | 캐시 히트 응답의 `searchedAt` 지연 | 응답 시각 − `searchedAt` ≤ TTL(10초) | 이 값이 TTL을 넘으면 TTL이 안 걸린 것이다(스펙 I5). **실패로 판정한다** |
| S3 | 캐시 켬/끔 결과 동등성 | 두 모드의 `items`가 동일 (`source` 제외) | 스펙 G5 |
| S4 | Redis 다운 중 실패율 | **0%.** 전부 200 + `source: DB` | 스펙 D7 fail-open |
| S5 | 검색→예약 409 비율 | **합격/불합격 대상이 아니라 관측 대상이다** | 아래 참고 |
| S6 | 초과 판매 | **0건.** 어떤 조건에서도 `remaining < 0`이 없고 판매 수량이 재고를 넘지 않는다 | 스펙 G4. **이것만은 절대 조건이다** |

**S5를 실패로 세지 말아 달라.** 검색 결과가 낡아 예약이 409로 실패하는 것은 F03이 설계한 정상 흐름이다(스펙 6절). 409 비율은 "얼마나 자주 헛걸음이 생기는가"를 보여주는 **품질 지표**이지 오류율이 아니다. 부하 리포트에서 이 둘을 섞으면 정상 동작이 장애처럼 보인다.

같은 이유로 부하 스크립트는 409를 받았을 때 **`fresh=true`로 재검색한 뒤 최대 2회까지 재시도**하는 것이 실제 클라이언트 동작에 맞다(스펙 6절 클라이언트 계약). 재시도 없이 409를 그냥 세면 실제보다 실패가 부풀려진다.

## 6. 시나리오 제안

| 시나리오 | 목적 | 구성 |
|---|---|---|
| L1 검색 단독 (캐시 켬 vs 끔) | 캐시의 값어치 | 같은 부하를 두 모드로. 처리량·p95·`source` 분포 비교 |
| L2 검색 키 분산 (인기 날짜 집중 vs 무작위) | 히트율이 성능에 미치는 영향 | 날짜 선택 분포만 바꿔 L1 반복 |
| L3 검색 + 예약 혼합 | 낡음이 실제로 얼마나 생기는가 | 검색 후 일정 비율이 예약 시도. 409 비율과 S1 측정 |
| L4 Redis 다운 주입 | fail-open 검증 | 부하 중 Redis 정지. S4 확인 |
| L5 캐시 스탬피드 관찰 | 스펙 D10의 미룬 판단을 검증 | 인기 키 하나에 집중 부하. **TTL 만료 순간 DB 쿼리가 튀는지** 관찰. 튀면 F03이 방어를 추가할 근거가 된다 |

L5가 F03에게 가장 필요한 측정이다. 스펙 D10에서 스탬피드 방어를 "측정 후 판단"으로 미뤘고, 그 측정을 F04에 의존하고 있다.

| `pricePerNight`·`totalPrice` | `room_type.base_price` 확정. 유지 | 확정 |
| 구현 착수 | F01 병합 후 | — |
