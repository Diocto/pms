## ⚠ 정말로 다시 써야 하는 두 절

나머지는 기계적이다. 이 둘만 **판단이 다시 필요하다.**

### R1. §7 락 순서 — 훅 안 락 금지의 근거 (PM이 지목한 그것)

지금 근거는 이렇게 쓰여 있다.

> 락을 잡는 바깥 빈과 트랜잭션을 여는 안쪽 빈이 분리돼 있다. 훅은 트랜잭션 안에서 불린다. 거기서 락을 잡으면 그 순서가 뒤집혀서, 커밋 전에 락이 풀리거나 락을 쥔 채 커밋을 기다리게 된다.

**"빈이 분리돼 있다"는 Spring 프록시 구조의 설명이다.** `@Transactional`이 프록시 경계에서 걸리기 때문에 락을 잡는 메서드와 트랜잭션을 여는 메서드를 다른 빈으로 쪼개야 했던 것이고, 파이썬에는 그 제약이 없다.

**규칙은 그대로 유효하다. 근거가 오히려 더 단순해진다.** SQLAlchemy는 세션과 트랜잭션이 **명시적**이라 "락 → `session.begin()` → `commit()` → 락 해제"를 그냥 그 순서로 쓰면 된다. 프록시 때문에 클래스를 쪼개야 할 이유가 없어진다.

**대신 새로 생기는 함정이 있어 보인다 — 확인이 필요하다.** 명시적 세션은 **훅이 어느 세션 안에서 도는지가 호출자에 달려 있다.** Spring은 트랜잭션이 스레드에 매여 있어 훅이 자기도 모르게 같은 트랜잭션에 들어갔지만, 파이썬에서는 **F01이 세션을 훅에 넘겨주지 않으면 F02가 자기 세션을 열어버릴 수 있다.** 그러면 "예약과 사용권이 같은 트랜잭션에서 커밋된다"(D3의 핵심 명제)가 조용히 깨진다.

**F01의 새 규칙 문서를 받으면 이것부터 확인한다.** 훅 시그니처가 세션을 명시적으로 받는지, 아니면 컨텍스트 변수로 공유되는지. 답에 따라 §7과 §10의 경고 블록을 다시 쓴다. **T21·T22(함께 커밋 / 함께 롤백)는 그대로 두면 되고, 오히려 이 함정을 잡는 테스트가 된다.**

### R2. §3 F01 계약 — 인터페이스 코드 블록

지금은 Java `interface` 5개와 `record` 4개가 코드 블록으로 박혀 있다. **계약의 내용(무엇을 언제 부르는가, 인자가 무엇인가, 반환이 무엇인가)은 전부 살지만 표기가 통째로 바뀐다.**

- `interface` → `Protocol` 또는 추상 베이스 (F01 선택을 따른다)
- `record` → `dataclass` / Pydantic 모델 (SQLModel 스택이니 후자일 가능성)
- `Optional<AppliedDiscount>` → `AppliedDiscount | None`
- `List<Hook>` 주입 → **Dependency Injector의 리스트 프로바이더**

**"구현이 0개면 아무 일도 안 일어난다"는 성질이 핵심이고, 그건 유지된다.** PM 말대로 컨테이너에서는 이게 기본 동작에 가깝다. 다만 **§10의 "F02를 통째로 들어내도 F01이 돌아야 한다"(절단 3순위 대비)를 컨테이너 구성으로 어떻게 보장하는지는 F01 규칙 문서를 봐야 쓸 수 있다.** 빈 리스트를 주입하는 것과 프로바이더를 등록하지 않는 것이 같은 결과인지 확인이 필요하다.

## 이 전환에서 잃는 것 — 정직하게

**전환 자체는 지금이 가장 싸다.** 구현이 0줄이고 스펙은 판단의 기록이라 대부분 언어 밖에 있다. 다만 두 가지는 실제로 잃는다.

- **F01·F04와 맞춰둔 계약 표기가 한 번 흔들린다.** 내용은 같아도 세 세션이 같은 타이밍에 같은 표기로 갈아타야 한다. 어긋나면 "훅 이름은 맞는데 시그니처가 다른" 상태가 생기고, 이건 컴파일 타임에 안 잡힌다 — **파이썬이라 더 그렇다**
- **`List<Port>` 주입으로 얻던 "구현 0개 = no-op"이 컨테이너 구성으로 옮겨간다.** 성질은 유지되지만 **보장의 위치가 타입 시스템에서 조립 설정으로 내려간다.** F02가 절단 후보 3순위라 이 성질이 실제로 쓰일 수 있으므로, **테스트로 고정한다** — "F02 프로바이더를 등록하지 않고 F01 예약 생성이 그대로 도는지". 지금 목록에 없는 테스트라 추가한다.

## 반영 결과 (2026-08-15)

규칙 문서 4종을 읽고 스펙을 갱신했다. **예상과 다른 것이 셋 나왔다.**

### 1. R1이 예상보다 컸다 — 테스트 목록의 핵심 자리가 바뀌었다

분류할 때는 "근거 문장을 다시 쓰면 된다"로 봤다. 실제로는 **테스트 하나가 무의미해졌다는 것을 알게 됐다.**

**T22("훅이 매진에 예외를 던지면 예약도 롤백된다")는 세션이 갈라진 구현도 통과한다.** 구현부가 예외를 던지면 자기 세션도 커밋 전이라 함께 롤백되기 때문이다. Java 판에서 D3의 증명이던 테스트가 **이 스택에서는 판별력이 0**이다.

**T22b를 추가했다** — 훅이 성공한 뒤 F01이 실패하는 경로. 세션 분리는 여기서만 드러난다. **스택 전환에서 테스트의 의도가 바뀐 유일한 지점이고, 분류 단계에서는 못 봤다.**

### 2. 해석기가 세션 안으로 들어왔다 — 호출 순서 그림이 바뀌었다

`resolve()`가 `session`을 첫 인자로 받게 되면서 **세션이 열린 뒤**에 불린다. Java 판 그림은 "락 → 해석기 → 가격 확정 → 트랜잭션 시작"이었다.

**순서 자체(해석기가 생성 훅보다 앞)는 그대로이고, 오히려 근거가 강해졌다.** "같은 트랜잭션이라 해석과 훅이 어긋날 걱정이 없다"를 Java 판에서는 문장으로 주장했는데, 이제 **시그니처가 강제한다.**

### 3. `PreCheckHook`만 세션을 안 받는다 — 게이트의 자리가 타입에 드러난다

넷 중 사전 검사만 `session`이 없다. **세션을 안 주는 것이 곧 "여기서 DB를 건드리지 마라"는 선언**이고, 게이트가 락보다 앞이라는 D5의 결정이 시그니처에 새겨졌다. 잔여를 DB에서 확인하고 싶어지는 순간 **그럴 수단이 없다는 것이 답**이다.
