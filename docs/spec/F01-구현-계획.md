# [F01] 구현 계획 — 착수 준비

- 상태: 준비 (승인 대상 아님)
- 작성일: 2026-08-15
- 부속 문서: `docs/spec/F01-예약-코어.md` (승인 대기)

**이 문서는 승인 게이트의 대상이 아니다.** 스펙의 D 항목이 승인되는 즉시 빨간 테스트부터 바로 쓸 수 있도록 순서와 단위를 미리 정해둔 것이다. 스펙이 "무엇을 만드는가"라면 이 문서는 "어떤 순서로 만드는가"다.

승인이 어떤 형태로 오든(전부 승인 / D4 절단 / D10 조건부) 즉시 착수할 수 있게 세 갈래를 다 준비했다.

## 1. TDD 실패 테스트 목록 (착수 순서)

**순서의 원칙:** 인프라가 필요 없는 것부터, 싼 것부터, 그리고 **동시성 테스트는 단일 스레드 테스트가 전부 초록이 된 뒤에 쓴다.** 빨간 동시성 테스트는 원인이 경합인지 로직인지 구분되지 않아 디버깅 비용이 몇 배가 된다.

각 항목은 **실패하는 테스트를 먼저 쓰고 실패를 눈으로 확인한 뒤** 통과할 만큼만 구현한다.

### B. 영속성 통합 (Testcontainers MySQL, 초)

**B-0. 트랜잭션 경계 — `TransactionManager` (D28). 1회차에서 가장 먼저 만든다**

`app/common/db.py`는 스캐폴딩에 없다. **F01이 만들고, 뒤 회차 전부가 이 위에 선다.**

| # | 테스트 | 기대 |
|---|---|---|
| T27a | `write()` 블록이 정상 종료 | 커밋된다. 새 세션으로 조회해 행이 보인다 |
| T27b | `write()` 블록 안에서 예외 | **롤백된다.** 블록 안에서 쓴 행이 남지 않는다 |
| T27c | `read()`로 조회한 뒤 블록을 나감 | **커밋되지 않는다.** 그리고 커넥션이 유휴 트랜잭션 상태로 남지 않는다 — `information_schema.innodb_trx`에 그 커넥션의 행이 없다 |
| T27d | `write()`를 연속 두 번 호출하고 두 번째에서 예외 | **첫 번째는 남는다.** "한 유스케이스에 `write()` 하나"가 규칙인 이유를 고정한다 |

**T27c가 이 넷 중 유일하게 조용한 실패를 잡는다.** `rollback()`을 빠뜨려도 조회 결과는 정상이고 테스트는 통과한다. 증상은 **부하가 걸려 커넥션 풀이 마를 때** 처음 나타난다. 그래서 결과가 아니라 **커넥션 상태를 직접 본다.**

## 2. D4(NO_SHOW) 절단 — **확정됨 (2026-08-15)**

관리자 판단: **"손님이 안 오면 취소 처리한다고 가정하자."** → `NO_SHOW` 상태와 스케줄러를 만들지 않는다.

미리 설계해둔 축소판을 그대로 적용한다. **절단 시한(2.4절) 안에 결정이 왔으므로 표 상수와 테스트 파라미터만 다르고 걷어낼 코드는 없다.**

### 2.1 정확히 무엇이 빠지는가

| 대상 | 빠지는 것 |
|---|---|
| 상태 | `NO_SHOW` 1개 → **7개에서 6개로** |
| 이벤트 | `NO_SHOW` 1개 → **7개에서 6개로** |
| 전이 | `CONFIRMED --NO_SHOW--> NO_SHOW` 1개 → 허용 전이 **8개에서 7개로** |
| 전수 표 | **49칸 → 36칸** (전이 7 + 멱등 6 + 거부 23) |
| 스케줄러 | 노쇼 스케줄러 1개 |
| API | `POST /api/internal/reservations/no-show` |
| 인덱스 | `idx_reservation_noshow (status, check_in)` |
| 테스트 | T22·T23(노쇼 조건), T72의 노쇼 부분 |

**남는 것:** `terminated_at` 컬럼은 그대로 쓴다(취소·만료·체크아웃이 쓴다). 상태 이력 테이블(D19)도 D4와 무관하게 남는다.

### 2.2 체크인 상한은 **따로 살린다**

`today < checkOut` 상한은 `NO_SHOW`에 묶여 있지 않다. **별개의 구멍이고, 조건 한 줄이라 비용이 거의 없다.**

상한이 없으면 체크아웃 날짜가 한참 지난 예약도 체크인할 수 있다. 이건 노쇼 처리 여부와 아무 상관이 없는 독립적인 결함이다. 원래 이 상한을 둔 이유 중 하나가 "노쇼 스케줄러가 멈춘 사이의 방어선"이었는데, **노쇼 스케줄러가 아예 없어지면 이 상한이 유일한 방어선이 되어 오히려 더 중요해진다.**

→ 테스트 T20·T21은 D4가 잘려도 **그대로 남는다.**

### 2.3 잘랐을 때 생기는 구멍과 기록 위치

구멍은 하나다. **`CONFIRMED`에서 나가는 출구가 취소와 체크인뿐이라, 손님이 오지 않은 예약은 영원히 `CONFIRMED`로 남는다.** 종료 상태에 도달하지 않는 경로가 상태머신에 남는다는 뜻이다.

이건 숨기지 않고 세 곳에 기록한다.

| 위치 | 무엇을 쓰는가 |
|---|---|
| 스펙 0.3절 「포함하지 않는 것」 | ✅ 반영됨 — "노쇼 자동 처리" 행 추가 |
| 스펙 1.4절 전이 표 아래 | ✅ 반영됨 — "D4 기각으로 생긴 구멍 — 알고 남긴다" 문단 |
| 스펙 부록 A의 D4 | ✅ 반영됨 — 기각 판단과 반영 결과 전체 |
| `docs/submission/03-설계.md` 9.5절 | ✅ 반영됨 — 구멍, 절단 근거, 자동 취소로 대신하지 않은 이유 |
| 00 문서 제외 표 | ⏳ D8로 PM에 전달 예정 (F01이 직접 고치지 않는다) |

**"몰라서 빠진 것"과 "알고 뺀 것"의 차이는 문서에만 남길 수 있다.** D5(크래시 틈)와 같은 원칙이다.

**자동 취소 스케줄러로 대신하지 않은 이유.** 쉬워 보이는 우회로지만 D15와 충돌한다. 취소는 재고를 복원하므로 노쇼를 자동 취소하면 **노쇼 객실이 자동으로 다시 팔린다.** 자동 전이를 만들지 않으면 자동 복원도 없어 D15가 그대로 지켜진다.

### 2.4 절단 결정의 마감 시점 — **여유 있게 지켜짐**

마감으로 잡았던 시점은 **dev-cycle 2회차(Reservation 애그리거트 + 전이 표) 착수 직전**이었다. 그 이후에 잘랐다면 전수 테스트(T11~T13)를 다시 쓰고 이력·스케줄러 코드를 걷어내야 했다.

**결정이 구현 착수 전에 왔으므로 걷어낼 코드가 없다.** 표 상수와 테스트 파라미터를 처음부터 36칸으로 쓰면 된다. 이 항목을 미리 설계해둔 값이 여기서 나왔다.

## 3. 구현 순서와 리뷰 단위

한 번에 전부 만들고 한 번 리뷰받으면 리뷰가 무의미해진다. **4회차로 나누고, 각 회차 끝에 리뷰어 3명(`concurrency-reviewer`·`domain-reviewer`·`architecture-reviewer`)을 병렬로 부른다.**

**앞 회차의 리뷰가 나오기 전에 다음 회차를 쓰지 않는다.** 1회차에서 지적받은 것이 2회차에 그대로 복제되는 것을 막기 위해서다.

### 3.1 회차 구성

| 회차 | 만드는 것 | 완료 기준 | 리뷰 초점 |
|---|---|---|---|
| **1** | 스키마 001~004·051~052, `inventory` 도메인·리포지토리 구현, **재고 차감·복원 조건부 UPDATE** | T27~T45 초록 | **여기가 가장 값진 리뷰다.** 동시성의 심장이고, 여기 패턴이 뒤 회차 전체에 복제된다 |
| **2** | `Reservation` 애그리거트, VO, **전이 표**, 상태 이력 | T1~T26 초록 | `domain-reviewer` 주도. 전이 표와 스펙 1.4절의 일치, 세터 부재, 애그리거트 경계 |
| **3** | 멱등성 포트·구현체, **분산락 구현체** | T49~T56의 락·멱등 부분 + 락 레벨 데드락 테스트 | `concurrency-reviewer` 주도. **D10 조건 검증(3.2절)** |
| **4** | 유스케이스 6종, **확장 훅 4개(D20·D22·D23)**, 컨트롤러, 만료 스케줄러 | T46~T86 전부 + **K1~K10 전부** 초록 | 세 명 전원. 트랜잭션 경계, 레이어 누수, **F02 훅 계약(T74~T80)** |

**1회차를 도메인 단위(2회차)보다 앞에 두는 이유.** TDD 리듬만 보면 인프라 없는 도메인 단위가 더 싸고 빠르다. 그런데 조건부 UPDATE 패턴은 재고 차감과 상태 전이 **양쪽에 쓰인다.** 재고 쪽을 먼저 리뷰받으면 그 교훈이 상태 전이 구현에 반영되지만, 순서를 바꾸면 같은 지적을 두 번 받는다. 리뷰 가치가 TDD 리듬보다 우선한다.

### 3.2 D10 조건에 대한 대비 (PM이 제안한 조건부 승인 형태)

PM이 관리자에게 제안한 조건은 두 가지로 이해했다. **둘 다 미리 설계해두면 손해가 없어서 지금 확정한다.**

**조건 (가) 락 획득 순서를 정하는 코드가 딱 한 곳에만 존재할 것**

내가 스스로 "정렬을 한 곳이라도 빠뜨리면 데드락이 나는데 재현이 어려운 버그"라고 썼다. 그 위험을 구조로 없앤다.

- 락 키 목록을 만드는 함수는 **하나뿐**이다. `StayPeriod.occupiedDates()`가 정렬된 날짜를 돌려주고, 그 결과로 락 키를 만드는 곳도 한 곳이다.
- **재고 차감 UPDATE의 실행 순서도 같은 목록을 쓴다.** 락 순서와 DB 락 순서가 다른 목록에서 나오면 그 자체가 데드락 원인이다. 두 곳이 같은 리스트를 공유하는지를 리뷰 항목으로 명시한다.
- 정렬은 코드에 **명시적으로** 남긴다. `.sorted()`를 지우면 깨지는 테스트(T56)를 둔다.

**조건 (나) K8을 통과하지 못하면 객실타입 단위 단일 락으로 되돌릴 것**

폴백이 싸도록 미리 설계한다. **락 포트가 "자원 키 목록"을 받게 만든다.**

```
LockPort.acquire_all(keys: list[str], *, wait_s: float, ttl_s: int)
  → 오름차순 획득, 실패 시 획득분 역순 해제
```

이러면 폴백은 **키 목록을 만드는 한 곳이 키를 1개만 반환하도록 바꾸는 것**으로 끝난다. 유스케이스·트랜잭션 경계·해제 로직은 손대지 않는다.

```
현행:  keys = 날짜별  →  ["lock:inventory:3:2026-09-01", ":09-02", ":09-03"]
폴백:  keys = 타입    →  ["lock:room-type:3"]
```

**K8을 3회차가 아니라 4회차에 두는 이유.** K8은 예약 생성 유스케이스 전체가 있어야 재현된다. 대신 3회차에서 **락 구현체만 놓고** 겹치는 키 집합을 반대 순서로 요청하는 테스트를 돌린다. 여기서 걸리면 유스케이스를 만들기 전에 잡는다. 4회차의 K8은 DB 행 락까지 포함한 최종 확인이다.

폴백 판단 시점은 **4회차의 K8 결과가 나온 직후**다. 그 시점에 되돌려도 위 구조 덕에 키 생성 한 곳만 바뀐다.

### 3.3 회차 간 규칙

- 각 회차는 **자기 테스트가 전부 초록**이어야 리뷰에 넘어간다. 빨간 채로 리뷰를 요청하지 않는다.
- 리뷰 지적은 **다음 회차로 미루지 않고 그 회차 안에서 반영**한다. 미루면 같은 패턴이 복제된다.
- 동시성 테스트는 `@pytest.mark.concurrency`로 분리한다. 회차 중에는 빼고 돌리고, **회차 끝(리뷰 요청 전)에는 반드시 포함해 돌린다.**
- 각 회차 끝에 `pytest` 전체를 돌린다. **스캐폴딩 테스트 5건이 깨졌다면 내 변경이 원인이다.**

## 4. 승인 형태별 착수 분기

승인이 어떤 형태로 오든 즉시 움직인다.

| 승인 형태 | 즉시 할 일 |
|---|---|
| **전부 승인** | **선행 커밋 없이 바로 1회차 착수** (T27a부터). 공유 설정은 이미 스캐폴딩으로 `main`에 들어갔다 |
| **D4 절단 조건부** | 위와 같되 2절의 축소판 적용. 전이 표를 36칸으로, 체크인 상한(T20·T21)은 살린다 |
| **D10 조건부** | 위와 같되 3.2절의 (가)(나)를 리뷰 항목으로 명시하고 착수. 이미 설계돼 있어 추가 작업 없음 |
| **일부 기각** | 해당 D 항목이 걸린 절만 스펙에서 고치고 재승인 요청. 기각된 항목에 의존하는 테스트를 목록에서 뺀다 |

**원래 첫 단계였던 "공유 파일 선행 커밋"은 사라졌다.** `Clock`의 `Asia/Seoul` 고정(D2)과 `PMS_` 키 6개(D10·D11·D17)가 **Python 스캐폴딩(PR #6)으로 이미 `main`에 있기 때문이다.**

대신 **1회차 안에 공유 파일이 하나 생긴다.** `app/common/db.py`의 `TransactionManager`(D28)는 스캐폴딩에 없고 F01이 만드는데, **유스케이스를 쓰는 세션 전부가 이 위에 선다.** 그래서 이 파일만 담은 작은 커밋을 1회차 초반에 `main`으로 올리고 PM에 알린다. 그래야 F02·F03·F04가 rebase로 받아간다.

**그리고 내가 임계 경로다.** F02(`201~`)와 F03은 **내 마이그레이션 `001`~`004`가 병합돼야** 자기 `down_revision`을 확정할 수 있다. 1회차 스키마를 먼저 올리는 것이 그 세션들의 착수 조건이다.
