- 작성일: 2026-08-15
- 대상: `docs/spec/F01-예약-코어.md` (4단 구조 재정렬본)

## 2. 살아남는 것 중 특히 확인이 필요했던 것 — 동시성 테스트

**K1~K10이 Python에서도 유효한가**가 이 전환의 가장 중요한 질문이다. 유효하다.

경합이 일어나는 자리가 **Python 바이트코드가 아니라 DB 행과 Redis 키**이기 때문이다. 스레드가 DB 드라이버 호출에 들어가면 GIL이 풀리므로, `threading.Barrier`로 100개 스레드를 모아뒀다 한 번에 출발시키면 **실제로 동시에 DB에 도달한다.** 잔여 10에 100 스레드를 붙여 성공이 정확히 10건인지 보는 검증은 그대로 성립한다.

바뀌는 것은 표기뿐이다.

| Java | Python |
|---|---|
| `CountDownLatch` | `threading.Barrier` |
| `ExecutorService` | `ThreadPoolExecutor` |
| `DeadlockLoserDataAccessException` | `sqlalchemy.exc.OperationalError` (MySQL 1213) |
| `@Tag("concurrency")` | `@pytest.mark.concurrency` |

**GIL 때문에 동시성 테스트가 무의미해지지 않는가**라는 의심은 정당하지만, 그건 CPU 바운드 경합에 해당한다. 우리가 재현하려는 것은 **DB 레벨 경합**이라 영향이 없다. 이 사실을 학습 노트 후보에 넣는다.

## 3. 다시 쓸 때 조심할 것 — "사라지는 함정"과 "모양만 바뀌는 함정"

PM이 짚은 대로 없어지는 것이 있다. 다만 **없어진다고 착각하면 안 되는 것**이 더 중요하다.

### 정말 사라지는 것

| 함정 | 왜 사라지나 |
|---|---|
| `@Transactional` 자기 호출이 프록시를 우회해 트랜잭션이 안 열린다 | SQLAlchemy는 세션·트랜잭션이 **명시적**이다. `with session.begin():`이 보이는 자리에서 시작하고 끝난다. 숨은 프록시가 없다 |
| **유스케이스를 두 빈으로 쪼개야 한다** | 락을 트랜잭션 밖에서 잡으려고 나눈 것인데, 명시적 트랜잭션에서는 **한 함수 안에서** `락 획득 → with begin() → 커밋 → 락 해제`가 그대로 읽힌다. **구조가 단순해진다** |

**두 빈 분리가 사라지는 것의 부수 효과 하나** — D23(사전 검사 훅)의 비용 논거가 더 싸진다. "이미 트랜잭션 밖 단계가 있어서 끼울 자리가 있다"고 했는데, 이제는 그냥 **함수 앞부분에 한 줄**이다. 결정은 그대로 유효하고 근거만 더 강해진다.

### 모양만 바뀌는 것 — **사라진 것으로 착각하면 안 된다**

| 함정 | Java | Python |
|---|---|---|
| **ORM 캐시와 벌크 UPDATE의 불일치** | JPA 1차 캐시. `@Modifying(clearAutomatically=true)` | **SQLAlchemy에도 identity map이 있다.** 벌크 `update()` 뒤에 이미 로드된 객체는 낡는다. `synchronize_session` 설정이나 `session.expire_all()`로 명시 처리해야 한다. **같은 함정이 이름만 바꿔 존재한다** |
| **갱신 행 수를 반드시 확인한다** | `@Modifying` 반환값 | `result.rowcount`. **버리면 모든 방어가 무너지는 것은 똑같다.** 이 프로젝트에서 가장 중요한 한 줄이다 |
| 시각을 유스케이스에서 한 번만 읽는다 | `Clock` 주입 | 시각 프로바이더 주입. `datetime.now()` 직접 호출 금지도 같다 |
| 락 획득은 트랜잭션 밖, 해제는 커밋 뒤 | `@Transactional` 경계 | `with session.begin():` 블록 밖/안. **순서 규칙은 완전히 같다** |
| FK 때문에 테스트 정리 삭제 순서 | 같음 | 같음 |

### 새로 생기는 것

- **SQLModel이 도메인에 들어온다.** CLAUDE.md의 "도메인 객체에 `@Entity`를 직접 붙인다" 방침은 SQLModel과 오히려 잘 맞는다(Pydantic + SQLAlchemy 통합이 설계 의도다). 다만 **Pydantic 검증이 도메인 규칙과 겹치는 자리**가 생긴다 — VO 생성자 검증을 Pydantic validator로 옮길지, 도메인 메서드로 남길지 규칙이 필요하다 → **D27**
- **`Decimal` vs `int`.** 금액을 원 단위 정수로 정한 D8은 그대로다. Python에서도 `int`를 쓰고 `Decimal`을 도입하지 않는다(통화·세금을 뺐으므로)
- **커넥션 풀 설정 위치.** `HikariCP` 설정 4줄 → SQLAlchemy `create_engine(pool_size=..., max_overflow=...)`. **부하테스트에서 풀이 병목인지 판단하려면 값이 명시돼 있어야 한다**는 원래 주석의 의도를 그대로 옮긴다

## 4. 새로 필요한 결정 셋

### D25. 동기(sync) + 스레드풀로 간다 — ✅ **승인됨**

- **결정:** FastAPI 라우트를 `def`(sync)로 쓰고 SQLAlchemy 동기 세션을 쓴다. `async def` + 비동기 드라이버를 쓰지 않는다.
- **이유:**
  1. **지금 설계가 거의 그대로 옮겨진다.** 락 → 트랜잭션 → 커밋 → 해제 순서, 조건부 UPDATE, 스레드 기반 동시성 테스트가 전부 표기만 바뀐다.
  2. FastAPI는 **`def` 핸들러를 자동으로 스레드풀에서 실행**하므로 DB 바운드 작업에 실제 병렬성이 나온다. 이 규모에서 async의 이득이 없다.
  3. **전환을 결정한 이유 자체가 "2일 안에 검토까지 해야 한다"였다.** async를 고르면 비동기 드라이버·세션 수명·테스트 하네스가 전부 새 학습거리가 되어 **전환의 목적을 스스로 깎는다.**
- **트레이드오프:** 커넥션 풀과 스레드풀 크기가 처리량 상한을 정하므로 F04 결과 해석 시 이 둘을 명시해야 한다. 그리고 "async를 다뤄봤다"를 보여줄 기회를 잃는다.
- **대안이었던 것:** `async def` + `asyncpg`/`aiomysql`(위 3번 이유로 기각), 혼용(세션 종류가 둘이 되어 어느 것이 실제 경로인지 흐려져 기각).
- **결과:** 승인. `coding-rules.md` 맨 앞에 규칙으로 반영됐다.

  ```json
  { "loadTest": {
      "pms.lock.enabled": false,
      "pms.lock.wait-millis": 200,
      "pms.lock.ttl-seconds": 3,
      "pms.reservation.hold-minutes": 10,
      "pms.reservation.expire-scan-interval": "30s",
      "pms.payment.decline-rate": 0.0
  } }
  ```

- **PM 제안(`/internal/config`)에서 경로만 바꿨다.** 내 기존 내부 API가 `/api/internal/reservations/expire`라 **같은 네임스페이스로 맞춘다.** 내부 엔드포인트가 두 군데로 갈리면 F04 스크립트와 문서에서 헷갈린다.
- **F04의 제약은 그대로 살아 있다 — 값의 출처가 락 코드가 실제로 쓰는 그 설정 객체여야 한다.** Dependency Injector에서 **같은 `Configuration` 프로바이더를 락 어댑터와 이 라우트에 함께 주입**하면 구조적으로 어긋날 수 없다. 오히려 Spring보다 명시적이다.
- **없어진 걱정 하나:** actuator `env` 안을 논의할 때 나왔던 "설정 전체가 노출된다"는 문제가 사라진다. **우리가 실을 키를 직접 고르기 때문이다.**
- **테스트는 그대로 옮긴다:** T87(응답에 `pms.lock.enabled`가 있다) · T88(평평한 문자열 키) · T89(**`false`로 기동하면 이 엔드포인트도 `false`를 말하고 락 어댑터도 실제로 no-op이다**).
- **결과:** 승인. F04에 전달됐다.

### D27. 도메인이 SQLModel에 의존하는 범위 — ✅ **승인됨**

- **결정:** 도메인 모델은 **SQLModel까지만** 의존한다. FastAPI·Dependency Injector·redis 타입이 도메인에 들어오면 안 된다. **원래 규칙("`jakarta.persistence` 외의 프레임워크에 의존하지 않는다")의 Python 대응이다.**
- **VO 검증을 어디에 두는가:** `StayPeriod`·`GuestCount`·`Money`의 규칙은 **도메인 메서드/생성자에 둔다.** Pydantic validator로만 표현하지 않는다.
  - 이유: 이 규칙들은 **`400`을 던지기 위한 입력 검증이 아니라 불변식**이다. Pydantic validator에만 두면 요청 파싱 계층의 관심사처럼 보이고, 도메인 객체를 코드에서 직접 만들 때(테스트·훅) 우회될 여지가 생긴다.
  - 다만 Pydantic이 타입 수준에서 잡아주는 것(음수 여부 등)은 **중복으로 두어도 된다.** VO와 DB CHECK를 둘 다 둔 것과 같은 논리다 — **중복이 아니라 방어선이다.**
- **결과:** 승인. 불변식과 입력 검증은 다른 것이라는 판단이 함께 받아들여졌다.

## 5. 훅 시그니처 — 세션을 명시적으로 넘긴다 (F02가 찾은 함정)

Spring은 트랜잭션이 스레드에 매여 있어서 **훅이 아무것도 안 해도 같은 트랜잭션에 자동으로 들어갔다.** SQLAlchemy는 그렇지 않다. 세션을 넘겨주지 않으면 훅 구현자가 자기 세션을 열 수 있고, 그러면 트랜잭션이 둘로 갈라진다.

```
F01 트랜잭션:   재고 차감 → 예약 INSERT → ... → 롤백
F02 트랜잭션:   사용권 발급 → 이미 커밋됨        ← 되돌아가지 않는다
```

**"함께 커밋하거나 함께 롤백한다"가 조용히 깨진다.** 조용히, 가 요점이다.

### 확정 시그니처

```python
class ReservationPreCheckHook(Protocol):
    def check(self, command: CreateReservationCommand) -> None: ...
    # 세션 없음. 락보다 앞이라 트랜잭션 자체가 없다 (D23)

class DiscountResolver(Protocol):
    def resolve(self, session: Session, ref: DiscountRef,
                room_type_id: int, period: StayPeriod) -> AppliedDiscount | None: ...

class ReservationCreationHook(Protocol):
    def on_created(self, session: Session, reservation_id: int,
                   command: CreateReservationCommand) -> None: ...

class ReservationReleaseHook(Protocol):
    def on_released(self, session: Session, reservation_id: int,
                    from_status: ReservationStatus, event: ReservationEvent) -> None: ...
```

- **세션을 첫 인자로 받는다.** 컨텍스트 변수나 전역으로 몰래 공유하지 않는다. **시그니처에 있으면 빠뜨릴 수 없다.**
- **구현부는 `session_factory`를 주입받지 않는다.** 받을 수 없으면 열 수 없다.
- **`ReservationPreCheckHook`만 세션을 안 받는다.** 세션을 안 주는 것이 곧 "여기서 DB를 건드리지 마라"는 선언이다.

### ⚠️ 이 제안이 내 스펙의 모순 하나를 드러냈다 — `DiscountResolver`의 위치

`DiscountResolver`에 세션을 준다면 **트랜잭션 안에서 불려야 한다.** 그런데 3.6절의 호출 순서 그림은 이렇게 그려져 있다.

```
… → 락 획득 → [DiscountResolver] → 가격 확정
                          ┌─ 트랜잭션 ─────────────┐
                          │ 재고 차감 → 예약 INSERT │
```

**해석기가 트랜잭션 밖에 있다.** 그런데 같은 절의 본문은 이렇게 말한다.

> 둘이 어긋날 걱정은 하지 않아도 된다. **같은 트랜잭션 안에서 같은 행을 읽고 쓰기 때문이다.**

**그림과 본문이 서로 다른 말을 하고 있었다.** 본문 쪽이 옳다 — 바로 아래 문장이 "그 판단이 **재고 확보와 같은 구간 안에** 있어야 한다"이므로 처음부터 트랜잭션 안을 의도했고, ASCII 그림을 잘못 그린 것이다.

**고친 순서:**

```
멱등 키 선점 → 입력 검증 → [PreCheckHook] → 락 획득
                          ┌─ 트랜잭션 ────────────────────────────┐
                          │ [DiscountResolver] → 가격 확정        │
                          │ → 재고 차감 → 예약 INSERT             │
                          │ → [CreationHook]                     │
                          └──────────────────────────────────────┘
                            커밋 → 락 해제
```

트랜잭션이 SELECT 하나만큼 길어지지만, 그 대가로 **해석과 사용권 발급이 같은 스냅샷을 본다.** 밖에서 읽으면 가격이 다른 시점의 데이터에 근거하게 되고, 훅의 조건부 UPDATE는 *재고*의 정합성만 지켜주지 *가격*의 정합성은 지켜주지 않는다.

### ⚠️ PM이 제안한 테스트로는 이 버그가 잡히지 않는다

PM은 "훅에서 예외를 던지면 호출부의 INSERT도 되돌아간다"(F02 T21·T22, 내 T79)를 이 함정을 잡는 테스트로 지목했다. **그 테스트는 이 버그를 통과시킨다.**

| 시나리오 | 세션이 갈라진 구현에서 무슨 일이 일어나나 | 잡히나 |
|---|---|---|
| **훅이 예외를 던진다** (T79) | F02가 자기 세션에 쓰기 전에 던지거나, 썼어도 커밋 전에 던진다 → 자기 세션도 롤백된다. F01도 롤백. **결과가 정상과 같다** | ❌ **못 잡는다** |
| **훅이 성공하고, 그 뒤 F01이 실패한다** | F02는 **이미 커밋했다.** F01만 롤백된다 → **F02 행이 살아남는다** | ✅ **잡는다** |

**버그는 훅이 성공한 뒤에만 드러난다.** 훅이 던지는 경로는 양쪽 구현이 같은 결과를 내므로 판별력이 없다.

그래서 테스트를 하나 추가한다.

| # | 테스트 | 기대 |
|---|---|---|
| **T79b** | 훅이 **성공적으로 행을 쓴 뒤**, F01이 그 다음 단계에서 예외를 던진다 | **훅이 쓴 행이 사라져야 한다.** 남아 있으면 훅이 별도 세션을 쓴 것이다 |

T79(훅이 던지면 전체 롤백)는 여전히 필요하다. 계약의 다른 절반이기 때문이다. **둘 다 있어야 계약이 닫힌다.**

덤으로 정적 검사도 붙일 수 있다 — 훅 구현 모듈이 `sessionmaker`·`create_engine`·`session_factory`를 import하지 않는지 보는 것이다. 값싸고 위반을 즉시 잡는다. 리뷰 항목으로 제안한다.
