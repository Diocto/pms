### [심각] `totalPrice` 계산에서 `roomCount` 곱이 빠졌다

- **리뷰어:** domain-reviewer, architecture-reviewer (독립 중복 지적)
- **위치:** `app/inventory/query/infrastructure/persistence.py:78`
- **문제:** `total_price = 단가 × 박수`로만 계산한다. 스펙 8절은 `단가 × 박수 × 객실수`다.
- **실패 시나리오:** `roomCount=2`, 3박, 단가 100,000원 → 스펙 기대 600,000원, 실제 응답 300,000원. F01 예약은 `단가 × 박 × 실`로 청구하므로(`tests/test_reservation_aggregate.py:157`) 검색 견적과 청구액이 2실 이상에서 항상 2배 어긋난다. F04·F05가 이 값을 그대로 소비한다. 기존 테스트는 전부 `roomCount=1`이라 잡지 못했다.
- **근거:** 스펙 8절 필드 표 "`totalPrice` | `pricePerNight × nights × roomCount`".
- **조치:** `* query.room_count` 추가 + `room_count=2`에서 총액을 단언하는 영속성 테스트 추가.
- **처리:** **수정함.** 실패 테스트(`test_T5_총액에는_객실_수가_곱해진다`, 빨강 확인: `300000 == 600000` 실패)를 먼저 넣고 고쳤다.

- **실패 시나리오:** 계약을 따르는 클라이언트가 `roomCount`를 생략하면 기대는 200(1실 기준)인데 실제로는 400 `INVALID_REQUEST`가 나간다. F04 k6 스크립트·F05 화면에서 원인 불명의 400이 터진다.

- **조치:** `Query(default=1, ...)` + 생략 요청이 200과 `roomCount: 1` 에코를 돌려주는 API 테스트.
- **처리:** **수정함.** 실패 테스트(`test_T20_roomCount는_선택이고_기본값은_1이다`, 빨강 확인) 먼저.

### [심각] C2 테스트에 읽기-쓰기 경합이 실제로 없다

- **리뷰어:** concurrency-reviewer
- **위치:** `tests/test_search_concurrency.py` C2 (구 223~277행)
- **문제:** 스펙 9절 C2는 "50 스레드가 검색**하는 동안** 1 스레드가 갱신"인데, 구현은 25스레드 물결이 전부 끝난 뒤 UPDATE를 단독 실행하고 다시 25스레드를 돌렸다 — 검색과 갱신이 겹치는 구간이 0이다. "1과 0 둘 다 관측" 단언은 이 구성에서 구성상 보장되어, 스펙이 금지한 "경합 미발생인데 초록불"을 테스트 스스로 만들었다. 죽은 코드(`completed` 이벤트, 함수 안 `import time`)는 동시 설계가 순차로 바뀐 흔적.
- **실패 시나리오:** 훗날 집계 1발이 두 쿼리로 리팩터링되어 단일 스냅샷(G1)이 깨져도 이 테스트는 전부 초록이다. ADR-0030이 "잠금 없는 읽기의 무결성은 C1·C2가 지킨다"고 선언한 방어선이 비어 있다.
- **근거:** 스펙 9절 C2 행·헛통과 표, CLAUDE.md 절대 규칙(동시성 코드에 동시성 테스트).
- **조치:** 갱신 스레드를 검색 50과 같은 배리어에 넣는다.
- **처리:** **수정함.** 재설계 — `Barrier(51)`로 검색 50 + 갱신 1이 함께 출발한다. 결정성은 물결 분리 대신 두 신호로 만들었다: ① 갱신은 최소 한 검색이 완료된 뒤에만 커밋(→ "1 관측" 보장, 커밋 시점에 나머지 검색이 한창 돌아 겹침 실재), ② 각 검색 스레드는 0을 볼 때까지 반복 조회(→ "0 관측" 보장). 단언 추가: 갱신 커밋 시각이 검색 시작 시각들 사이에 떨어졌다(겹침 실증), 커밋 이후 시작된 검색은 전부 0. 죽은 코드 제거. 초록 확인.

### [중요] 캐시 히트가 TTL을 연장하지 않는다는 검증이 없다

- **리뷰어:** concurrency-reviewer
- **위치:** `app/inventory/query/infrastructure/cache.py` `get` / 테스트 공백
- **문제:** 코드상 연장하지 않지만 이를 고정하는 단언이 없다. C3의 잔여 TTL 단언은 히트가 TTL을 풀로 연장해도 통과한다.
- **실패 시나리오:** 누군가 `get`을 `GETEX`(읽을 때마다 만료 갱신)로 바꾸면 인기 키는 사실상 영영 안 만료되어 낡음의 상한(G2)이 사라지는데 스위트는 전부 초록이다. I5와 같은 급의 회복 불가 실패다.
- **근거:** 스펙 6절 "캐시 히트면 변화 없다. TTL 연장도 하지 않는다", I5의 방어 논리.
- **조치:** put 직후 TTL 기록 → get 여러 번 → `ttl <= ttl_before` 단언.
- **처리:** **수정함.** `test_T15_조회는_TTL을_연장하지_않는다` 추가.
