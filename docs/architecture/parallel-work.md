# 병렬 작업 규칙

여러 세션이 동시에 작업할 때 지키는 규칙이다. 세션을 시작하기 전에 읽는다.

## 왜 규칙이 필요한가

충돌에는 두 종류가 있다.

**텍스트 충돌**은 git이 잡아준다. 같은 줄을 둘이 고치면 병합할 때 멈춰서 알려준다. 성가시지만 안전하다.

**의미 충돌**은 git이 못 잡는다. A 세션이 `Reservation`에 상태를 하나 추가하고 B 세션이 같은 클래스의 다른 메서드를 고쳤다면, git은 아무 불평 없이 자동 병합한다. 그런데 상태 전이 표에 새 상태가 반영되지 않았다. 컴파일도 되고 병합도 됐는데 도메인이 깨졌다.

동시성이 주제인 프로젝트에서 도메인 불변식이 조용히 깨지는 건 치명적이다. 그래서 **도메인만 강하게 잠그고 나머지는 병합으로 푼다.**

## 계층별 정책

| 대상 | 정책 | 이유 |
|---|---|---|
| 도메인 모델 (`*/domain/**`) | **Hard.** 소유 세션만 수정 | 의미 충돌이 가장 비싸고 git이 못 잡는다 |
| Flyway 마이그레이션 | **Hard.** 번호 대역 예약 | 충돌하면 DB 상태 복구가 비싸다 |
| 공통 설정·인프라 | **사전 확정.** 개발 중 수정 최소화 | 미리 만들어두면 건드릴 일이 없다 |
| 애플리케이션·프레젠테이션·인프라 | Soft. 충돌하면 병합 | 유스케이스별로 파일이 갈려 충돌이 드물다 |
| 테스트 | Soft | 파일이 분리된다 |
| 문서 | Soft | 파일이 분리된다 |

## 코어는 순차, 확장은 병렬

예약 코어, 그러니까 `Reservation` 애그리거트와 재고 차감과 동시성 제어는 **한 세션이 끝까지 만든다.** 이 프로젝트의 심장이고, 나누면 의미 충돌이 확실히 난다.

코어가 완성되고 병합된 뒤에 그 위에 붙는 것들을 병렬로 돌린다. 조회·검색, 프로모션, k6 부하테스트 스크립트, 제출 문서 정리는 서로 겹치지 않는다.

**병렬을 위한 병렬은 코어 구간에서 손해다.**

## feature 시작 전에 선언하는 것

각 feature 스펙에 아래를 명시한다. 선언하지 않고 시작하지 않는다.

```markdown
## 소유 범위
- 소유 패키지: (예: com.pms.promotion.**)
- 읽기만 하는 패키지: (예: com.pms.inventory.domain)
- Flyway 번호 대역: (00 문서의 feature 분할 표에서 확인)
- 수정이 필요한 공유 파일: 없음
```

**소유하지 않은 도메인 패키지는 읽기만 한다.** 수정이 필요하면 작업을 멈추고 관리자에게 알린다. 몰래 고치지 않는다.

## Flyway 번호 대역

마이그레이션 파일 이름이 겹치면 즉시 충돌한다. 대역을 미리 나눈다.

실제 배정은 `docs/spec/00-problem-and-scope.md`의 feature 분할 표가 진실이다. 현재 배정:

| 대역 | 소유 |
|---|---|
| V001 ~ V099 | F01 예약 코어 (공통 스키마·시드 포함) |
| V101 ~ V199 | 예비 (미배정) |
| V201 ~ V299 | F02 선착순 프로모션 |
| V301 ~ V399 | F03 가용 객실 검색 — **예약만 하고 현재 미사용** |

F03이 대역을 쓰지 않기로 한 이유는 기록해둘 값이 있다. 재고 테이블의 PK가 자연키 복합키 `(room_type_id, stay_date)`라 클러스터드 인덱스가 날짜 범위 조회를 이미 커버한다. 커버링 인덱스를 따로 만들면 조회는 그대로인데 **F01의 재고 차감 UPDATE에 인덱스 유지 비용만 얹는다.** 이 프로젝트에서 가장 뜨거운 쓰기 경로다.

**대역은 회수하지 않는다.** 병합 후 실측(EXPLAIN)이 예상과 다르면 V301이 필요해질 수 있다.

**이미 적용된 마이그레이션 파일은 절대 수정하지 않는다.** 고칠 게 있으면 새 버전을 추가한다. 적용된 파일을 고치면 체크섬이 어긋나 Flyway가 시작을 거부한다.

## ADR 번호 대역

의사결정 이력(`docs/decisions/ADR-NNNN-*.md`)도 번호가 겹친다. 세션 셋이 동시에 결정을 남기면 전부 다음 번호를 집어 같은 번호의 ADR이 세 개 생긴다. 파일명이 달라도 번호가 겹치면 이력을 인용할 수 없다.

Flyway와 같은 방식으로 대역을 나눈다.

| 대역 | 소유 |
|---|---|
| ADR-0001 ~ 0006 | 사용됨 (하네스 구축 단계) |
| ADR-0007 ~ 0019 | F01 예약 코어 |
| ADR-0020 ~ 0029 | F02 선착순 프로모션 |
| ADR-0030 ~ 0039 | F03 가용 객실 검색 |
| ADR-0040 ~ 0049 | F04 부하테스트 |
| ADR-0050 ~ | PM 세션 (하네스·규칙 개정) |

`docs/decisions/INDEX.md`는 여러 세션이 같이 쓰는 파일이다. **자기가 추가한 줄만 넣고 다른 줄은 건드리지 않는다.** 줄 단위로 갈리므로 git이 자동 병합한다.

## 학습 노트는 세션이 직접 쓰지 않는다

`docs/learning/INDEX.md`의 대기 목록은 모든 세션이 추가하고 싶어 하는 한 파일이라 충돌이 잦다.

feature 세션은 이 파일을 직접 고치지 않는다. 새 개념이 나오면 **자기 스펙 문서 끝에 "학습 노트 후보" 목록으로 적어둔다.** PM이 병합할 때 모아서 INDEX에 넣는다.

## 제출 문서 소유

`docs/submission/`은 여러 세션이 동시에 쓰게 되는 곳이라 파일 단위로 주인을 정한다. 파일이 갈리므로 충돌하지 않는다.

| 파일 | 소유 | 원천 |
|---|---|---|
| `01-문제-정의.md` | PM | `docs/spec/00-problem-and-scope.md` |
| `02-구현-범위.md` | PM | `docs/spec/` 전체 |
| `03-설계.md` | F01 (코어). F02·F03 몫은 PM이 나중에 합친다 | 각 feature 스펙, `docs/decisions/` |
| `04-부하테스트.md` | F04 | `docs/load-test/report.md` |
| `05-AI-활용.md` | PM | 하네스 구조, `docs/reports/`, `docs/reviews/` |

**자기 파일만 쓴다.** 다른 파일에 들어가야 할 내용이 보이면 직접 쓰지 말고 PM에게 알린다.

원천 문서를 복사하지 않는다. 원천은 합의와 작업을 위한 문서이고 제출 문서는 **처음 보는 사람을 설득하는 문서**라 필요한 것이 다르다. 결정을 번호순으로 옮기면 실패한다.

## 공유 파일

아래 파일들은 여러 세션이 동시에 건드리기 쉽다. **하네스 세팅 단계에서 미리 채워두는 것이 목표**이며, 개발 중에는 되도록 손대지 않는다.

**PM 세션만 고친다. feature 세션은 수정 금지.**

- `CLAUDE.md`, `docs/architecture/**`
- `docs/spec/00-problem-and-scope.md` — 승인된 범위 문서다. 여기에 무언가를 더하거나 빼야 한다고 판단되면 직접 고치지 말고, **자기 스펙의 결정 검토란에 제안으로 올려 관리자 승인을 받는다.**
- `docs/learning/INDEX.md` — 위의 학습 노트 절 참고

**절차를 밟으면 고칠 수 있다.**

- `build.gradle`
- `src/main/resources/application.yml`
- `docker-compose.yml`
- `com.pms.common.**` (공통 예외, 응답 포맷, 설정)

**줄 단위로 갈려 자동 병합된다. 자기 줄만 추가한다.**

- `docs/decisions/INDEX.md`

"절차를 밟으면 고칠 수 있다"로 분류된 파일을 꼭 고쳐야 하면 이렇게 한다.

1. 관리자에게 알린다.
2. **해당 변경만 담은 작은 커밋**을 만들어 `main`에 먼저 반영한다.
3. 다른 세션들이 `main`을 rebase해 받아간다.

큰 feature 브랜치에 공유 파일 변경을 섞어두면 병합할 때까지 다른 세션이 받지 못한다.

## worktree 운영

각 세션은 자기 worktree에서 작업한다.

```
.claude/worktrees/<feature-name>/     브랜치: worktree-<feature-name>
```

**세션을 시작하면 파일을 하나라도 만들기 전에 먼저 worktree를 만든다.** 여러 세션을 같은 폴더에서 열어도 된다. worktree를 각자 만들었다면 git이 보는 작업 공간이 분리되므로 서로 덮어쓰지 않는다. 위험한 것은 폴더가 같은 것이 아니라 **worktree 없이 `main`에서 그대로 작업하는 것**이다. 그러면 브랜치와 커밋이 서로를 밀어낸다.

worktree 이름은 feature 코드를 대문자로 쓴다 (`F01`, `F02`). 이름이 제각각이면 어느 세션 것인지 추적하기 어렵다.

시작 직후 `git worktree list`로 자기 worktree가 잡혀 있는지 한 번 확인한다.

worktree는 세션과 함께 사라질 수 있다. **작업이 끝나면 반드시 커밋하고 `main`에 병합한다.** 커밋하지 않은 작업은 없어진다고 생각한다.

병합 순서는 관리자가 정한다. 세션이 임의로 `main`에 병합하지 않는다.

## 통합 절차

feature가 승인되면 이 순서로 통합한다.

1. 작업 브랜치에서 최신 `main`을 rebase한다.
2. **전체 테스트를 돌린다.** 동시성 테스트를 포함해서 돌린다. 자기 feature 테스트만 통과하는 건 의미가 없다.
3. `./gradlew build`로 컴파일과 검증이 통과하는지 본다.
4. `main`에 병합한다.
5. 다른 세션에 병합 사실을 알린다.

**2단계에서 다른 feature의 테스트가 깨지면 의미 충돌이 일어난 것이다.** 병합을 멈추고 원인을 찾는다. 깨진 테스트를 고쳐서 통과시키는 것으로 끝내지 않는다. 왜 깨졌는지 먼저 이해한다.

## 세션 간 소통

관리자가 여러 세션의 허브다. 세션끼리 직접 조율하지 않는다.

작업 중 아래 상황이 생기면 즉시 관리자에게 보고한다.

- 소유하지 않은 도메인 패키지를 수정해야 할 때
- 공유 파일을 수정해야 할 때
- 다른 feature의 스펙과 모순되는 요구를 발견했을 때
- 병합 후 다른 feature의 테스트가 깨졌을 때
