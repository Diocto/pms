# 테스트 규칙

## 순서를 지킨다

실패하는 테스트를 먼저 쓴다. 구현부터 쓰고 테스트를 나중에 붙이지 않는다.

순서를 지키는 이유는 규율 때문이 아니다. 테스트를 먼저 쓰면 **쓰기 어려운 설계가 즉시 드러나기 때문**이다. 유스케이스 테스트를 쓰려는데 DB를 띄워야만 한다면, 그건 레이어가 새고 있다는 신호다. 구현을 먼저 하면 이 신호를 놓치고 나중에 갚는다.

한 사이클은 이렇다.

1. 실패하는 테스트를 쓴다. **실패를 눈으로 확인한다.** 통과하는 걸 보고 넘어가면 그 테스트는 아무것도 검증하지 않을 수 있다.
2. 통과할 만큼만 구현한다.
3. 정리한다. 테스트는 계속 통과해야 한다.

## 통과했는데 아무것도 증명하지 못하는 테스트

**실패보다 위험한 것은 아무것도 증명하지 못하는 초록불이다.** 실패는 눈에 띄지만 이건 안 띈다. 그리고 리포트에는 "검증 통과"로 적히고, 읽는 사람은 검증됐다고 믿는다.

실제로 이 프로젝트에서 나온 사례다.

> 멱등 키가 `(사용자, 키)` 조합인데 재시도마다 다른 사용자 번호를 썼다. 1,000건이 전부 성공하고 "중복 예약 0건"이 나왔다. **멱등성이 작동해서가 아니라 애초에 중복 요청을 보내지 않은 것이다.**

**모든 테스트에 이 질문을 던진다.**

> 이 테스트가 통과했는데도 시스템이 망가져 있을 수 있는 경우는 무엇인가.

답을 못 찾으면 다행이고, 찾으면 그것을 막는 조건을 테스트에 추가한다. 동시성 테스트는 **경합이 실제로 일어났는지**를 함께 확인해야 한다 — 실패 건수가 0이면 요청이 겹치지 않았다는 뜻이고, 그런 통과는 무의미하다.

**검증 도구 자체도 검증한다.** "결과가 비면 통과" 형태의 검증은 쿼리 오타 하나로 전부 초록이 된다. 일부러 불변식을 깨뜨려 두고 검증이 그것을 잡는지 확인한 뒤 되돌린다. 몇 분이면 되고, 이게 없으면 "모든 검증 통과"가 무의미할 수 있다는 가능성이 리포트에 남는다.

## 테스트 계층

| 계층 | 대상 | 인프라 | 속도 |
|---|---|---|---|
| 도메인 단위 | 애그리거트, VO, 전이 표 | 없음 | 밀리초 |
| 유스케이스 | 유스케이스 구현 | 포트를 가짜 구현으로 | 밀리초 |
| 영속성 통합 | 리포지토리, 마이그레이션, 제약 | Testcontainers MySQL | 초 |
| 동시성 | 경합 상황의 불변식 | Testcontainers MySQL + Redis | 초 |
| API | 라우터부터 DB까지 | Testcontainers 전체 | 초 |

**대부분의 테스트는 위 두 계층에 있어야 한다.** 통합 테스트는 실제로 DB가 필요한 것만 쓴다. 도메인 규칙을 통합 테스트로 검증하고 있으면 잘못 배치된 것이다.

## SQLite를 쓰지 않는다

SQLite는 락 동작이 MySQL과 다르다. 행 수준 락이 없고, `SELECT ... FOR UPDATE`를 사실상 무시하며, 격리 수준과 데드락 감지가 다르다. **동시성이 주제인 프로젝트에서 SQLite로 동시성 테스트를 하면 그 테스트는 아무것도 증명하지 못한다.** 통과해도 운영에서 깨지고, 실패해도 진짜 문제인지 알 수 없다.

CHECK 제약 동작도 다르다. **3차 방어선을 검증한다면서 SQLite를 쓰면 그 검증이 거짓이다.**

Testcontainers로 실제 MySQL을 띄운다. 느리지만 이건 타협 대상이 아니다.

## Testcontainers 설정

**컨테이너는 테스트 전체에서 하나만 띄운다.** 세션 스코프 픽스처로 만들고 재사용해야 전체 시간이 감당된다.

```python
@pytest.fixture(scope="session")
def mysql_container():
    with MySqlContainer("mysql:8.4") as c:
        yield c

@pytest.fixture(scope="session")
def redis_container():
    with RedisContainer("redis:7.4-alpine") as c:
        yield c
```

**마이그레이션은 컨테이너가 뜬 뒤 한 번 돌린다.** 모델에서 테이블을 자동 생성하지 않는다 — **스키마의 진실은 마이그레이션이고, 자동 생성으로 테스트하면 마이그레이션이 틀려도 모른다.** CHECK 제약과 인덱스가 실제로 걸렸는지는 마이그레이션을 돌려야만 확인된다.

**테스트 간 데이터 격리는 각 테스트가 책임진다.** 트랜잭션 롤백으로 격리하는 방식은 동시성 테스트에서 쓸 수 없다 — 여러 스레드가 각자 세션을 열어야 하기 때문이다. 동시성 테스트에서는 테이블을 직접 비우거나 시나리오마다 다른 날짜·객실타입을 쓴다.

## 동시성 테스트

동시성 코드에는 **반드시** 동시성 테스트가 따라붙는다. 단일 스레드 테스트만 있으면 리뷰에서 반려된다.

핵심은 셋이다. 스레드들이 **동시에 출발**해야 하고, 검증은 **불변식**을 봐야 하며, **경합이 실제로 일어났는지**를 확인해야 한다.

```python
def test_동시_예약_요청은_재고_수량을_초과하지_않는다(...):
    재고, 동시요청 = 10, 100
    재고를_준비한다(room_type_id, 날짜, 재고)

    출발선 = threading.Barrier(동시요청)      # 전원이 도착해야 열린다
    성공, 재고부족, 예상밖 = [], [], []
    lock = threading.Lock()

    def 시도():
        출발선.wait()                          # 여기 모였다가 함께 출발
        try:
            result = usecase.create(요청())
            with lock: 성공.append(result)
        except InsufficientInventoryError as e:
            with lock: 재고부족.append(e)
        except Exception as e:                 # 예상 못 한 것은 따로 센다
            with lock: 예상밖.append(e)

    with ThreadPoolExecutor(max_workers=동시요청) as pool:
        list(pool.map(lambda _: 시도(), range(동시요청)))

    assert not 예상밖                           # 데드락·NPE가 하나라도 있으면 실패
    assert len(성공) == 재고
    assert len(재고부족) >= 동시요청 - 재고 - 5  # 경합이 실제로 일어났는가
    assert 잔여재고를_조회한다(room_type_id, 날짜) == 0
    assert 예약_행_수를_센다(room_type_id, 날짜) == 재고
```

**GIL은 문제가 되지 않는다.** 경합이 일어나는 자리는 파이썬 바이트코드가 아니라 **DB 행과 Redis 키**다. 스레드가 DB 드라이버 호출에 들어가면 GIL이 풀리므로, 배리어로 모아둔 스레드들이 실제로 동시에 DB에 도달한다. "GIL 때문에 동시성 테스트가 무의미하다"는 CPU 바운드 경합 이야기이고 우리 것이 아니다.

**`Barrier`의 인원수를 스레드 수와 정확히 맞춘다.** 하나라도 도착하지 않으면 전부 영원히 기다린다. 풀 크기가 요청 수보다 작으면 배리어가 열리지 않으므로 **`max_workers`를 요청 수 이상으로 잡는다.**

주의할 점이 더 있다.

**출발 신호 없이 루프에서 바로 제출하면 경합이 안 일어난다.** 먼저 제출된 작업이 이미 끝나버린다.

**예외를 뭉뚱그려 세지 않는다.** 예상한 예외(재고 부족)와 예상 못 한 예외(데드락, 타입 오류)를 구분해서 센다. 예상 못 한 것이 하나라도 있으면 테스트는 실패해야 한다. MySQL 데드락은 `OperationalError`로 오고 에러 코드가 1213이다.

**결과 수뿐 아니라 DB 상태를 본다.** 성공 10건이 나왔어도 실제 예약 행이 11건 들어갔을 수 있다.

**멱등성 테스트는 같은 키로 동시에 보낸다.** 그리고 **사용자 값도 같아야 한다** — 키가 사용자와 조합되므로, 사용자가 다르면 서로 다른 요청이 되어 아무것도 검증하지 못한다.

**1차 방어선을 끈 테스트를 반드시 쓴다.** 분산락을 끄고 같은 조건으로 돌려서 여전히 불변식이 지켜지는지 확인한다. **이게 없으면 다층 방어는 주장일 뿐이다.**

**락을 껐다고 믿지 말고 확인한다.** 설정이 실제로 반영되지 않으면 두 회차가 같은 조건이 되고, 결과는 "차이 없음"으로 나온다. 그리고 그 결론은 "락이 없어도 되더라"로 읽혀서 정반대 주장을 만든다.

## 전이 표는 전수 검증한다

상태 × 이벤트의 **모든 칸**을 순회한다. 허용은 전이되고, 멱등은 상태가 그대로이며, 나머지는 예외가 나야 한다.

```python
@pytest.mark.parametrize("status,event", [(s, e) for s in Status for e in Event])
def test_전이_표의_모든_칸이_표대로_동작한다(status, event): ...
```

**표의 크기가 곧 테스트 수다.** 상태 6개 × 이벤트 6개면 36칸 전부를 본다. 거부 칸을 빠뜨리면 "표에 없는 전이가 막힌다"를 증명하지 못한다.

**스펙의 표와 코드의 표가 같은지도 확인한다.** 둘이 어긋나면 문서가 거짓말을 하는 것이다.

## 확장 지점이 트랜잭션을 공유하는지 검증한다

다른 feature가 참여하는 확장 지점은 **테스트 두 개가 있어야 계약이 닫힌다.**

```
(1) 확장 지점이 예외를 던진다        → 호출부가 쓴 행도 사라져야 한다
(2) 확장 지점이 행을 쓰고 성공한 뒤,
    호출부가 그다음 단계에서 실패한다 → 확장 지점이 쓴 행도 사라져야 한다
```

**(1)만으로는 부족하다.** 세션이 갈라진 구현도 (1)을 통과한다 — 구현부가 예외를 던지면 자기 세션도 커밋 전이라 함께 롤백되기 때문이다. **버그는 구현부가 성공한 뒤에만 드러난다.**

## 테스트 이름

한국어로 시나리오를 쓴다. 실패했을 때 무엇이 깨졌는지 바로 읽혀야 한다.

```python
def test_확정된_예약은_체크아웃일_이후_체크인할_수_없다(): ...
```

"성공한다", "정상 동작한다" 같은 이름은 쓰지 않는다. **무엇이 성공인지가 이름에 있어야 한다.**

## 구조

Given-When-Then으로 나누고 빈 줄로 구분한다. 주석으로 표시할 필요는 없다. 세 덩어리가 눈에 보이면 된다.

한 테스트는 하나를 검증한다. 여러 필드를 함께 보는 건 괜찮지만, 서로 다른 시나리오를 한 테스트에 넣지 않는다.

**픽스처가 무엇을 준비하는지 이름에 드러낸다.** `setup()` 같은 이름은 실패했을 때 아무것도 알려주지 않는다.

## 테스트하지 않는 것

게터·세터, 프레임워크 동작, 라이브러리 자체. 컨테이너가 의존성을 주입하는지는 테스트하지 않는다.

**커버리지 숫자를 목표로 삼지 않는다.** 채우려고 의미 없는 테스트를 쓰면 유지보수 비용만 는다. 대신 **동시성과 상태 전이는 빠짐없이** 덮는다.

## 실행

```bash
pytest                          # 전체
pytest -m concurrency           # 동시성만
pytest -m "not concurrency"     # 개발 중 빠른 확인
```

동시성 테스트는 느리므로 `@pytest.mark.concurrency`로 분리한다. 개발 중에는 빼고 돌리고, **커밋 전에는 반드시 포함해 돌린다.**
