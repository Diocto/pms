# 부하테스트 리포트

- 상태: **골격.** 수치는 실행 후 채운다 (2026-08-15 작성, 실행 예정 8/16~17)
- 설계 문서: `docs/load-test/scenarios.md`
- 스크립트: `load-test/`
- 실행 결과 원본: `docs/load-test/results/`

> **이 문서를 채우는 사람에게.** `⟨…⟩`로 표시된 자리에 실측값을 넣는다. **판정 기준은 이미 확정돼 있으므로 고치지 않는다.** 결과를 보고 기준을 맞추면 이 리포트는 아무것도 증명하지 못한다. 기준을 바꿔야 할 이유가 생기면 그 사실 자체를 §8에 적는다.

## 1. 결론

⟨실행 후 세 문장으로. 무엇을 주장했고, 무엇이 참으로 확인됐고, 무엇이 한계인가.⟩

| 명제 | 결과 |
|---|---|
| (가) 잔여 N실에 N보다 많은 요청이 몰려도 성공은 정확히 N, 재고는 음수가 되지 않는다 | ⟨통과 / 실패⟩ |
| (나) 같은 멱등성 키로 반복 요청해도 예약은 한 건만 생긴다 | ⟨통과 / 실패⟩ |
| (다) 전이 표에 없는 상태 전이는 동시 요청 상황에서도 통과하지 않는다 | ⟨통과 / 실패⟩ |
| (라) 락 유무·캐시 유무의 처리량과 정확성 차이 | ⟨측정 결과 요약⟩ |

## 2. 실행 환경과 그 한계

**이 절을 먼저 읽어야 뒤의 숫자를 옳게 읽을 수 있다.** 뒤로 미루면 변명이 되고, 앞에 두면 측정의 전제가 된다.

### 환경

| 항목 | 값 |
|---|---|
| 머신 | Apple M2, 8코어, 16GB |
| 구성 | **앱·MySQL·Redis·k6가 전부 같은 노트북 한 대에서 동시 실행** |
| DB | MySQL 8.4, 격리 수준 REPEATABLE-READ |
| 캐시·락 | Redis 7.4 |
| 커넥션 풀 | HikariCP 최대 20, 최소 유휴 5, 커넥션 타임아웃 3초 |
| k6 | v0.57.0 |
| 실행 시각 | ⟨기입⟩ |
| 동시에 돌던 다른 프로세스 | ⟨기입⟩ |

### 이 수치가 무엇의 근거이고 무엇의 근거가 아닌가

**부하 생성기가 피시험 대상과 CPU·메모리를 나눠 쓴다.** 그래서 처리량과 지연의 **절대값은 이 시스템의 성능 한계가 아니다.** k6가 CPU를 뺏어 앱이 못 낸 성능일 수도 있고 그 반대일 수도 있으며, 이 환경에서는 둘을 분리할 수 없다.

| 무엇 | 근거로 쓸 수 있는가 |
|---|---|
| "초당 N건을 처리했다" | **아니다.** 이 환경에서 잰 절대 처리량은 시스템의 능력이 아니다 |
| "락을 켜면 p99가 X배가 됐다" | **그렇다.** 같은 머신·같은 부하에서 조건 하나만 바꿔 잰 차이다 |
| "재고 10에 성공이 정확히 10건이었다" | **그렇다.** 참·거짓이 갈리는 명제이고 머신 성능과 무관하다 |

**성능 수치는 참고, 불변식 검증은 결론.** 이 리포트의 주장은 전부 뒤쪽 두 줄 위에 서 있다.

### 기본값과 다르게 설정한 값

**재현하려는 사람이 같은 조건을 만들 수 없으면 그 수치는 근거가 못 된다.**

| 키 | 기본 | 실행값 | 어느 시나리오에서 | 왜 |
|---|---|---|---|---|
| `pms.lock.enabled` | true | true / **false** | S5 | 두 회차를 대조한다 |
| `pms.reservation.hold-minutes` | 10 | **1** | S4-B | 만료×확정 경합을 만들려고 10분을 기다릴 수 없다 |
| `pms.reservation.expire-scan-interval` | 30s | ⟨기입⟩ | S4-B | 만료 판정이 자주 돌아야 경합 창이 촘촘해진다 |
| `pms.payment.decline-rate` | 0.0 | 0.0 / **1.0** | S4 / 결제 분기 회차 | 경합 회차에 확률적 거절을 섞으면 실패 원인이 경합인지 결제인지 구분되지 않는다 |
| `pms.search.cache.enabled` | true | true / **false** | S8 | 두 회차를 대조한다 |
| `pms.search.cache.ttl-seconds` | 10 | 10 | S8 | stale window 합격선의 기준값 |

## 3. 무엇을 증명하려 했는가

이 과제의 목표는 동시성·멱등성·상태 전이를 **말이 아니라 수치로 증명하는 것**이다(`docs/spec/00-problem-and-scope.md` 1절). 그래서 이 리포트의 목차는 시나리오가 아니라 **명제**다. 시나리오는 명제를 증명하는 수단이고, 어느 명제에도 걸리지 않는 시나리오는 만들지 않았다.

| 명제 | 대응 시나리오 |
|---|---|
| **(가)** 초과 판매가 일어나지 않는다 | S1 순간 집중 · S1-C 부분 소진 · S2 지속 부하 · S7 프로모션 스파이크 |
| **(나)** 같은 요청을 여러 번 보내도 예약은 한 건이다 | S3-A 재시도 폭주 · S3-B 더블클릭 |
| **(다)** 전이 표 밖의 전이는 통과하지 않는다 | S4 취소×확정 · S4-B 만료×확정 · 전 시나리오 공통 검증 |
| **(라)** 상대 비교로 서사를 만든다 | S5 락 대조 · S8 캐시 대조 · L5 스탬피드 관찰 |
| (종합) 오래 돌려도 재고가 새지 않는다 | S6 혼합 지속 |

### 판정 기준을 실행 전에 확정했다

각 시나리오의 임계값과 불변식 검증 SQL은 **부하를 넣기 전에** `docs/load-test/scenarios.md`에 숫자로 확정했고, 그 문서는 관리자 확인을 거쳤다. **결과를 보고 기준을 맞춘 것이 아니라는 뜻이다.** 실행 후 기준을 바꿨다면 §8에 그 사실과 이유를 적는다.

### 불변식과 임계값은 급이 다르다

- **불변식은 하드 게이트다.** 하나라도 깨지면 그 시나리오는 실패이고 리포트에 실패로 쓴다.
- **임계값은 참고선이다.** 로컬 머신에서 잰 수치라 못 넘겼다고 설계가 틀린 것은 아니며, 못 넘긴 이유를 병목 분석으로 설명한다.

## 4. 명제별 결과

### (가) 초과 판매가 일어나지 않는다

> 잔여 N실에 N보다 훨씬 많은 동시 요청이 몰려도 성공 건수는 정확히 N이고 재고는 절대 음수가 되지 않는다.

**리포트의 핵심 등식:** `k6가 받은 201 응답 수 = DB의 예약 행 수 = 초기 재고 수`

| 시나리오 | 대상 | 재고 | 요청 | 성공(기대) | 성공(실측) | 잔여 | 음수 행 | 판정 |
|---|---|---|---|---|---|---|---|---|
| S1 순간 집중 | 스위트(3) | 10 | 200 | 10 | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ |
| S1-C 부분 소진 | 오션뷰스위트(5) | 20 | 300 (실수 합 600) | 실수 합 ≤ 20 | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ |
| S2 지속 부하 | 스탠다드(1) | 100 | ~6,000 | 100 | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ |
| S7 프로모션 | 스탠다드(1) 특가 | 20 | ~8,000 | 20 | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ |

**S7은 거절이 400이다.** 특가가 소진되면 정가로 조용히 넘어가지 않고 `400`으로 거절한다(fail-closed). 돈이 걸린 판단이라 그렇게 설계했고, 조용히 정가로 넘어가면 사용자가 기대한 것보다 더 청구된다. 그래서 금액까지 검증했다.

| 금액·원자성 검증 | 기대 | 실측 |
|---|---|---|
| 특가 예약의 `price_per_night`가 전부 75,000 | 정가 박힌 행 0 | ⟨⟩ |
| 특가 단가인데 사용권이 없는 예약 (할인만 받음) | 0 | ⟨⟩ |
| 사용권 수 == 특가 예약 수 | 20 == 20 | ⟨⟩ |
| 일반 재고 부족 409 (**나오면 측정 오염**) | 0 | ⟨⟩ |

**일반 재고 부족 409가 섞이면 그 실행은 폐기한다.** 특가 20이 소진되기 전에 일반 재고가 먼저 바닥났다는 뜻이고, 그러면 잰 것이 "특가 선착순 정확성"이 아니라 "일반 재고 고갈"이다. 대상을 100실짜리로 고른 이유가 이걸 피하기 위해서다.

**S1-C가 (가)의 어려운 판본이다.** 1실씩 빠지면 마지막 한 칸에서만 경계 판단이 필요하지만, 요청 실수가 섞이면 "잔여 2에 3실 요청은 거절, 2실 요청은 통과"를 원자적으로 판단해야 한다. 조건이 `remaining > 0`이 아니라 `remaining >= :n`이어야 하고, 여기가 틀리면 재고가 −1로 내려간다.

⟨해석: 거절이 어떻게 분포했는가, 락 실패(503)는 몇 %였는가, 경계 판정이 고르게 작동했는가⟩

### (나) 같은 요청을 여러 번 보내도 예약은 한 건이다

> 같은 멱등성 키로 같은 요청을 여러 번 보내도 예약은 한 건만 생긴다.

| 시나리오 | 키 개수 | 요청 | 201(기대) | 201(실측) | 200 재반환 | DB 행 수 | 키 중복 | 판정 |
|---|---|---|---|---|---|---|---|---|
| S3-A 재시도 폭주 | 20 | 1,000 | 20 | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ |
| S3-B 더블클릭 | 100 | 200 | 100 | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ | ⟨⟩ |

**DB 행 수만 세지 않았다.** 키당 201 응답이 정확히 1건인지도 함께 확인했다. 어떤 키에서 201이 두 번 나왔다면 그 순간 예약이 두 건 생긴 것이고, 뒤에 하나가 지워졌더라도 (나)는 이미 깨진 것이다. 그리고 같은 키의 모든 2xx 응답이 **동일한 확인번호와 동일한 금액**을 돌려주는지 검사했다 — 행이 하나여도 클라이언트가 두 예약이 있다고 믿으면 멱등이 아니다.

| 추가 검사 | 결과 |
|---|---|
| 키당 확인번호가 하나인가 (`idem_code_mismatch`) | ⟨⟩ |
| 키당 금액이 일정한가 (`idem_price_mismatch`) | ⟨⟩ |

⟨해석⟩

### (다) 전이 표 밖의 전이는 통과하지 않는다

> 전이 표에 없는 상태 전이는 동시 요청 상황에서도 통과하지 않는다.

전이 표는 **49칸 = 허용 8 + 멱등 성공 7 + 거부 34**다.

| 시나리오 | 대상 | 쌍/건수 | PENDING 잔류 | 금지 전이 통과 | 재고 정합 | 판정 |
|---|---|---|---|---|---|---|
| S4 취소×확정 | 300쌍 (600요청) | ⟨⟩ | ⟨0이어야⟩ | ⟨0이어야⟩ | ⟨⟩ | ⟨⟩ |
| S4-B 만료×확정 | 400건 + 만료 배치 | ⟨⟩ | ⟨0이어야⟩ | ⟨0이어야⟩ | ⟨⟩ | ⟨⟩ |

**두 요청이 실제로 겹쳤다는 증거를 함께 실었다.** 금지 전이 거절이 0건이면 "완벽하다"가 아니라 "경합이 일어나지 않았다"일 가능성이 크다. 경합이 일어났다는 증거 없이 경합에 안전하다고 쓸 수 없다.

| 경합 발생 증거 | 값 |
|---|---|
| S4 `rej_transition` (409 INVALID_STATE_TRANSITION) | ⟨1 이상이어야⟩ |
| S4-B 확정 요청 중 만료에 밀려 거절된 수 | ⟨⟩ |

**S4-B가 배치 특유의 버그를 노린다.** 만료는 한 번의 호출이 대상 전부를 훑으며 상태를 바꾸고 재고를 복원한다. 그 배치가 도는 동안 개별 확정 요청이 같은 행을 건드리면, 확정된 예약이 만료되거나 한 예약의 재고가 두 번 복원된다. 단일 요청 시나리오로는 잡히지 않는다.

| 배치 멱등성 | 값 |
|---|---|
| 만료 배치가 보고한 `expiredCount` 합계 | ⟨⟩ |
| 최종 EXPIRED 행 수 | ⟨⟩ |
| 두 값이 같은가 (다르면 이중 만료) | ⟨⟩ |

#### 운영 데이터로 한 증명

거부된 전이는 예외로 트랜잭션이 롤백되므로 이력에 남지 않는다. 그래서 "금지 전이가 **시도됐다가 막혔다**"는 DB로 증명할 수 없다. 대신 이력에 남은 조합을 전부 뽑아 허용 8행의 부분집합인지 확인했다.

> **부하테스트 중 발생한 ⟨N⟩건의 상태 전이가 전부 전이 표 안에 있었다.**

| 증명 수단 | 무엇을 보이는가 |
|---|---|
| F01의 전이 표 49칸 전수 테스트 | 코드가 거부하도록 짜여 있다 |
| **이 리포트의 공통 검증** | **실제 부하에서 한 건도 새지 않았다** |

둘은 다른 증명이고, 후자는 운영 데이터로만 나온다.

⟨실제로 관측된 전이 조합 목록을 여기 붙인다⟩

### (라) 상대 비교로 서사를 만든다

절대 수치는 이 머신에서만 참이지만, **같은 머신·같은 부하에서 조건 하나만 바꿔 잰 두 값의 차이**는 설계 판단의 근거가 된다.

#### S5. 분산락 있음 vs 없음

같은 부하(재고 100, 300 RPS × 20초)를 `pms.lock.enabled`만 바꿔 3회씩 교차 실행하고 중앙값을 채택했다.

**축 1 — 정확성 (양쪽 모두 통과해야 한다)**

| | 락 ON | 락 OFF |
|---|---|---|
| 성공 건수 (기대 100) | ⟨⟩ | ⟨⟩ |
| `remaining < 0` 행 | ⟨0이어야⟩ | ⟨0이어야⟩ |
| 보존식 | ⟨⟩ | ⟨⟩ |

**락 OFF에서도 성공이 정확히 100건인가 — 이것이 이 리포트에서 가장 중요한 한 줄이다.** `coding-rules.md`의 다층 방어는 "1차(분산락)가 뚫려도 2차(조건부 UPDATE)가 막는다"고 주장한다. 락을 껐는데도 정확하다면 그 주장이 참이고, **Redis가 죽어도 데이터가 깨지지 않는다**는 뜻이다.

⟨락 OFF에서 초과 판매가 나왔다면, 그건 이 테스트의 실패가 아니라 **발견**이다. §8에 하이라이트로 쓴다.⟩

**축 2 — 비용 (여기서는 차이가 나야 정상)**

| 항목 | 락 ON | 락 OFF | 차이 | 해석 |
|---|---|---|---|---|
| 달성 RPS | ⟨⟩ | ⟨⟩ | ⟨⟩ | 락이 처리량을 얼마나 깎았나 |
| p50 | ⟨⟩ | ⟨⟩ | ⟨⟩ | |
| p95 | ⟨⟩ | ⟨⟩ | ⟨⟩ | |
| **p99** | ⟨⟩ | ⟨⟩ | ⟨⟩ | 락 대기는 꼬리에 얹힌다 |
| 503 락 실패 | ⟨⟩ | 0 | ⟨⟩ | **정확성 대신 내준 가용성의 양** |
| 거절(409) 응답의 p95 | ⟨⟩ | ⟨⟩ | ⟨⟩ | 락 OFF는 DB까지 갔다 오므로 느릴 것으로 예상 |
| HikariCP 활성 커넥션 (최대 20) | ⟨⟩ | ⟨⟩ | ⟨⟩ | 경합이 DB로 내려간 만큼 커넥션이 오래 잡히나 |

⟨해석: 예상은 "락 ON은 경합을 앱 앞단에서 흡수해 DB 부담이 낮은 대신 락 대기·503이 생기고, 락 OFF는 503이 사라지는 대신 지연 꼬리와 커넥션 점유가 는다"였다. 실측이 이 그림과 다르면 **그림이 아니라 실측을 쓴다.**⟩

#### S7-C. 카운터 게이트 있음 vs 없음

**S5와 같은 구조의 실험이다.** F02의 1차 방어는 분산락이 아니라 Redis 카운터 게이트다. 게이트가 없으면 매진 뒤 요청도 전부 락을 잡고 트랜잭션을 열고 조건부 UPDATE에서 0건을 받고 롤백한다.

**축 1 — 정확성 (양쪽 동일해야 한다)**

| | 게이트 ON | 게이트 OFF |
|---|---|---|
| 성공 건수 (기대 20) | ⟨⟩ | ⟨⟩ |
| 특가 잔여 / 음수 행 | ⟨0 / 0⟩ | ⟨0 / 0⟩ |
| 정가 청구 건 | ⟨0⟩ | ⟨0⟩ |

**두 회차의 성공 건수가 다르면 게이트가 정확성에 영향을 준 것이고, 그건 결함이다.** 게이트는 정확성에 기여하지 않도록 설계됐다.

**축 2 — 비용**

| 항목 | 게이트 ON | 게이트 OFF | 해석 |
|---|---|---|---|
| 달성 RPS | ⟨⟩ | ⟨⟩ | |
| p95 / p99 | ⟨⟩ | ⟨⟩ | 매진 요청이 DB까지 가는 비용이 꼬리에 얹힌다 |
| 거절 응답 p95 | ⟨⟩ | ⟨⟩ | 게이트 ON이 확실히 짧아야 한다 |
| HikariCP 활성 커넥션 (최대 20) | ⟨⟩ | ⟨⟩ | **매진 요청이 커넥션을 잡아먹으면 특가와 무관한 일반 예약까지 밀린다** |
| 빠른 거절 : 느린 거절 (`promo_reject_fast` : `promo_reject_slow`) | ⟨⟩ | ⟨⟩ | 게이트가 실제로 앞단에서 잘랐는가 |

**이 비율은 대리 지표다.** k6는 클라이언트라 게이트가 잘랐는지 조건부 UPDATE가 잘랐는지 직접 볼 수 없다 — 둘 다 400을 준다. 그래서 지연(경계 50ms)으로 추정했다. 정확한 분해는 앱 카운터가 있으면 그걸 쓴다.

**그리고 카운터 자체에 원리적 오차가 있다.** 게이트를 통과한 뒤 실패하는 경로 중 일반 재고 부족·멱등 충돌은 F02 훅을 아예 부르지 않아 카운터가 되돌려지지 않는다. 방향은 과소 판매라 안전하지만, **"게이트가 자른 건수"에 이 오차가 섞이므로 게이트 정확도가 실제보다 좋아 보일 수 있다.**

#### S5와 S7-C를 나란히 놓으면

| | 1차 방어선 | 정확성을 책임지는가 | 대가 |
|---|---|---|---|
| 예약 (S5) | Redis 분산락 | **아니다.** 조건부 UPDATE가 책임진다 | 503 락 실패 (가용성) |
| 특가 (S7-C) | Redis 카운터 게이트 | **아니다.** 조건부 UPDATE가 책임진다 | ⟨측정 결과⟩ |

**두 실험이 같은 결론을 가리킨다 — 1차 방어선은 정확성이 아니라 비용을 위한 것이다.** 정확성은 2차(조건부 UPDATE)와 3차(DB 제약)가 보장하고, 1차는 그 경합이 DB에 도달하기 전에 앞단에서 흡수한다. 그래서 1차를 꺼도 데이터는 깨지지 않고 **느려지거나 자원을 더 쓸 뿐**이다.

⟨실측이 이 그림과 다르면 그림이 아니라 실측을 쓴다.⟩

#### S8. 캐시 있음 vs 없음

| 항목 | 캐시 ON | 캐시 OFF | 해석 |
|---|---|---|---|
| 검색 p95 | ⟨⟩ | ⟨⟩ | 캐시의 직접 효과 |
| **예약 API p95** | ⟨⟩ | ⟨⟩ | **캐시의 진짜 값어치.** 검색이 DB를 덜 때린 만큼 예약이 편해졌는가 |
| 달성 RPS | ⟨⟩ | ⟨⟩ | |
| 캐시 히트율 (`source=CACHE` 비율) | ⟨⟩ | 0 | |
| HikariCP 활성 커넥션 | ⟨⟩ | ⟨⟩ | |
| 초과 판매 | ⟨0이어야⟩ | ⟨0이어야⟩ | **절대 조건** |

**캐시는 공짜가 아니다.** 낡은 결과를 보여준 대가로 사용자는 "검색에는 있었는데 예약하려니 없다"는 헛걸음을 한다. 이득과 비용을 나란히 놓는다.

| 정합성 비용 | 값 | 합격선 |
|---|---|---|
| stale window (재고가 0이 된 뒤 검색에서 사라지기까지) | ⟨⟩ | ≤ 12초 (TTL 10 + 2) |
| 캐시 히트 응답의 나이 (응답 시각 − `searchedAt`) | ⟨⟩ | ≤ 10초 |
| 검색→예약 409 비율 | ⟨⟩ | **합격선 없음. 관측 지표** |
| 재시도 2회 후에도 실패한 비율 | ⟨⟩ | 관측 지표 |

**검색→예약 409를 오류율에 섞지 않았다.** 검색 결과가 낡아 예약이 409로 실패하는 것은 F03이 설계한 정상 흐름이다. 이걸 오류율에 넣으면 정상 설계가 장애처럼 보인다. 부하 스크립트도 실제 클라이언트처럼 `fresh=true`로 재검색해 최대 2회까지 재시도한다.

#### L5. 캐시 스탬피드 관찰 (합격·불합격 없음)

F03이 스탬피드 방어 도입 여부를 "측정 후 판단"으로 미뤘고, 이 측정이 그 판단 근거다. **F04는 숫자만 싣고 결론은 F03이 낸다.**

| 관측 항목 | 값 |
|---|---|
| 캐시 미스 수 (`source=DB`) | ⟨⟩ |
| TTL 만료 횟수 (60초 ÷ 10초) | 약 6회 |
| 미스가 만료 시각에 뭉치는가 | ⟨⟩ |
| 만료 순간의 p99 상승 | ⟨⟩ |
| HikariCP 활성 커넥션 최대 (풀 20) | ⟨⟩ |

**판단 기준:** 만료 순간 DB 조회가 한 자릿수면 방어가 불필요하고, 수십~수백이면 방어를 넣을 근거가 된다.

### (종합) 오래 돌려도 재고가 새지 않는다 — S6

5분간 예약·확정·취소·조회를 섞어 약 60,000건을 돌렸다. **짧은 시나리오가 못 잡는 것을 노린다.**

| 검증 | 기대 | 실측 |
|---|---|---|
| 보존식 위반 행 (`잔여 + 점유 = total_quantity`) | 0 | ⟨⟩ |
| `remaining < 0` (초과 판매) | 0 | ⟨⟩ |
| `remaining > total_quantity` (복원 과다) | 0 | ⟨⟩ |
| 예약당 복원 이벤트가 2줄 이상 (이중 복원) | 0 | ⟨⟩ |
| 과거 체크아웃 요청이 DB에 새어들어감 | 0 | ⟨⟩ |
| 후반부 RPS가 전반부의 80% 이상 | — | ⟨⟩ |

**보존식만으로는 부족하다.** 보존식은 최종 상태만 보므로 **두 번 깎고 두 번 되돌린 경우를 통과시킨다.** 최종 잔여가 맞아떨어지기 때문이다. 타이밍이 조금만 달랐으면 음수로 내려갔을 실행이 운으로 통과한다. 그래서 이력 줄 수로 **복원이 예약당 정확히 한 번**인지 함께 셌다 — 최종 상태가 아니라 일어난 사건을 세는 것이라 운으로 맞아떨어진 경우를 구분해낸다.

**과거 체크아웃 프로브를 섞은 이유.** F01의 규칙은 대부분 DB CHECK 제약이 최후 방어선으로 받쳐주지만 `checkOut > today` 하나만 예외다. MySQL CHECK에 `CURDATE()`를 쓸 수 없어 **애플리케이션 검증 한 겹이 전부**다. 방어선이 한 겹뿐인 곳은 뚫려볼 값이 있다.

## 5. 이 실험이 통과했는데도 시스템이 망가져 있을 수 있는 경우

**부하테스트에서 가장 위험한 실패 모드는 실패가 아니다. 아무것도 증명하지 못한 초록불이다.** 실패는 눈에 띄지만 이건 안 띄고, 리포트에는 "검증 통과"로 적히며, 그 문장을 읽는 사람은 검증됐다고 믿는다.

설계 단계에서 시나리오마다 이 질문을 던지고 대응을 붙였다.

| 시나리오 | 통과했는데도 망가져 있을 수 있는 경우 | 대응 | 실측 확인 |
|---|---|---|---|
| S3 | 재시도마다 사용자가 달라 **애초에 중복 요청이 아니었다** | 키마다 전용 사용자를 묶고, `201 == 키 개수`를 하드 게이트로 | ⟨⟩ |
| S6 | **두 번 깎고 두 번 되돌렸다.** 최종 잔여가 맞아 보존식을 통과한다 | 이력 줄 수로 복원 횟수를 센다 | ⟨⟩ |
| S1 | 요청이 겹치지 않고 순차 도달했다 | VU 200 × 1회로 도달 시점을 겹치고, `rej_inventory ≥ 180`으로 경합량 확인 | ⟨⟩ |
| S4 | 두 요청이 안 겹쳐 경합 상황 자체가 안 만들어졌다 | `rej_transition ≥ 1`을 하드 게이트로. 0이면 재실행 | ⟨⟩ |
| S1-C | 경계 판정(잔여 2에 3실)이 한 번도 안 걸렸다 | 1·2·3실 균등 혼합, 최종 잔여 3 이상이면 실패 | ⟨⟩ |
| S2·S5 | 앱이 느려 실제 부하가 목표보다 작았다 | 도착률 고정 모델 사용. 달성 RPS가 목표의 80% 미만이면 병목 분석 | ⟨⟩ |
| **S5** | **락 스위치가 실제로는 안 꺼져 두 회차가 같은 조건이었다** | 실행 전 `/actuator/env`로 값 확인 | ⟨⟩ |
| S4-B | `hold-minutes`가 길어 만료가 0건이었다 | `CONFIRMED + EXPIRED == 400`을 하드 게이트로 | ⟨⟩ |
| S7 | 특가가 아니라 **일반 재고가 먼저 바닥났다** | 일반 재고 100실짜리를 대상으로 골라 여유를 둔다 | ⟨⟩ |
| S8 | 검색 조건이 흩어져 히트율이 0이었다 | `cache_hit_rate`를 함께 싣고, 집중·분산 두 회차를 비교 | ⟨⟩ |
| L5 | 조건이 흩어져 만료가 흩어졌다 | 캐시 키를 하나로 고정 | ⟨⟩ |

**S5의 경우가 특히 위험하다.** 스위치가 안 꺼지면 명제 (라)가 통째로 무효화되면서 "차이 없음"이라는 그럴듯한 결론이 리포트에 실리고, 그 결론은 "락이 없어도 되더라"로 읽혀 정반대 주장을 만든다.

### 검증기를 검증했다

이 리포트의 불변식 검증은 전부 **"결과가 비면 통과"** 형태다. 그래서 쿼리가 조용히 잘못되면 — 컬럼명 오타, 날짜 범위 어긋남, JOIN 조건 실수 — **모든 검증이 초록이 된다.** 검증 체계 전체가 한 번에 무력화되는데 아무도 모른다.

그래서 일부러 깨진 상태를 만들어 검증 쿼리가 실제로 잡아내는지 확인했다 (`load-test/verify/selftest.sh`).

| 일부러 만든 위반 | 검증 쿼리가 잡았는가 |
|---|---|
| 보존식 위반 (잔여 +1) | ⟨⟩ |
| 복원 과다 (잔여 = 총량 + 5) | ⟨⟩ |
| 초과 판매 (잔여 = −1) | ⟨잡음 / DB CHECK가 UPDATE 자체를 거부⟩ |
| 원래 값 복구 후 다시 조용해지는가 | ⟨⟩ |

**세 번째 조작은 두 겹을 동시에 검사한다.**

원래 의도는 "내 검증 쿼리가 음수를 잡는가"였다. 그런데 재고에 `CHECK (remaining >= 0)` 제약이 걸려 있으면 **그 UPDATE 자체가 DB에서 거부된다.** 그러면 검증 쿼리는 잡을 기회조차 없다.

이건 selftest의 실패가 아니다. **3차 방어선(DB 제약)이 실제로 살아 있다는 증거**다. 다층 방어의 마지막 겹은 평소에 아무 일도 하지 않아서 살아 있는지 확인할 방법이 마땅치 않은데, 이 조작이 그걸 건드린다.

| 세 번째 조작의 결과 | 무엇을 알려주는가 |
|---|---|
| UPDATE가 거부됨 | **DB CHECK 제약이 걸려 있다.** 애플리케이션 1·2차가 전부 뚫려도 잘못된 데이터는 저장되지 않는다 |
| UPDATE가 통과하고 검증 쿼리가 잡음 | 검증 쿼리는 정상이지만 **DB 제약이 없다.** 3차 방어선을 확인해야 한다 |
| UPDATE가 통과하고 검증 쿼리가 못 잡음 | **검증기가 고장났다.** 부하 결과를 믿을 수 없다 |

즉 하나의 조작으로 **"내 검증기가 동작하는가"와 "DB 제약이 걸려 있는가"를 함께** 확인한다.

⟨실제 결과와 그 해석을 여기 쓴다.⟩

## 8. 설계 대비 달라진 것

⟨실행하면서 시나리오 설계와 달라진 점을 전부 적는다. 판정 기준을 바꿨다면 왜 바꿨는지도. 없으면 "없음".⟩

> **이 절을 지우지 마라.** 실제로 기준을 바꿀 일이 생기면 그때 이 절을 지우고 싶어진다. **그 유혹이 오는 시점이 이 절이 가장 필요한 시점이다.** 기준을 바꾸는 것 자체는 정당할 수 있지만, 바꿨다는 사실을 감추면 이 리포트 전체가 "결과에 맞춰 기준을 조정한 문서"가 된다. 바꾼 이유를 적으면 여전히 정직한 문서다.

## 9. 재현 방법

```bash
# 1. 인프라
docker compose up -d

# 2. 앱 (설정은 §2의 표를 따른다)
./gradlew bootJar
java -jar build/libs/pms.jar

# 3. 시나리오 하나 실행
cd load-test
./reset.sh s1
k6 run s1-inventory-burst.js --summary-export=../docs/load-test/results/s1-summary.json
mysql -h127.0.0.1 -upms -ppms pms < verify/s1.sql
mysql -h127.0.0.1 -upms -ppms pms < verify/common.sql
```

**네 단계가 다 끝나야 한 시나리오가 끝난 것이다.** `reset.sh`를 빼먹으면 이전 실행 데이터가 섞여 판정이 무의미해지고, `verify/*.sql`을 빼먹으면 k6가 받은 응답만 보고 DB 실제 상태를 안 본 것이 된다.

실행 순서와 소요 시간은 `docs/load-test/scenarios.md` §5에 있다.
