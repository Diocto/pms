# 부하테스트 리포트

- 상태: **본편 실측 기입 완료** (2026-08-16 실행 — 0번 준비 검증 + 필수 7회차 + S5 대조 6회 + selftest 2회). 검색 실험 2종(S8·L5)만 컨펌 대기로 비어 있다
- 설계 문서: `docs/load-test/scenarios.md`
- 스크립트: `load-test/`
- 실행 결과 원본: `docs/load-test/results/`

> **이 문서를 채우는 사람에게.** `⟨…⟩`로 표시된 자리에 실측값을 넣는다. **판정 기준은 이미 확정돼 있으므로 고치지 않는다.** 결과를 보고 기준을 맞추면 이 리포트는 아무것도 증명하지 못한다. 기준을 바꿔야 할 이유가 생기면 그 사실 자체를 §8에 적는다.

## 1. 결론

같은 객실에 수백 명이 동시에 몰려도 초과 판매·중복 예약·금지 전이가 0건이라고
주장했고, 약 11만 요청(폭주·지속·혼합 소크·대조 6회)에 걸쳐 그 세 가지가
전부 0건임이 확인됐다 — 특히 분산락을 꺼도 성공 건수가 정확히 재고와 같아,
"1차 방어선이 뚫려도 2차가 막는다"는 설계 주장이 실측으로 섰다. 한계는 부하
생성기와 서버가 한 머신을 나눠 쓴다는 것으로, 절대 처리량·지연은 이 시스템의
능력이 아니며 이 리포트의 결론은 전부 참·거짓이 갈리는 불변식과 조건 하나만
바꾼 상대 비교 위에만 서 있다.

| 명제 | 결과 |
|---|---|
| (가) 잔여 N실에 N보다 많은 요청이 몰려도 성공은 정확히 N, 재고는 음수가 되지 않는다 | **통과** (S1 10/10 · S1-C 20/20 · S2 100/100, 음수 0행) |
| (나) 같은 멱등성 키로 반복 요청해도 예약은 한 건만 생긴다 | **통과** (S3-A 20키/1,000요청, S3-B 100키 더블클릭 — 중복 생성·번호 불일치 0) |
| (다) 전이 표에 없는 상태 전이는 동시 요청 상황에서도 통과하지 않는다 | **통과** (경합 실물 196+262건 전부 거절, 이력 5,034건 전수 표 안) |
| (라) 락 유무·캐시 유무의 처리량과 정확성 차이 | 락: **꺼도 정확성 동일**, 켜면 중앙값 +22ms·503 발생 대신 꼬리 지연 1/3 (§4). 캐시: 실행 전 (컨펌 대기) |

## 2. 실행 환경과 그 한계

**이 절을 먼저 읽어야 뒤의 숫자를 옳게 읽을 수 있다.** 뒤로 미루면 변명이 되고, 앞에 두면 측정의 전제가 된다.

### 환경

| 항목 | 값 |
|---|---|
| 머신 | Apple M2, 8코어, 16GB |
| 구성 | **앱·MySQL·Redis·k6가 전부 같은 노트북 한 대에서 동시 실행** |
| DB | MySQL 8.4, 격리 수준 REPEATABLE-READ |
| 캐시·락 | Redis 7.4 |
| 앱 | FastAPI + uvicorn, 워커 **4** (전 회차 동일) |
| DB 커넥션 풀 | 프로세스당 15 (SQLAlchemy 기본: 상시 5 + 초과 10), 대기 타임아웃 30초 |
| k6 | v0.57.0 |
| 실행 시각 | 2026-08-16 02:00~02:30 (0번~S4), 03:0x (S4-B), 22:10~22:55 (S1-C~S6) |
| 동시에 돌던 다른 프로세스 | 다른 feature 세션들의 Claude 프로세스, F05의 uvicorn(포트 8000, 유휴) — 부하 중 CPU를 나눠 썼다 |

### 이 수치가 무엇의 근거이고 무엇의 근거가 아닌가

**부하 생성기가 피시험 대상과 CPU·메모리를 나눠 쓴다.** 그래서 처리량과 지연의 **절대값은 이 시스템의 성능 한계가 아니다.** k6가 CPU를 뺏어 앱이 못 낸 성능일 수도 있고 그 반대일 수도 있으며, 이 환경에서는 둘을 분리할 수 없다.

| 무엇 | 근거로 쓸 수 있는가 |
|---|---|
| "초당 N건을 처리했다" | **아니다.** 이 환경에서 잰 절대 처리량은 시스템의 능력이 아니다 |
| "락을 켜면 p99가 X배가 됐다" | **그렇다.** 같은 머신·같은 부하에서 조건 하나만 바꿔 잰 차이다 |
| "재고 10에 성공이 정확히 10건이었다" | **그렇다.** 참·거짓이 갈리는 명제이고 머신 성능과 무관하다 |

**성능 수치는 참고, 불변식 검증은 결론.** 이 리포트의 주장은 전부 뒤쪽 두 줄 위에 서 있다.

### 기본값과 다르게 설정한 값

**재현하려는 사람이 같은 조건을 만들 수 없으면 그 수치는 근거가 못 된다.**

| 키 | 기본 | 실행값 | 어느 시나리오에서 | 왜 |
|---|---|---|---|---|
| `PMS_LOCK_ENABLED` | true | true / **false** | S5 | 두 회차를 대조한다 |
| `PMS_RESERVATION_HOLD_MINUTES` | 10 | **1** | S4-B | 만료×확정 경합을 만들려고 10분을 기다릴 수 없다 |
| `PMS_PAYMENT_DECLINE_RATE` | 0.0 | 0.0 (전 회차) | 전부 | 경합 회차에 확률적 거절을 섞으면 실패 원인이 경합인지 결제인지 구분되지 않는다. 결제 거절 분기만 따로 보는 회차는 이번 실행 계획에 없었다 |
| `PMS_SEARCH_CACHE_ENABLED` | true | true / **false** | S8 | 두 회차를 대조한다 |
| `PMS_SEARCH_CACHE_TTL_SECONDS` | 10 | 10 | S8 | stale window 합격선의 기준값 |

**보류 시간을 S4-B에서만 줄인 것은 편의가 아니라 제약이다.** 앱에 주기적으로 도는 만료 스캐너가 있어서, 보류 시간이 시나리오 길이보다 짧으면 **부하 도중에 예약이 만료되며 재고가 돌아온다.** 그러면 "재고 100에 성공 정확히 100"이 100을 넘고, 우리는 그걸 초과 판매로 오진하게 된다. 나머지 시나리오는 전부 기본 10분을 유지했고, 가장 긴 S6가 5분이라 만료가 끼지 않는다.

### 바꾸지 않았지만 결과를 좌우한 값

**손대지 않은 설정도 결과에 대한 주장을 하려면 같이 적어야 한다.**

| 키 | 실행값 | 왜 적는가 |
|---|---|---|
| `PMS_LOCK_WAIT_MILLIS` | 200 (기본값 그대로) | **S5의 락 실패 건수를 사실상 이 값이 정한다.** 이 값이 2초였다면 실패 수는 훨씬 작았을 것이다 — 우리가 잰 것은 락의 본질적 비용이 아니라 **이 파라미터에서의 비용**이다 |
| `PMS_LOCK_TTL_SECONDS` | 3 (기본값 그대로) | 트랜잭션이 이보다 길면 락이 자동으로 풀리고 `LockNotOwnedError`가 난다. 5절 로그 관찰 참조 |
| `PMS_RESERVATION_EXPIRE_SCAN_SECONDS` | 30 (기본값 그대로) | 만료가 언제 일어나는지를 정한다. S4-B의 만료 건수 해석에 필요하다 |
| DB 커넥션 풀 크기 | 프로세스당 15 (상시 5 + 초과 10) | 아래 참조 |

**이 표는 손으로 옮겨 적은 것이므로 그 자체로는 증거가 아니다.** 실행 시점의 실제 설정은 `reset.sh`가 앱의 설정 노출 엔드포인트에서 받아 **`results/settings-<시나리오>.json`에 그대로 저장한다.** 표와 그 파일이 어긋나면 **파일이 맞다.** 표를 고친다.

### 동시 처리 한계가 어디서 왔는가

**앱 프로세스 수: `uvicorn app.main:app --workers` 4 — 전 회차 동일.** 회차마다 다르면 그 대조는 조건 하나만 바꾼 것이 아니게 된다. S5의 여섯 회차 전부 4였다.

**이번 실행에서 앱 카운터(`RuntimeReport`의 `counters`)로 판정한 회차는 없다.** 카운터를 싣던 주인(F02 게이트)이 폐기돼(ADR-0058) 이 칸은 현재 빈 dict다. 다만 조건 둘은 계약과 함께 남는다 — 카운터가 생기는 날, 지키지 않으면 그 판정은 무효다:

1. **차분 판정.** 카운터는 누적이라 절대값이 아니라 **회차 전후 두 GET의 차분**으로 읽는다.
2. **워커 1 전제.** 카운터는 프로세스 단위라 워커 여럿이면 **합산 안 된 한 프로세스 몫이 진짜처럼 나온다** — 게이트가 100건을 잘랐는데 34가 찍히는 식이다. `reset.sh`가 `REQUIRE_SINGLE_PROCESS=1`로 이를 실행 전에 검사한다(응답의 `processId`를 10회 표본해 2종 이상이면 중단).

**워커 수는 선언이 아니라 실물로 적었다.** 위 값 4는 기동 명령의 `--workers`가 아니라 `reset.sh`의 프로세스 표본(응답 `processId` 종수) 관측과 함께 남긴다. 매 회차 10회 표본에서 pid가 2~3종 관측돼 멀티 워커가 확정됐다(표본이 모든 워커에 고루 가지는 않으므로 4종 전부가 찍히지는 않는다).

앱의 요청 핸들러가 `async def`가 아니라 `def`라 FastAPI가 이를 스레드풀에서 돌린다. 동시에 처리되는 요청 수의 상한은 대략 **워커 수 × 스레드풀 크기**이고, 그 아래에 다시 **DB 커넥션 풀 크기**가 있다. 커넥션 풀이 더 작으면 남는 스레드는 전부 커넥션을 기다리며 서 있는다.

> **이 상한에 걸린 상태에서 잰 지연은 락 경합이 아니라 커넥션 대기를 잰 것이다.** 겉보기로는 구분되지 않는다. 그래서 "락을 켜니 p99가 X배"라고 쓰기 전에 두 회차 모두 이 상한에 닿지 않았음을 먼저 확인했다. **확인 결과: S5 여섯 회차의 앱 로그 전부에서 풀 고갈 신호(`QueuePool` 대기 초과·`TimeoutError`·MySQL 1040)가 0건**이고, 최대 지연(261/767ms)이 커넥션 대기 타임아웃(30초)과 두 자릿수 차이다. 단, 재기동 직후 워밍업 없이 폭주를 넣으면 이 상한이 실제로 무너진다는 것을 S4-B 2차 실행에서 관측했다(§8 — F01 조립기 결함, 당일 수정됨).

## 3. 무엇을 증명하려 했는가

이 과제의 목표는 동시성·멱등성·상태 전이를 **말이 아니라 수치로 증명하는 것**이다(`docs/spec/00-problem-and-scope.md` 1절). 그래서 이 리포트의 목차는 시나리오가 아니라 **명제**다. 시나리오는 명제를 증명하는 수단이고, 어느 명제에도 걸리지 않는 시나리오는 만들지 않았다.

| 명제 | 대응 시나리오 |
|---|---|
| **(가)** 초과 판매가 일어나지 않는다 | S1 순간 집중 · S1-C 부분 소진 · S2 지속 부하 |
| **(나)** 같은 요청을 여러 번 보내도 예약은 한 건이다 | S3-A 재시도 폭주 · S3-B 더블클릭 |
| **(다)** 전이 표 밖의 전이는 통과하지 않는다 | S4 취소×확정 · S4-B 만료×확정 · 전 시나리오 공통 검증 |
| **(라)** 상대 비교로 서사를 만든다 | S5 락 대조 · S8 캐시 대조 · L5 스탬피드 관찰 |
| (종합) 오래 돌려도 재고가 새지 않는다 | S6 혼합 지속 |

### 판정 기준을 실행 전에 확정했다

각 시나리오의 임계값과 불변식 검증 SQL은 **부하를 넣기 전에** `docs/load-test/scenarios.md`에 숫자로 확정했고, 그 문서는 관리자 확인을 거쳤다. **결과를 보고 기준을 맞춘 것이 아니라는 뜻이다.** 실행 후 기준을 바꿨다면 §8에 그 사실과 이유를 적는다.

### 불변식과 임계값은 급이 다르다

- **불변식은 하드 게이트다.** 하나라도 깨지면 그 시나리오는 실패이고 리포트에 실패로 쓴다.
- **임계값은 참고선이다.** 로컬 머신에서 잰 수치라 못 넘겼다고 설계가 틀린 것은 아니며, 못 넘긴 이유를 병목 분석으로 설명한다.

## 4. 명제별 결과

### (가) 초과 판매가 일어나지 않는다

> 잔여 N실에 N보다 훨씬 많은 동시 요청이 몰려도 성공 건수는 정확히 N이고 재고는 절대 음수가 되지 않는다.

**리포트의 핵심 등식:** `k6가 받은 201 응답 수 = DB의 예약 행 수 = 초기 재고 수`

| 시나리오 | 대상 | 재고 | 요청 | 성공(기대) | 성공(실측) | 잔여 | 음수 행 | 판정 |
|---|---|---|---|---|---|---|---|---|
| S1 순간 집중 | 스위트(3) | 10 | 200 | 10 | **10** | 0 | 0행 | **통과** |
| S1-C 부분 소진 | 오션뷰스위트(5) | 20 | 300 (실수 합 600) | 실수 합 ≤ 20 | 실수 합 **20** (12건) | 0 | 0행 | **통과** |
| S2 지속 부하 | 스탠다드(1) | 100 | 6,000 | 100 | **100** | 0 | 0행 | **통과** |

S7 프로모션 스파이크(특가 20에 ~8,000 요청)는 F02 폐기(ADR-0058, 2026-08-16)로 함께 폐기됐다. "0에서 갑자기 최대치"라는 스파이크 형태의 부하는 이번 범위에서 다루지 않으며, 순간 집중(S1)이 (가)의 집중 부하 판본을 담당한다.

**S1-C가 (가)의 어려운 판본이다.** 1실씩 빠지면 마지막 한 칸에서만 경계 판단이 필요하지만, 요청 실수가 섞이면 "잔여 2에 3실 요청은 거절, 2실 요청은 통과"를 원자적으로 판단해야 한다. 조건이 `remaining > 0`이 아니라 `remaining >= :n`이어야 하고, 여기가 틀리면 재고가 −1로 내려간다.

거절의 분포: S1은 재고 부족 409가 42건, 락 실패 503이 148건(요청의 74%) —
200건이 재고 행 하나의 락을 다투면 대기 한도 200ms를 넘기는 쪽이 다수다.
S1-C도 같은 모양(409 73건, 503 215건)이고, 도착률을 고정한 S2는 503 비율이
24%(1,440/6,000)로 떨어진다. 503의 계약은 "잠시 뒤 다시"이고, 재시도가
성사돼도 성공 총량은 재고를 넘지 않았다.

경계 판정: S1-C의 성공 12건이 1실×6·2실×4·3실×2로 고르게 섞였고 최종 잔여가
0이다 — 잔여 2에 3실은 거절하고 2실은 통과시키는 판단이 마지막 칸까지
작동했다는 실물이다. 잔여가 3 이상 남았다면 자리가 있는데 거절한 것(초과
판매의 반대편 오류)인데, 그 행은 없다.

### (나) 같은 요청을 여러 번 보내도 예약은 한 건이다

> 같은 멱등성 키로 같은 요청을 여러 번 보내도 예약은 한 건만 생긴다.

| 시나리오 | 키 개수 | 요청 | 201(기대) | 201(실측) | 200 재반환 | DB 행 수 | 키 중복 | 판정 |
|---|---|---|---|---|---|---|---|---|
| S3-A 재시도 폭주 | 20 | 1,000 | 20 | **20** | 392 | 20 | 0 | **통과** |
| S3-B 더블클릭 | 100 | 200 | 100 | **100** | 45 | 100 | 0 | **통과** |

**DB 행 수만 세지 않았다.** 키당 201 응답이 정확히 1건인지도 함께 확인했다. 어떤 키에서 201이 두 번 나왔다면 그 순간 예약이 두 건 생긴 것이고, 뒤에 하나가 지워졌더라도 (나)는 이미 깨진 것이다. 그리고 같은 키의 모든 2xx 응답이 **동일한 확인번호와 동일한 금액**을 돌려주는지 검사했다 — 행이 하나여도 클라이언트가 두 예약이 있다고 믿으면 멱등이 아니다.

| 추가 검사 | 결과 |
|---|---|
| 키당 확인번호가 하나인가 (`idem_code_mismatch`) | 0 (A·B 모두) |
| 키당 금액이 일정한가 (`idem_price_mismatch`) | 0 (A·B 모두) |

명제 (나)의 완전한 문장은 실행에서 이렇게 정정됐다 — **"폭주 중 몇 번 거절될
수는 있어도, 재시도가 성사되는 순간까지 합쳐 예약은 키당 정확히 1건이다."**
첫 실행에서 20키 중 1키가 폭주 단계에서 생성 0건으로 끝났다(담당 요청이 재고
락 대기에서 번번이 503, 같은 키의 나머지는 전부 "처리 중" 409). 중복은 0건 —
정합성이 아니라 가용성을 내준 것이고, 실제 클라이언트처럼 간격을 둔 마무리
재시도 단계를 넣자 전 키가 정확히 1건으로 수렴했다. `201 == 키 개수` 하드
게이트가 이 상태를 잡아냈다는 점이 이 회차의 부수 성과다.

나머지 응답 분포: A는 "처리 중" 409가 593건, 락 실패 503이 15건. B는 409가
91건, 503이 64건 — 더블클릭 200건이 같은 재고 락 하나를 다퉜다.

### (다) 전이 표 밖의 전이는 통과하지 않는다

> 전이 표에 없는 상태 전이는 동시 요청 상황에서도 통과하지 않는다.

전이 표는 **36칸(상태 6 × 이벤트 6) = 허용 7 + 멱등 성공 6 + 거부 23**이다.

> **전이 완결성을 주장할 때 반드시 함께 적는 예외.** 노쇼 처리가 **이번 범위에서 유예**돼(추후 작업) `NO_SHOW` 상태가 없다. 그 결과 **`CONFIRMED`에서 자동으로 빠져나가는 출구가 없다.** 나타나지 않은 손님의 예약은 운영자가 수동 취소하기 전까지 CONFIRMED에 남아 재고를 계속 점유한다.
>
> 이건 부하테스트가 발견한 결함이 아니라 **의도적으로 뒤로 미룬 범위**다. 필요 없다고 판단한 게 아니라 **필요하지만 예약 코어를 먼저 끝내기로 한 것**이고, F01도 그 근거와 함께 제출 문서에 적었다. 우리가 증명하는 것은 **"36칸 표를 벗어난 전이가 한 건도 없었다"**이지, **"모든 예약이 종료 상태에 자동 도달한다"**가 아니다. 뒤엣것을 주장하면 사실과 다르다.
>
> 다만 **보존식은 이 구멍과 무관하게 성립한다.** CONFIRMED로 남은 예약은 재고를 점유하는 게 맞고, 활성 집합(`status NOT IN ('CANCELLED','EXPIRED')`)이 그렇게 세기 때문이다.

| 시나리오 | 대상 | 쌍/건수 | PENDING 잔류 | 금지 전이 통과 | 재고 정합 | 판정 |
|---|---|---|---|---|---|---|
| S4 취소×확정 | 300쌍 (600요청) | 300쌍 전부 종결 | **0** | **0** | 복원 예약당 정확히 1회 | **통과** |
| S4-B 만료×확정 | 400건 + 만료 배치 | CONFIRMED 138 + EXPIRED 262 = 400 | **0** | **0** | 보존식 diff 0, 복원 과다 0 | **통과** |

**두 요청이 실제로 겹쳤다는 증거를 함께 실었다.** 금지 전이 거절이 0건이면 "완벽하다"가 아니라 "경합이 일어나지 않았다"일 가능성이 크다. 경합이 일어났다는 증거 없이 경합에 안전하다고 쓸 수 없다.

| 경합 발생 증거 | 값 |
|---|---|
| S4 `rej_transition` (409 INVALID_STATE_TRANSITION) | **196** (기준: 1 이상) |
| S4-B 확정 요청 중 만료에 밀려 거절된 수 | **262** |

**S4-B가 배치 특유의 버그를 노린다.** 만료는 한 번의 호출이 대상 전부를 훑으며 상태를 바꾸고 재고를 복원한다. 그 배치가 도는 동안 개별 확정 요청이 같은 행을 건드리면, 확정된 예약이 만료되거나 한 예약의 재고가 두 번 복원된다. 단일 요청 시나리오로는 잡히지 않는다.

| 배치 멱등성 | 값 |
|---|---|
| 만료 배치가 보고한 `expiredCount` 합계 | 257 |
| 최종 EXPIRED 행 수 | 262 |
| 보고 합계가 EXPIRED 행 수를 **넘지 않는가** (넘으면 이중 만료) | **넘지 않음** (차이 5건 = 배경 스캐너 몫), 예약당 EXPIRE 이력 2줄 이상 0행 |

**두 값이 같기를 기대하지 않는다.** 앱에 `PMS_RESERVATION_EXPIRE_SCAN_SECONDS` 주기로 도는 배경 스캐너가 따로 있어서, **우리가 부르지 않은 만료가 섞인다.** S4-B는 보류 시간을 1분으로 줄이고 최대 120초를 돌므로 그 스캐너가 반드시 한 번 이상 돈다. 그래서 보고 합계가 실제 EXPIRED보다 **작을 수 있고 그건 정상이다.** 등호로 판정하면 정상 실행이 실패로 뜬다 — 판정은 한쪽 방향으로만 한다.

#### 운영 데이터로 한 증명

거부된 전이는 예외로 트랜잭션이 롤백되므로 이력에 남지 않는다. 그래서 "금지 전이가 **시도됐다가 막혔다**"는 DB로 증명할 수 없다. 대신 이력에 남은 조합을 전부 뽑아 허용 7행의 부분집합인지 확인했다.

> **부하테스트 중 발생한 상태 전이가 전부 전이 표 안에 있었다** — 마지막 공통 검증 시점에 남아 있던 5,034건 전수 확인, 회차별 초기화로 지워진 이력도 각 회차의 검증 시점에 같은 전수 확인을 통과했다(회차별 결과 문서).

| 증명 수단 | 무엇을 보이는가 |
|---|---|
| F01의 전이 표 36칸 전수 테스트 | 코드가 거부하도록 짜여 있다 |
| **이 리포트의 공통 검증** | **실제 부하에서 한 건도 새지 않았다** |

둘은 다른 증명이고, 후자는 운영 데이터로만 나온다.

실제로 관측된 조합은 전 회차를 합쳐 다음 네 가지가 전부였고, 모두 허용 7행
안이다.

| 전이 | 대표 건수 (마지막 검증 시점) |
|---|---|
| PENDING → CONFIRM → CONFIRMED | 1,042 |
| PENDING → CANCEL → CANCELLED | 3,125 |
| PENDING → EXPIRE → EXPIRED | 485 |
| CONFIRMED → CANCEL → CANCELLED | 382 |

허용 표의 나머지 3행 — 결제 실패(PENDING→PAYMENT_FAILED, 거절률 0.0으로
실행), 체크인·체크아웃(CONFIRMED→CHECK_IN, CHECKED_IN→CHECK_OUT, 부하에
그 이벤트 없음) — 은 이번 부하가 만들지 않으므로 나타나지 않는 것이 맞다. 표 밖 조합, 종료 상태 이중 도달, 예약당
복원 이벤트 2줄 이상은 모든 검증 시점에서 0행이었다.

### (라) 상대 비교로 서사를 만든다

절대 수치는 이 머신에서만 참이지만, **같은 머신·같은 부하에서 조건 하나만 바꿔 잰 두 값의 차이**는 설계 판단의 근거가 된다.

#### S5. 분산락 있음 vs 없음

같은 부하(재고 100, 300 RPS × 20초)를 `PMS_LOCK_ENABLED`만 바꿔 3회씩 교차 실행하고 중앙값을 채택했다.

**축 1 — 정확성 (양쪽 모두 통과해야 한다)**

| | 락 ON | 락 OFF |
|---|---|---|
| 성공 건수 (기대 100) | **100 / 100 / 100** (3회 전부) | **100 / 100 / 100** (3회 전부) |
| `remaining < 0` 행 | 0행 | 0행 |
| 보존식 | 잔여 0 + 점유 100 = 100 | 잔여 0 + 점유 100 = 100 |

**락 OFF에서도 성공이 정확히 100건인가 — 이것이 이 리포트에서 가장 중요한 한 줄이다.** `coding-rules.md`의 다층 방어는 "1차(분산락)가 뚫려도 2차(조건부 UPDATE)가 막는다"고 주장한다. 락을 껐는데도 정확하다면 그 주장이 참이고, **Redis가 죽어도 데이터가 깨지지 않는다**는 뜻이다.

실측: **락 OFF에서도 6회 중 6회 전부 정확히 100건이었다.** 초과 판매는 나오지
않았고, 2차 방어선(조건부 UPDATE) 단독으로 정확성이 유지됐다. 대조의 전제도
확인됐다 — 회차마다 `reset.sh`가 설정 엔드포인트에서 스위치 값을 실측해
기대값과 일치했고, ON 회차의 앱 로그에 `LockNotOwnedError`가 0건이라 "락이
온전히 작동하는 상태"에서 잰 것이 맞다.

**축 2 — 비용 (여기서는 차이가 나야 정상)**

| 항목 | 락 ON | 락 OFF | 차이 | 해석 |
|---|---|---|---|---|
| 달성 RPS | 300 (도착률 유지, 드롭 0) | 300 (동일) | 없음 | 이 부하 수준에서 락이 처리량을 깎지는 않았다 |
| p50 | 27ms | 5ms | 5.4배 | 락 대기(최대 200ms)가 **모든** 요청에 얹힌다 |
| p95 | 195ms | 106ms | 1.8배 | 같은 방향 |
| 최대 지연 (p99 대용 — 요약본에 p99 미수출) | 261ms | **767ms** | OFF가 3배 | **꼬리는 OFF가 길다** — 경합이 DB 행 락으로 내려간 비용 |
| 503 락 실패 | 354건 (중앙값, 회차별 250~867) | 0건 | — | **정확성 대신 내준 가용성의 양** |
| 거절(409) 응답의 p95 | (op별 분해 미수출 — §8) | 〃 | — | 전체 분포로 갈음: 중앙값 기준 OFF가 빠르다 |
| DB 커넥션 풀 활성 커넥션 (최대 15/프로세스) | 미계측 | 미계측 | — | 부하 중 표본을 뜨지 않았다. 대신 풀 고갈 신호(로그) 0건으로 상한 미도달만 확인 (§2) |

해석: "락 ON은 경합을 앱 앞단에서 흡수해 503을 내고, OFF는 전부 받되 지연
꼬리가 길어진다"는 기대 그림 그대로다. 다만 **"OFF의 거절이 더 느릴 것"이라는
예상은 틀렸다** — 중앙값 기준 OFF(5ms)가 ON(27ms)보다 빠르다. 이 부하에서
거절 경로의 지배 비용은 DB 왕복이 아니라 락 대기였다. 그림이 아니라 실측을
쓴다. 요약하면 **락의 값어치는 정확성이 아니라 부하 분산이다**: 정확성은 2차
방어선이 이미 보장하고(축 1), 락은 그 경합이 DB에 내려가기 전에 앱 앞단에서
잘라 꼬리 지연을 3분의 1로 누르는 대신, 중앙값 지연과 503 거절을 값으로
치른다.

S7-C(카운터 게이트 유무 대조)는 F02 폐기(ADR-0058)로 함께 폐기됐다. "1차 방어선은 정확성이 아니라 비용을 위한 것"이라는 명제는 S5 하나로 증명한다 — 락을 꺼도 성공 건수가 같다는 결과가 그 문장의 전부다.

#### S8. 캐시 있음 vs 없음

> **아직 실행 전이다.** F03 검색이 2026-08-16 밤 main에 병합돼 이제 돌릴 수
> 있고, 별도 컨펌 문서(`docs/reports/F04-검색실험-컨펌.md`)가 관리자 판정을
> 기다린다. 아래 표의 빈 칸은 그 승인 뒤 채운다. L5도 같다.

| 항목 | 캐시 ON | 캐시 OFF | 해석 |
|---|---|---|---|
| 검색 p95 | ⟨⟩ | ⟨⟩ | 캐시의 직접 효과 |
| **예약 API p95** | ⟨⟩ | ⟨⟩ | **캐시의 진짜 값어치.** 검색이 DB를 덜 때린 만큼 예약이 편해졌는가 |
| 달성 RPS | ⟨⟩ | ⟨⟩ | |
| 캐시 히트율 (`source=CACHE` 비율) | ⟨⟩ | 0 | |
| DB 커넥션 풀 활성 커넥션 | ⟨⟩ | ⟨⟩ | |
| 초과 판매 | ⟨0이어야⟩ | ⟨0이어야⟩ | **절대 조건** |

**캐시는 공짜가 아니다.** 낡은 결과를 보여준 대가로 사용자는 "검색에는 있었는데 예약하려니 없다"는 헛걸음을 한다. 이득과 비용을 나란히 놓는다.

| 정합성 비용 | 값 | 합격선 |
|---|---|---|
| stale window (재고가 0이 된 뒤 검색에서 사라지기까지) | ⟨⟩ | ≤ 12초 (TTL 10 + 2) |
| 캐시 히트 응답의 나이 (응답 시각 − `searchedAt`) | ⟨⟩ | ≤ 10초 |
| 검색→예약 409 비율 | ⟨⟩ | **합격선 없음. 관측 지표** |
| 재시도 2회 후에도 실패한 비율 | ⟨⟩ | 관측 지표 |

**검색→예약 409를 오류율에 섞지 않았다.** 검색 결과가 낡아 예약이 409로 실패하는 것은 F03이 설계한 정상 흐름이다. 이걸 오류율에 넣으면 정상 설계가 장애처럼 보인다. 부하 스크립트도 실제 클라이언트처럼 `fresh=true`로 재검색해 최대 2회까지 재시도한다.

#### L5. 캐시 스탬피드 관찰 (합격·불합격 없음)

F03이 스탬피드 방어 도입 여부를 "측정 후 판단"으로 미뤘고, 이 측정이 그 판단 근거다. **F04는 숫자만 싣고 결론은 F03이 낸다.**

| 관측 항목 | 값 |
|---|---|
| 캐시 미스 수 (`source=DB`) | ⟨⟩ |
| TTL 만료 횟수 (60초 ÷ 10초) | 약 6회 |
| 미스가 만료 시각에 뭉치는가 | ⟨⟩ |
| 만료 순간의 p99 상승 | ⟨⟩ |
| DB 커넥션 풀 활성 커넥션 최대 | ⟨⟩ |

**판단 기준:** 만료 순간 DB 조회가 한 자릿수면 방어가 불필요하고, 수십~수백이면 방어를 넣을 근거가 된다.

### (종합) 오래 돌려도 재고가 새지 않는다 — S6

5분간 예약·확정·취소·조회를 섞어 약 60,000건을 돌렸다. **짧은 시나리오가 못 잡는 것을 노린다.**

| 검증 | 기대 | 실측 |
|---|---|---|
| 보존식 위반 행 (`잔여 + 점유 = total_quantity`) | 0 | **0행** (전 객실타입 × 10일) |
| `remaining < 0` (초과 판매) | 0 | **0행** |
| `remaining > total_quantity` (복원 과다) | 0 | **0행** |
| 예약당 복원 이벤트가 2줄 이상 (이중 복원) | 0 | **0행** |
| 과거 체크아웃 요청이 DB에 새어들어감 | 0 | **0** (프로브 1,198건 전부 400 거절) |
| 후반부 RPS가 전반부의 80% 이상 | — | 충족 — 도착률 고정 200/s가 5분 내내 유지됨 (드롭 0, 총 60,000 반복) |

**보존식만으로는 부족하다.** 보존식은 최종 상태만 보므로 **두 번 깎고 두 번 되돌린 경우를 통과시킨다.** 최종 잔여가 맞아떨어지기 때문이다. 타이밍이 조금만 달랐으면 음수로 내려갔을 실행이 운으로 통과한다. 그래서 이력 줄 수로 **복원이 예약당 정확히 한 번**인지 함께 셌다 — 최종 상태가 아니라 일어난 사건을 세는 것이라 운으로 맞아떨어진 경우를 구분해낸다.

**과거 체크아웃 프로브를 섞은 이유.** F01의 규칙은 대부분 DB CHECK 제약이 최후 방어선으로 받쳐주지만 `checkOut > today` 하나만 예외다. MySQL CHECK에 `CURDATE()`를 쓸 수 없어 **애플리케이션 검증 한 겹이 전부**다. 방어선이 한 겹뿐인 곳은 뚫려볼 값이 있다.

## 5. 이 실험이 통과했는데도 시스템이 망가져 있을 수 있는 경우

**부하테스트에서 가장 위험한 실패 모드는 실패가 아니다. 아무것도 증명하지 못한 초록불이다.** 실패는 눈에 띄지만 이건 안 띄고, 리포트에는 "검증 통과"로 적히며, 그 문장을 읽는 사람은 검증됐다고 믿는다.

설계 단계에서 시나리오마다 이 질문을 던지고 대응을 붙였다.

| 시나리오 | 통과했는데도 망가져 있을 수 있는 경우 | 대응 | 실측 확인 |
|---|---|---|---|
| S3 | 재시도마다 사용자가 달라 **애초에 중복 요청이 아니었다** | 키마다 전용 사용자를 묶고, `201 == 키 개수`를 하드 게이트로 | 게이트가 실제로 한 번 물었다 — 첫 실행에서 굶은 키 1개를 잡아 회차를 실패시켰고, 마무리 재시도 추가 후 20/20 |

| S1-C | 경계 판정(잔여 2에 3실)이 한 번도 안 걸렸다 | 1·2·3실 균등 혼합, 최종 잔여 3 이상이면 실패 | 최종 잔여 0, 성공에 2·3실 혼재 |

**S5의 경우가 특히 위험하다.** 스위치가 안 꺼지면 명제 (라)가 통째로 무효화되면서 "차이 없음"이라는 그럴듯한 결론이 리포트에 실리고, 그 결론은 "락이 없어도 되더라"로 읽혀 정반대 주장을 만든다. **위 표의 S5 두 줄은 서로 다른 경로로 같은 거짓 결론에 도달한다** — 하나는 조건이 안 바뀌어서, 하나는 차이가 지표에 안 잡혀서. 그래서 둘 다 자동 장치로 막았다.

### 응답에 안 나오는 신호 — 로그 관찰 결과

**모든 실패가 응답으로 나오지는 않는다.** 두 가지는 서버 로그를 봐야 잡히므로, 회차마다 앱 표준 출력을 파일로 받아 실행 후 셌다.

| 신호 | 뜻 | 기대 | 실측 |
|---|---|---|---|
| `LockNotOwnedError` | 내가 쥔 락이 TTL(기본 3초)을 넘겨 자동으로 풀렸고, **그 사이 다른 요청이 같은 락을 가져갔다.** 그 순간 임계 구역에 둘이 있었다 | **0건** | **전 회차 0건** (S5 여섯 회차 포함, 로그 grep) |
| `INTERNAL_ERROR` | 예상 못 한 예외. 원인은 응답에 안 실리고 로그에만 남는다 | **0건** | **판정에 쓴 전 회차 0건.** 유일한 예외는 폐기된 S4-B 2차 실행 — 5xx 21건이 나와 회차 자체를 버리고 원인(§7)을 잡은 뒤 재실행했다 |

> **`LockNotOwnedError`가 0이 아니면 성능 문제가 아니다.** 1차 방어선(분산락)이 그 순간 작동하지 않았다는 증거다. 락 TTL이 트랜잭션 최장 시간보다 짧다는 뜻이므로, 파라미터를 조정하고 그 회차를 다시 돌린다.
>
> **다만 그때도 재고 불변식은 깨지지 않아야 한다.** 2차 방어선(조건부 UPDATE)과 3차(DB 제약)가 남아 있기 때문이다. 그러니 이 오류가 몇 건 있었는데 재고가 멀쩡했다면 그건 **다층 방어가 실제로 작동한 관측 기록**이고, 그 자체로 실을 값어치가 있다. 의도한 상태는 아니므로 그렇게 쓴다.

### 검증기를 검증했다

이 리포트의 불변식 검증은 전부 **"결과가 비면 통과"** 형태다. 그래서 쿼리가 조용히 잘못되면 — 컬럼명 오타, 날짜 범위 어긋남, JOIN 조건 실수 — **모든 검증이 초록이 된다.** 검증 체계 전체가 한 번에 무력화되는데 아무도 모른다.

그래서 일부러 깨진 상태를 만들어 검증 쿼리가 실제로 잡아내는지 확인했다 (`load-test/verify/selftest.sh`).

| 일부러 만든 위반 | 대상 | 검증 쿼리가 잡았는가 |
|---|---|---|
| 보존식 위반 (잔여 −1, CHECK 안쪽에서) | 재고 | 잡음 (기대 1, 실제 1) |
| 복원 과다 (잔여 = 총량 + 5) | 재고 | **DB CHECK가 UPDATE 자체를 거부** + 상한 제약의 스키마 존재를 information_schema로 확인 |
| 초과 판매 (잔여 = −1) | 재고 | **DB CHECK가 UPDATE 자체를 거부** — 3차 방어선 생존 확인 |
| **이력의 `event`를 없는 표기로 변경** | 이력 | 잡음 (기대 1, 실제 1) |
| **한 예약에 복원 이벤트를 두 줄로 복제** | 이력 | 잡음 (기대 1, 실제 1) |
| 원래 값 복구 후 다시 조용해지는가 | 둘 다 | 확인 (복구 후 위반 0) |

실행은 두 번 했다 — 0번(재고 쪽, 이력이 없어 이력 항목은 구조만)과 S6 뒤
2차(이력 5,034건 위에서 이력 조작 2종 실검출). 둘 다 종료 코드 0.

**이력 쪽 두 줄을 나중에 추가했고, 그게 더 중요하다.** 재고 쿼리는 컬럼명이 틀리면 에러로 시끄럽게 터진다. 그런데 **이력 쿼리는 값 필터라서 표기만 어긋나도 조용히 0행을 돌려준다.**

```sql
WHERE event IN ('CANCEL', 'PAYMENT_FAILED', 'EXPIRE')
```

저장된 값이 `cancel`이면 이 필터는 아무것도 못 잡고, **"이중 복원 0건"이 초록불로 뜬다.** 깨진 게 아니라 아무것도 검사하지 않은 것이다. 그리고 **"재고 복원이 정확히 한 번"을 DB로 증명하는 유일한 수단이 이 쿼리다** — 무력화되면 명제 (다)의 운영 데이터 증명이 통째로 사라진다.

**그래서 사람 눈에 맡기지 않고 종료 코드로 강제했다.** `verify/run.sh`가 위반을 세기 **전에** 검사 대상이 0이 아닌지 먼저 단언하고, 0이면 검증을 진행하지 않는다.

| 실행 전 단언 | 실패하면 |
|---|---|
| 기대 표기(`CANCEL` 등)를 벗어난 `event`·`to_status`가 0행인가 | 실제 저장된 표기를 찍고 **중단** |
| (전이가 있는 시나리오만) 이력 행이 1건 이상인가 | 중단 |
| (전이가 있는 시나리오만) 복원 이벤트 필터가 1건 이상을 잡는가 | 중단 |

**마지막 줄이 핵심이다.** 필터가 실제로 무언가를 잡고 있어야, 그다음 `HAVING COUNT(*) > 1`이 0행인 것이 의미를 갖는다.

단언은 **시나리오별로 다르게** 건다. S1처럼 생성만 하는 시나리오는 이력이 비어 있는 게 정상이라, 거기까지 "복원 이벤트 1건 이상"을 요구하면 정당한 실행이 실패한다. **잘못 우는 게이트는 조작자가 꺼버리므로 없느니만 못하다.**

**세 번째 조작은 두 겹을 동시에 검사한다.**

원래 의도는 "내 검증 쿼리가 음수를 잡는가"였다. 그런데 재고에 `CHECK (remaining >= 0)` 제약이 걸려 있으면 **그 UPDATE 자체가 DB에서 거부된다.** 그러면 검증 쿼리는 잡을 기회조차 없다.

이건 selftest의 실패가 아니다. **3차 방어선(DB 제약)이 실제로 살아 있다는 증거**다. 다층 방어의 마지막 겹은 평소에 아무 일도 하지 않아서 살아 있는지 확인할 방법이 마땅치 않은데, 이 조작이 그걸 건드린다.

| 세 번째 조작의 결과 | 무엇을 알려주는가 |
|---|---|
| UPDATE가 거부됨 | **DB CHECK 제약이 걸려 있다.** 애플리케이션 1·2차가 전부 뚫려도 잘못된 데이터는 저장되지 않는다 |
| UPDATE가 통과하고 검증 쿼리가 잡음 | 검증 쿼리는 정상이지만 **DB 제약이 없다.** 3차 방어선을 확인해야 한다 |
| UPDATE가 통과하고 검증 쿼리가 못 잡음 | **검증기가 고장났다.** 부하 결과를 믿을 수 없다 |

즉 하나의 조작으로 **"내 검증기가 동작하는가"와 "DB 제약이 걸려 있는가"를 함께** 확인한다.

실제 결과는 첫째 줄이었다 — **UPDATE가 거부됐다** (`ERROR 3819`,
`ck_inventory_remaining_lower/upper`). 음수도 총량 초과도 DB가 표현 자체를
거부하므로, 그 두 상태는 검증 쿼리가 잡을 기회조차 없이 원천 차단된다.
그래서 selftest는 그 두 항목을 "쿼리가 잡는가"에서 "제약이 스키마에
존재하는가"(information_schema 조회)로 대체했다 — 구조가 게이트보다 강하다.
보존식 위반(총합은 안 맞지만 값은 범위 안)은 CHECK로 막을 수 없는 종류라
여전히 쿼리가 잡아야 하고, 실제로 잡았다.

## 6. 병목 분석

**숫자를 나열하지 않는다. 무엇이 한계였는지 근거와 함께 쓴다.**

이번 실행에서 지연의 몸통은 회차 유형별로 달랐다.

- **폭주 회차(S1·S4)의 p95(1.1s대)는 연결 수립 비용이다.** 수백 VU가 동시에
  TCP 연결을 여는 순간 `http_req_connecting` p95가 229ms(S4)로, 잰 것은 락
  경합이 아니라 한 머신이 600 연결을 받는 비용이다. 도착률 고정 회차(S2·S5·
  S6)는 같은 총량에서 p95가 19~205ms로 내려간다 — 병목이 앱 로직이 아니라
  연결 폭주였다는 교차 증거다.
- **락 ON 회차의 지연 중앙값(27ms)은 락 대기다.** 같은 부하에서 락만 끄면
  5ms로 떨어진다(§4 (라)). 503은 락 대기 상한(200ms)이 만든 가용성 비용이고,
  그 상한을 넘긴 요청이 S2에서 24%, 폭주 S1에서 74%였다.

| 후보 | 근거로 볼 지표 | 실측 | 판단 |
|---|---|---|---|
| DB 커넥션 풀 (최대 15/프로세스) | 풀 고갈 신호 로그(QueuePool 대기 초과·1040) | 판정 회차 전부 0건 | 상한 미도달. 단 냉시동+폭주 조합에서는 무너진다 (§7) |
| 락 대기 | 503 발생률, ON/OFF 중앙값 차이 | ON 27ms ↔ OFF 5ms, 503 최대 74% | **락 ON 회차의 주 병목** |
| MySQL 행 락 경합 | InnoDB 행 락 대기 수·시간 | 미계측 | OFF 회차의 꼬리(최대 767ms)가 정황 증거이나 직접 계측은 안 했다 — 한계로 남긴다 |
| CPU | 앱·DB·k6 각각의 CPU 점유 | 미계측 | 부하 중 표본을 뜨지 않았다. 절대 수치를 결론에 안 쓰는 이유의 하나 |
| k6 자신 | k6 프로세스의 CPU | 미계측 | 위와 같음. 도착률 유지(드롭 0)로 k6 포화가 없었다는 간접 확인만 있다 |

## 7. 발견한 문제와 조치

**부하테스트로 찾은 버그가 있으면 그게 이 리포트의 하이라이트다.**

| # | 무엇을 발견했나 | 어느 시나리오에서 | 원인 | 조치 | 재검증 |
|---|---|---|---|---|---|
| 1 | **냉시동 직후 폭주가 서버를 무너뜨린다** — MySQL 1040(연결 한도 초과)로 5xx 21건 | S4-B 2차 실행 | 조립기의 엔진 싱글턴이 스레드 안전이 아니라서, 재기동 후 첫 DB 접근이 동시 폭주면 스레드마다 엔진을 만든다 (lsof 실측: 워커 셋이 각 44연결) | F04는 실행 절차에 순차 워밍업을 추가해 우회하고 F01에 실측 보고. **F01이 당일 근본 수정** — 싱글턴 전부를 스레드 안전형으로 교체 + 동시 첫 접근 테스트 (D34, 커밋 3bb786c) | 워밍업 후 워커당 연결 정확히 1개, 이후 전 회차 5xx 0건. 수정 병합 후 워밍업 없는 재실행은 남은 과제 |

동시성 명제 (가)(나)(다)의 범위에서는 발견된 결함이 없다 — 다만 "버그가
없었다"가 아니라, **이 실험들이 잡을 수 있었던 버그의 범위는 §5에 적은
대로이며 그 범위 안에서 발견되지 않았다**가 정확한 문장이다. 위 1번은 그
범위 밖(기동 절차)에서 부하테스트가 덤으로 잡은 실물 결함이다.

## 8. 설계 대비 달라진 것

1. **명제 (나)의 문장을 정정했다.** "몇 번을 보내도 한 건"에서 **"재시도가
   성사되는 순간까지 합쳐 키당 정확히 한 건"**으로. 폭주만으로는 키 하나가
   생성 0건으로 끝날 수 있고(503 연속 — 정합성이 아니라 가용성 문제),
   실제 클라이언트처럼 간격을 둔 마무리 재시도 단계를 스크립트에 추가했다.
   `201 == 키 개수` 게이트는 그대로다 — 기준을 낮춘 게 아니라 부하 모양을
   현실에 맞춘 것이다.
2. **S4-B의 시간축을 세 번 고쳤다.** 생성 직후 일괄 확정(1차) → 45초 지연
   일괄(3차)은 모두 게이트가 초록인데 경합이 0건인 거짓 통과였다. 만료
   경계는 창이 아니라 점이라, 확정을 54초부터 요청당 30ms 시차로 펼쳐
   관통시키는 방식(4차)으로 확정했다. 판정 기준(`CONFIRMED+EXPIRED==400`,
   EXPIRED>0 존재 확인)은 바꾸지 않았고, 그 기준이 세 번의 거짓 통과를
   전부 잡아냈다.
3. **selftest의 재고 조작 2종(음수, 총량 초과)을 "쿼리가 잡는가"에서 "CHECK
   제약이 존재하는가"로 대체했다.** DB가 그 상태의 표현 자체를 거부해 심는
   것이 불가능했기 때문 — 자세한 근거는 §5.
4. **재기동 후 순차 워밍업을 실행 절차에 추가했다** (§7의 1번 우회).
5. **S1-C의 k6 임계값 문법 오류 1건 수정** (`value<=20` → `count<=20`) —
   Counter 지표는 count로만 판정된다. 요청이 나가기 전 기동 단계 오류라
   측정에는 영향 없고, 판정 의미도 동일하다.
6. **판정 주체.** 실행 계획의 승인과 각 회차의 통과 판정은 관리자 부재
   중 PM의 컨펌으로 진행했다(ADR-0059, 선 조치 후 보고). 관리자가 뒤집는
   회차는 다시 돈다.
7. **S8·L5는 실행 전이다.** F03 병합이 본편 실행 뒤에 이뤄져, 별도 컨펌
   문서로 분리했다(`docs/reports/F04-검색실험-컨펌.md`). §4의 해당 표가
   비어 있는 이유다. S5의 op별 거절 p95는 k6 요약본이 태그별 분해를
   수출하지 않아 전체 분포로 갈음했다 — 다음 실행에서 태그별 Trend를
   추가하면 잴 수 있다.

> **이 절을 지우지 마라.** 실제로 기준을 바꿀 일이 생기면 그때 이 절을 지우고 싶어진다. **그 유혹이 오는 시점이 이 절이 가장 필요한 시점이다.** 기준을 바꾸는 것 자체는 정당할 수 있지만, 바꿨다는 사실을 감추면 이 리포트 전체가 "결과에 맞춰 기준을 조정한 문서"가 된다. 바꾼 이유를 적으면 여전히 정직한 문서다.

## 9. 재현 방법

```bash
# 1. 인프라
docker compose up -d

# 2. 앱 (설정은 §2의 표를 따른다). 로그를 파일로 받아둔다 — §5의 로그 관찰에 쓴다
PMS_LOCK_ENABLED=true uvicorn app.main:app --workers N \
    > docs/load-test/results/app-s1.log 2>&1 &

# 3. 검증기를 먼저 검증한다
cd load-test
./verify/selftest.sh

# 4. 시나리오 하나 실행
./reset.sh s1
k6 run s1-inventory-burst.js --summary-export=../docs/load-test/results/s1-summary.json
./verify/run.sh s1          # 전제 단언 -> common.sql -> s1.sql
```

**네 단계가 다 끝나야 한 시나리오가 끝난 것이다.** `reset.sh`를 빼먹으면 이전 실행 데이터가 섞여 판정이 무의미해지고, 검증을 빼먹으면 k6가 받은 응답만 보고 DB 실제 상태를 안 본 것이 된다.

**`verify/run.sh`로 돌리지 `mysql < verify/x.sql`을 직접 치지 않는다.** SQL만 돌리면 결과가 "비어 있음"으로 보이는데 **그게 통과인지 미검사인지 구분되지 않는다.** `run.sh`는 위반을 세기 전에 검사 대상이 0이 아닌지 먼저 단언하고, 0이면 종료 코드 1로 중단한다.

실행 순서와 소요 시간은 `docs/load-test/scenarios.md` §5에 있다.
