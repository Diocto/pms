## selftest 1차 (검증기 자체 검증) — 통과

| 심은 오류 | 결과 |
|---|---|
| 보존식 위반 (잔여 −1) | 검증 쿼리가 정확히 1건 잡음 |
| 복원 과다 (잔여 = 총량+5) | **DB CHECK 제약(`ck_inventory_remaining_upper`)이 UPDATE 자체를 거부** — 3차 방어선 생존 확인, 제약 존재를 information_schema로 확인 |
| 초과 판매 (잔여 = −1) | **DB CHECK 제약(`ck_inventory_remaining_lower`)이 거부** — 동일 |
| 이력 event 오표기 | 표기 검사가 1건 잡음, 복구 확인 |
| 이중 복원 | 건너뜀 (이력 조합 없음 — 계획대로 S6 후 2차에서) |

**배운 것:** 원래 selftest는 "잔여 +1"로 보존식을 깨뜨리려 했는데 CHECK 제약이 그 상태 자체를 거부했다. 심을 수 없는 오류는 검증 쿼리 검증 대신 **제약의 존재 확인**으로 대체했다(selftest.sh 수정). 게이트가 잡을 일을 구조가 금지하면 게이트 검증은 구조 확인으로 대체된다.

## (상태 코드, code) 짝 실물 유도 — 5종 전부 계약과 일치

| 유도 방법 | 기대 | 실측 |
|---|---|---|
| 정상 생성 | 201 + camelCase 본문 | 201, `confirmationCode`·`pricePerNight` 등 전부 camelCase |
| 같은 (userId, 키) 재요청 | 200 + 기존 예약 (D18) | 200 |
| guestCount=0 | 400 `INVALID_REQUEST` | 일치 |
| 없는 확인번호 취소 | 404 `RESOURCE_NOT_FOUND` | 일치 |
| 잔여 10에 11실 요청 | 409 `INSUFFICIENT_INVENTORY` | 일치 |
| CANCELLED에 confirm | 409 `INVALID_STATE_TRANSITION` | 일치 |

503 `LOCK_ACQUISITION_FAILED`와 409 `REQUEST_IN_PROGRESS`는 단건으로 유도되지 않아 계획대로 부하 회차(S1·S5) 로그로 갈음한다.

에러 본문 형태: `{"code", "message", "traceId"}` — 분류기의 code 우선 판정과 맞음.
