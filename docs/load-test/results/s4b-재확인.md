# S4-B 재확인 — 워밍업 없이, 수정 병합 뒤 (2026-08-17)

리포트가 "남은 과제"로 적어둔 한 줄을 닫는 회차다. 조립기 스레드 안전 수정
(예약 코어 D37)이 main에 병합된 뒤, **F04가 우회책으로 넣었던 순차 워밍업을
빼고** 같은 부하를 다시 넣었다. 새 시나리오가 아니라 **같은 시나리오를 우회책
없이 돌린 것**이다.

## 무엇을 확인하려 했나

2026-08-16 S4-B 2차 실행에서 재기동 직후 폭주가 서버를 무너뜨렸다 — MySQL
1040(연결 한도 초과)으로 5xx 21건. 원인은 조립기의 싱글턴이 스레드 안전이
아니라, 냉시동 상태에서 스레드 수십 개가 동시에 첫 DB 접근을 하면 스레드마다
엔진이 생기는 것이었다(lsof 실측: 워커 셋이 각 44연결). F04는 앱 코드를
건드리지 않고 **재기동 후 순차 워밍업**으로 우회했고, F01이 근본 수정을 했다.

그래서 지금까지 리포트가 말할 수 있는 것은 "고쳤다"까지였다. **"고쳐졌음을
부하에서 확인했다"는 이 회차가 만든다.**

**두 회차의 차이는 코드 수정 하나뿐이다.** 워밍업을 뺀 것도, 워커 4도, 부하

대조는 수정의 효과를 그대로 보여준다.

연결 수 표본이 특히 명확하다. 생성 단계(순차)에서는 한 워커만 1개를 잡고
있다가, 54초의 확정 폭주가 시작되자 **워커 4개가 각각 1개씩** 열었다. 수정
전이라면 바로 이 순간 워커마다 스레드 수십 개가 각자 엔진을 만들어 44개로
튀었다. 즉 이 회차는 **문제가 터지던 바로 그 지점을 통과했다.**

## 남는 것

워밍업 절차는 실행 스크립트에서 빼지 않았다. 앞선 회차들이 수정 병합 전에
돌았으므로 그 기록과 조건을 맞추려면 필요하고, 이 회차가 "빼도 된다"를
보였으니 문서로 남기는 것으로 충분하다.

- reset·verify·k6 전부 종료 코드 0, 임계값 미달 없음
- k6 원본: `s4b-nowarm-k6-summary.json`, 설정 스냅샷: `settings-s4b.json`
- 조건: 워커 4, 락 ON, `PMS_RESERVATION_HOLD_MINUTES=1`, **워밍업 없음**, main에 D37 병합된 상태
