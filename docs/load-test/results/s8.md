# S8 — 조회 폭주 속 예약 · 캐시 유무 대조 (2026-08-17 01:2x)

명제 (라)의 캐시 축. 검색을 초당 500건 × 60초(3만 건) 흘리면서 그 사이에
예약을 섞고, `PMS_SEARCH_CACHE_ENABLED`만 바꿔 두 회차를 돌렸다. 회차마다
재기동 → 순차 워밍업 → 초기화(스위치 실측 확인) 순서를 지켰고 워커는 양쪽 4로
고정했다. 대상 대역 10-01~10-10(검색 안전 구간).

먼저 한계: 한 머신에서 앱·DB·Redis·k6가 함께 돌았으므로 절대 수치가 아니라
**ON/OFF 차이의 방향**만 결론으로 쓴다.

## 판정 — 통과 (양 회차 k6·verify 종료 코드 0)

| 항목 | 캐시 ON | 캐시 OFF |
|---|---|---|
| 초과 판매 / 보존식 위반 / 복원 과다 | 0행 | 0행 |
| 서버 오류 / 400 / 404 / 미지 코드 | 0 | 0 |
| 캐시 히트율 (`source=CACHE`) | **99.82%** | **0%** (대조 성립) |
| 스위치 실측 (`reset.sh`) | `true` 확인 | `false` 확인 |
| 검색 성공 표본 | 30,124건 | 30,124건 |
| 달성 부하 | 502 RPS | 502 RPS |

## 핵심 — 캐시의 값어치는 검색이 아니라 **예약**에서 나온다

| 항목 | 캐시 ON | 캐시 OFF | 차이 |
|---|---|---|---|
| 검색 p50 / p95 | 1.99ms / 8.64ms | 2.72ms / 10.97ms | **1.3배 (거의 없음)** |
| 검색 최대 | 81ms | **933ms** | 11.5배 |
| **예약 p95** | **24.7ms** | **385.3ms** | **15.6배** |
| 예약 p50 / 최대 | 11.3ms / 25.5ms | 35.1ms / 399.9ms | 3.1배 / 15.7배 |

**검색 p95는 두 회차가 사실상 같은데 예약 p95는 15배 차이난다.** 이 시나리오를
설계할 때 세운 가설 — "캐시가 빨라지는 것은 당연하고, 봐야 할 것은 검색이 DB를
덜 때린 만큼 예약이 편해졌는가" — 가 그대로 실측됐다. 검색은 캐시가 없어도
인덱스 조회 한 번이라 중앙값이 빠르지만, 초당 500건이 DB 커넥션을 잡아먹는
동안 **같은 풀을 쓰는 예약이 밀린다.** 캐시가 사는 것은 검색의 속도가 아니라
**예약이 쓸 커넥션**이다.

꼬리에서도 같은 그림이다: 캐시 OFF의 검색 최대 933ms는 커넥션 대기가 만든
값이고, 캐시 ON에서는 81ms로 눌린다.

## 캐시의 가격 — 낡은 결과

| 정합성 비용 | 캐시 ON | 캐시 OFF | 기준 |
|---|---|---|---|
| 응답의 낡음 (중앙값 / p95 / 최대) | 4,974ms / 9,474ms / **10,000ms** | 1ms / 2ms / 337ms | **≤ 12초** (TTL 10 + 왕복 2) |
| 검색→예약 409 비율 | 16.67% (3/18) | 12.50% (2/16) | 합격선 없음 · 관측 지표 |

낡음의 중앙값 4.97초는 TTL 10초의 정확히 절반으로, 균등하게 도착하는 요청이
TTL 구간 어디에서나 캐시를 만난다는 이론값과 일치한다. 최대 10.0초는 TTL이
실제로 걸려 있다는 증거다 — 안 걸렸다면 회차 길이(60초)까지 늘어난다.

**검색→예약 409 비율은 표본이 18건·16건뿐이라 두 회차의 차이(16.7% ↔ 12.5%)를
캐시의 효과라고 말하지 않는다.** 이 회차는 재고가 넉넉한 대역을 써서 예약
경합 자체가 적었다. 방향만 적으면 캐시 ON이 조금 높고, 그것이 "검색에는
있었는데 예약하려니 없다"는 헛걸음의 실물이다. 정확한 값을 원하면 재고를
빠듯하게 잡은 별도 회차가 필요하다 — 이번 범위에는 없다.

## 실행에서 정정한 것 — 낡음 기준을 설계 문서 값으로 되돌렸다

1차 실행이 `response_staleness_ms` 임계값 하나로 실패했다(최대 10,402ms >
10,000ms). 확인해 보니 **스크립트에 적힌 10초가 틀린 기준**이었다. 설계
문서(`scenarios.md` §4 S8)가 부하 전에 확정한 값은 **12초(TTL 10 + 2)**이고,
그 2초 여유는 바로 이 측정의 왕복분을 덮으라고 있던 것이다 — 이 지표는
`클라이언트 수신 시각 − 서버의 searchedAt`이라 네트워크·서버 응답 시간이
포함돼서, TTL 만료 직전에 꺼낸 응답이 부하 중 1초 걸려 도착하면 11초로
찍힌다(같은 회차 검색 최대가 933ms였다). **TTL은 정상인데 게이트가 우는
구조**였다.

결과를 보고 기준을 낮춘 것이 아니라 **사전 확정 기준으로 되돌린 것**이므로,
스크립트 주석과 리포트 §8에 근거를 함께 남긴다. 정정 후 초기화부터 다시 돌린
회차가 위 표의 값이다.

- 양 회차: reset(스위치 확인 포함)·k6·`verify/run.sh s8` 전부 종료 코드 0
- k6 원본: `s8on-k6-summary.json`·`s8off-k6-summary.json`, 설정 스냅샷: `settings-s8on.json`·`settings-s8off.json`
- 조건: 워커 4 고정, 락 ON, 만료 기본값, 캐시 TTL 10초, 재기동마다 순차 워밍업 24건
- 판정 주체: PM 컨펌(ADR-0059, D1·D2·D3 승인)
