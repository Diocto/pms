## 세 번 실패하고 얻은 것 — 경계는 창이 아니라 점이다

이 회차는 4차 시도에서야 경합을 실체화했다. 앞의 세 번은 모두 **게이트가
초록인데 경합이 0건**인, 판정 문서가 경계해 온 "통과했지만 아무것도 증명 못 한
실행"이었다. 실패 자체가 절차 결함 두 개를 드러내서 회차 기록에 남긴다.

1. **1차: 생성 직후 일괄 확정.** hold 1분짜리 400건이 8초 만에 전부 확정돼
   만료 창에 아무도 없었다. expired 0, 경합 0, 그러나 k6는 초록.
2. **2차: 확정을 45초로 지연.** 이번엔 냉시동 폭주가 서버를 무너뜨렸다 —
   MySQL 1040(연결 한도 초과)로 5xx 21건. 원인은 앱의 엔진 싱글턴이 스레드
   안전이 아니라서, 첫 DB 접근이 폭주면 워커당 엔진이 수십 개 생기는 것
   (lsof 실측: 워커 셋이 각 44연결). 앱 코드는 F01 소유라 손대지 않고,
   **재기동 후 순차 워밍업 요청**(warmup)을 실행 절차에 넣어 우회했다.
   워밍업 후 워커당 연결 1개 확인. F01에 근본 수정(ThreadSafeSingleton)을
   별도 전달했고, **F01이 당일 수정 완료**(D34, 커밋 3bb786c — 싱글턴 전부
   ThreadSafeSingleton 교체 + 스레드 16개 동시 첫 접근 테스트, 218 passed).
   F04 회차들은 수정 병합 전 실행이라 워밍업 절차를 유지한 기록이다.
3. **3차: 45초 일괄 발사.** 폭주가 1초 만에 끝나 전원이 만료(60초) 전에
   확정됐다. 경계는 **점**이라 스치기만 해서는 안 걸린다.
4. **4차(이번): 54초부터 요청당 30ms 시차로 12초에 걸쳐 발사(54~66초) +
   만료 트리거 52~72초 연사.** 앞쪽 138건은 만료 전에 확정(정상), 뒤쪽
   262건은 EXPIRED 뒤 확정 시도가 전부 409로 거절(경합 증거). 배경
   스캐너(30초 주기)도 창 안에 들어 만료 573건 중 일부를 가져갔다.

`expired_reported`는 배경 스캐너 때문에 하한을 걸 수 없는 지표다. 그래서
"경합이 실제로 있었나"는 k6 임계값이 아니라 **결과 문서의 존재 확인**(EXPIRED
> 0 그리고 409 거절 > 0)으로 판정한다 — 1·3차의 거짓 초록이 이 규칙의 근거다.
