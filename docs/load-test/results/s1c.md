# S1-C — 재고 경합·부분 소진 (2026-08-16 22:14)

명제 (가)의 어려운 판본. 재고 20(오션뷰 스위트)에 1·2·3실 혼합 300건 동시 —
요청 실수 합 600, 재고의 30배. 경계 판단이 `remaining > 0`이 아니라
`remaining >= 요청 실수`여야 통과하는 시나리오다.

## 판정 — 통과 (k6·verify 종료 코드 0, 임계값 미달 없음)

| 항목 | 기대 | 실측 |
|---|---|---|
| 팔린 방 합계 (k6 `rooms_sold`) | ≤ 20 (초과 판매 금지 — 주 표적) | **정확히 20** |
| DB 성공 예약의 실수 합 | = k6 합계 | 20 (12건: 1실×6, 2실×4, 3실×2) |
| remaining < 0 인 행 | 0행 | 0행 |
| 보존식 (잔여 + 점유 = 총량) | diff 0 | 0 + 20 = 20, diff 0 |
| 최종 잔여 | 0 (1실 요청이 100건 남아 있어 끝까지 채워져야 정상) | 0 |
| 서버 오류 / 400 / 미지 코드 | 0 | 0 / 0 / 0 |
| p95 | <1s 참고선 | 640ms |

거절 내역: 재고 부족 409가 73건, 락 실패 503이 215건. 합 288 + 성공 12 = 300,
체크 900/900 전부 통과. 락 실패가 재고 거절보다 많은 것은 300건이 재고 행
하나의 락을 다투며 대기 한도(200ms)를 넘긴 것으로, S1의 148건과 같은 패턴이다.
503의 계약("잠시 뒤 다시")에 따라 재시도하면 재고 부족 409로 수렴한다.

최종 잔여 0이면서 성공 분포에 2·3실이 섞여 있다 — "잔여 2에 3실은 거절,
2실은 통과"의 경계 판단이 실제로 작동했다는 뜻이다. 잔여가 3 이상으로 남았다면
들어갈 자리가 있는데 거절한 것(초과 판매의 반대편 오류)인데, 그 행은 없다.

## 실행 기록 — 임계값 문법 오류 1회

첫 실행은 k6 기동 단계에서 실패했다(`value<=20` — Counter 지표는 `count`로만
판정 가능). 요청이 나가기 전의 문법 오류라 재고 상태는 오염되지 않았고,
`count<=20`으로 고쳐 reset부터 다시 돌린 것이 이 결과다. Counter의 `count`는
add()로 쌓인 합계(호출 횟수 아님)이므로 의미는 설계 그대로다.
