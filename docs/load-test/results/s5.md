# S5 — 락 유무 대조 (2026-08-16 22:2x~22:4x, ON·OFF 교대 각 3회)

명제 (라)+(가). S2와 완전히 같은 부하(스탠다드 100실, 초당 300 × 20초 ≈
6,000건)를 분산락 ON(9-12)과 OFF(9-13)에 번갈아 넣었다. 회차마다 재기동 →
순차 워밍업 → 초기화 → 스위치 실측 확인(`reset.sh`가 설정 엔드포인트를 읽어
기대값과 다르면 중단 — 6회 전부 일치) 순서를 지켰고, 워커 수는 전 회차 4로
고정했다. 지연·건수는 3회의 **중앙값**을 채택한다.

먼저 한계: 이 대조가 잰 것은 로컬 한 머신(앱·DB·Redis·k6 동거) 조건의
상대 비교다. 절대 수치는 장비에 따라 달라지므로 ON/OFF의 **차이의 방향**만
결론으로 쓴다.

## 축 1 — 정확성: 양쪽 모두, 6회 전부 통과

| 항목 | 락 ON (3회) | 락 OFF (3회) |
|---|---|---|
| 생성(201) — 기대 정확히 100 | 100 / 100 / 100 | **100 / 100 / 100** |
| 최종 잔여 / 재고 음수 행 | 0 / 0행 | 0 / 0행 |
| 서버 오류 · `INTERNAL_ERROR` 로그 | 0 | 0 |
| `LockNotOwnedError` 로그 (락이 먼저 풀린 증거) | 0 | — (락 없음) |

**락을 꺼도 정확히 100건이다.** 1차 방어선(분산락) 없이 2차(DB 조건부
UPDATE)만으로 초과 판매가 0이라는 뜻이고, Redis가 죽어도 데이터는 안 깨진다는
다층 방어 주장의 실측 증명이다. `LockNotOwnedError` 0건은 ON 회차가 "락이
온전히 작동하는 상태"에서 측정됐다는 전제 확인이다.

## 축 2 — 비용: 차이는 여기서 난다 (중앙값, 본 부하 구간)

| 비교 항목 | 락 ON | 락 OFF | 읽기 |
|---|---|---|---|
| 지연 중앙값 | 27ms | 5ms | 락 대기(최대 200ms)가 모든 요청에 얹힌다 |
| p95 | 195ms | 106ms | 같은 방향 |
| 최대 지연 | 261ms | **767ms** | OFF는 꼬리가 3배 — 경합이 DB 행 락으로 내려간 비용 |
| 락 실패 503 | 354건 | 0건 | ON이 정확성 유지 대신 내준 가용성 |
| 재고 부족 409 | 5,547건 | 5,900건 | OFF는 거절 전량이 DB까지 갔다 온다 |

회차별 원자료: ON은 (p95 195/245/192ms, 503이 250~867건), OFF는 (p95
106/150/18ms, 503 0건). ON 2회차가 다소 튀었으나(503 867건) 세 회차 모두
정확성 축은 동일하게 통과라 중앙값 채택 규칙대로 처리했다.

기대 그림과의 대조: "락 ON은 경합을 앱 앞에서 흡수해 503을 내고, OFF는 전부
받되 지연 꼬리가 길어진다"는 그림 그대로다. 다만 "OFF의 거절이 더 느릴 것"
이라는 예상과 달리 **중앙값은 OFF가 빠르다** — 이 부하에서는 재고 소진 후
거절 경로의 지배 비용이 DB 왕복이 아니라 락 대기였기 때문이다. 실측을 쓴다.

- 6회 전부: reset(스위치 확인 포함) 통과, k6 종료 코드 0, `rsv_created==100` 게이트 통과
- k6 원본: `s5on-{1,2,3}-k6-summary.json`·`s5off-{1,2,3}-k6-summary.json`, 설정 스냅샷: `settings-s5on.json`·`settings-s5off.json`
- 조건: 워커 4 고정, 만료 기본값, 재기동마다 순차 워밍업 24건 (F01 싱글턴 수정 D34 병합 전 실행)
- 판정 주체: PM 컨펌(ADR-0059)
