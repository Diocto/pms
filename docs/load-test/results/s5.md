# S5 — 분산락 켜고 끄기 대조 (2026-08-16 21:37~21:45)

명제 (라) + (가). 같은 부하(재고 100, 300 RPS × 20초 ≈ 6,000건, S2 스크립트 그대로)를
락 ON(09-12)과 락 OFF(09-13)에 번갈아 3회씩, 총 6회 넣었다. 매 회차 초기화 →
스위치 실물 확인 → 워밍업 30초 → 본 부하 20초 → DB 검증.

## 판정 — 통과

- **정확성: 양쪽 모두, 6회 전부 성공이 정확히 100건.** 잔여 0, `remaining < 0` 0행, 보존식 diff 0.
- **비용: 차이가 나야 할 곳에서만 났다.** 락을 끄면 거절이 빨라지고 503이 사라지는 대신,
  경합이 DB로 내려가 행 락 대기가 0회 → 회당 수백 회로 늘고 커넥션 점유가 4배가 된다.
- 서버 오류(500) 0, 400/404/미지 코드 0, `LockNotOwnedError` 0 — 6회 전부.
- 달성 부하 6,000건/20초 = 300 RPS, 6회 편차 0% (합격선 ±20% 이내).

## 해석 — "정합성은 DB가 지키고, 락은 비용을 줄인다"의 실측판

1. **정합성은 락에 서 있지 않다.** 락을 꺼도 성공은 정확히 100건이었다. 초과 판매를
   막은 것은 Redis가 아니라 DB의 조건부 UPDATE다.
2. **락이 사는 것은 DB의 평온이다.** 락 ON에서 MySQL 행 락 대기는 **0회**다. 6,000건의
   경합이 전부 Redis 앞단에서 직렬화됐고, DB는 커넥션 6개·스레드 3개로 일했다. 락을
   끄자 같은 경합이 DB 안으로 내려가 행 락 대기 수백 회, 락 대기 누적 최대 20초,
   커넥션 점유 4배가 됐다. **재고 행 하나짜리 이번 실험에서도 이 정도이니, 인기 날짜가
   여럿이면 이 비용은 행 수만큼 곱해진다.**
3. **락의 가격은 두 가지다.** (a) 요청의 9% 안팎(중앙값 554건)이 락을 200ms 기다리다
   재고를 확인조차 못 하고 503으로 돌아갔다 — 이 건수는 `PMS_LOCK_WAIT_MILLIS=200`이
   정한 값이다. (b) 모든 요청이 락 큐를 거치므로 중앙값 지연이 4.3ms → 27.4ms로 6.4배가
   된다.
4. **꼬리는 반대로 락이 이긴다.** 설계 문서의 기대 그림은 "락 OFF에서 503이 사라져
   요청이 다 처리되는 대신 p99가 나빠진다"였고 그대로 나왔다 (p99 473 vs 343ms,
   최대 797 vs 516ms). 락 ON의 지연 분포는 락 대기 상한이 천장을 만들어 좁고, OFF는
   DB 행 락 경합이 만드는 꼬리가 회차마다 요동친다 (성공 중앙값이 3회차에 282ms까지).
   **락 ON은 평균을 내주고 꼬리의 예측 가능성을 산다.**
5. 기대 그림과 다르게 나온 것 하나: 기대는 "락 OFF에서 거절이 DB까지 갔다 오므로 느릴
   것"이었지만, 실측은 반대로 OFF 거절이 6배 빨랐다(4.3 vs 26.3ms). ON에서는 거절조차
   락 큐에 줄을 서기 때문이다. 그림이 아니라 실측을 쓴다.
