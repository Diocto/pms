# 낡음을 다루는 두 층 — 서버 캐시와 화면의 스냅샷

**대상 독자: 백엔드 경험이 있는 컴퓨터공학 전공자.**

- 분류: 프론트엔드
- 작성일: 2026-08-15
- 처음 마주친 맥락: "화면에 예약 가능이라 떠 있는데 누르면 409가 난다"를 화면이 어떻게 다뤄야 하는지 설계하면서 (F05 시안 S2, `frontend/lib/booking-flow.ts`)

## 한 줄 정의

사용자가 보는 데이터는 서버 캐시(TTL 동안 낡음)와 화면이 들고 있는 스냅샷(조회한 순간부터 낡음)의 **두 층에서 각각 낡으며**, 두 층의 대응 전략은 다르다.

## 왜 존재하는가

검색처럼 읽기가 몰리는 경로는 서버가 캐시로 막는다(이 프로젝트의 F03: Redis, TTL 10초). 여기까지는 백엔드 개발자에게 익숙하다. 프론트에서 새로운 것은 **화면 자체가 두 번째 캐시라는 사실**이다. 서버 캐시가 아무리 신선해도, 사용자가 결과를 30초 들여다보다 버튼을 누르면 그 판단은 30초 묵은 스냅샷에 근거한다. 즉:

```
실제 재고 ──(TTL ≤ 10초)── 서버 캐시 ──(응답 후 무한정)── 화면 스냅샷 → 사용자의 클릭
```

읽기 경로를 아무리 고쳐도 두 번째 층의 낡음은 없앨 수 없다. **쓰기 시점 검증**(예약 생성 때 서버가 재고를 다시 판정)이 유일한 진실이고, 화면의 일은 낡음을 없애는 게 아니라 **낡음이 드러난 순간을 잘 처리하는 것**이다.

## 어떻게 동작하는가 — 이 화면의 대응

1. **낡음을 표시한다.** 결과 위에 "14:03:22 기준 · 최대 10초 전 정보"를 상시 표기. 감추면 실패를 설명할 수 없다.
2. **실패를 정상 흐름으로 처리한다.** 409를 받으면: 사실 통보("방금 마감") → `fresh=true`로 캐시 우회 재조회 → 남아 있으면 같은 멱등성 키로 자동 재시도 → 최대 2회에서 멈추고 대안 안내.
3. **재시도에 상한을 둔다.** 없는 재고에 계속 부딪히는 건 사용자에게도 서버에도 손해다.

## 코드로 보면

```ts
// 개념만 남긴 형태 (실제: frontend/lib/booking-flow.ts)
for (let attempt = 0; ; attempt++) {
  try { return await create(); }               // 판정은 언제나 쓰기 시점의 서버
  catch (e) {
    if (!is409(e)) throw e;                    // 낡음이 아닌 실패는 이 흐름의 일이 아니다
    if (attempt >= 2) return "sold-out";
    if (!(await checkFresh())) return "sold-out"; // 캐시 우회 재조회
  }                                            // 남아 있으면 같은 키로 한 번 더
}
```

## 언제 어떤 층을 손보는가

| 증상 | 층 | 대응 |
|---|---|---|
| 조회 응답이 느리다 | 서버 캐시 | TTL·키 설계 (백엔드의 일) |
| "가능"인데 누르면 실패한다 | 화면 스냅샷 | 실패의 UX 설계 (이 노트) |
| 실패가 잦아 불만이 된다 | 둘 다 | TTL 축소 ↔ 조회 부하 트레이드오프를 수치로 |

## 흔한 오해와 함정

- "실시간으로 맞추면 되지 않나" — 웹소켓으로 잔여를 밀어줘도 클릭 순간과의 틈은 남는다. 트래픽만 늘고 근본은 그대로다. 그래서 이 프로젝트는 실시간 표시 자체를 만들지 않았다(시안 D6 계열 결정).
- 재시도를 새 멱등성 키로 보내는 실수 — 서버가 다른 요청으로 보고 중복 예약이 될 수 있다. **재시도는 같은 시도이므로 같은 키다.**

## 이 프로젝트에서는

`frontend/lib/booking-flow.ts`가 위 흐름 그대로이고 테스트 6건이 상한·순서를 고정한다. F03의 서버 캐시(TTL 10초)와 정확히 같은 문제 — "낡은 값을 얼마나 참을 것인가" — 를 화면 층에서 푼 것이다.
