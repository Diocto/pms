# 프론트엔드 상태 — 요청-응답으로 끝나지 않는 프로그램

**대상 독자: 백엔드 경험이 있는 컴퓨터공학 전공자.**

- 분류: 프론트엔드
- 작성일: 2026-08-15
- 처음 마주친 맥락: 상태 관리 라이브러리를 쓸지 정해야 했고, "안 쓴다"로 결정했다 (F05 시안 D4). 이 노트는 그 판단의 근거다

## 한 줄 정의

프론트엔드 상태란 화면이 살아 있는 동안 계속 유지·변경되는 값들이며, 프론트가 어려운 진짜 이유는 이 상태가 **요청 하나로 끝나지 않고 계속 살아 있다**는 데 있다.

## 왜 존재하는가

백엔드 핸들러는 요청마다 깨끗하게 시작해서 응답과 함께 끝난다. 상태는 DB에 있고, 코드는 무상태다. 화면은 반대다 — 사용자가 머무는 몇 분 동안 하나의 장수 프로세스가 돌고, 그 안에 입력값·조회 결과·진행 단계·타이머가 전부 쌓인다. **백엔드에서 DB가 하던 "상태의 보관" 역할을, 프론트에서는 코드 스스로 해야 한다.** 상태 관리 라이브러리들은 이 보관소를 전역으로 표준화하는 도구다.

## 어떻게 동작하는가 — 상태를 놓을 수 있는 자리들

| 자리 | 수명 | 특징 |
|---|---|---|
| 컴포넌트 useState | 그 화면이 떠 있는 동안 | 기본값. 화면이 닫히면 사라진다 |
| URL (쿼리·경로) | 링크가 사는 동안 | 새로고침·뒤로가기·공유 무료. **서버의 "요청 파라미터"에 가장 가깝다** |
| React Context | 앱이 떠 있는 동안 | 여러 화면이 공유. 내장 기능 |
| localStorage | 브라우저에 영구 | 새로고침을 넘긴다. 서버는 못 본다 |
| 전역 스토어 라이브러리 | 앱이 떠 있는 동안 | 화면 사이 공유 상태가 **많을 때** 값을 한다 |

핵심 판단은 "어떤 라이브러리를 쓰나"가 아니라 **"이 상태의 수명이 무엇과 같아야 하나"**다. 수명을 정하면 자리는 따라온다.

## 코드로 보면

```tsx
// 검색 조건 — 수명은 "이 검색 결과를 가리키는 동안" = URL과 같다
router.replace(`/search?checkIn=2026-09-01&checkOut=2026-09-04`);

// 멱등성 키 — 수명은 "이 예약 시도 하나" = 주문서 화면과 같다 → useRef
const idemKeyRef = useRef(crypto.randomUUID());

// 사용자 식별값 — 수명은 "이 브라우저" → localStorage + Context
```

## 언제 라이브러리를 쓰고 언제 쓰지 않는가

| 상황 | 판단 |
|---|---|
| 화면 사이를 넘나드는 공유 상태가 두어 개 | 필요 없다. URL과 Context로 끝난다 |
| 장바구니처럼 여러 화면이 같은 것을 읽고 쓰는 상태가 많음 | 그때 도입을 검토한다 |
| 서버 데이터 캐시가 필요함 | 상태 관리가 아니라 데이터 페칭 계층의 문제다 ([[낡음을-다루는-두-층]]) |

## 흔한 오해와 함정

- "React 프로젝트면 일단 상태 관리 라이브러리부터" — 그 라이브러리가 보관할 상태가 무엇인지 먼저 답해야 한다. 답이 두 개 이하면 도구가 문제보다 크다.
- URL에 실을 수 있는 상태를 메모리에 두면, 새로고침·뒤로가기·링크 공유가 전부 고장 난 채로 출시되고 나서야 발견된다.

## 이 프로젝트에서는

화면 사이 공유가 필요한 상태는 정확히 둘이었다: 검색 조건(→ URL 쿼리, `frontend/app/search/page.tsx`)과 확인번호(→ URL 경로). 사용자 식별값 하나만 Context+localStorage(`frontend/components/user-context.tsx`), 나머지(진행 단계, 카운트다운, 입력 오류)는 전부 화면 안 useState다. **그래서 상태 관리 라이브러리를 쓰지 않았고, 이것이 D4로 승인됐다.** 도입했다면 "왜 있는지 모르는 의존성"이 됐을 것이다.
