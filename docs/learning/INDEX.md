# 학습 노트

개발하면서 나온 개념을 나중에 읽으려고 모아두는 곳이다. **이 프로젝트를 몰라도 읽히게** 쓴다. 다른 프로젝트에서 다시 찾아볼 수 있어야 한다.

의사결정 이력(`docs/decisions/`)과 다른 물건이다. ADR은 "이 과제에서 왜 MySQL을 골랐나"이고, 학습 노트는 "갭락이 무엇이고 언제 걸리는가"다.

제출 대상이 아니다.

## 쓰는 방식

개발 중에는 흐름을 끊지 않는다. 새 개념이 나오면 **아래 대기 목록에 제목만 추가**한다. 본문은 나중에 몰아서 쓰거나, 궁금할 때 그때 쓴다.

**feature 세션은 이 파일을 직접 고치지 않는다.** 자기 스펙 끝에 "학습 노트 후보" 목록으로 쌓아두면 PM이 병합할 때 여기로 모은다. 여러 세션이 한 파일을 동시에 고치면 충돌하기 때문이다 (`parallel-work.md`).

## 대기 목록

아직 본문을 쓰지 않은 것들. F01~F04 스펙의 후보 목록을 병합했고, 겹치는 것은 하나로 합쳤다.

### 동시성 제어

- [ ] 조건부 UPDATE로 경합 없애기 — read-modify-write를 한 문장으로 줄이는 것이 동시성 제어의 기본. **갱신 행 수(0이냐 1이냐)가 "내가 이겼는가"의 답이 된다**는 것까지
- [ ] 분산락이 안전하려면 — TTL, 소유 토큰, Lua 원자 해제, 락과 트랜잭션의 순서
- [ ] 락 전순서 고정으로 데드락을 없애는 원리와 그 증명
- [ ] 선착순 재고에서 분산락과 원자적 카운터 중 무엇을 1차 방어로 둘 것인가
- [ ] **1차 방어선은 정확성이 아니라 비용을 위한 것이다** — 락이든 카운터든, 껐을 때 결과가 같아야 하고 느려지기만 해야 한다
- [ ] 다층 방어의 각 층을 개별로 끌 수 있어야 검증 가능해지는 이유 — 끌 수 없는 층은 살아 있는지 확인할 방법이 없다
- [ ] Redis 카운터와 DB 잔여가 어긋날 때 어느 방향의 오차를 허용할 것인가 — 과소 판매는 안전, 과대 판매는 치명. **잘못 통과는 뒷단이 잡아주지만 잘못 거절은 아무도 안 잡아준다**
- [ ] InnoDB 갭락과 넥스트키 락 — MySQL 일별 재고 행을 잠글 때 만나게 될 것
- [ ] Testcontainers와 H2의 차이 — 락 동작이 달라 동시성 테스트가 무의미해지는 이유

### 멱등성

- [ ] 멱등성 키 패턴 — SETNX + TTL, 처리 중 상태, DB 유니크라는 최종 방어선. **Redis는 빠른 길이고 DB 유니크가 정답**이라는 2층 구조
- [ ] 멱등 재요청에 200을 돌려주는 것과 409를 돌려주는 것의 차이 — 409를 주면 클라이언트가 실패로 읽고 재시도가 재시도를 부른다
- [ ] 멱등 키의 범위를 무엇으로 잡을 것인가 — 키 문자열만인가, (사용자, 키) 조합인가. 범위를 잘못 잡으면 **테스트가 중복 요청을 아예 안 보내면서 통과한다**

### 상태 관리

- [ ] 상태머신 구현 방식 비교 — if-else, enum 집합, 전이 테이블, State 패턴, sealed interface
- [ ] 상태 전이 표를 데이터로 두고 전수 테스트로 고정하는 방법 — 표 크기가 (상태 × 이벤트)면 빈칸 전부가 테스트 대상이다
- [ ] 부수 효과를 상태 전이의 *결과*로 묶기 — 되돌릴 요청은 여럿인데 기회는 한 번일 때, 전이에 성공한 하나만 부수 효과를 실행하게 하는 구조
- [ ] 상태 이력 테이블로 "정확히 한 번"을 증명하기 — 최종 수량만 보면 "두 번 깎고 두 번 되돌린" 경우를 놓친다. 그리고 **거부된 전이는 롤백과 함께 사라지므로 시도는 기록할 수 없다**

### 데이터베이스

- [ ] Flyway와 ddl-auto의 차이 — 스키마 관리 방식을 정하다 나온 개념. update가 위험한 이유
- [ ] 이중 복원과 재고 누수 — 하한(`>= 0`)만큼 상한(`<= total_quantity`)이 중요한 이유. 초과 판매는 항의로 발견되지만 복원 과다는 아무도 발견하지 못한다
- [ ] 자연키 복합 PK와 대리키 + 유니크 인덱스 — **잠금 범위**(쓰기)와 **커버링 여부**(조회) 두 축에서 갈리는 차이
- [ ] `@Modifying` 벌크 UPDATE와 JPA 1차 캐시 불일치
- [ ] SQLAlchemy 세션과 트랜잭션의 수명이 다른 것 — 세션을 넘겨받은 쪽이 자기 것을 열면 한 묶음이 조용히 둘로 갈라진다
- [ ] MySQL CHECK 제약의 한계 — `CURDATE()` 같은 비결정적 함수를 못 쓴다. 그래서 DB가 못 받쳐주는 규칙이 생긴다
- [ ] MySQL에 부분 유니크 인덱스가 없어서 생기는 "취소 후 재구매" 문제
- [ ] InnoDB 일관된 읽기와 잠금 읽기의 차이 — 조회가 쓰기 경로에 간섭하지 않는 이유
- [ ] PostgreSQL EXCLUDE 제약과 GiST — 기간 겹침을 DB가 직접 거부하는 방법. MySQL을 골라서 안 썼지만 알아둘 것

### 캐시와 조회

- [ ] 캐시 무효화 전략: TTL 만료(당기기) vs 이벤트 전파(밀기) — 정확성과 지연의 축이 다르다
- [ ] **무효화가 헛도는 경합** — 캐시 미스로 옛 값을 읽는 사이 무효화가 지나가면, 뒤늦게 그 옛 값이 캐시에 앉아 만료까지 남는다. 이벤트 무효화만으로 갈 수 없는 이유
- [ ] 캐시 스탬피드와 stale-while-revalidate
- [ ] 낙관적 낡음을 정상 흐름으로 설계하기 — 검색이 조금 낡아 예약이 실패하는 것을 장애가 아니라 설계로 다루기
- [ ] CQRS 읽기 측에 도메인 모델을 두지 않는 판단 기준
- [ ] 캐시 정합성의 비용을 수치로 재는 법 — stale window 측정

### 경계와 의존

- [ ] 훅(콜백) 인터페이스로 의존 방향 뒤집기 — 의존성 역전이 병렬 작업의 소유 경계와 만나는 지점
- [ ] `List<Port>` 주입으로 구현체 0개를 정상 상태로 만들기 — 확장 지점이 있어도 아무도 안 쓰면 아무 일도 안 일어나는 구조
- [ ] **확장 지점이 몇 개를 넘으면 호출 순서 자체가 계약이 되는가** — 훅을 늘릴 것인가 상대에게 진입점을 줄 것인가
- [ ] 질의와 명령을 나누는 이유 — 같은 데이터를 읽는 자리와 바꾸는 자리를 분리했을 때 얻는 것
- [ ] 남의 "정확히 한 번" 보장 위에 자기 방어선을 한 겹 더 두는 이유
- [ ] 돈이 걸린 판단에서 fail-closed — 못 찾았을 때 조용히 기본값으로 넘어가면 안 되는 경우
- [ ] fail-open과 fail-closed를 한 시스템 안에서 방향을 나눠 적용하는 기준 — 캐시는 열고 재고 판정은 닫는다
- [ ] 바운디드 컨텍스트를 나눌 때 소유권(병렬 작업)이 경계를 결정하는 경우
- [ ] 트랜잭션 밖 외부 호출이 남기는 크래시 틈과 결제 원장·정산 배치
- [ ] 같은 값을 두 곳에 저장할 때의 판단 기준과 일치 검증 테스트

### 검증과 측정

- [ ] **아무것도 증명하지 못하는 초록불** — 테스트가 통과했는데도 시스템이 망가져 있을 수 있는 경우를 목록으로 만드는 습관
- [ ] **검증기를 검증하기** — 일부러 불변식을 깨뜨려 검증 쿼리가 실제로 잡는지 확인하기. "결과가 비면 통과" 형태의 검증이 오타 하나로 전부 초록이 되는 것을 막는다
- [ ] 불변식 기반 부하테스트 — 처리량이 아니라 보존식(`잔여 + 점유 = 총량`)을 판정 기준으로 삼는 방식
- [ ] k6 executor 선택 — `shared-iterations` / `constant-arrival-rate` / `ramping-arrival-rate`가 각각 무엇을 측정하는 도구인가
- [ ] 도착률 고정과 동시 사용자 고정의 차이 — 대조 실험에는 왜 도착률 고정이어야 하는가
- [ ] 정중한 거절(4xx)과 장애(5xx)를 구분해 세지 않으면 생기는 오독
- [ ] 같은 머신에서 부하 생성기와 피시험 대상을 함께 돌릴 때 측정값이 오염되는 방식과, 그럼에도 상대 비교가 유효한 이유
- [ ] 판정 기준을 실행 전에 확정하기 — 결과를 보고 기준을 맞추지 않았다는 것을 문서로 증명하는 방법

### 도메인 (숙박)

- [ ] 오버부킹과 OOO 대응 — 객실 고장 시 재고 축소(OOO/OOS 구분), 초과 판매 해소 순서(수리 → 업그레이드 흡수 → 일정 변경 유도 → 워킹), 투숙 중 강제 이동. 방 이동 요청은 같은 타입이면 배정 모듈 일, 타입 변경이면 예약 변경 연산
- [ ] 홀드-확정 2단계(좌석 홀드 패턴)와 단일 트랜잭션의 비교
- [ ] 되돌리기(보상)를 미는 방식과 당기는 방식 — 이벤트 발행 대 폴링
