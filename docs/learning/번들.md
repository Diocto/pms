# 번들 — 사용자가 다운로드하는 배포물

**대상 독자: 백엔드 경험이 있는 컴퓨터공학 전공자.**

- 분류: 프론트엔드
- 작성일: 2026-08-15
- 처음 마주친 맥락: 라이브러리를 넣을지 말지 판단할 때마다 "이게 번들에 얼마를 더하나"가 기준의 절반이었다 (F05 시안 D2·D3·D4)

## 한 줄 정의

번들은 프론트엔드 코드와 그 의존성을 묶어 브라우저로 배송하는 산출물이며, 그 크기가 **사용자가 첫 화면에서 기다리는 시간**에 직결된다.

## 왜 존재하는가

백엔드에서 의존성을 하나 추가하면 비용은 배포 서버가 진다 — 이미지가 커지고 콜드 스타트가 느려진다. 프론트에서는 **그 비용을 사용자가 진다.** `import`한 라이브러리는 전부 번들에 실려, 페이지를 여는 모든 사용자가 매번(캐시 전까지) 내려받고 파싱한다. 콜드 스타트가 "요청마다, 사용자 쪽에서" 일어나는 셈이다.

그래서 프론트의 의존성 추가는 백엔드보다 한 단계 더 엄격한 질문을 거쳐야 한다: 서버라면 "운영 부담을 질 가치가 있나"지만, 프론트는 **"모든 사용자의 로딩 시간을 늘릴 가치가 있나"**다.

## 어떻게 동작하는가

빌드 도구가 `import` 그래프를 따라가 실제로 쓰이는 코드만 모아 JS 파일 몇 개로 묶는다(트리 셰이킹). Next.js는 경로별로 쪼개서(코드 스플리팅) 첫 페이지에 필요한 만큼만 먼저 보낸다. `next build`가 경로마다 **First Load JS**를 출력하는데, 이것이 "이 페이지를 처음 열 때 내려받는 JS 총량"이다.

이 프로젝트의 실측치 (T1 시점 `next build` 출력):

```
Route (app)                    Size    First Load JS
┌ ○ /                         132 B        103 kB
├ ○ /search                   132 B        103 kB
└ ƒ /reservations/[code]      132 B        103 kB
```

103kB는 거의 전부 React+Next 런타임이다. 화면 코드 자체는 경로당 1kB 미만 — **기준선은 프레임워크가 정하고, 이후의 증가는 전부 의존성 선택이 정한다.**

## 코드로 보면

```ts
// 이 한 줄의 가격은 "코드 한 줄"이 아니라 "그 패키지의 번들 기여분"이다.
import { useQuery } from "@tanstack/react-query"; // ≈ +12kB (gzip)
// 우리가 실제로 필요했던 것: fetch 감싸기 + 재시도 규칙 → 직접 쓰면 +1kB 미만
```

## 언제 의존성을 받아들이는가

| 상황 | 판단 |
|---|---|
| 직접 쓰면 수백 줄 이상이고 틀리기 쉬운 것 (날짜 국제화, 에디터) | 받아들인다 |
| 직접 쓰면 수십 줄인 것 (페칭 감싸기, 상태 두어 개) | 안 받는다 |
| 개발 전용 도구 (vitest, typescript) | 번들에 안 실린다 — 이 저울의 대상이 아니다 |

## 흔한 오해와 함정

- "devDependencies에 넣으면 가볍다" — 구분의 기준은 package.json 섹션이 아니라 **런타임 코드가 import하느냐**다. dependencies에 있어도 import 안 하면 번들에 없다.
- 번들 크기는 기능이 아니라 사용자 경험 예산이라, 늘어난 것을 되돌리기가 어렵다. 넣을 때 재는 것이 뺄 때 재는 것보다 훨씬 싸다.

## 이 프로젝트에서는

런타임 의존성은 next·react·react-dom **셋뿐**이다. 스타일 라이브러리(D2), 페칭·검증 라이브러리(D3), 상태 관리(D4)를 전부 직접 쓴 코드로 대체했고, 그 대체 비용은 lib/ 아래 파일 몇 개(각 100줄 안팎, 테스트 포함)였다. 세 화면 규모에서는 이 교환이 명백히 이득이다 — 화면이 늘어 저울이 기울면 그때 다시 잰다.
