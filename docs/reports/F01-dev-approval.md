# [F01] 승인 요청: 개발 완료

- 날짜: 2026-08-16 · 단계: 개발 완료 승인
- 스펙: `docs/spec/F01-예약-코어.md` (8/15 승인) · 코드: PR #13~#24 (전부 병합 또는 병합 대기)

## 뭘 만들었나

예약 시스템의 코어입니다. 예약을 만들면 날짜별 재고가 깎이고, 결제하면 확정되고, 취소·만료되면 재고가 돌아옵니다. 체크인·체크아웃까지 상태 여섯 개가 전이 표 하나로 움직입니다.

만드는 방식은 4회차로 나눠서, 매 회차 테스트를 먼저 쓰고 리뷰어 셋을 붙였습니다. 지적은 그 회차 안에서 고쳤습니다.

## 숫자

테스트 216개 전부 통과입니다. 실제 MySQL과 Redis를 띄워 돌렸고, 그중 15개가 스레드 수십~수백 개를 동시에 쏘는 동시성 테스트입니다.

가장 중요한 결과는 이겁니다.

> 잔여 10개에 100명이 동시에 예약하면 성공은 정확히 10명. **분산락을 완전히 꺼도 결과가 같습니다.**

즉 데이터를 지키는 건 락이 아니라 DB의 조건부 UPDATE입니다. 락은 비용을 줄여줄 뿐이고, Redis가 통째로 죽어도 초과 판매는 일어나지 않습니다. 같은 방식으로 확인한 것들:

- 같은 요청을 50번 동시에 보내도 예약은 1건. Redis 멱등 장치를 무력화해도 DB 유니크 제약이 1건을 지킴
- 취소와 만료가 겹쳐도 재고 복원은 정확히 1번
- 날짜가 겹치는 예약을 반대 순서로 100건 쏴도 데드락 0건

이 검증들이 헛돌지 않는지도 확인했습니다. 검사 장치를 일부러 깨뜨려 빨간불이 들어오는 것을 보고 되돌리는 절차를 대조 테스트마다 거쳤습니다.

## 리뷰가 잡아준 것 하나

4회차 리뷰에서 돈이 걸린 버그가 나왔습니다. 손님이 결제 버튼을 누른 사이에 취소나 시간 만료가 먼저 처리되면, 돈은 나갔는데 예약은 취소된 채 남을 수 있었습니다. 이런 때 환불을 불러야 하는데, 원래 짜임새로는 환불을 부르지 못하고 지나가는 길이 있었습니다. 어떤 길로 오든 반드시 환불하고 실패를 알리도록 고쳤고(D32), 테스트로 붙박아 두었습니다. 리뷰어 셋을 매 회차 부르는 값이 여기서 돌아왔다고 봅니다.

## 동의해 주실 것 — 구현 중 결정 4건

스펙에 없던 걸 구현하다 정한 것들입니다. 각각 뒤집으면 어떻게 되는지 함께 적습니다.

| # | 결정 | 뒤집으면 |
|---|---|---|
| D29 | 투숙 기간은 최대 30박. 무제한이면 한 요청이 락 수천 개를 잡고 다른 손님을 막을 수 있어서입니다 | 숫자만 바꾸면 됨 (코드 한 줄) |
| D30 | 방이 없어서 거절된 요청을 똑같이 다시 보내면, "처리 중"이 아니라 처음과 같은 "방 없음" 답을 받게 함 | 코드 몇 줄 |

| D32 | 결제는 승인됐는데 그 사이 취소·만료가 먼저 처리된 경우, 어떤 길로 오든 반드시 환불하고 실패로 알림 | 위 버그가 되살아남. 뒤집을 이유가 없다고 봅니다 |

## 판단 지점이었던 것 — 반영 완료

확정에 소유자 확인이 없다는 것을 여쭈었고, "당연히 필요하다"는 답을 받아 바로 넣었습니다(D33). 이제 남의 확인번호로 확정을 눌러도 404로 막히고 결제는 불리지 않습니다. 체크인·체크아웃은 프런트 직원이 손님 대신 처리하는 자리라 그대로 열어 두었습니다. 반영 후 테스트 216개 전부 통과입니다.

## 안 한 것, 한계

- 결제 승인 직후 서버가 죽으면 결제만 되고 예약은 만료됩니다. 모의 결제라 실제 피해가 없어 고치지 않고 문서에 남겼습니다. 실제 PG를 붙이면 결제 원장과 정산 대조가 필요합니다.
- 노쇼 자동 처리는 없습니다 (8/15에 유예 결정하신 것).
- 부하테스트는 F04 몫입니다. F04가 쓸 설정 확인 API와 시드는 준비돼 있습니다.
- Java 흔적 정리를 마쳤습니다. 전환 분류 문서는 이력으로 옮기고, 스펙의 옛 스택 서술 다섯 곳을 다듬었습니다.
