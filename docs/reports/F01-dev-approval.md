## 1. 무엇을 만들었는가

**문제:** 같은 객실을 여러 사람이 동시에 예약할 때 — 초과 판매(C1), 데드락(C2), 중복 예약(C3), 전이 경합(C4~C5), 이중 복원(C6).

**해법의 뼈대는 SQL 세 문장입니다.** 재고 차감(`WHERE remaining >= :n`), 상태 전이(`WHERE status = :expected`), 재고 복원(`WHERE remaining + :n <= total_quantity`). 읽고-판단하고-쓰는 세 단계를 한 문장으로 줄이면 그 사이에 끼어들 틈이 없습니다. **재고 복원은 상태 전이의 결과입니다** — 전이 UPDATE에서 1을 받은 쪽만 복원하므로 취소·결제실패·만료가 동시에 와도 복원은 정확히 한 번입니다.

## 3. 도메인 흐름 (예약 생성 — 열두 줄이 곧 계약)

```
멱등 키 선점(Redis) → [사전검사 훅] → 락 획득(날짜 오름차순)
  ┌ 트랜잭션 ──────────────────────────────┐
  │ [할인 해석] → 가격 확정 → 재고 차감    │
  │ → 예약 INSERT → [생성 훅]             │
  └────────────────────────────────────────┘
  커밋 → 락 해제 → 멱등 결과 저장(Redis)
```

상태 전이는 표 36칸(허용 7·멱등 6·거부 23)이 유일한 진실이고, `apply_event()`가 판정·UPDATE·이력 기록을 한 몸으로 묶어 **표 밖의 전이가 DB에 도달할 코드 경로가 없습니다.**

## 4. 동시성과 멱등성 — 실측

| 경합 지점 | 방어 | 검증 (실측) |
|---|---|---|
| 초과 판매 (C1) | 조건부 UPDATE + CHECK | **K1: 잔여 10 / 100스레드 → 성공 정확히 10 · 잔여 0 · DB 행 10** |
| 데드락 (C2) | 전순서 고정 (락·행 접근 동일 목록) | **K8: 겹치는 기간 역순 100요청 → 데드락(1213) 0건** |
| 중복 예약 (C3) | Redis SET NX + DB UK | **K3: 같은 키 50 동시 → 예약 1건.** K4: Redis 무력화 → **UK가 1건 사수, 49건은 500이 아니라 200 재생** |
| 전이 경합 (C4·C5) | `WHERE status = :expected` | **K5: 확정 25+취소 25 → 최종 상태 하나, 복원 동반 전이 ≤ 1** |
| 이중 복원 (C6) | 복원 = 전이 승자의 결과 | **K6: 취소 50+만료 10 → 복원 정확히 1회 (이력으로 검증)** |
| 부분 소진·유령 점유 | 트랜잭션 롤백 | **K7: 가운데 날짜만 잔여 1 → 성공 1, 실패 99의 부분 차감 0** |

**1차 방어선을 껐을 때 (K2 — 이 과제의 핵심 증명):** `PMS_LOCK_ENABLED=false`로 분산락을 통째로 끄고 K1과 같은 조건으로 돌린 결과 — **성공 정확히 10 · 잔여 0 · 데드락 0 (K2b).** 정확성은 2층(조건부 UPDATE)에 있고 락은 비용 절감 장치라는 설계 주장이 실험으로 성립합니다.

**검증 장치 자체의 검증:** 대조 테스트 3종(모델-스키마 autogenerate·에러 코드 계약·시드 계약)은 전부 **일부러 깨뜨려 빨개지는 것을 확인**했고, 순회 기반 검사는 모집단 0이면 실패합니다.
