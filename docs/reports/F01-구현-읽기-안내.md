## 프로젝트 구조


## 유스케이스

### 프론트 화면에서 시작하는 흐름

손님 화면 기준으로 이렇게 흘러갑니다.

1. 방을 고르고 예약 버튼 → `POST /api/reservations` — 방이 잡히고 10분짜리 결제 대기 상태가 됨
2. 결제 버튼 → `POST /api/reservations/{확인번호}/confirm` — 결제 후 확정
3. 마음이 바뀌면 → `POST /api/reservations/{확인번호}/cancel`
4. 결제를 안 하고 10분이 지나면 → 서버 안 스케줄러가 알아서 만료시킴 (손님 동작 없음)
5. 호텔 프런트 직원이 → `.../check-in`, `.../check-out`
6. 내 예약 보기 → `GET /api/reservations/{확인번호}`

모든 요청은 `X-User-Id` 헤더로 누구인지 밝힙니다. 라우터는 `presentation/router.py` 한 파일이고 얇습니다. 실제 일은 아래 두 파일이 합니다.

- 예약 만들기: `application/usecases/create_reservation.py`
- 확정·취소·만료·체크인아웃: `application/usecases/transition_reservation.py`

### 예약 만들기 — POST /api/reservations

순서가 곧 설계입니다. `create_reservation.py` 첫머리 주석에 같은 그림이 있습니다.

```
같은요청 판별 칸 선점 (Redis) → 사전 검사 → 날짜별 락 (Redis)
  → 트랜잭션: 가격 확정 → 재고 차감 → 예약 저장 → 커밋
→ 락 해제 → 결과 저장 (Redis)
```

보면 좋을 부분 세 가지입니다.

- **재고 차감이 "읽고 판단하고 쓰기"가 아닙니다.** "남은 수가 충분하면 깎아라"라는 조건이 UPDATE 한 문장 안에 들어 있어서(`inventory/infrastructure/persistence.py`), 몇 명이 동시에 와도 DB가 줄 세워 판정합니다. **락과 Redis가 전부 죽어도 이 문장 하나가 초과 판매를 막습니다.** 락은 정답을 지키는 장치가 아니라 헛수고(어차피 실패할 요청이 DB까지 가는 것)를 줄이는 장치입니다.
- **같은 요청을 두 번 보내도 예약은 하나입니다.** Redis에 요청마다 칸을 만들어 두 번째부터는 저장된 답을 돌려주고, Redis가 뚫려도 DB의 유니크 제약이 두 번째 저장을 거부해 기존 예약으로 답합니다.
- **거절도 기억합니다.** 방이 없어 거절되면 그 칸에 "거절로 끝남"을 남겨, 같은 요청을 다시 보내면 똑같은 "방 없음" 답을 받습니다 (D30).

### 확정 — POST .../confirm

1. 예약을 읽어 내 것인지 확인 (남의 확인번호면 404, 결제 안 부름)
2. 결제를 부름 — 트랜잭션 밖에서. DB 연결을 쥔 채 바깥 호출을 기다리지 않으려는 것
3. 성공하면 "상태가 아직 PENDING이면 CONFIRMED로 바꿔라"라는 조건부 UPDATE

보면 좋을 부분: 3번의 조건이 "지금 다시 읽은 상태"가 아니라 **"결제를 하기로 판단했을 때 본 상태"** 라는 점입니다. 결제하는 사이 취소나 만료가 먼저 처리됐다면 UPDATE가 0줄을 바꾸고, 그때는 방금 받은 돈을 돌려주고 409로 알립니다. 다시 읽어 판단하면 진 줄을 모르고 지나가는 길이 생깁니다 — 4회차 리뷰가 잡은 버그였고, 이 순서 자체가 백로그 검토 대상입니다(아래 추가 사항).

### 취소 — POST .../cancel

내 것인지 확인하고, 조건부 UPDATE로 상태를 바꾸고, 이겼을 때만 재고를 되돌리고 이력을 남깁니다. 이미 취소된 예약을 또 취소하면 새로 처리하지 않고 200으로 같은 답을 줍니다. 되돌리기도 조건부라서(총 수량 초과 금지) 취소와 만료가 겹쳐도 두 번 되돌아가지 않습니다.

### 만료 — 스케줄러 + POST /api/internal/reservations/expire

기한 지난 결제 대기 예약을 주기적으로 찾아 한 건씩 처리합니다. 손님의 취소와 겹치면 조용히 넘어갑니다(그 예약은 이미 끝났으므로). internal 주소는 테스트와 부하테스트가 주기를 기다리지 않고 바로 부르는 용도입니다.

### 체크인·체크아웃 — POST .../check-in, .../check-out

날짜가 맞는지 확인하고 전이 표대로 상태를 바꿉니다. 이 둘만 소유자 확인이 없는데, 프런트 직원이 손님 대신 처리하는 자리라서 열어 뒀습니다 (D33에서 결정).
