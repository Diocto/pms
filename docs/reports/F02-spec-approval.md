## 1. 무엇을 만들었는가

**문제.** F01은 여러 날짜에 흩어진 재고 행을 다룹니다. 요청마다 건드리는 행이 조금씩 다릅니다. 특가는 다릅니다. 오픈 시각에 수백 요청이 **재고 행 딱 하나**로 몰립니다. 게다가 그 트래픽의 대부분은 매진 뒤에 들어오는, 어차피 실패할 요청입니다. 이것들이 DB 커넥션을 다 잡아먹으면 특가와 무관한 일반 예약까지 같이 죽습니다.

**해법.** 세 겹으로 막습니다.

1. Redis 잔여 카운터 게이트가 **매진 뒤 요청을 락보다도 앞에서 잘라냅니다.** 줄을 세우는 게 아니라 일찍 자릅니다.
2. DB 조건부 UPDATE 한 줄(`remaining >= 1`)로 초과 판매를 막습니다. 읽고-판단하고-쓰는 세 단계를 한 단계로 줄입니다.
3. DB CHECK 제약(`0 <= remaining <= total_quantity`)이 최후 방어선입니다.

**1번을 껐을 때도 결과가 같다는 것**을 동시성 테스트로 증명하는 것이 이 feature의 핵심 검증입니다 (시나리오 S2). 그리고 **껐다 켠 처리량 차이가 F04 리포트의 수치**가 됩니다.

**스택이 바뀌면서 문제가 하나 늘었습니다.** Java·Spring에서는 훅이 아무것도 안 해도 호출부와 같은 트랜잭션에 자동으로 들어갔습니다. **SQLAlchemy는 그렇지 않습니다.** 훅 구현체가 자기 세션을 열면 트랜잭션이 둘로 갈라지고, 이 스펙 전체가 딛고 선 명제("예약과 특가는 함께 커밋되거나 함께 롤백된다")가 **조용히** 깨집니다. **조용히, 가 핵심입니다 — 단일 스레드 테스트는 전부 초록으로 통과합니다.** 이걸 막는 것이 새 [필수] 항목 D16입니다.

## 3. 도메인 흐름

```
POST /api/reservations  (discounts=[{PROMOTION, "1:2026-09-14"}])   ← F01 소유 입구
  멱등 선점 → 입력 검증                                     ← F01
  [사전 검사 훅] 카운터 DECR, 음수면 거부                    ← ★F02   세션도 락도 없음
  락 획득                                                  ← F01
     ┌─ tx.write() — 트랜잭션 (F01이 연다) ──────────┐
     │ [할인 해석기] 특가 단가 확정                  │ ← ★F02  읽기만
     │ 일반 재고 -1 → Reservation 생성(특가 단가)    │ ← F01
     │            → [생성 훅] 특가 -1 + 사용권 발급   │ ← ★F02  매진이면 예외 → 전체 롤백
     └───────────────────────────────────────────────┘
  커밋 → 락 해제 → 201

취소·만료 시: 전이 UPDATE 1건 성공 → [반납 훅] 특가 +1              ← ★F02  같은 세션 안
```

**해석기가 트랜잭션 안으로 들어왔습니다.** 지난 판본에서는 락 획득 직후 트랜잭션 **밖**에 그렸습니다. `resolve()`가 이제 `session`을 인자로 받으므로 세션이 열린 뒤여야 합니다. **순서 자체는 그대로이고 근거가 강해졌습니다** — 지난 판본에서 문장으로 주장하던 "같은 트랜잭션이라 해석과 차감이 어긋날 걱정이 없다"를 **시그니처가 강제합니다.**

**사전 검사 훅만 세션을 받지 않습니다.** 넷 중 유일합니다. **세션을 안 주는 것이 곧 "여기서 DB를 건드리지 마라"는 선언**이고, 게이트가 Redis만 봐야 한다는 D5의 결정이 타입에 드러납니다.

**특가 예약 전용 엔드포인트는 없습니다.** 일반 예약과 같은 `POST /api/reservations`에 할인 한 줄을 더 실어 보내는 것이고, **F02는 그 흐름에 끼는 네 조각**(사전 검사·해석기·생성 훅·반납 훅)입니다.

**넷 모두 F01이 정의한 `Protocol`이고 구현자는 F02뿐입니다.** F01이 여기에 선을 그었고 저도 그대로 받습니다 — **다섯 번째가 필요해지면 훅을 더 만들 것이 아니라 F02가 자기 진입점을 갖는 쪽을 다시 봅니다.** 그때는 요청 전에 PM을 거칩니다.

`PromotionClaim`의 상태 전이 표입니다. 표에 없는 조합은 전부 거부합니다.

|---|---|---|---|
| USED | RELEASE | RELEASED | — |
| USED | (그 외) | **금지** | — |
| RELEASED | RELEASE | RELEASED | 조용히 성공하되 **재고를 다시 되돌리지 않음** |

## 4. 동시성과 멱등성

**경합 지점과 방어 수단**

| 경합 지점 | 방어 | 검증 방법 |
|---|---|---|
| `promotion_inventory` 단일 행에 수백 요청 | 1차 카운터 게이트(락보다 앞) → 2차 조건부 UPDATE → 3차 CHECK `remaining >= 0` | S1: 재고 10, 200 스레드 → 성공 정확히 10. S2: 게이트 끄고 동일 결과 |
| 같은 행에 차감(-1)과 스케줄러 복원(+1)이 동시 | 상태 전이 조건부 UPDATE가 1건일 때만 복원 + CHECK `remaining <= total_quantity` | S7: 청구 50 + 스케줄러 2인스턴스 동시 |
| 일반 재고 행 (특가 + 일반 예약이 함께) | **F01의 방어를 그대로 씁니다. F02는 자기 경로를 만들지 않습니다** | S3: 일반 재고 5, 특가 20 → 성공 5건 |
| 같은 멱등 키 중복 요청 | Redis 선점 + DB UNIQUE `(user_id, idempotency_key)` | S4: 같은 키 100 스레드 → 사용권 1장 |
| **훅 구현체가 자기 세션을 여는 것** (스택 전환으로 새로 생김) | **주입 차단** — 훅에 `session_factory`도 `TransactionManager`도 주지 않는다. 받을 수 없으면 열 수 없다 | **T22b**(훅 성공 후 호출부 실패), T37·T38(정적 확인) |

**동시성이 아닌 곳에서 온 새 위험이라 따로 씁니다.** 위 마지막 줄은 스레드 경합이 아니라 **구현 실수**입니다. 그런데 결과는 동시성 버그와 똑같습니다 — 데이터가 어긋나고, 재현이 어렵고, 테스트는 초록입니다.

**여기서 중요한 판단이 하나 있었습니다. 원래 이 자리의 증명은 T22("훅이 매진에 예외를 던지면 예약도 롤백된다")였는데, 그 테스트는 판별력이 0입니다.** 세션이 갈라진 구현도 통과합니다 — 구현부가 예외를 던지면 자기 세션도 커밋 전이라 함께 롤백되기 때문입니다. **정상 구현과 결과가 같습니다.**

| 시나리오 | 세션이 갈라진 구현에서 | 잡히나 | 테스트 |
|---|---|---|---|
| 훅이 예외를 던진다 (매진) | 자기 세션도 커밋 전이라 함께 롤백. 정상 구현과 같은 결과 | ❌ | T22 |
| **훅이 성공한 뒤 F01이 실패한다** | **F02는 이미 커밋했다. 특가가 깎이고 사용권 행이 살아남는다** | ✅ | **T22b** |

**증명의 무게를 T22에서 T22b로 옮겼습니다.** 둘 다 씁니다 — T22가 계약의 절반을 지키고, T22b가 세션 분리를 잡습니다. F01이 대응하는 것을 T79b로 넣었습니다.

**1차 방어를 껐을 때 (설계상의 예정 결과)**

게이트를 끄고 S1을 그대로 돌리는 것이 **시나리오 S2**입니다. 기대값은 "성공 건수가 여전히 정확히 재고 수와 같다"입니다. **정확성은 조건부 UPDATE와 CHECK가 책임지고 게이트는 비용만 줄이므로, 이 테스트는 설계상 통과해야 정상입니다.**

**아직 실행하지 않았습니다.** 문서 단계이고 코드가 없습니다. 승인 후 dev-cycle에서 실측값을 보고합니다.

**멱등성**

- 키: `Idempotency-Key` 헤더 → Redis `promotion:idem:{user_id}:{key}`, TTL 24시간
- 재요청: 저장된 결과를 200으로 반환. 재처리하지 않음
- 처리 중 재요청: 409 `REQUEST_IN_PROGRESS`
- **Redis가 죽어도** `uk_claim_idempotency`가 두 번째 사용권 INSERT를 거부합니다. 정확성은 DB가 지키고 Redis는 속도만 담당합니다

## 5. 테스트 결과

| # | 무엇을 잡는가 |

**다섯 다 없어도 나머지 테스트는 전부 초록입니다.** 그리고 다섯이 막는 것은 전부 **아무것도 안 봤는데 통과로 보이는** 상태입니다. 예컨대 T36이 없고 상태가 소문자로 저장되면, F04의 검증 SQL `WHERE status IN ('USED','RELEASED')`가 **0행을 돌려주고 모든 불변식이 통과로 보입니다.**

**Java 판에서 컴파일러와 타입 시스템이 하던 몫이 여기서는 테스트로 내려왔습니다.** 그게 이 전환의 실질 비용이고, 스펙 §9와 분류 문서에 그렇게 적었습니다.

**F03 세션의 발견(PM 경유)으로 셋을 더 넣었습니다.** 설정 값만 노출하면 "값은 `false`인데 컨테이너는 Redis 구현을 물고 있는" 배선 실수를 못 잡습니다. **F02는 게이트가 fail-open이라 반대 방향 사각지대가 하나 더 있습니다** — "켰는데 Redis가 죽어 전부 통과"는 실행 전 확인으로는 잡을 수 없습니다.

|---|---|

## 7. 남은 것

- **구현 코드 전체.** F01이 main에 병합된 뒤에 시작합니다 (관리자 지시 대기)
- **`201` 리비전의 `down_revision` 한 줄.** F01의 마지막 리비전 번호를 기다립니다. **판단이 아니라 사실을 기다리는 것**이고, 리비전 파일의 나머지는 미리 쓸 수 있습니다
- **ADR.** 승인되면 ADR-0020 대역으로 남깁니다. 후보는 D1(구역 분리), D3(훅 기반 단일 트랜잭션), D5(카운터 게이트), **D16(세션 분리 방어)** 넷입니다
- **공유 파일 선행 커밋.** `app/common/errors.py` 코드 2개와 `app/common/config.py` 게이트 스위치를 올립니다 (D12). **순서는 F01 → F03 → F02이고, 예외 클래스와 `error_codes.py` 등록을 같은 커밋에 넣습니다** — F01의 계약 테스트가 미등록 예외를 잡습니다. **F04의 "아는 코드" 목록에 두 코드를 알립니다** (PM 경유) — 목록에 없는 코드가 나가면 그 실패가 전부 `unknown_rejection`으로 분류됩니다
- **설정 노출 기여자 구현.** 탑재 방식은 확정됐고(`RuntimeContributor`, F01이 공유 파일을 먼저 커밋), F02는 구현 하나를 자기 컨테이너에 등록합니다. **F02가 두 번째 노출 경로를 만들면 그 순간 "두 곳에서 따로 읽는" 상태가 됩니다**
- **F04와의 조율.** D2가 승인되면 F04의 특가 스파이크 판정식에 "그날 총 판매량 ≤ 총 객실 수"를 추가할 수 있습니다
- **학습 노트.** `docs/learning/INDEX.md`는 PM 소유라 건드리지 않고 스펙 §14에 후보를 제목만 쌓았습니다

| D8 | **1인 1건 제한을 두지 않는다** | 한 사람이 특가를 쓸어갈 수 있다. 선착순의 공정성 장치가 빠진다 | 순수 선착순으로 가도 괜찮습니까? |
| D10 | 쿠폰 확장 자리를 "예약 1건에 붙는 적용 근거 1행" 형태로 남긴다 | 쿠폰이 안 붙으면 필요보다 한 겹 일반적인 모양이 남는다 | 이 정도로 00 D5의 "확장에 열린 구조" 조건을 충족한 것으로 봐도 괜찮습니까? |
| D14 | **지나간 밤은 팔지 않는다**는 규칙을 F02가 스스로 세운다 (판매 창 ≤ 투숙일 다음날 00:00) | 프로모션 운영 유연성이 준다. MySQL이 CHECK를 거부하면 도메인 검증만 남는다 | F01이 과거 날짜를 막지 않는 것을 F02가 자기 규칙으로 보완해도 괜찮습니까? |
| D18 ★ | **중복 관련 에러 코드를 만들지 않는다** — 같은 키 재요청은 F01이 200으로 처리하고, 다른 키 재청구는 D8상 정상 성공이라 **발동 조건이 남지 않습니다.** F02 UK 발동은 시스템 이상이라 500 + 로그 | D8이 뒤집혀 1인 1건 제한이 생기면 그때 코드를 만들며 공유 파일을 한 번 더 건드리게 된다 | **PM·F01 권고(전용 코드 신설)와 다른 결론입니다.** 갈리는 지점은 "재청구를 막는 규칙이 있는가"이고 D8에 따르면 없습니다. **D8과 함께 판단해주십시오** |

### [참고] — 반대가 없으면 그대로 갑니다

| # | 결정 | 포기한 것 |
|---|---|---|
| D7 | 특가 단가가 **예약과 사용권 양쪽에** 남는다 (예약=청구액, 사용권=할인이 승인한 값) | 같은 숫자가 두 곳에 저장된다 → 일치 검증 테스트(T33)로 막는다 |
| D9 | 같은 (객실타입, 날짜)에 프로모션은 **하나만** (UNIQUE) | 기간이 겹치지 않는 두 특가도 못 만든다 |
| D11 | 생성 훅 안에서 애그리거트 둘을 함께 수정 | 원칙에 예외가 하나 더 는다. **한 트랜잭션이 네 애그리거트를 건드리게 된다** |
| D12 | 공유 파일에 에러 코드 2개 + 게이트 스위치 1개 추가 (한 커밋) | 다른 세션이 rebase해야 한다. F02가 잘리면 죽은 설정이 남는다 |
| D13 | 특가 재고에 **F01의 자연키 복합 PK 패턴**을 그대로 채택 | 대리키가 없어 API 경로가 `/api/promotions/{roomTypeId}/{stayDate}`로 길어진다 |
| D15 | `DiscountRef.reference`를 **`"{roomTypeId}:{stayDate}"`** 형식으로. 형식의 주인은 F02 | 식별자를 문자열로 직렬화해 파싱 코드가 생긴다 |
| D17 ★ | **API 표기는 `camelCase`.** 제 snake_case 제안이 기각됐고, 그 판단이 옳습니다 | 파이썬 코드와 API 응답의 필드 이름이 눈으로 볼 때 다르다. **`ApiModel` 상속을 빠뜨리면 그 엔드포인트만 조용히 `snake_case`로 나간다** |

> **D17은 지난 판본의 유일한 미결이었고, 이제 닫혔습니다.** 제가 든 근거는 "번역 계층이 재현성을 깎는다"였는데, **그 논리는 번역이 여러 곳에 흩어져 손으로 이뤄질 때만 성립합니다.** `ApiModel` 한 곳에서 자동 변환되면 사람이 옮겨 적을 자리가 없어 어긋날 곳도 없습니다. 그리고 **제가 실제로 걱정한 자리는 하나뿐이었습니다** — 부하테스트가 읽는 설정 키. 규칙은 그 한 자리만 정확히 예외로 도려냈습니다(`{ "loadTest": { "PMS_PROMOTION_GATE_ENABLED": false } }`). **일반 규칙을 바꿔 풀 문제가 아니었습니다.**
>
> **그리고 뒤늦게 근거가 하나 더 생겼습니다.** 오늘 **F05 프론트엔드(Next.js)가 범위에 추가**되면서 API를 실제로 소비하는 클라이언트가 생겼고, 그쪽 관례도 `camelCase`입니다. **제 안대로 갔다면 번역 계층이 없어지는 게 아니라 프론트엔드로 옮겨갔을 뿐입니다.**

## 9. 판단이 필요한 지점

### 먼저 — D2가 왜 이 스펙에서 가장 무거운 질문인가

PM 세션과 F04 세션이 **서로 모르는 상태에서 같은 질문에 막혔습니다.** "특가로 팔린 방도 실제 객실을 하나 차지하는가."

F04는 특가 스파이크 시나리오(특가 20실에 3초간 8000건)를 설계하다 이 질문에 걸렸습니다. 답에 따라 **합격 판정식 자체가 달라지기 때문**입니다.

| 특가가 일반 재고를 | F04가 증명할 수 있는 것 |
|---|---|
| 차감하지 않으면 | "특가 성공이 정확히 20건" — 그것뿐입니다 |
| **차감하면 (제 결정)** | "특가 성공이 정확히 20건 **그리고** 그날 총 판매량이 총 객실 수를 넘지 않았다" |

아래쪽이 훨씬 강한 명제이고, **그게 00 §1이 막겠다고 선언한 초과 판매 그 자체입니다.** 반대로 특가를 별도 풀로 두면 같은 방을 특가로도 팔고 일반가로도 파는 셈이 되어, 우리가 만들지 않겠다고 한 오버부킹을 우리 손으로 만드는 것이 됩니다.

### 나머지 판단 지점

| 질문 | 추천 | 근거 |
|---|---|---|
| D1의 두 갈래 — 세 구역(D안) vs 재고 구역에 통합(A안) | **D안(세 구역)** | A안은 F02가 F01 소유 도메인 모듈에 클래스를 넣어야 해서 병렬 작업 규칙의 hard 소유를 정면으로 어깁니다. **A안을 고르시려면 특가 재고 소유권을 F01로 넘기는 feature 분할 변경이 함께 필요합니다** |
| 훅 구현체를 `infrastructure/`에 두는 것 | **그대로** | 훅은 방향으로 보면 들어오는 쪽인데 `presentation`의 정의는 HTTP입니다. **방향이 아니라 하는 일로 갈랐습니다** — 몸통이 전부 SQL·Redis 접근입니다. `application/`에 두면 SQL이 유스케이스 계층으로 올라오고, 그건 규칙이 명시적으로 금지한 것입니다 |
| 게이트도 락처럼 라이브러리 것을 쓸 것인가 | **게이트는 그대로** | 규칙이 겨냥하는 것은 **여러 명령을 엮은 프로토콜**입니다. `DECR` 하나를 부르는 것은 직접 구현이 아니라 사용이고, `redis-py`에 대체할 상위 장치도 없습니다. **락으로 바꾸면 D5가 기각한 것으로 되돌아갑니다** — 락은 줄을 세우고, 선착순에 필요한 것은 일찍 자르기입니다 |
| 카운터 재동기화 주기 | **60초** | 어긋남은 과소 판매 방향이라 급하지 않고, 더 짧게 하면 부하테스트 중에 그 자체가 노이즈가 됩니다 |
| 훅에서 예외가 나면 취소를 실패시킬 것인가 | **실패시킨다** | 취소는 성공했는데 특가만 안 돌아온 상태는 조용히 재고를 잃고 사후 발견이 어렵습니다. **눈에 보이는 실패가 조용한 손실보다 낫습니다** |
| D8(1인 1건 제한)을 넣을 것인가 | **넣지 않음** | `(promotion_id, user_id)` 유니크가 필요한데 취소한 사람이 다시 못 삽니다. MySQL에 부분 유니크가 없어 상태 컬럼을 비우는 우회가 필요하고 그러면 반납 이력이 지워집니다 |
