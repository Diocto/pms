# [F02] 승인 요청: 스펙 검토

- 날짜: 2026-08-15
- 단계: 스펙 승인
- 판정 요청: 승인

## 한눈에 보기

- **무엇을 했는가:** F02(선착순 특가) 착수 브리핑과 스펙을 썼습니다. 코드는 한 줄도 쓰지 않았습니다 (F01 병합 전이므로).
- **핵심 판단:** 특가는 일반 재고에서 떼어낸 몫으로 봅니다. 그래서 특가 예약은 특가 재고와 일반 재고를 **둘 다** 줄입니다. 대신 한 트랜잭션으로 묶지 않고 **재고를 먼저 잡고(홀드) 예약을 만든 뒤 확정**하는 2단계로 처리합니다.
- **확인이 필요한 것:** 결정 14개를 등급으로 나눴습니다. **[필수] 4개(D1·D2·D3·D5)만 보셔도 됩니다.** 나머지 10개는 반대가 없으면 그대로 갑니다.
- **리스크:** F01 스펙이 아직 승인 전입니다. F01에 의존하는 서술 12개를 스펙 §13에 모으고, 각각 "반대로 나오면 얼마나 바뀌는지"를 적어뒀습니다. F01 세션이 전달한 확정본으로 이 중 **5개가 이미 해소**됐고, **설계가 흔들리는 항목은 없습니다.** 남은 것 중 1순위는 V4(주문서에 특가 단가를 넘길 자리가 있는가)입니다.

## 1. 무엇을 만들었는가

**문제.** F01은 여러 날짜에 흩어진 재고 행을 다룹니다. 요청마다 건드리는 행이 조금씩 다릅니다. 특가는 다릅니다. 오픈 시각에 수백 요청이 **재고 행 딱 하나**로 몰립니다. 게다가 그 트래픽의 대부분은 매진 뒤에 들어오는, 어차피 실패할 요청입니다. 이것들이 DB 커넥션을 다 잡아먹으면 특가와 무관한 일반 예약까지 같이 죽습니다.

**해법.** 세 겹으로 막습니다.

1. Redis 잔여 카운터로 **매진 뒤 요청을 DB에 닿기 전에 잘라냅니다.** 줄을 세우는 게 아니라 일찍 자릅니다.
2. DB 조건부 UPDATE 한 줄(`remaining >= 1`)로 초과 판매를 막습니다. 읽고-판단하고-쓰는 세 단계를 한 단계로 줄입니다.
3. DB CHECK 제약(`0 <= remaining <= total_quantity`)이 최후 방어선입니다.

**1번을 껐을 때도 결과가 같다는 것**을 동시성 테스트로 증명하는 것이 이 feature의 핵심 검증입니다 (시나리오 S2).

## 3. 도메인 흐름

```
멱등 키 선점(Redis) → 카운터 게이트(DECR)
  → [TX1 · 프로모션 구역] 판매 창 검증 → 특가 재고 -1 → 홀드 생성(HELD)
  → [TX2 · F01 소유]     일반 재고 -1 → 예약 생성(PENDING)
  → [TX3 · 프로모션 구역] 홀드 확정(CLAIMED, reservation_id 기록)
  → 멱등 결과 저장 → 201
```

TX2가 실패하면 TX3 대신 홀드를 반납(`RELEASED`)하고 특가 재고를 되돌립니다.

`PromotionClaim`의 상태 전이 표입니다. 표에 없는 조합은 전부 거부합니다.

| 현재 | 이벤트 | 다음 | 멱등 처리 |
|---|---|---|---|
| HELD | ATTACH | CLAIMED | 이미 CLAIMED이고 같은 예약이면 성공 처리, 다른 예약이면 거부 |
| HELD | RELEASE | RELEASED | 이미 RELEASED면 성공 처리 (재고는 다시 안 되돌림) |
| CLAIMED | RELEASE | RELEASED | 위와 같음 |
| CLAIMED | ATTACH | **금지** | — |
| RELEASED | ATTACH | **금지** | — |
| RELEASED | RELEASE | RELEASED | 멱등 |

## 4. 동시성과 멱등성

**경합 지점과 방어 수단**

| 경합 지점 | 방어 | 검증 방법 |
|---|---|---|
| `promotion_inventory` 단일 행에 수백 요청 | 1차 Redis 카운터 게이트 → 2차 조건부 UPDATE → 3차 CHECK `remaining >= 0` | S1: 재고 10, 200 스레드 → 성공 정확히 10 |
| 같은 행에 차감(-1)과 스케줄러 복원(+1)이 동시 | 상태 전이 조건부 UPDATE가 1건일 때만 복원 + CHECK `remaining <= total_quantity` | S7: 청구 50 + 스케줄러 2인스턴스 동시 |
| 일반 재고 행 (특가 + 일반 예약이 함께) | **F01의 방어를 그대로 씁니다. F02는 자기 경로를 만들지 않습니다** | S3: 일반 재고 5, 특가 20 → 성공 5건 |
| 같은 멱등 키 중복 요청 | Redis 선점 + DB UNIQUE `(user_id, idempotency_key)` | S4: 같은 키 100 스레드 → 사용권 1장 |
| 스케줄러 인스턴스 둘이 같은 건 반납 | 상태 조건부 UPDATE + CHECK 상한 | 스케줄러 통합 테스트 |

**1차 방어선을 껐을 때 (설계상의 예정 결과)**

`promotion.gate.enabled=false`로 카운터 게이트를 끄고 S1을 그대로 돌리는 것이 **시나리오 S2**입니다. 기대값은 "성공 건수가 여전히 정확히 재고 수와 같다"이며, 이것이 Redis 장애 시의 동작과 같습니다.

**아직 실행하지 않았습니다.** 문서 단계이고 코드가 없습니다. 승인 후 dev-cycle에서 실측값을 보고합니다.

**멱등성**

- 키: `Idempotency-Key` 헤더 → Redis `promotion:idem:{userId}:{key}`, TTL 24시간
- 재요청: 저장된 결과를 200으로 반환. 재처리하지 않음
- 처리 중 재요청: 409 `REQUEST_IN_PROGRESS`
- **Redis가 죽어도** `uk_claim_idempotency`가 두 번째 사용권 INSERT를 거부합니다. 정확성은 DB가 지키고 Redis는 속도만 담당합니다

## 5. 테스트 결과

**없습니다.** 이번 단계는 스펙 작성이며 코드를 쓰지 않았습니다. 승인 없이 구현을 시작하지 않는다는 규칙에 따른 것입니다.

대신 **승인 대기 중에 테스트 설계를 미리 끝내 뒀습니다.** 스펙 §9에 있습니다.

- **9-1 동시성 시나리오 8개(S1~S8).** 각각 스레드 수·재고 수·기대 결과를 숫자로 적었고, 그중 셋(S1/S2 초과 판매, S4 유니크 제약, S7 이중 복원)은 준비·실행·검증·**실패하면 무슨 뜻인가**까지 상세 설계했습니다
- **9-2 TDD 실패 테스트 목록 27개(T1~T27).** 승인 직후 빨간 테스트부터 쓸 순서입니다
- **9-3 F04에 넘길 특가 시드 값.** F01 시드 계약 확정본에 맞춰 절대 날짜로 확정했습니다 — P1(스탠다드 100실, 2026-09-14, 20실 한정, 75,000원), P2(같은 타입, 09-15, 오픈 순간 재현용), P3(디럭스, 09-16, 이미 종료). **P1을 100실짜리 타입에 연 것이 중요합니다.** 20실짜리 타입에 20실 특가를 열면 특가가 그날 일반 재고를 통째로 먹어서, 부하테스트가 재는 것이 특가 경합인지 일반 재고 고갈인지 구분되지 않습니다

## 7. 남은 것

- **구현 코드 전체.** F01이 main에 병합된 뒤에 시작합니다 (관리자 지시 대기)
- **ADR.** 스펙이 승인되면 ADR-0020 대역으로 남깁니다. 후보는 D1(구역 분리), D3(홀드 2단계), D5(카운터 게이트) 셋입니다
- **F01 스펙 대조.** F01 승인 직후 스펙 §13 표를 훑습니다. 12개 중 5개(V1·V2·V5·V6·V12)는 F01 세션이 전달한 확정본으로 이미 해소했습니다. 남은 7개 중 **V4(주문서에 특가 단가를 넘길 자리가 있는가)를 1순위로 봅니다.** 코드 변경은 작지만 응답 필드의 의미와 제출 문서의 정직성 기술이 함께 움직이는 항목이라서입니다
- **V12는 닫혔고, 그 과정에서 실제 지뢰를 하나 제거했습니다.** F01 시드가 `CURDATE()` 기준이라 실행 시각에 따라 재고 날짜가 달라지는 상태였습니다. 특가 투숙일이 재고 범위를 벗어나면 전건 실패하는데 **응답이 409 재고부족이라 정상 동작처럼 보입니다.** 같은 문제가 F03·F04에도 있어 F01 스펙에 "시드 데이터 계약" 절이 생겼고, **고정 절대 날짜 2026-08-01~10-29로 확정**됐습니다. 되살아나지 않도록 회귀 테스트(T16c)를 목록에 넣었습니다
- **F04와의 조율.** D2가 승인되면 F04의 특가 스파이크 판정식에 "그날 총 판매량 ≤ 총 객실 수"를 추가할 수 있습니다. PM 경유로 F04에 알려야 합니다
- **학습 노트.** `docs/learning/INDEX.md`는 PM 소유라 건드리지 않고 스펙 §14에 후보 7건을 제목만 쌓았습니다

## 9. 판단이 필요한 지점

### 먼저 — D2가 왜 이 스펙에서 가장 무거운 질문인가

PM 세션과 F04 세션이 **서로 모르는 상태에서 같은 질문에 막혔습니다.** "특가로 팔린 방도 실제 객실을 하나 차지하는가."

F04는 특가 스파이크 시나리오(특가 20실에 3초간 8000건)를 설계하다 이 질문에 걸렸습니다. 답에 따라 **합격 판정식 자체가 달라지기 때문**입니다.

| 특가가 일반 재고를 | F04가 증명할 수 있는 것 |
|---|---|
| 차감하지 않으면 | "특가 성공이 정확히 20건" — 그것뿐입니다 |
| **차감하면 (제 결정)** | "특가 성공이 정확히 20건 **그리고** 그날 총 판매량이 총 객실 수를 넘지 않았다" |

아래쪽이 훨씬 강한 명제이고, **그게 00 §1이 막겠다고 선언한 초과 판매 그 자체입니다.** 스파이크 한가운데서도 재고 불변식이 지켜졌다는 것을 수치로 보이는 것이 이 과제의 목표라면, D2는 그 목표에 직접 연결됩니다.

반대로 특가를 별도 풀로 두면 같은 방을 특가로도 팔고 일반가로도 파는 셈이 되어, 우리가 만들지 않겠다고 한 오버부킹을 우리 손으로 만드는 것이 됩니다.

### 나머지 판단 지점

| 질문 | 추천 | 근거 |
|---|---|---|
| D1의 두 갈래 — 세 구역(D안) vs 재고 구역에 통합(A안) | **D안(세 구역)** | A안은 F02가 F01 소유 도메인 패키지에 클래스를 넣어야 해서 병렬 작업 규칙의 hard 소유를 정면으로 어깁니다. 그리고 F02가 절단될 때(00 D4 3순위) F01 도메인에서 특가 코드를 떼어내야 합니다. **A안을 고르시려면 특가 재고 소유권을 F01로 넘기는 feature 분할 변경이 함께 필요합니다** |
