# [F03] 승인 요청: 개발 완료

- 날짜: 2026-08-16
- 단계: 개발 완료 승인
- 판정 요청: 승인

---

## 한눈에 보기

- 무엇을 했는가: 가용 객실 검색 API(`GET /api/availability`)를 스펙 그대로 구현했다. 검색·빈 결과 사유 판정·10초 캐시·장애 시 DB 직행까지.
- 핵심 판단: 검색은 잠그지 않고 읽는다(ADR-0030). 낡은 화면의 대가는 예약 시점의 거절(409)로 받고, 그 흐름 전체를 테스트로 증명했다.
- 확인이 필요한 것: 결정 검토란 [확인] 3건. 판단 필요 지점은 없다.
- 리스크: 검색 결과가 최대 10초 낡을 수 있다(스펙 승인 사항). 그 상한 자체를 테스트가 지킨다.

## 1. 무엇을 만들었는가

여러 사람이 같은 방을 두고 검색·예약을 동시에 하는 상황에서, 검색이 **빠르고 죽지 않으면서도 거짓말의 상한이 있게** 만들었다. 결과가 비면 이유(매진 / 판매 전 / 맞는 방 없음)를 구분해 알려주고, 캐시가 죽어도 검색은 계속 된다. 프런트(F05)가 이 API로 실제 예약 흐름을 이미 돌렸다(어긋남 0건).

## 2. 코드 구조

```
app/inventory/query/            (F03 소유, 조회 전용 — 재고를 쓰는 코드 없음)
├── application/  commands.py(투숙기간 VO·판정), ports.py(포트 2종), usecases/(검색 흐름)
├── infrastructure/  persistence.py(집계·진단 SQL), cache.py(Redis·NoOp)
├── presentation/  router.py(라우터), schemas.py(응답), actuator.py(설정 노출 기여자)
└── container.py  (조립 — 캐시 켬/끔을 설정 하나로)
```

레이어 위반 없음(2회차 리뷰까지 확인). 공유 파일은 세 곳에 자기 줄만 더했다(config·containers·main). F01 소유 모듈은 import하지 않고 SQL로만 읽는다.

## 3. 도메인 흐름

```
요청 → 기간 검증(과거·역전·31박 거절) → 캐시 조회 → 히트면 즉시 응답(출처 CACHE)
     → 미스면 DB 집계 1회 → 비면 같은 스냅샷에서 진단 1회 → 캐시 적재 → 응답(출처 DB)
```

빈 결과 판정 순서: 호텔 없음(404) → 맞는 방 없음 → 판매 전 → 매진.

## 4. 동시성과 멱등성

검색은 쓰기가 없어 멱등이다. 경합은 "남이 쓰는 동안 읽는 것"에서 온다.

| 경합 지점 | 방어 | 검증 |
|---|---|---|
| 조회 폭주 | 잠금 없는 스냅샷 읽기 + 캐시 | C1: 100 스레드, 응답 전부 동일·누락 0 |
| 읽는 중에 재고가 0으로 | 단일 집계 쿼리(한 시점 스냅샷) | C2: 검색 50 + 갱신 1 동시, 중간값 0건 |
| 캐시의 낡은 값 | 만료 10초가 상한 | C3: 지우기 전후 옛 값/새 값 경계 확인 |
| Redis 죽음 | 실패를 삼키고 DB 직행 + 경고 로그 | C5: 정지 확인 후 50회 전부 200 |
| 낡은 화면 → 예약 | 예약 시점 조건부 차감이 거절 | C6: 검색→409→재검색에서 방 소멸 확인 |

1차 방어선(캐시)을 끄면: C1 캐시 off 회차, C4(켬/끔 결과 동등성 20조건)가 캐시 없이도 같은 답임을 증명한다.

## 6. 리뷰 이력

| 라운드 | 심각 | 중요 | 결과 |
|---|---|---|---|
| 1회차 | 3 | 4 | 재작업 → 전부 반영 (`docs/reviews/F03-1회차-리뷰.md`) |
| 2회차 | 0 | 1 | 통과. 중요 1건(테스트 판별력)은 라운드 안에서 수정 (`F03-2회차-리뷰.md`) |

1회차 심각: 총액에 객실 수 곱 누락(검색가와 예약 청구액이 2실부터 어긋나는 버그), roomCount 필수 오구현, C2 테스트에 실제 경합 없음. 셋 다 실물 재검증까지 마쳤다.

## 7. 남은 것

- 캐시 무효화를 예약 경로와 연결하지 않았다(스펙 D6·ADR-0031, 승인된 유예). 자리는 있다.
- fail-open의 예외 범위 좁히기는 반영하지 않았다. 목록에 없는 예외가 검색을 죽이는 쪽이 더 나쁘다는 사유를 리뷰 문서에 남겼고, 2회차 리뷰어가 타당 판정했다.
- 부하 검증(F04)과 캐시 적중률 측정은 F03 범위 밖이다.

## 8. 결정 검토란

개발 구간에서 작성자가 내린 결정. 스펙의 D1~D16은 스펙 승인 때 확정됐으므로 다시 묻지 않는다.

| 번호 | 등급 | 결정 | 확인 질문 |
|---|---|---|---|
| DV1 | [확인] | C1 동시성 테스트를 100 동시 대신 "한랭 50+온기 50 두 물결"로 바꿨다. 100 동시는 전원이 적재 전에 조회를 지나 멀쩡한 코드가 실패로 찍히는 것을 실측했다. 스펙 9절을 구현에 맞춰 정정 | 스펙과 구현이 달라진 것을 정정으로 닫는 방식에 동의합니까? |
| DV2 | [확인] | C2는 확률(스레드 수 늘리기) 대신 결정성 설계로 — 갱신은 첫 검색 완료 후에만 커밋, 각 검색은 0을 볼 때까지 반복. 경합은 실재하면서 흔들림 없이 재현된다 | 동시성 증명을 이 방식으로 받는 것에 동의합니까? |
| DV3 | [확인] | 캐시 실패는 유스케이스가 잡는다(스펙 문구는 "어댑터"였다 → 정정). 어댑터가 삼키면 운영 조작 실패까지 조용해진다 | 문구 정정으로 닫는 것에 동의합니까? |
| DV4 | [참고] | main 수신은 되감기(rebase) 금지 규칙에 따라 병합 커밋으로 받았다 | — |
