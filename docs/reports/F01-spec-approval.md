## 한눈에 보기

예약의 전 생명주기(생성·확정·취소·만료·체크인아웃·노쇼)와 일별 재고 차감·복원을 설계했습니다. 폐기된 초안은 쓰지 않고 새로 썼고, 업계 정합성 검토의 **반영 후보 7개를 전부 채택**했습니다.

**반드시 판단하셔야 할 것은 5개(D1·D4·D7·D10·D17)입니다.** 뒤집히면 스펙을 다시 쓰거나 다른 세션 산출물이 바뀝니다. 나머지 14개는 동의 여부만 확인하면 됩니다.

승인되면 곧바로 (1) 공유 파일 2건을 선행 커밋으로 `main`에 올리고, (2) TDD 개발 사이클에 들어갑니다. **F02·F03·F04 세 세션이 이 승인을 기다리고 있습니다.**

## 1. 무엇을 만들기로 했는가

동시성 방어의 축을 **조건부 UPDATE 세 줄**로 좁혔습니다. 재고 차감, 상태 전이, 재고 복원. 읽고-판단하고-쓰는 세 단계를 SQL 한 줄로 줄이면 그 사이에 끼어들 틈이 없어집니다.

```sql
UPDATE room_daily_inventory SET remaining = remaining - :count
 WHERE room_type_id = :roomTypeId AND stay_date = :date AND remaining >= :count
```

가장 중요한 판단은 **재고 복원을 상태 전이의 "결과"로 묶은 것**입니다. 재고를 되돌리려는 요청은 셋(취소·결제 실패·만료)인데 되돌릴 기회는 한 번뿐입니다. 그 "한 번"을 상태 전이 UPDATE가 정합니다 — 상태를 바꾸는 데 성공한 하나만 갱신 행 수 1을 받고, 나머지는 0을 받아 **복원 코드에 아예 들어가지 못합니다.**

셋째 방어선은 `CHECK remaining <= total_quantity`입니다. 하한(`>= 0`)은 다들 챙기지만 **상한이 없으면 이중 복원이 아무 신호 없이 성공합니다.** 팔 수 있는 방보다 많은 방이 생기는데 아무도 모릅니다.

→ 상세: 스펙 7.2절 / 상태 전이 표(49칸): 스펙 4.3절 / DB 설계: 스펙 5절

## 2. 불리한 것 먼저

- **테스트를 하나도 돌리지 않았습니다.** 스펙 단계라 코드 변경이 0건입니다(`git status`상 `src/` 변경 없음). 4절의 수치는 전부 *기대값*이며 개발 완료 보고서에서 실측으로 대체합니다.
- **레이어 규칙 예외 1건.** 예약 생성이 재고·예약 두 애그리거트를 한 트랜잭션에서 고칩니다. `ddd.md` 원칙 위반이지만 **00 문서 D6에서 승인된 예외**이고, 스펙에 예외임을 명시했습니다.
- **닫지 못한 틈 1건.** 모의 결제 성공 직후 크래시하면 결제만 되고 예약은 `PENDING`으로 남아 만료됩니다. 이번에 닫지 않고 한계로 문서화했습니다(D5). 실 PG라면 결제 원장 + 정산 배치가 필요합니다.
- **D4(`NO_SHOW`)는 00 문서의 승인된 전이 표를 넓히는 유일한 항목**입니다. 지금 그 표에 `NO_SHOW`가 없습니다.

## 3. 동시성 방어 요약

| 경합 | 방어 | 증명 |
|---|---|---|
| 같은 재고 행 (초과 판매) | 조건부 UPDATE + CHECK `>= 0` | K1: 잔여 10 / 100스레드 → 성공 정확히 10 |
| 여러 재고 행 (데드락) | 날짜 오름차순 전순서 고정 | K8: 반대 순서 요청 → 데드락 0건 |
| 같은 멱등 키 | Redis `SET NX` + DB `UNIQUE` | K3: 같은 키 50 동시 → 예약 1건 |
| 확정↔취소↔만료 (이중 복원) | 복원을 전이 성공의 결과로 묶음 + CHECK `<= total_quantity` | K6·K10: 복원 1회, 이력 줄 1개 |

**1차 방어선을 끈 상태의 증명이 핵심입니다.** `pms.lock.enabled=false`로 분산락을 통째로 끄고 K1과 같은 조건으로 돌려(K2), 여전히 성공 10건·잔여 0이어야 합니다. 멱등성도 같은 방식으로 Redis를 무력화하고 DB 유니크 제약만으로 검증합니다(K4).

동시성 시나리오는 10개(K1~K10)입니다. → 스펙 9절

## 4. 결정 검토란

### [필수] 5개 — 먼저 봐주십시오

#### D1. 인원수 필드를 넣고 정원을 검증한다 (반영 후보 1) · 하위 영향: F04

- **결정:** `guest_count` 컬럼 + 생성 시 `guestCount ≤ capacity × roomCount` 검증. 위반은 400.
- **이유:** 00 문서 서사가 "인원으로 검색"인데 인원이 저장되지 않으면 `capacity`가 죽은 컬럼이 됩니다. 그리고 **인원 없이 쌓인 예약 행은 사후 복구가 불가능합니다.**
- **트레이드오프:** 동시성과 무관한 필드·검증·실패 분기가 늘어납니다.
- **대안:** 인원을 아예 빼기(00 서사와 F03 검색이 무너짐), 받되 검증 안 하기(죽은 데이터).
- **확인 질문:** 인원수 필드와 정원 검증을 넣어도 괜찮습니까?

#### D4. `NO_SHOW` 상태 추가 + 체크인 상한 (반영 후보 4) · 하위 영향: 00 문서, F04

- **결정:** `CONFIRMED --NO_SHOW--> NO_SHOW` 전이 추가(하루 주기 스케줄러 + 수동 트리거), 체크인 조건에 `today < checkOut` 상한.
- **이유:** 지금 `CONFIRMED`에서 나가는 출구가 취소와 체크인뿐입니다. **손님이 안 오면 그 예약은 영원히 `CONFIRMED`로 남습니다.** 상태머신이 간판인데 종료 상태에 도달 못 하는 경로가 있는 것은 스스로 만든 약점입니다. 체크인 상한은 별개 구멍입니다 — 없으면 체크아웃일이 지난 예약도 체크인됩니다.
- **트레이드오프:** 상태 6→7개, 전이 표 36→49칸, 스케줄러 추가. **하루 일정에서 순수한 추가 작업입니다.**
- **대안:** 상한만 넣고 `NO_SHOW`는 빼기(기간 지난 `CONFIRMED`가 영원히 남음), 노쇼를 `CANCELLED`로(요금 처리가 정반대라 뭉치면 되돌릴 수 없음).
- **확인 질문:** 일정 부담을 감수하고 넣어도 괜찮습니까? 승인 시 **00 문서 §4 전이 표 갱신을 PM 세션에 맡겨도** 괜찮습니까?

#### D7. 외부 식별자를 무작위 확인번호로 (반영 후보 7) · 하위 영향: F04 (경로 전면)

- **결정:** `confirmation_code`(12자 무작위, UK)를 API 경로와 응답에 쓰고, auto-increment `id`는 내부 전용.
- **이유:** 연속 번호를 노출하면 예약 총량 추정과 열거 조회가 가능합니다. 그리고 **식별자 형식 변경은 API를 파괴하는 변경이라 나중에는 못 고칩니다.** 비용은 컬럼 1개 + UK 1개입니다.
- **트레이드오프:** 모든 조회가 UK 인덱스를 한 번 더 탑니다. 코드 생성·충돌 재시도 로직이 붙습니다. **F04가 이 경로로 k6 스크립트를 이미 쓰고 있어, 뒤집으면 모든 경로와 응답 파싱이 바뀝니다.**
- **대안:** `id` 노출(열거 가능, 되돌릴 수 없음), UUIDv4(36자라 전화로 못 부름).
- **확인 질문:** F04 스크립트가 문자열 코드를 다뤄야 하더라도, 무작위 확인번호를 외부 식별자로 써도 괜찮습니까?

#### D10. 분산락을 `(객실타입, 날짜)` 단위로 여러 개 잡는다

- **결정:** 락 키를 `lock:inventory:{roomTypeId}:{stayDate}`로. 3박이면 락 3개를 **날짜 오름차순** 획득, 실패 시 역순 전체 해제 후 503.
- **이유:** 객실타입 단위 락 하나면 단순하지만 **겹치지 않는 날짜 예약까지 전부 직렬화**되어, 인기 객실에 트래픽이 몰리면 처리량이 락 하나의 속도로 수렴합니다. 부하테스트로 보여줄 수치가 사라집니다. 데드락은 전순서 고정으로 막습니다.
- **트레이드오프:** 다중 락 획득·해제·부분 실패 롤백 로직이 필요합니다. Redis 왕복이 날짜 수만큼 늘고, **정렬을 한 곳이라도 빠뜨리면 데드락**이 나는데 재현이 어려운 버그입니다.
- **대안:** 객실타입 단위 단일 락(직렬화), 기간 전체를 한 키로(겹치는 기간과 상호 배제 안 됨), 락 없이 조건부 UPDATE만(다층 방어 선언과 어긋나고 락 유무 비교 실험 불가).
- **확인 질문:** 락 어댑터 복잡도를 감수하고 날짜 단위 다중 락으로 가도 괜찮습니까?

#### D17. 분산락 On/Off 스위치를 운영 프로파일에서도 연다 (F04 요청)

- **결정:** `pms.lock.enabled`(기본 `true`)로 분산락을 끌 수 있게. **테스트 프로파일에 한정하지 않습니다.** 꺼진 채 기동하면 WARN 로그.
- **이유:** `coding-rules.md`가 이미 "1차 방어선을 껐을 때도 불변식이 지켜지는지 증명한다"를 요구합니다. **스위치가 없으면 K2를 못 돌리고, 그 명제를 증명할 수 없습니다.** 프로파일로 제한하지 않는 이유는 F04가 운영 프로파일에 부하를 걸기 때문이고, 거기서 락 유무를 비교 못 하면 가장 흥미로운 수치가 사라집니다.
- **트레이드오프:** 설정 실수로 운영에서 꺼질 수 있습니다(데이터는 2·3차 방어로 안전하나 처리량 저하). 락 꺼진 경로가 별도 테스트 대상이 됩니다.
- **대안:** 테스트 프로파일 한정(F04 비교 실험 불가), 스위치 없이 가짜 락 빈 주입(**통합 동시성 테스트와 부하테스트에서는 못 씀** — 정작 증명이 필요한 계층).
- **확인 질문:** 운영에서도 끌 수 있게 두고, 꺼진 채 기동 시 경고 로그를 남기는 것으로 괜찮습니까?

| D17을 운영에서 켜는 게 위험하지 않은가? | **위험하지 않다고 봅니다** | 락을 꺼도 안전하다는 것이 우리 설계의 주장이고 K2가 그걸 증명합니다. 주장이 참이면 운영에서 꺼지는 것은 사고가 아니라 성능 저하입니다. 거짓이면 프로파일로 감출 게 아니라 설계를 고쳐야 합니다 |
