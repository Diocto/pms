# [F04] 컨펌 요청: 검색 실험 2종 (S8·L5)

- 날짜: 2026-08-16
- 단계: 실행 전 컨펌 (본편 7종은 승인받아 완주함 — 결과는 `docs/load-test/results/`)
- 판정 요청: **"이대로 돌려도 된다" / "이건 빼고 돌려라" / 재작업**

## 한눈에 보기

- 무엇을 돌리나: 검색(객실 찾기)이 붙은 실험 2종. F03의 검색 기능이 방금 본선에 합쳐져 이제 돌릴 수 있다
- 무엇이 나오나: ① 검색 결과 임시 저장(캐시)을 켰을 때 예약까지 편해지는가의 수치 ② 임시 저장이 일제히 만료되는 순간 DB에 몰리는 파도의 크기
- 전부 돌리면: 약 50분. 리스크 없음 — 로컬 전용, 실험 전 초기화 스크립트가 로컬이 아니면 스스로 멈춘다

## 1. 회차마다 무엇을 알게 되고, 무엇이 나와야 통과인가

| 순서 | 실험 | 이걸 돌리면 알게 되는 것 | 통과 조건 | 소요 |
|---|---|---|---|---|
| 1 | S8 검색 폭주 속 예약 (임시 저장 켬/끔 각 1회) | 검색이 초당 500번 몰릴 때, 임시 저장이 검색만 빠르게 하는 게 아니라 **예약까지 편하게 하는가** (검색이 DB를 덜 잡는 만큼 예약이 덜 밀리는가) | 양쪽 모두: 서버 오류 0, 예약 정합성 유지. 켬/끔의 차이는 합격선이 아니라 **측정값** | 30분 |
| 2 | L5 만료 파도 관찰 | 인기 검색 조건의 임시 저장이 만료되는 순간, 대기하던 요청이 DB로 몇 건이나 한꺼번에 몰리는가 | **합격·불합격 없음.** 방어 장치를 넣을지 말지는 F03이 이 측정값을 보고 판단한다 (F03 스펙 D10) | 20분 |

- S8에서 "검색에는 있었는데 예약하니 없다"(낡은 결과의 헛걸음)는 실패가 아니라 F03이 설계한 정상 흐름이므로, 오류가 아닌 관측 지표로 따로 센다.
- 뺄 수 있는 것: L5 (측정 전용이라 증명이 걸려 있지 않다). S8은 명제 (라)의 캐시 축이라 빼면 대조 증명이 락 하나로 줄어든다.

## 2. 이 실험으로 알 수 없는 것 (리포트에도 같은 문장으로 적는다)

- 한 대의 컴퓨터에서 앱·DB·부하 도구가 같이 돌므로, 절대 수치가 아니라 **켬/끔의 상대 비교**만 의미가 있다.
- 낡은 결과를 얼마나 오래 보여줄지(만료 시간 10초)의 최적값 — 측정은 현재 설정 하나에서만 한다.
- 실제 사용자의 검색 조건 분포 — 실험은 조건을 일부러 한 점(L5) 또는 좁은 대역(S8)에 모은다.

## 3. 선행 작업 (승인과 무관하게 실행 전에 끝내야 하는 것)

1. 본선(main)을 F04 작업 가지에 합친다 — F03 검색 코드와 F01의 동시 기동 결함 수정(D34)이 들어온다.
2. 초기화 스크립트에 **임시 저장 스위치 실측 확인**을 넣는다. 락 대조 때와 같은 규칙 — 껐다고 생각했는데 켜져 있으면 두 회차가 같은 조건이 되므로, 스위치 값을 읽어 기대와 다르면 부하를 넣지 않고 멈춘다.
3. 두 회차의 워커 수(4)를 같게 고정하고 기록한다.
