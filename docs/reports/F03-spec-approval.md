# [F03] 승인 요청: 스펙 검토

- 날짜: 2026-08-15
- 단계: 스펙 승인
- 판정 요청: 승인 / 조건부 승인 / 재작업
- 대상 문서: `docs/spec/F03-가용-객실-검색.md`, `docs/briefings/F03.md`, `docs/spec/F03-검색-API-계약.md`

---

## 한눈에 보기

- **무엇을 했는가:** 가용 객실 검색(UC-1) 스펙을 썼습니다. 착수 브리핑과 F04에 넘길 API 계약 문서도 함께 만들었습니다. 코드는 한 줄도 쓰지 않았습니다(F01 병합 전).
- **핵심 판단:** 검색은 **정확성을 책임지지 않습니다.** 재고의 진실은 예약 시점의 조건부 UPDATE(F01)가 정하고, 검색은 후보만 제시합니다. 그래서 검색이 낡아 예약이 409로 실패하는 것을 **버그가 아니라 정상 흐름으로 설계**했고, 그 경로를 시퀀스 다이어그램과 클라이언트 계약으로 문서화했습니다.
- **확인이 필요한 것:** D 항목 13개. 특히 D3(잠금 읽기를 쓰지 않음), D5(캐시 단위와 TTL 10초), D6(이벤트 무효화를 자리만 남기고 뺌), D9(빈 결과의 이유를 3가지로 구분)입니다.
- **리스크:** 캐시 무효화가 TTL 만료에만 의존합니다. 즉 **재고가 바뀌어도 최대 10초간 옛 결과가 보이는 것이 기본 동작**입니다. 이것이 이 설계에서 가장 불리한 사실이며, 아래 1절에서 먼저 밝힙니다.

---

## 0. 불리한 것 먼저

승인 판단에 필요한 약점을 먼저 적습니다.

| # | 불리한 사실 | 왜 이렇게 됐나 | 감수하는 근거 |
|---|---|---|---|
| 1 | **재고 변경을 감지하는 수단이 없다.** 무효화가 TTL 만료에만 의존하므로, 재고가 바뀌어도 최대 10초 동안 옛 결과가 보이는 것이 사고가 아니라 기본 동작이다 | F01의 재고 차감 코드에 훅을 넣을 수 없다(소유 범위). 넣으려면 F01 수정 승인이 필요하고, 절단 1순위인 캐시에 F01을 결합시키게 된다 | 이벤트 무효화를 붙여도 **정합성 보장 수준은 그대로다**. 개선되는 것은 낡음의 평균 지속 시간이지 "낡을 수 있다"는 사실이 아니다. 그리고 낡음의 최악은 예약 실패이지 초과 판매가 아니다 (D6) |
| 2 | **검색 결과의 정확성을 스스로 보장하지 않는다.** 잠금 읽기를 쓰지 않기로 했고, `fresh=true`조차 예약 성공을 약속하지 않는다 | 검색이 재고 행에 락을 걸면 이 프로젝트의 심장인 재고 차감이 조회 트래픽 때문에 느려진다 | 락을 걸어도 얻는 것이 없다. 응답 직후 재고는 또 바뀐다 (D3) |
| 3 | **F03이 Flyway 대역을 한 개도 쓰지 않는다.** 인덱스 튜닝 산출물이 없다 | F01이 자연키 복합 PK를 확정해 클러스터드 인덱스가 검색 쿼리를 이미 커버한다 | 중복 인덱스는 F01의 재고 UPDATE에 유지 비용만 얹는다. **안 만드는 것이 옳은 결론이지만, 보여줄 산출물이 줄어드는 것은 사실이다** (D8) |
| 4 | **캐시 스탬피드 방어가 없다.** 인기 날짜의 TTL 만료 순간 DB로 부하가 몰릴 수 있다 | 절단 1순위인 캐시 위에 방어 장치를 얹는 것은 순서가 틀렸다고 판단했다 | F04 부하테스트(L5 시나리오)로 실제 크기를 먼저 잰다. 측정 없는 최적화를 하지 않는다 (D10) |
| 5 | **`salesOpenUntil`은 시드 데이터에서 추론한 값이다.** 진짜 판매 정책이 아니다 | 00 D1로 관리자 기능을 뺐기 때문에 "판매 기간"이라는 개념이 도메인에 없다 | 한계를 문서에 명시했다. 실제 서비스라면 객실타입에 판매 시작·종료일 컬럼이 있어야 한다 (D9) |
| 6 | **미확정 의존이 하나 남았다.** A8(업무 시간대 Asia/Seoul, `Clock` 주입) | F01 회신에 타임존 고정 여부가 없었다 | 영향이 "판정 기준 존 한 줄"이라 승인을 막지 않는다고 판단했다. F01 병합 시 확인한다 |
| 7 | **테스트 결과가 없다.** 이 보고서에는 실행 출력이 한 줄도 없다 | 스펙 승인 단계이고, 구현 착수 자체가 F01 병합 이후로 묶여 있다 (일정 제약) | 테스트 계획만 제출한다. 숫자는 개발 완료 승인 때 붙인다 |

## 1. 무엇을 만들려 하는가

**문제.** 고객은 예약을 누르기 전에 "지금 잡을 수 있는 방"을 봐야 합니다. 그런데 검색이 보여주는 재고와 실제 재고는 같은 순간을 가리키지 않습니다. 화면을 그리는 사이에도 다른 사람이 그 방을 예약하고, 캐시를 붙이면 그 간격이 더 벌어집니다.

**해법의 요지는 "간격을 없애자"가 아니라 "간격을 인정하고 책임을 나누자"입니다.**

- 검색은 **후보 제시**만 책임집니다. 빠르고, 낡을 수 있습니다.
- 예약은 **정확성**을 책임집니다. 조건부 UPDATE가 원자적으로 판정합니다.
- 그래서 검색 결과가 낡아 예약이 409로 실패하는 경로가 생기는데, 이것을 **오류 처리가 아니라 정상 흐름으로 설계**했습니다. 409를 받은 클라이언트는 `fresh=true`로 캐시를 우회해 재검색하고, 최대 2회까지 재시도합니다.

이 판단이 맞다는 근거는 방어 계층을 세어 보면 나옵니다.

| 계층 | 수단 | 무엇을 막나 |
|---|---|---|
| 1차 | Redis 결과 캐시 | DB 부하 — **정확성에는 영향 없음** |
| 2차 | 단일 집계 쿼리 (락 없음) | 조회 지연 — **정확성에는 영향 없음** |
| 3차 | 예약 시점 조건부 UPDATE + `remaining >= 0` CHECK (F01) | **초과 판매** |

**정확성을 지키는 계층은 3차 하나뿐입니다.** 그래서 캐시가 낡아도, 캐시를 통째로 꺼도, Redis가 죽어도 초과 판매는 생기지 않습니다. 반대로 검색을 아무리 정확하게 만들어도 3차를 대신할 수는 없습니다. 검색이 재고를 홀드하지 않기로 한 이유가 여기 있습니다.

## 2. 코드 구조 (설계안)

아직 만든 파일은 없습니다. 스펙이 정한 구조입니다.

```
com.pms.inventory.query
├── application/
│   ├── port/in/SearchAvailableRoomsUseCase        유스케이스 인터페이스
│   ├── port/out/AvailabilityQueryPort             재고 집계 조회 포트
│   ├── port/out/AvailabilityCachePort             캐시 포트 (구현 2개)
│   ├── usecase/SearchAvailableRoomsService        캐시 조회 → DB 조회 → 캐시 적재
│   └── dto/                                       Query(입력), Result·View(출력), StayRange(VO)
└── adapter/
    ├── in/web/AvailabilitySearchController        요청 검증·변환만
    └── out/
        ├── persistence/AvailabilityQueryAdapter   네이티브 집계 쿼리
        └── cache/RedisAvailabilityCacheAdapter    pms.search.cache.enabled=true
            NoOpAvailabilityCacheAdapter           pms.search.cache.enabled=false
```

**레이어 규칙에서 형식적으로 어긋나 보이는 곳 두 군데를 먼저 밝힙니다.**

| 어긋나 보이는 곳 | 규칙 | 왜 이렇게 했나 |
|---|---|---|
| `domain/` 디렉터리가 없다 | `clean-architecture.md`의 패키지 구조에는 `domain/`이 있다 | 조회 전용 슬라이스라 불변식을 지킬 상태가 없다. 애그리거트를 억지로 만들면 데이터 덩어리만 는다 (D2) |
| 유스케이스에 `@Transactional`이 없다 | `coding-rules.md`의 "트랜잭션 경계는 유스케이스에 있다" | 단일 SELECT라 원자성 대상이 없고, 트랜잭션을 열면 Redis 왕복이 그 안에 들어가 같은 문서의 "캐시 갱신은 트랜잭션 밖에서" 규칙을 어기게 된다 (D12) |

둘 다 규칙을 몰라서가 아니라 규칙끼리 충돌하는 지점에서 내린 판단이며, 각각 D 항목으로 올렸습니다.

**소유 범위 준수 상황**

| 항목 | 상태 |
|---|---|
| 소유 패키지 `com.pms.inventory.query.**` 밖 수정 | 없음 |
| `com.pms.inventory.domain` 수정 | 없음. SQL로 읽기만 한다 (JPA 엔티티도 import하지 않는다) |
| 재고 테이블 쓰기 | 없음. `INSERT`/`UPDATE`/`DELETE` 0건 |
| Flyway V301~V399 | **0개 사용** |
| 공유 파일 수정 | 없음. `application.yml`도 건드리지 않는다 (설정 기본값을 코드에 둔다) |
| PM 소유 문서 수정 | 없음 |

## 3. 도메인 흐름

도메인 상태를 바꾸지 않는 유스케이스입니다. 유일한 부수효과는 캐시 항목이고, 그것도 지워져도 정확성에 영향이 없습니다.

```
요청 검증 → (캐시 조회) → 집계 쿼리 1회 → (결과가 비면 진단 쿼리 1회) → (캐시 적재) → 응답
```

| 순서 | 대상 | 변화 |
|---|---|---|
| 1 | `room_daily_inventory` | **없음.** SELECT만. 잠금 읽기도 하지 않는다 |
| 2 | `room_type`, `hotel` | **없음** |
| 3 | 예약 애그리거트 | **없음.** 참조하지 않는다 |
| 4 | Redis 캐시 항목 | 미스이거나 `fresh=true`면 새로 쓰이고 TTL 시작. 히트면 변화 없음(TTL 연장도 안 함) |

**상태를 가진 것은 캐시 항목뿐이고, 이 문서의 정합성 논의가 전부 그 위에서 벌어집니다.**

| 캐시 상태 | 사용자가 보는 것 |
|---|---|
| 없음 | DB 직접 조회 결과. `source: DB` |
| 신선 | 정확한 결과. `source: CACHE` |
| 낡음 | 최대 TTL초 동안 옛 잔여. 낙관적 낡음이면 예약 단계 409로 이어진다 |

**"신선 → 낡음" 전이를 F03이 감지할 수 없다는 것**이 이 설계의 핵심 제약입니다(0절 1번).

## 4. 동시성과 정합성

F03은 쓰기를 하지 않으므로 경합으로 데이터가 깨질 일이 없습니다. 대신 다른 형태의 동시성 문제가 있습니다.

**경합 지점과 방어 수단**

| 경합 지점 | 방어 | 검증 방법 |
|---|---|---|
| 검색의 집계 SELECT와 F01의 재고 UPDATE가 같은 행에 동시 접근 | **아무 락도 걸지 않는 것이 방어다.** InnoDB 일관된 읽기로 스냅샷을 본다 | 테스트 C2: 재고 1인 행에 50 스레드 검색 + 1 스레드 갱신. `minRemaining`이 1 또는 0이며 그 사이 값이나 부분 결과가 없을 것 |
| 한 쿼리가 여러 날짜 행을 훑는 도중 일부가 갱신됨 | 집계 쿼리 한 발로 처리해 한 시점의 일관된 스냅샷 보장 | 테스트 C2와 동일 시나리오에서 날짜별 값 섞임 0건 |
| 인기 캐시 키 TTL 만료 순간의 스탬피드 | **방어하지 않는다.** F04에서 먼저 측정 (D10) | F04 L5 시나리오 |
| 409를 받은 클라이언트들의 동시 재검색 | 클라이언트 계약의 재시도 상한 2회 | 테스트 C6 |

**1차 방어선을 껐을 때**

이 feature에서 1차(캐시)를 끄는 것은 정확성을 개선하는 방향입니다. 그래서 증명해야 할 것은 "불변식이 지켜지는가"가 아니라 **"캐시를 껐을 때도 똑같이 동작하는가"**입니다.

| 검증 | 방법 |
|---|---|
| 캐시 끔 = DB 직행으로 완전 동작 | 테스트 C4: 20가지 조건을 캐시 on/off 두 모드로 실행, `items` 완전 동일 (`source`만 다름) |
| Redis 죽어도 동작 | 테스트 C5: Redis 정지 후 50회 검색, 전부 200 + `source: DB`, 예외 0건 |
| 캐시가 낡아도 초과 판매 없음 | 테스트 C6: 재고 1, 2 스레드가 같은 캐시 결과로 예약 시도 → 1건 201, 1건 409, **재고 음수 0건** |

**무효화가 실패했을 때 무엇이 보이는가** — 스펙 7절에 7가지(I1~I7)를 표로 정리했습니다. 요지는 이렇습니다.

- I1~I4(무효화 누락·지연·호출 실패·Redis 다운)는 **설계상 허용된 실패**이고 전부 TTL이 상한을 보장합니다. 최악이 "사용자 한 번 헛걸음"입니다.
- I5~I7(TTL 누락·캐시 키 충돌·`searchedAt` 덮어씀)은 **구현 실수로만 생기고 스스로 회복되지 않습니다.** 각각 전용 테스트로 막습니다. 특히 **I5(TTL이 안 걸림)가 가장 위험**합니다. 낡음의 상한이 사라지기 때문입니다.
- **어느 칸에도 "초과 판매"가 없습니다.**

**사용자에게 보장하는 것**

| # | 보장 |
|---|---|
| G1 | 결과의 모든 항목은 `searchedAt` 시각의 **하나의 일관된 스냅샷**이다. 항목별로 다른 시점이 섞이지 않는다 |
| G2 | 최대 `staleToleranceSeconds`초만큼 낡을 수 있다. **얼마나 낡을 수 있는지를 응답에 실어 보낸다** |
| G3 | `fresh=true`면 캐시를 우회해 DB 커밋 기준 최신 스냅샷을 준다 |
| G4 | 캐시가 얼마나 낡았든, 꺼져 있든, Redis가 죽었든 **초과 판매는 없다** |
| G5 | 캐시를 켜고 끈 결과가 다르지 않다. 다른 것은 낡음의 창뿐이다 |

**보장하지 않는 것:** 검색 시점의 잔여가 예약 시점까지 유지된다는 것. `fresh=true`의 결과조차 예약 성공을 약속하지 않습니다.

**멱등성:** 조회는 본래 멱등이고 상태를 바꾸는 연산이 없어 멱등성 키가 필요 없습니다. "Redis가 죽어도 중복이 막히는가"는 F03에 해당하지 않습니다. 막아야 할 중복 쓰기가 없습니다.

## 5. 테스트 계획 (실행 결과 없음)

**이 단계에서는 실행한 테스트가 없습니다.** 구현 착수가 F01 병합 이후로 묶여 있습니다. 계획만 제출합니다.

| 계층 | 무엇을 검증하나 |
|---|---|
| 도메인 단위 | `StayRange` 규칙: 체크아웃 역전, 0박, 31박, 과거 체크인, 체크아웃 당일 제외, `nights()` |
| 유스케이스 | 캐시 히트·미스·`fresh` 분기, 캐시 장애 폴백, 캐시 히트 시 `searchedAt`이 저장 시각인지(I7). **DB 없이 돈다** |
| 영속성 통합 | 집계 쿼리 정확성(기간 커버, 중간 행 누락, 인원 필터, `minRemaining`, 정렬) + 진단 쿼리의 `emptyReason` 4가지 전수 |
| 캐시 통합 | 적재·히트·evict, **TTL이 실제로 걸렸는지 Redis `TTL` 명령으로 확인**(I5), 빈 결과 캐시, 캐시 키 완전성(I6) |
| 성능 | `EXPLAIN`으로 클러스터드 PK 범위 스캔이 쓰이고 추가 테이블 접근이 없는지 확인 |

| # | 시나리오 | 스레드 | 기대 |
|---|---|---|---|

## 6. 리뷰 이력

| 라운드 | 심각 | 중요 | 결과 |
|---|---|---|---|
| — | — | — | 스펙 단계라 코드 리뷰 없음 |

다만 **작성 중 F01 세션과 PM을 통해 두 차례 교차 확인**을 받았고, 그 결과가 스펙에 반영됐습니다.

| 받은 것 | 반영 |
|---|---|
| F01 확정 스키마 (자연키 복합 PK, `base_price` 등) | 5절 계약표 A1~A7을 확정으로 닫음. **V301 인덱스 계획을 철회**(D8) |
| F01의 지적: "90일 밖은 행 자체가 없다. 매진으로 볼지 판매 전으로 볼지 네가 정해라" | **D9를 다시 씀.** 판정은 fail-closed 유지, 응답은 `emptyReason` 3종으로 구분 |
| PM 지시: 가정 항목마다 "바뀌면 얼마나 고치나"를 적을 것 | 5절 계약표에 영향도 칸 추가 |

| F04 질문: TTL 몇 초인가 | 잠정 10초로 답하고 `docs/spec/F03-검색-API-계약.md`에 합격선 6개(S1~S6)로 정리해 전달 |

F01은 F03의 확정 3가지(잠금 읽기 안 씀 / 409를 정상 흐름으로 둠 / 재고 쓰기 없음)가 자기 UC-2 설계 전제와 충돌하지 않는다고 확인했습니다.

## 8. 결정 검토란

스펙 11절에 D1~D13이 전부 있습니다. 여기서는 **판단이 갈릴 만한 것 위주로 압축**했고, 번호는 스펙과 같습니다. 전체 트레이드오프·대안은 스펙을 봐 주세요.

| # | 결정 | 포기한 것 | 확인 질문 |
|---|---|---|---|
| D1 | F01 스키마 의존을 표 하나로 모으고 병합 시 대조 | 같은 정보가 표와 본문 두 곳에 있어 한쪽만 고치면 어긋난다. A8이 미확정인 채 승인받는다 | A8 하나가 미확정인 상태로 승인해도 괜찮습니까? |
| D2 | 도메인 애그리거트를 만들지 않고 읽기 모델만 만든다 | SQL이 문자열로 노출돼 컬럼 변경이 컴파일에 안 잡힌다. `StayRange`가 F01 `StayPeriod`와 **의도적으로 중복**된다 | 조회 전용 슬라이스에 도메인 모델을 두지 않아도 괜찮습니까? 중복을 감수해도 됩니까? |
| **D3** | **검색은 어떤 잠금 읽기도 하지 않는다** | **검색 결과의 정확도.** 낡음을 없앨 수단을 스스로 포기한다 | 검색 정확도를 포기하고 예약 경로에 간섭하지 않는 쪽을 택해도 괜찮습니까? |
| D4 | 날짜별 반복 조회 대신 집계 쿼리 한 발 | 판정 로직 일부가 SQL에 들어가 단위 테스트로 검증 못 한다 | 판정이 SQL에 들어가는 것을 감수해도 괜찮습니까? |
| **D5** | **캐시 단위 = 검색 결과 전체, TTL 기본 10초** | **히트율.** 재고 행 단위 캐시였다면 훨씬 높았을 것이다. 재고 한 행이 바뀌면 그 행을 포함한 수많은 기간 조합이 전부 낡는데 정밀하게 걷어낼 방법이 없다 | 히트율을 포기하고 단순한 결과 캐시로 가도 괜찮습니까? TTL 10초에 동의합니까? |
| **D6** | **이벤트 기반 무효화는 자리만 남기고 연결하지 않는다** | **낡음이 최대 TTL초 지속되어, 연동이 있었다면 피했을 409가 실제로 발생한다** | 이벤트 무효화를 이번 범위에서 빼도 괜찮습니까? |
| D7 | Redis 장애 시 캐시를 미스로 강등 (fail-open) | Redis가 조용히 죽어도 겉보기 정상이라 장애를 늦게 발견한다 | 캐시 장애를 사용자에게 노출하지 않아도 괜찮습니까? |
| D8 | **인덱스를 하나도 추가하지 않는다 (Flyway 대역 미사용)** | "조회 성능을 위해 인덱스를 설계했다"고 보여줄 산출물이 없어진다 | F03이 Flyway를 전혀 쓰지 않고 EXPLAIN 확인으로만 마무리해도 괜찮습니까? |
| **D9** | **판정은 fail-closed, 응답은 매진·판매 전·인원 부적합 3종 구분** | 응답 필드 2개와 빈 결과 경로의 분기·테스트가 는다. **`salesOpenUntil`이 진짜 판매 정책이 아니라 시드 데이터에서 추론한 값이다** | 빈 결과의 이유를 3가지로 구분해 응답하는 데 동의합니까? 추론값이라는 한계를 문서에 남기는 것으로 충분합니까? |
| D10 | 스탬피드 방어를 F04 측정 이후로 미룬다 | 스파이크에서 캐시가 오히려 부하를 몰아줄 수 있고, 대응이 일정 후반에 몰린다 | 측정 이후로 미뤄도 괜찮습니까? |
| D11 | 검색 API는 인증 헤더를 요구하지 않는다 | 다른 API와 비일관해지고, 익명 트래픽이라 남용 방어 근거가 없다 | 검색만 열어두는 비일관을 감수해도 괜찮습니까? |
| D12 | 검색 유스케이스는 트랜잭션을 열지 않는다 | "트랜잭션 경계는 유스케이스에" 규칙과 형식적으로 어긋난다. 쿼리가 둘이라 서로 다른 시점을 볼 수 있다 | 조회 전용 유스케이스에 한해 트랜잭션을 열지 않아도 괜찮습니까? |

## 9. 판단이 필요한 지점

| 질문 | 추천 | 근거 |
|---|---|---|
| 캐시 TTL을 몇 초로 확정할까요? | **10초** | TTL은 정합성 장치가 아니라 부하 흡수 장치입니다. 1초로 줄여도 사용자가 화면을 보고 예약을 누르는 시간이 이미 그보다 길어 409는 그대로 납니다. 반대로 60초로 늘리면 비관적 낡음(취소로 방이 생겼는데 안 보임)이 눈에 띄게 커집니다. 10초는 두 방향 모두 감당 가능한 중간값이며, 설정값이라 부하테스트 결과를 보고 바꿀 수 있습니다 |
| 빈 결과의 이유를 3종으로 구분할까요, 그냥 빈 목록만 줄까요? (D9) | **구분하는 쪽** | 비용이 낮습니다 — 진단 쿼리는 **결과가 비었을 때만** 나가므로 정상 경로는 쿼리 1회 그대로입니다. 반면 가치는 큽니다. 매진이면 다른 날짜를 찾고 판매 전이면 나중에 오는데, 뭉쳐서 주면 세 경우 모두 사용자가 잘못된 행동을 합니다. F01 세션도 같은 의견이었습니다. 다만 `salesOpenUntil`이 추론값이라는 한계는 인정합니다 |
| 이벤트 기반 무효화를 나중에라도 붙일까요? (D6) | **붙이지 않는 쪽. 붙인다면 F01·F03 모두 완료된 뒤 별도 승인 사안으로** | 붙여도 정합성 보장 수준(G1~G5)이 한 줄도 바뀌지 않습니다. 개선되는 것은 낡음의 평균 지속 시간뿐입니다. 그런데 비용은 F01 코드 수정 + 절단 시 F01까지 손봐야 하는 결합입니다. **자랑거리로는 좋지만 증명 대상(동시성·멱등성)과는 무관한 투자입니다** |
| F03 구현을 F01 병합 전에 일부라도 시작할까요? | **시작하지 않는 쪽** | 읽을 테이블이 없어 통합 테스트가 하나도 못 돕니다. 단위 테스트만 쓸 수 있는 `StayRange` 정도인데, 그것 때문에 병렬 규칙의 예외를 만들 가치가 없습니다. 대신 이 대기 시간에 F04에 넘길 계약 문서를 먼저 만들어 뒀습니다 |
