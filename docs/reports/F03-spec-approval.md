- 날짜: 2026-08-15
- 단계: 스펙 승인
- 판정 요청: 승인 / 조건부 승인 / 재작업
- 대상: `docs/spec/F03-가용-객실-검색.md` (본문), `docs/briefings/F03.md`, `docs/spec/F03-검색-API-계약.md`

---

## 한눈에 보기

가용 객실 검색(UC-1) 스펙입니다. **검색은 정확성을 책임지지 않고 후보만 제시합니다. 재고의 진실은 예약 시점의 조건부 UPDATE(F01)가 정합니다.** 그래서 검색이 낡아 예약이 409로 실패하는 것을 버그가 아니라 정상 흐름으로 설계했습니다.

- **판단하실 것: [필수] 5개** (D2·D3·D5·D6·D9). 나머지 9개는 5절 한 줄 표에 있습니다.
- **가장 불리한 사실:** 재고 변경을 감지할 수단이 없어 **최대 10초간 옛 결과가 보이는 것이 사고가 아니라 기본 동작**입니다.
- **승인되면 시작되는 것은 없습니다.** 구현은 F01 병합 이후이고, 그때 TDD 21단계(스펙 9절)의 1번 빨간 테스트부터 씁니다.
- 코드·설정·마이그레이션 변경 0건. 배정받은 Flyway 대역 V301~V399를 **한 개도 쓰지 않습니다.**

## 1. 불리한 것 먼저

| # | 불리한 사실 | 감수하는 근거 |
|---|---|---|
| 1 | **재고 변경을 감지할 수단이 없다.** 최대 10초 옛 결과가 보이는 것이 기본 동작 | F01 코드에 훅을 넣을 수 없다. 이벤트를 붙여도 **정합성 보장 수준은 그대로**고 낡음의 평균 지속 시간만 준다 (D6) |
| 2 | **검색 정확성을 스스로 보장하지 않는다.** `fresh=true`도 예약 성공을 약속하지 않는다 | 검색이 락을 걸면 조회 트래픽이 재고 차감을 느리게 만든다. 걸어도 응답 직후 재고는 또 바뀐다 (D3) |
| 3 | **Flyway 대역을 한 개도 안 쓴다.** 인덱스 튜닝 산출물이 없다 | F01의 자연키 PK가 이미 커버한다. 중복 인덱스는 재고 UPDATE 비용만 얹는다. **옳은 결론이지만 보여줄 게 준 건 사실** (D8) |
| 4 | **캐시 스탬피드 방어가 없다** | 절단 1순위 캐시 위에 방어를 얹는 건 순서가 틀렸다. F04 L5로 먼저 잰다 (D10) |
| 5 | **`salesOpenUntil`이 판매 정책이 아니라 시드에서 추론한 값** | 00 D1로 관리자 기능을 빼 "판매 기간" 개념이 도메인에 없다 (D9) |
| 6 | **검색과 예약의 날짜 경계가 다르다.** 클라이언트가 "검색에 안 보이는데 예약은 되는" 날짜를 만날 수 있다 | 검색이 과거를 허용하면 `SOLD_OUT`으로 떨어져 "매진"이라는 틀린 안내를 한다. F01이 예약에 `checkOut > today`를 두기로 해 두 규칙이 층으로 정리됐다 — 예약은 진행 중인 투숙까지, 검색은 아직 시작하지 않은 투숙만 (D14) |
| 7 | **테스트 결과가 한 줄도 없다** | 스펙 단계이고 착수가 F01 병합에 묶여 있다. 계획만 제출한다 |

## 2. 핵심 판단 하나

| 계층 | 수단 | 막는 것 |
|---|---|---|
| 1차 | Redis 결과 캐시 | DB 부하 — **정확성 영향 없음** |
| 2차 | 단일 집계 쿼리 (락 없음) | 조회 지연 — **정확성 영향 없음** |
| 3차 | 예약 시점 조건부 UPDATE + CHECK (**F01**) | **초과 판매** |

**정확성을 지키는 계층은 3차 하나뿐입니다.** 그래서 캐시가 낡아도, 꺼도, Redis가 죽어도 초과 판매가 없습니다. 반대로 검색을 아무리 정확하게 만들어도 3차를 대신할 수 없습니다 — 검색이 재고를 홀드하지 않기로 한 이유입니다. 409를 받은 클라이언트는 `fresh=true`로 재검색하고 최대 2회 재시도합니다(스펙 6절 시퀀스 2개).

**소유 범위 준수:** `inventory.query.**` 밖 수정 0건, `inventory.domain` 수정 0건(SQL로 읽기만), 재고 쓰기 0건, Flyway 0개, 공유 파일·PM 소유 문서 0건. 레이어 규칙과 형식적으로 어긋나는 두 곳(`domain/` 없음, `@Transactional` 없음)은 D2·D12로 올렸습니다.

## 3. [필수] 판단이 필요한 5개

### D2. 도메인 애그리거트를 만들지 않고 읽기 모델만 만든다

- **결정:** `inventory.query`에 `domain` 패키지를 두지 않는다. 네이티브 집계 쿼리 + 전용 projection으로 읽고 F01 엔티티를 import하지 않는다.
- **이유:** 애그리거트는 함께 지킬 불변식의 범위인데 조회 전용에는 지킬 상태가 없다. F01 엔티티에 결합하면 F01 필드 변경이 F03 컴파일을 깬다.
- **트레이드오프:** SQL이 문자열로 노출돼 컬럼 변경이 컴파일에 안 잡힌다. `StayRange`가 F01 `StayPeriod`와 **의도적으로 중복**된다.
- **대안:** JPQL로 F01 엔티티 조회(결합·성능). 불변식 없는 도메인 모델 만들기(`ddd.md` 위반).
- **확인 질문:** 조회 전용 슬라이스에 도메인 모델을 두지 않고 VO 중복을 감수해도 괜찮습니까?

### D3. 검색은 어떤 잠금 읽기도 하지 않는다

- **결정:** `FOR UPDATE`·공유락·`LockModeType`·분산락 전부 안 쓴다. InnoDB 일관된 읽기 스냅샷을 그대로 쓴다.
- **이유:** 검색이 재고 행에 락을 걸면 조회 트래픽이 재고 차감을 느리게 만든다. 게다가 얻는 게 없다 — 응답 직후 재고는 또 바뀐다.
- **트레이드오프:** 이미 팔린 방을 보여줄 수 있다. **낡음을 없앨 수단을 스스로 포기**하고 그 대가를 예약 409로 받는다.
- **대안:** 공유락으로 읽는 순간만 정확하게(예약 처리량을 깎고도 응답 이후는 못 막는다). 검색이 재고를 홀드(조회가 쓰기가 된다).
- **확인 질문:** 검색 정확도를 포기하고 예약 경로에 간섭하지 않는 쪽을 택해도 괜찮습니까?

### D5. 캐시 단위를 "검색 결과 전체"로 잡고 TTL 기본 10초

- **결정:** 키 `avail:{hotelId}:{checkIn}:{checkOut}:{guestCount}:{roomCount}`로 결과를 통째로 저장한다. 재고 행 단위 캐시를 안 쓴다.
- **이유:** 히트 시 DB 쿼리가 0이라 캐시 유무 비교가 선명하다. 단순해서 캐시 on/off 동등성 증명이 쉽다. TTL은 정합성 장치가 아니라 부하 흡수 장치다.
- **트레이드오프:** **히트율을 포기한다.** 날짜 조합이 많아 키가 흩어지고, 재고 한 행이 바뀌면 그 행을 포함한 수많은 기간 조합이 낡는데 정밀히 걷어낼 방법이 없다.
- **대안:** 재고 행 단위 캐시를 MGET으로(히트율·무효화 정밀도는 낫지만 부분 미스 병합 로직이 붙어 on/off 동등성 증명이 어려워진다).
- **확인 질문:** 히트율을 포기하고 결과 캐시로 가도 괜찮습니까? (**TTL 10초라는 숫자만 바뀌는 건 설정값이라 스펙 재작성이 아닙니다. 캐시 단위를 바꾸라는 판정이면 7절을 다시 씁니다.**)

### D6. 이벤트 기반 무효화는 자리만 남기고 연결하지 않는다

- **결정:** `evictHotel()` 진입점만 두고 F01의 재고 변경 경로와 연결하지 않는다. 기본 무효화는 TTL 만료와 `fresh=true` 재적재다.
- **이유:** (1) F01 소유 패키지에 훅을 못 넣는다. (2) 절단 1순위 캐시에 F01을 결합시키면 절단할 때 F01까지 손봐야 한다. (3) 붙여도 정합성 보장 수준이 그대로다. (4) **이벤트 단독은 오히려 위험하다** — 캐시 미스로 DB를 읽은 요청이 무효화가 지나간 뒤 자기 값을 쓰면 지울 키가 없어 무효화가 헛돌고 **낡은 값이 영구히 박힌다**(스펙 I8). TTL이 있어야 풀린다.
- **트레이드오프:** 낡음이 최대 TTL초 지속되어 **연동이 있었다면 피했을 409가 실제로 발생한다.**
- **대안:** F01 유스케이스가 커밋 후 `evictHotel` 호출(F01 수정 승인 + 절단 결합). Redis pub/sub(같은 문제에 인프라만 는다).
- **확인 질문:** 이벤트 무효화를 자리만 남기고 이번 범위에서 빼도 괜찮습니까?

### D9. 판정은 fail-closed, 응답은 "매진 / 판매 전 / 인원 부적합"을 구분한다

- **결정:** 기간 중 하루라도 재고 행이 없으면 결과에서 제외하되, 결과가 비면 진단 쿼리 1회로 `SOLD_OUT` / `NOT_YET_OPEN` / `NO_FITTING_ROOM_TYPE`을 구분해 준다. `NOT_YET_OPEN`이면 `salesOpenUntil`(시드 기준 **2026-10-29**)도 준다.
- **이유:** 두 층의 요구가 다르다. 판정은 안전하게 틀려야 하고(행 없는 날짜를 "제약 없음"으로 보면 매진을 가용으로 표시한다), 안내는 정직해야 한다(매진이면 다른 날짜를 찾고 판매 전이면 나중에 온다 — 정반대 행동). 비용은 **결과가 빌 때만 나가는 쿼리 1회**로 정상 경로는 그대로 1회다.
- **트레이드오프:** 응답 필드 2개와 분기·테스트가 는다. 더 중요하게는 **`salesOpenUntil`이 시드에서 추론한 값**이다. 실제 서비스라면 판매 시작·종료일 컬럼이 있어야 한다.
- **대안:** 셋을 뭉쳐 빈 목록만 주기(가장 싸지만 세 경우 모두 사용자가 잘못된 행동을 한다). `room_type`에 판매 기간 컬럼 추가(F01 소유 침범, 불가).
- **확인 질문:** 빈 결과의 이유를 3종으로 구분하는 데 동의합니까? 추론값이라는 한계를 문서에 남기는 것으로 충분합니까?

## 5. 검증 계획

쓰기가 없어 경합으로 데이터가 깨지지 않습니다. 검증할 것은 **"캐시를 껐을 때도 똑같이 동작하는가"**입니다.

| 시나리오 | 조건 | 기대 |
|---|---|---|
| C2 읽기-쓰기 경합 | 재고 1인 행을 50 스레드가 읽는 중 1이 0으로 | `minRemaining`은 1 또는 0뿐. 중간값·부분 결과 없음 |
| C4 캐시 on/off 동등성 | 20가지 조건을 두 모드로 | `items` 완전 동일 (`source`만 다름) |
| C5 Redis 다운 | 정지 후 50회 | 전부 200 + `source: DB`, 예외 0건 |
| **C6 핵심 서사** (F01 병합 후) | 재고 1, 2 스레드가 같은 캐시 결과로 예약 | 1건 201, 1건 409, **재고 음수 0건**. 재검색 시 해당 타입 소멸 |

**무효화가 실패하는 8가지(I1~I8)를 스펙 7절에 표로 정리했습니다.** I1~I4·I8은 설계상 허용된 실패이고 전부 TTL이 상한을 보장합니다. I5~I7은 구현 실수로만 생기고 **스스로 회복되지 않아** 전용 테스트로 막습니다. **어느 칸에도 초과 판매가 없습니다.**

TDD 21단계는 스펙 9절에 순서대로 있습니다. **17번(무효화를 스쳐 지나간 늦은 쓰기 재현)이 가장 값진 테스트**입니다 — 나중에 누가 "이벤트 무효화를 붙였으니 TTL은 빼도 되겠다"고 판단하면 이 테스트가 먼저 깨집니다.
