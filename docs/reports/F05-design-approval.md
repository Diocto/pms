- 날짜: 2026-08-15

- 판정 요청: 승인

## 한눈에 보기

- 무엇을 했는가: 화면 3개(검색 → 예약 주문서 → 예약 상세)의 시안을 상태 14종까지 그렸다. 브라우저에서 보는 판본: https://claude.ai/code/artifact/51e18487-8421-48a6-ab9c-3590ccb8339d (파일: `docs/design/F05-화면-시안.html`)
- 핵심 판단: 409(재고 부족)를 오류가 아니라 "방금 마감 → 최신 재고 자동 확인 → 자동 재시도(최대 2회) → 대안 안내"의 4단계 정상 흐름으로 그렸다. 결제 거절(200 + CANCELLED)도 성공 화면과 분리했다.
- 확인이 필요한 것: [필수] 3건 (D5 렌더링 구성, D7 목록 없음, D8 체크인아웃 제외), [확인] 6건 — 스택 선택 포함
- 리스크: F01·F03 스펙이 아직 승인 대기라, 이 시안은 그 계약이 그대로 확정된다고 전제했다. 특히 F03 D9(`emptyReason`)가 부결되면 검색 화면의 빈 결과 3분할을 다시 그려야 한다.

## 1. 무엇을 만들었는가

**문제.** 이 시스템은 검색 결과가 최대 10초 낡을 수 있게 설계되어 있어(F03 캐시 TTL), "예약 가능"이라 떠 있는 방이 누르는 순간 없을 수 있다. 이것은 장애가 아니라 설계다. 화면이 이 실패를 "오류가 발생했습니다"로 뭉개면 그 주장의 증거가 사라진다.

**해법.** 화면 3개를 정상 흐름 1개 + 실패·경계 상태 11종으로 그렸다.

| 화면 | 상태 수 | 핵심 |
|---|---|---|
| S1 객실 검색 | 6 | 빈 결과를 매진 / 판매 전 / 인원 초과로 **구분해** 말한다. 결과 위에 "최대 10초 전 정보" 상시 표기 |
| S2 예약 주문서 | 4 | **409의 4단계 자동 처리** (이 시안의 핵심), 제출 중 버튼 잠금, 멱등성 키의 수명 규칙 |
| S3 예약 상세 | 6 | 결제 대기 카운트다운, **결제 거절은 200이어도 실패 화면**, 만료·취소·404 |

브리핑의 「반드시 다뤄야 할 화면 상태」 7종은 전부 시안에 있다. 대응 위치: SOLD_OUT·NOT_YET_OPEN·NO_FITTING_ROOM_TYPE → S1 상태 3·4·5, 409 재고 부족 → S2 상태 3, REQUEST_IN_PROGRESS → S2 상태 2, 200+CANCELLED → S3 상태 3, 503 → 응답→문구 매핑 표.

## 2. 산출물 구조

```
docs/design/
└── F05-화면-시안.html   화면 3개 × 상태 14종 목업 + 화면 이동 지도
                          + 응답→문구 매핑 표 + 디자인 토큰 + 스택 제안
                          + 교육 노트 계획(6편) + 결정 검토란 D1~D9
docs/reports/
└── F05-design-approval.md   이 문서
```

코드는 아직 없다. 승인 후 `frontend/` 아래에만 만든다. `frontend/` 밖 산출물은 문서 둘뿐이다(문서는 parallel-work의 Soft 대역).

## 3. 화면 흐름

```
S1 검색 ──객실 선택(조건은 URL 쿼리)──▶ S2 주문서 ──201 PENDING──▶ S3 상세
   ▲                                        │ 409 × (1 + 재시도 2회)
   └────── 다른 날짜·객실로 ◀───────────────┘
상단 "예약 확인"(확인번호 입력) ─────────────────────────────────▶ S3 상세
```

- 검색 조건과 확인번호는 전부 URL에 실린다. 새로고침·뒤로가기·링크 공유가 별도 상태 저장 없이 동작한다.
- 목록 화면은 없다(D7). F01에 목록 API가 없고, 백엔드에 추가를 요구하지 않는다는 브리핑 원칙을 따랐다.

## 4. 동시성과 멱등성 — 화면이 지는 몫

백엔드 게이트가 아니므로 테스트 수치는 없다. 대신 화면이 계약에서 지는 책임을 어떻게 이행하는지가 이 절이다.

| 계약 | 화면의 이행 | 시안 위치 |
|---|---|---|
| 멱등성 키는 클라이언트가 만든다, 같은 시도에는 같은 키 | 주문서 진입 시 1회 발급. 연타·타임아웃 재시도·409 재시도 전부 같은 키. 성공하거나 입력이 바뀌면 새 키 | S2 노트 |
| 409는 정상 흐름 | "방금 마감" → `fresh=true` 재검색 → 자동 재시도 → 2회 실패 시 대안. 수동 재시도 버튼 없음 | S2 상태 3 |
| REQUEST_IN_PROGRESS | 오류로 안 보여주고 버튼 잠근 채 같은 키로 재요청 | S2 상태 2 |
| 결제 거절 = 200 + status: CANCELLED | HTTP 상태가 아니라 본문 `status`로 분기. 성공 화면과 완전 분리 | S3 상태 3 |
| 만료 판정은 서버 몫 | 카운트다운이 0이 되어도 화면이 스스로 만료 처리하지 않고 재조회 | S3 상태 1 |
| 남의 예약은 404 | "없는 번호"와 구분하지 않고 같은 화면 | S3 상태 6 |

**보안·유지보수 기본 (PM 지시 요구 2).** X-User-Id가 인증이 아니라는 사실(누구나 값을 정할 수 있고, 남의 확인번호+식별값을 알면 조회·취소 가능)을 시안 본문에 명시했고 구현 시 API 모듈 주석에도 남긴다(ADR-0006, 알고 뺀 것). 오류 화면은 traceId만 노출한다. API 호출은 `lib/api.ts` 한 곳, 응답은 경계에서 검증(타입 단언 금지), 클라이언트 검증은 UX일 뿐 판정은 서버 — 전부 시안에 반영돼 있다.

## 7. 남은 것

- **구현 전부** — 승인 후 `frontend/`에 시작한다.
- **교육 노트 6편의 본문** — 제목·구성은 시안에 확정(D9), 본문은 구현 중 실제 판단이 생긴 시점에 쓴다.
- **하지 않은 것:** 다크 테마(과제 시연 화면에 비용이 값을 못 함 — 시안 토큰 절에 명시), 모바일 전용 레이아웃(세로로 쌓이는 수준까지만), 체크인·체크아웃 버튼(D8).

## 8. 결정 검토란

전체 9건. 다섯 갈래 상세는 시안 문서의 결정 검토란에 있고, 여기는 등급과 확인 질문만 모은다.

### [필수] — 번호별로 답해주셔야 합니다

**D5. 세 화면의 본체는 클라이언트 컴포넌트, 서버 컴포넌트는 뼈대만**

- **결정:** 검색·주문서·상세의 본체를 클라이언트 컴포넌트로 만든다.
- **이유:** 세 화면 모두 상호작용(검색 실행, 제출·자동 재시도, 카운트다운)이 본질이라 브라우저에서 돌아야 한다.
- **트레이드오프:** Next.js 서버 렌더링의 이점을 얕게 쓴다. 첫 페인트에 데이터가 실리지 않는다.
- **대안이었던 것:** 검색 결과를 서버 컴포넌트로 렌더 — 10초 낡는 데이터를 서버에서 미리 그리면 하이드레이션 직후 재검증이 필요해 오히려 복잡해져 기각.
- **확인 질문:** 클라이언트 컴포넌트 중심 구성으로 가도 괜찮습니까?

**D7. 목록 화면 없음 · 호텔 2곳 상수 · 확인번호로 재진입** `· 하위 영향: 뒤집히면 F01에 목록 API 요구가 생긴다`

- **결정:** 예약 목록·호텔 목록 화면을 만들지 않는다. 재방문 진입은 상단 확인번호 입력.
- **이유:** F01에 해당 API가 없고, 백엔드에 아무것도 요구하지 않는다는 브리핑 원칙을 따른다.
- **트레이드오프:** 확인번호를 잃으면 예약을 다시 못 찾는다. 실서비스라면 안 되는 UX지만 과제의 증명 대상과 무관하다.
- **대안이었던 것:** localStorage에 내 예약 번호 보관 — 서버에 없는 목록이라는 거짓 화면이 되어 기각.
- **확인 질문:** 목록 없이 확인번호 진입으로 가도 괜찮습니까?

**D8. 체크인·체크아웃 버튼을 화면에 두지 않는다**

- **결정:** S3 상세는 CHECKED_IN·CHECKED_OUT을 표시만 하고 일으키는 버튼은 없다.
- **이유:** 화면 셋은 고객 여정이고 체크인·체크아웃은 프런트 직원 액션이다(F01 2.1절). 시연은 API 직접 호출로 충분하다.
- **트레이드오프:** 상태 머신의 마지막 두 전이를 화면에서 일으킬 수 없다.
- **대안이었던 것:** 상세 화면에 개발자용 버튼 — 고객 화면에 직원 행동이 섞여 기각.
- **확인 질문:** 체크인·체크아웃은 표시만 하고 버튼은 빼도 괜찮습니까?
