## 2. 규칙 문서 개정 4건을 어떻게 반영했는가

전부 `main`의 `docs/architecture/`에 있는 규칙입니다. **제가 내린 결정이 아니라 따라야 할 규칙이므로, 새로 여쭙는 것이 아니라 적용 결과를 보고합니다.**

### ① 레이어 개명 — 바깥 층을 둘로 나눴습니다

`presentation`(들어오는 경계)과 `infrastructure`(나가는 경계)로 나눕니다. **둘 다 바깥이지만 화살표 방향이 반대입니다** — `presentation`은 유스케이스를 *부르고*, `infrastructure`는 유스케이스가 정의한 계약을 *구현합니다*.

한 이름으로 묶으면 DB 접근 코드가 화면 코드 옆에 앉게 되고, 읽는 사람이 파일을 열어봐야 어느 쪽인지 압니다. **이름이 자리를 설명하지 못하면 다음 사람이 잘못된 자리에 놓습니다.**

만료 스케줄러는 `presentation`에 뒀습니다. 라우터와 같은 성격(유스케이스를 부르기만 함)이고, 들어오는 계기가 HTTP냐 시각이냐만 다릅니다.

### ② 세션과 트랜잭션의 수명 — **제가 만들어야 할 파일이 하나 생겼습니다**

**이번 개정에서 F01에 가장 크게 걸린 항목입니다.** → 스펙 **D28**

Java에서는 트랜잭션이 스레드에 매여 있어서 어노테이션 하나면 끝났습니다. Python에서 쓰는 SQLAlchemy는 그렇지 않아서, **"어디서부터 어디까지가 한 묶음인가"를 코드에 직접 써야 합니다.**

규칙은 **세션 하나 = 트랜잭션 하나**입니다. 한 요청 처리 중에 저장을 두 번 하면 **그 사이에 남이 끼어듭니다** — 재고를 깎아 저장하고 나서 예약을 넣다가 실패하면 재고만 줄어든 상태가 남습니다.

그래서 트랜잭션을 여는 문을 **딱 두 개**로 좁힙니다. `app/common/db.py`에 만들고, **이 파일은 스캐폴딩에 없어서 제가 1회차에서 만듭니다.**

```python
with self._tx.write() as session:   # 쓰기 — 블록을 나오면 저장, 예외면 전부 되돌림
with self._tx.read() as session:    # 조회 — 저장하지 않음
```

**조회용을 따로 둔 이유가 사소해 보이는데 그렇지 않습니다.** SQLAlchemy는 첫 조회에서 트랜잭션을 자동으로 열고, 그것을 닫지 않으면 **DB 연결이 "쓰는 중" 상태로 반납됩니다.** 이게 쌓이면 연결이 고갈되는데, **테스트에서는 전혀 드러나지 않고 부하가 걸려야 나타납니다.** 그래서 검증 테스트(T27c)를 결과가 아니라 **연결 상태를 직접 보는 방식**으로 설계했습니다.

**어노테이션 방식을 기각한 근거가 제 스펙의 열두 줄입니다.** 예약 생성 유스케이스를 열두 줄로 적어보면 **락이 트랜잭션 바깥에 있다는 사실이 눈에 보입니다.** 어노테이션으로 감싸면 그게 사라지고 순서는 다시 문서에만 남습니다. 이 프로젝트는 그 순서가 틀리면 바로 버그입니다.

**F01에서 직접 걸린 자리는 만료 스케줄러(UC-5)입니다.** 만료 대상을 한 번에 다 처리하지 않고 **건마다 따로** 처리합니다. 한 묶음으로 하면 마지막 한 건이 실패할 때 앞의 999건이 전부 되돌아갑니다. 그리고 **먼저 조회한 목록은 처리 시점에 이미 낡았을 수 있습니다** — 그 사이 사용자가 결제를 마쳤을 수 있습니다. 그래서 처리하는 쪽이 "아직 미결제인가"를 **다시 확인하고 스스로 판정합니다.** 조회는 후보를 좁히는 것이지 판정이 아닙니다.

### ③ 분산락 — **이미 있는 것을 직접 만들지 않습니다**

관리자께서 짚어주신 항목입니다. 락 하나를 안전하게 잡고 푸는 데 필요한 것(중복 방지 저장, 획득마다 다른 표식, 남의 락을 지우지 않는 안전장치, 대기 시간 제한)이 **Redis 파이썬 라이브러리에 이미 전부 들어 있습니다.**

직접 쓰면 검증되지 않은 코드가 하나 더 생기는데, **락은 평소에는 정상으로 보이고 경합이 몰릴 때만 깨집니다.** 그래서 틀려도 조용합니다.

**우리가 직접 쓰는 것은 여러 개를 한 묶음으로 다루는 부분뿐입니다.** 3박 예약은 재고 3일치를 함께 잠가야 하는데, 라이브러리는 하나씩만 다룹니다. 그 **순서·중간 실패 정리·역순 해제**가 우리 몫입니다.

**대기 시간 제한을 전체에 한 번만 겁니다.** 키마다 "200ms까지 기다려"를 그대로 주면 **3박 예약이 600ms를 기다립니다.** 남은 시간을 계산해 넘깁니다.

**하나 더 확정한 것:** 락이 예상보다 일찍 풀려 남이 가져간 상황(`LockNotOwnedError`)을 **삼키지 않고 로그로 남깁니다.** 이건 "설정한 락 유지 시간이 실제 처리 시간보다 짧다"는 신호이고, **F04가 부하테스트 결과를 해석할 때 직접 쓰입니다.**

**Redlock(여러 대의 Redis에 과반수로 락을 거는 방식)은 기각했습니다.** 우리는 Redis가 한 대이고, 더 근본적으로 **이 설계에서 락은 정확성을 책임지지 않습니다** — 초과 판매를 실제로 막는 것은 2층의 조건부 UPDATE입니다. **정확성이 걸려 있지 않은 장치를 정교하게 만드는 것은 값을 못 만듭니다.**

### ④ 계층 간 데이터는 Pydantic · 결제는 교체 가능한 자리 뒤에

계층을 넘나드는 데이터 그릇을 전부 Pydantic으로 통일했습니다(원래 스펙은 파이썬 기본 `dataclass`였습니다). **얻는 것이 셋입니다** — 도메인 객체에서 응답으로 옮기는 코드가 한 줄로 줄고, **Swagger 문서가 코드에서 자동으로 나와 문서와 구현이 어긋날 자리가 없어지고**, 잘못된 값이 경계에서 걸립니다.

**결제 거절은 에러가 아니라 정상적인 반환값입니다.** 예외로 던지면 유스케이스가 정상 흐름을 `try/except`로 다루게 되고, **진짜 장애(네트워크 끊김)와 구분이 사라집니다.** 거절되면 예약은 취소로 가고, 그건 실패가 아니라 결과입니다.

**모의 결제의 기본 거절률은 `0.0`(항상 승인)이고 결정적입니다.** 기본이 확률적이면 테스트가 가끔 깨지는데, 그때 원인이 경합인지 결제인지 구분되지 않습니다.

## 3. 보고서 제출 직전에 추가된 것 둘 — **제출 후 추가 표시**

### 에러 코드 계약 위반 수정 (F03 발견, PR #9)

스캐폴딩의 `NotFoundError` 기본 코드가 계약에 없는 `NOT_FOUND`였습니다. **HTTP 404는 정상으로 나가고 문자열만 달라서, 눈으로는 멀쩡하고 부하테스트가 문자열을 비교할 때에야 드러나는 종류입니다.** `RESOURCE_NOT_FOUND`로 고쳤습니다.

같은 종류의 구멍이 하나 더 있었습니다 — 계약의 `503 LOCK_ACQUISITION_FAILED`(락 혼잡)가 예외 갈래 어디에도 안 걸려 **400으로 나갈 상태**였습니다. 그러면 부하 리포트에서 혼잡이 "클라이언트 버그"처럼 읽힙니다. 503 갈래를 새로 뒀습니다.

**재발 방지 장치를 함께 만들었습니다.** 계약 전체를 스펙 2.1절 표와 `app/common/error_codes.py`(기계 검증본)에 두고, 테스트가 코드베이스의 모든 예외 클래스를 훑어 계약 밖 코드를 잡습니다. **일부러 버그를 되돌려 테스트가 그것을 잡는 것까지 확인했습니다.** → PR #9 (공유 파일이라 별도 커밋)

### D26 응답에 `implementations` 추가 (F03 발견, PM 지시)

설정 값은 "무엇을 의도했는가"이고 주입된 클래스는 "실제로 무엇이 들어갔는가"입니다. 둘이 갈라지면 — **값은 `false`인데 실제로는 Redis 락이 물려 있으면** — F04의 락 On/Off 대조가 무의미해집니다. 그래서 `/api/internal/config`가 **실제로 주입된 구현체의 클래스 이름**을 함께 보고합니다. 값은 손으로 적지 않고 실물에서 뽑습니다(T89b~T89d 추가).

**그리고 스키마를 먼저 올려야 합니다.** F02·F03은 자기 마이그레이션이 **어느 것 다음에 오는지**를 제 `001`~`004`가 병합돼야 확정할 수 있습니다. 두 세션의 착수 조건이 제 1회차입니다.

## 5. 불리한 것 먼저

- **테스트를 하나도 돌리지 않았습니다.** 스펙 단계라 F01 기능 코드가 0줄입니다. 스펙에 적힌 기대 수치는 전부 *기대값*이며 개발 완료 보고서에서 실측으로 대체합니다. (스캐폴딩+계약 테스트 11건은 초록이지만 그건 실행 환경·공통 계층 검증이지 F01 기능이 아닙니다.)
- **레이어 규칙 예외 1건.** 예약 생성이 재고·예약 두 구역을 한 묶음으로 고칩니다. `ddd.md` 원칙 위반이지만 **00 문서 D6에서 승인된 예외**이고 스펙에 명시했습니다.
- **닫지 못한 틈 1건.** 모의 결제 성공 직후 프로세스가 죽으면 결제만 되고 예약은 미결제로 남아 만료됩니다. 이번에 닫지 않고 한계로 문서화했습니다(D5).
- **확장 지점이 넷이고 구현자는 F02 하나뿐입니다.** 명백한 설계 냄새라 D23에 적었고, 다섯 번째가 필요해지면 훅을 더 만들지 않는다는 선을 그었습니다.
- **표기 규칙에 의도적 예외를 하나 뒀습니다.** API 응답은 전부 `camelCase`인데 `/api/internal/config`의 설정 키만 대문자·밑줄(`PMS_LOCK_ENABLED`)입니다. **이 응답은 사람이 읽고 셸에 그대로 옮겨 적는 유일한 응답**이라, 표기를 통일하면 그 옮겨 적기가 깨집니다. 규칙 문서도 같은 예외를 명시하고 있습니다.

## 6. 동시성 방어 요약 — **바뀌지 않았습니다**

| 경합 | 방어 | 증명 |
|---|---|---|
| 같은 재고 행 (초과 판매) | 조건부 UPDATE + CHECK `>= 0` | K1: 잔여 10 / 100스레드 → 성공 정확히 10 |
| 여러 재고 행 (데드락) | 날짜 오름차순 전순서 고정 | K8: 반대 순서 요청 → 데드락 0건 |
| 같은 멱등 키 | Redis `SET NX` + DB `UNIQUE` | K3: 같은 키 50 동시 → 예약 1건 |
| 확정↔취소↔만료 (이중 복원) | 복원을 전이 성공의 결과로 묶음 + CHECK `<= total_quantity` | K6·K10: 복원 1회, 이력 줄 1개 |

**1차 방어선을 끈 상태의 증명이 핵심입니다.** `PMS_LOCK_ENABLED=false`로 분산락을 통째로 끄고 K1과 같은 조건으로 돌려(K2) 여전히 성공 10건·잔여 0이어야 합니다. → 스펙 4.3절
