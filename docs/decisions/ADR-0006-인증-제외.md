# ADR-0006. 인증은 X-User-Id 헤더 식별로 대체

- 날짜: 2026-08-14 (기록은 2026-08-15)
- 상태: 채택
- 관련 feature: 전체

## 문제

예약에는 "누가"가 필요하다. 그런데 회원가입·로그인·토큰 검증을 제대로 붙이면 반나절 이상이 들고, 이 과제의 관심사(동시성·멱등성·상태 전이)와는 무관하다.

## 산출물

모든 API가 `X-User-Id` 헤더로 사용자를 식별한다. 회원 테이블 없음. `reservation.user_id`는 VARCHAR(50)로 헤더 값을 그대로 저장한다.

## 검토한 대안

### 대안 A. Spring Security + JWT

- 장점: 실무와 같다.
- 단점: 설정·필터·토큰 발급까지 최소 반나절. 부하테스트 스크립트도 토큰 발급 단계가 필요해진다.
- 채택하지 않은 이유: 과제 본질과 무관한 비용이 크다.

### 대안 B. 요청 본문에 userId 포함

- 단점: 자원 경로마다 본문 구조가 달라지고, 인증이라는 관심사가 API 계약 여기저기에 스며든다.
- 채택하지 않은 이유: 헤더가 관심사를 한곳에 모은다.

## 결정

`X-User-Id` 헤더 기반 식별. 인증·인가는 명시적으로 범위 밖이다.

## 근거

멱등성 키 네임스페이스(`user + key`)와 본인 확인에 필요한 것은 "식별자"뿐이고, 그 식별자의 진위 검증은 과제의 채점 요소가 아니다.

## 대가

- 누구나 헤더만 바꾸면 타인 행세를 할 수 있다. 문서에 명시하고 감수한다.
- 헤더 검증(빈 값, 50자 초과)은 애플리케이션에서 해야 한다. 안 하면 DB 길이 오류가 500으로 샌다.
- MySQL 기본 콜레이션이 대소문자 무시라 `User1`과 `user1`이 같은 멱등 네임스페이스가 된다. 클라이언트가 일관된 ID를 쓰면 무해하다.

## 되돌리는 비용

낮다. 인증 필터를 추가하고 헤더 대신 토큰 클레임에서 userId를 뽑도록 바꾸면 나머지 코드는 그대로다.
