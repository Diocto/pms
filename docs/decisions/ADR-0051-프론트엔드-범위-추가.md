# ADR-0051. 프론트엔드를 범위에 추가

- 날짜: 2026-08-15
- 상태: 채택
- 관련 feature: F05
- **결정자: 관리자**

> 소급 기록이다. 결정은 2026-08-15에 대화로 내려졌고 ADR은 2026-08-16에 썼다.

## 문제

과제 범위는 백엔드 API만이었다. 동시성·멱등성·상태 전이를 증명하는 것이 목표였고, 화면은 없어도 그 증명에 영향이 없다.

그런데 마감 이틀 전 시점에 이런 상황이었다. 백엔드는 스펙 승인 대기로 멈춰 있었고, 세션 몇은 할 일이 없어 문서만 고치고 있었다. 남는 자원이 있는데 쓸 데가 없었다.

## 결정

**화면 세 개(검색·예약 주문서·예약 상세)를 만든다.** 스택은 지원 기업의 프론트 스택과 같게 Next.js를 쓴다.

관리자 지시 원문:

> "F05로 간단한 프론트엔드 구현도 진행해줘 / 디자인 시안 작성 - 내가 검토 - 디자인확정시 구현진행(이 과정에서 프레임워크는 핸디즈 프론트 스택이랑 똑같이해줘)"

> "해당부분은 기본적인 구현은 하되 보안, 유지보수 관점에서 기본적인 것들은 지키게 구현한 뒤, 교육 노트는 백엔드 경험 있는 컴공 전공자가 프론트엔드 공부할수있게 해줘"

## 검토한 대안

### 대안 A. 범위를 늘리지 않는다

- 장점: 마감이 이틀인데 새 스택을 들이지 않는다. 백엔드에 집중한다.
- 단점: 놀고 있는 자원이 그대로 논다. 백엔드가 승인 대기로 멈춘 동안 아무도 아무것도 못 만든다.
- 채택하지 않은 이유: **프론트엔드는 백엔드를 기다리지 않아도 만들 수 있다.** 가짜 응답으로 화면을 끝까지 그릴 수 있어서, 승인 대기와 무관하게 진행된다.

### 대안 B. 백엔드 세션을 더 붙인다

- 장점: 증명에 직접 기여한다.
- 채택하지 않은 이유: 백엔드 세션은 서로의 계약을 물고 있어 더 붙일수록 협의만 늘어난다. 실제로 그렇게 됐다([낭비 정리 보고서](../reports/낭비-정리.md)).

## 대가

- **잘리면 가장 먼저 잘린다.** 증명에 기여하지 않으므로 절단 순서 1순위다.
- 리뷰어 3종이 백엔드 기준이라 프론트에 그대로 안 맞는다. F05가 지적을 반박하며 걸러야 한다.
- 제출 문서에서 "범위를 넓혔다"가 "핵심에 집중하지 않았다"로 읽힐 위험이 있다.

## 되돌리는 비용

**거의 0이다.** `frontend/` 디렉터리 하나이고 백엔드가 이걸 참조하지 않는다. 지우면 끝난다.

이게 이 결정을 싸게 만든 핵심이다. **백엔드에 아무것도 요구하지 않는다**는 제약을 브리핑에 박아서, F05가 목록 API 같은 걸 요청하지 못하게 했다.

## 결과 (2026-08-16 기준)

화면 3개 완료, 테스트 65건 통과, 교육 노트 6편. **F05가 다섯 세션 중 실행되는 코드를 가장 많이 만들었다(4,704줄).** 대안 A를 골랐다면 그 시간이 통째로 없었다.
