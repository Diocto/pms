# ADR-0053. PM 역할을 스펙 층으로 축소

- 날짜: 2026-08-16
- 상태: 채택
- 관련 feature: 전체 (하네스)
- **결정자: 관리자**

## 문제

하네스 두 줄이 모든 대화를 PM으로 통과시키고 있었다.

- `CLAUDE.md`: PM 역할에 **"구현 세션 질문 응대"**
- `parallel-work.md`: **"세션끼리 직접 조율하지 않는다"**

스펙 단계에서는 맞는 규칙이었다. 결정이 문서에 남아야 하고, 세션끼리 대화로 정하면 기록이 안 남는다.

**구현 단계에서는 반대로 작동했다.** F02가 F01의 훅 시그니처를 묻는 건 기록할 결정이 아니라 사실 확인인데, PM이 중간에서 옮기며 왕복이 늘었다. 그리고 **PM은 코드를 안 보므로 옮기는 과정에서 틀린 답이 섞였다.**

실제 피해:

- PM이 클래스 이름을 잘못 옮겨 **두 세션의 문서 열 곳이 오염**됐다 (`ConfigReporter` → 실제는 `ConfigContributor`)
- 시나리오 번호를 소유자 표시 없이 전달해 **엉뚱한 실험에 반영될 뻔**했다 (F02의 `S4`와 F04의 `S4`가 다른 것)
- **PM 조언 일곱 건이 세션 반박으로 철회**됐다

관리자 지시 원문:

> "PM 의 역할이너무 크다 지금 - 기술적인 부분 조율을 너가 전달받아서 피드백을 주고 있는데 실구현을 진행할때는 구현 세션들끼리 해야한다"
> "스펙상 동작이나 추상적/구체적인 유스케이스만 정하는거지, 기술적까지 응대하는건 너 역할이 아님. 줄이자"
> "작업이 한번 시작되면 - PM 에 보고하지 말고 알아서 진행하게 해. 결정사항이 필요한게 나오면 기록해두거나 바로 물어볼것(관리자인 나에게)"

## 결정

**PM은 스펙 층에서 멈춘다.** 무엇을 만드는가, 어떤 유스케이스가 범위 안인가, 누가 무엇을 소유하는가까지다. **어떻게 만드는가는 아니다.**

막혔을 때 갈 곳을 셋으로 나눴다.

| 모호한 것 | 어디로 |
|---|---|
| 이 기능이 범위 안인가 | 관리자에게 직접 |
| 남의 코드가 어떻게 생겼나 | 그 세션에 직접 |
| 어떻게 구현할까 | 스스로. 소유자니까 |

**진행 보고를 없앴다.** PM은 현황판과 git으로 본다. 보고를 받아야 아는 상태라면 현황판이 잘못 만들어진 것이다.

## 검토한 대안

### 대안 A. PM을 그대로 두되 응답 속도를 높인다

- 채택하지 않은 이유: 속도가 문제가 아니었다. **PM이 코드를 안 본다는 게 문제**라, 빨리 답해도 틀린 답이 빨리 갈 뿐이다.

### 대안 B. PM을 없앤다

- 장점: 왕복이 0이 된다.
- 채택하지 않은 이유: 공유 파일 병합 순서와 소유권 중재는 누군가 해야 한다. 세션끼리는 서로 양보를 정할 근거가 없다.

## 근거

**PM이 답할 수 있는 질문과 답하면 안 되는 질문이 성격으로 갈린다.**

- "누가 정할 권한이 있는가" → PM. 소유권 정보는 PM이 갖고 있다
- "그게 어떻게 생겼는가" → 코드를 가진 세션. PM은 추측할 뿐이다

## 대가

- **결정이 대화로 사라질 수 있다.** 세션끼리 정한 것은 문서에 안 남을 수 있다. 이걸 막으려고 "기술 질문의 답은 코드와 테스트에 남는다"를 전제로 뒀는데, **코드에 안 남는 합의가 생기면 이 전제가 깨진다.**
- PM이 세션 상태를 늦게 안다. 현황판이 15분 주기라 그 사이는 모른다.
- 세션끼리 잘못 합의해도 PM이 못 잡는다.

## 되돌리는 비용

**싸다.** 문서 두 곳을 되돌리면 된다. 다만 되돌려야 할 상황이라면 그건 세션끼리 합의가 틀렸다는 뜻이라, 그 피해가 먼저 드러난 뒤일 것이다.
