# ADR-0002. 도메인 모델과 JPA 엔티티 통합

- 날짜: 2026-08-14
- 상태: **채택 (결론 유효, 도구는 바뀜).** JPA → SQLModel. [ADR-0050](ADR-0050-기술-스택-전환.md) 참고
- 관련 feature: 전체

> **"도메인 모델과 ORM 모델을 통합한다"는 결론은 지금도 그대로다.** 바뀐 것은 ORM뿐이다.
> 아래 본문의 `JPA 엔티티`는 지금 `SQLModel 테이블 클래스`로, `@Entity`는 `table=True`로 읽으면 된다.
> 근거(마감이 짧고, 매핑 계층이 새 버그 원천이 된다)는 도구와 무관하게 성립한다.

## 문제

Clean Architecture를 따르기로 했는데, 정석은 순수 도메인 객체와 JPA 엔티티를 분리하고 매핑 계층을 두는 것이다. 그런데 마감이 3일 반이다. 분리하면 클래스와 매핑 코드가 두 배로 늘고, 매핑 실수가 새로운 버그 원천이 된다.

## 산출물

도메인 모델 클래스에 `@Entity`가 직접 붙는다. 별도 영속성 모델과 매퍼가 없다.

## 검토한 대안

### 대안 A. 완전 분리 (정석)

- 장점: 도메인이 JPA로부터 완전히 자유롭다. 아키텍처 순수성이 가장 높다.
- 단점: 애그리거트마다 도메인 클래스, JPA 엔티티, 양방향 매퍼가 필요하다. 더티 체킹을 못 쓰고 상태 비교로 갱신을 직접 관리해야 한다.
- 채택하지 않은 이유: 3일 반에 이 비용은 동시성 구현 깊이를 갉아먹는다. 이 과제에서 아키텍처 순수성은 동시성보다 후순위다.

### 대안 B. 핵심 애그리거트만 분리

- 장점: 비용과 순수성의 절충.
- 채택하지 않은 이유: 기준이 흐릿해져 "왜 이건 분리하고 저건 통합했나"를 매번 설명해야 한다. 일관성 없는 구조가 어느 한쪽보다 나쁘다.

## 결정

통합한다. 도메인 객체에 `@Entity`를 직접 붙인다.

대신 대가를 규칙으로 제한한다. `domain` 패키지는 `jakarta.persistence`와 JDK에만 의존할 수 있고, Spring Data의 `JpaRepository`는 `adapter/out/persistence`에 격리하며 도메인에는 순수 리포지토리 인터페이스만 둔다.

## 근거

통합의 실질적 위험은 "도메인이 프레임워크에 오염되는 것"인데, 오염 경로의 대부분은 JPA 자체가 아니라 Spring 타입과 리포지토리 인터페이스다. 그 경로를 규칙으로 막으면 통합의 이득(코드 절반, 더티 체킹)을 취하면서 위험의 대부분을 제거할 수 있다.

## 대가

- 도메인 테스트에 `jakarta.persistence` 어노테이션이 클래스패스에 있어야 한다.
- JPA 요구사항(기본 생성자, 지연 로딩 프록시)이 도메인 설계에 스며든다. 기본 생성자는 `protected`로 제한해 완화한다.
- "Clean Architecture인데 도메인이 JPA에 묶였다"는 지적 가능성. 이 문서가 답이다.

## 되돌리는 비용

중간이다. 나중에 분리하려면 애그리거트마다 영속성 모델과 매퍼를 추가하면 되고, 도메인 인터페이스는 이미 분리돼 있어 어댑터만 바뀐다.
