# ADR-0055. 레이어 경계 결정 셋 — 이름·데이터 계약·외부 연동

- 날짜: 2026-08-15
- 상태: 채택
- 관련 feature: 전체
- **결정자: 관리자**

> 소급 기록이다. 셋 다 스택 전환([ADR-0050](ADR-0050-기술-스택-전환.md)) 직후 규칙 문서를 다시 쓰는 과정에서 관리자가 지시했다.
> 서로 다른 결정이지만 **전부 "레이어 경계에서 무엇이 오가는가"**라 한 문서에 묶었다.

## 결정 ①. 바깥 레이어 이름을 `adapter`가 아니라 `presentation`으로

### 문제

Clean Architecture 통칭은 `adapter`(어댑터)인데, 그 안에 들어오는 것(HTTP 컨트롤러)과 나가는 것(DB·Redis)이 섞인다. 둘은 의존 방향이 다르다. 컨트롤러는 애플리케이션을 부르고, 영속성은 애플리케이션이 부른다.

관리자 지시 원문: **"adapter 는 presentation 으로 수정해줘"**

### 결정

바깥을 둘로 나눈다. **`presentation`**(들어오는 쪽 — 라우터, 요청·응답 모델)과 **`infrastructure`**(나가는 쪽 — 영속성, Redis, 결제).

### 대가

통칭에서 벗어나 처음 보는 사람이 한 번 더 확인해야 한다. 다만 **디렉터리 이름이 의존 방향을 말해주는 값이 더 크다고 봤다.**

## 결정 ②. 레이어 간 데이터는 Pydantic 모델로 주고받는다

### 문제

파이썬은 컴파일러가 없어서 dict를 그냥 넘기면 **키 오타가 런타임까지 산다.** 게다가 API 응답 표기(`camelCase`)와 파이썬 표기(`snake_case`)가 다른데, 변환을 손으로 하면 빠뜨린 곳이 조용히 어긋난다.

관리자 지시 원문: **"각 레이어간 통신은 Pydantic으로 하자 - SQLModel 과의호환성 + Swagger 자동화 고려"**

### 결정

레이어를 넘는 데이터는 전부 Pydantic 모델이다. dict를 넘기지 않는다.

- `presentation`의 응답 모델은 **`ApiModel`을 상속**해 `camelCase` 변환을 한 곳에서 받는다
- `Command`·`Result`는 `frozen`이다

### 근거

관리자가 든 근거 둘이 맞았다. SQLModel이 Pydantic 위에 있어 **도메인 모델과 계약 모델이 같은 도구**를 쓰고, FastAPI가 Pydantic에서 **Swagger를 자동 생성**한다. 후자는 나중에 F05가 백엔드와 맞추는 수단이 됐다.

### 대가

**`ApiModel` 상속을 빠뜨리면 그 엔드포인트만 조용히 `snake_case`로 나간다.** 읽는 쪽에서는 필드가 없는 것으로 보이고, 부하테스트에서는 표본이 0건이 되어 게이트가 통과해버린다. F01이 이걸 막는 전수 검사 테스트를 `common`에 넣었다.

## 결정 ③. 외부 결제는 언제든 갈아 끼울 수 있게 두고, 지금은 가짜로 만든다

### 문제

결제는 이 과제의 관심사가 아니다. 그런데 예약 흐름에는 결제 단계가 있어야 상태 전이(확정·거절·만료)를 증명할 수 있다.

관리자 지시 원문: **"외부 결제 모듈은 언제든 신규구현해서 어댑터처럼 붙일수있도록 구현 - 우리는 일단 가짜 결제모듈을 구현해두고 그게 동작하는것처럼 해두자"**

### 결정

`PaymentPort` Protocol을 두고 `FakePaymentAdapter`를 구현한다. 유스케이스는 포트만 안다.

**거절은 예외가 아니라 정상 응답의 한 갈래다.** 결제 거절은 `200 + status: CANCELLED`로 나간다.

### 근거

거절을 예외로 만들면 **"시스템이 고장난 것"과 "결제가 거절된 것"이 같은 경로로 흐른다.** 둘은 화면도 다르고 재시도 여부도 다르다.

### 대가

가짜 구현이라 실제 결제사의 타임아웃·중복 승인·부분 실패를 못 본다. **거절률 기본값을 0.0으로 고정**해 테스트가 가끔 깨지지 않게 했는데, 그만큼 실전과 멀어진다.
