# ADR-0004. 병렬 작업 충돌 정책

- 날짜: 2026-08-14
- 상태: 채택
- 관련 feature: 전체 (워크플로우)

## 문제

feature 하나를 agent 세션 하나가 맡고, 관리자가 2~3개 세션을 동시에 돌린다. 이때 코드 충돌을 어떻게 다룰지 정해야 했다. 전부 강하게 잠글지(사전 분할), 자유롭게 두고 병합에서 풀지(사후 병합) 논의가 필요했다.

핵심 관찰은 충돌이 두 종류라는 것이다. 텍스트 충돌은 git이 잡아주지만, **의미 충돌**(두 세션이 같은 도메인을 다른 전제로 수정, git은 깨끗하게 자동 병합, 도메인 불변식은 파괴)은 git이 못 잡는다. 동시성이 주제인 과제에서 도메인 불변식이 조용히 깨지는 것이 가장 비싼 사고다.

## 산출물

`docs/architecture/parallel-work.md`. feature 스펙의 소유 범위 절.

## 검토한 대안

### 대안 A. 전부 hard (엄격한 사전 분할)

- 장점: 충돌이 거의 사라진다.
- 채택하지 않은 이유: 정확히 나누려면 애그리거트 경계를 미리 알아야 하는데 그건 스펙이 끝나야 안다. 예약 도메인은 애그리거트가 몇 개 안 돼서 억지로 나누면 설계가 어색해진다. 3일 반에 사전 분할 설계 비용이 아깝다.

### 대안 B. 전부 soft (사후 병합)

- 장점: 세션이 자유롭고 빠르다.
- 채택하지 않은 이유: 의미 충돌이 테스트를 빠져나가면 발견 자체가 안 된다. 발견돼도 병합 시점에 몰려서 디버깅이 비싸다.

## 결정

계층별 차등 + 코어 순차.

| 대상 | 정책 |
|---|---|
| 도메인 모델 | hard (소유 세션만 수정) |
| Flyway 마이그레이션 | hard (feature별 번호 대역: V101~, V201~, ...) |
| 공통 설정·인프라 | 사전 확정 (하네스 세팅 때 미리 구축) |
| 애플리케이션·어댑터·테스트·문서 | soft (충돌 시 병합) |

그리고 예약 코어(Reservation + 재고 + 동시성 제어)는 병렬 대상에서 제외하고 한 세션이 순차로 완성한다. 병렬은 코어 병합 후 그 위에 붙는 것들(조회, 프로모션, 부하테스트, 문서)에만 적용한다.

## 근거

의미 충돌의 비용은 계층마다 다르다. 도메인은 가장 비싸고 git이 못 잡으므로 hard, 어댑터는 파일이 유스케이스별로 갈려 충돌 자체가 드물므로 soft. 비용이 있는 곳에만 규칙 비용을 지불하는 배치다.

## 대가

- 코어 구간(약 하루)은 병렬화 이득을 포기한다.
- 소유 선언·번호 대역 같은 관리 오버헤드가 생긴다.
- soft 영역에서 병합 충돌은 여전히 일어날 수 있다. 감수한다.

## 되돌리는 비용

낮다. 문서 규칙이라 언제든 조정할 수 있다. 다만 느슨하게 바꾼 뒤 의미 충돌이 나면 그 복구 비용은 크다.
