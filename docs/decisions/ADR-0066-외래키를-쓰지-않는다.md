# ADR-0066. 외래키를 쓰지 않는다 — 참조는 id 값으로만

- 날짜: 2026-08-17
- 상태: 채택
- **결정자: 관리자**

## 문제

스키마에 외래키 4개가 걸려 있었다 — `room_type→hotel`, `room_daily_inventory→room_type`, `reservation→room_type`, `reservation_status_history→reservation`. 관리자의 설계 방침은 처음부터 "외래키 없이 참조 id만 기록"이었는데 구현이 어긋나 있었다.

## 결정

**외래키 제약 4개를 전부 제거한다.** 참조는 id 값으로만 기록하고, 존재 검증은 애플리케이션이 한다.

관리자 지시 원문:

> "FK 쓰지마." / "내가 원하는건 FK 제약으로 인한 성능 저하나 데드락을 배제하고 싶은거야. 논리적으로 신경써야 할것도 많으니"

## 근거

**외래키 검사는 공짜가 아니다 — 쓰기마다 부모 행을 잠근다.** InnoDB는 자식 행을 INSERT할 때 참조 무결성을 확인하면서 **부모 행에 공유 잠금(S lock)** 을 건다. 이 시스템의 가장 뜨거운 경로가 정확히 그 모양이다:

- 예약 INSERT마다 해당 `room_type` 행에 공유 잠금
- 상태 이력 INSERT마다(모든 전이에서 일어난다) 해당 `reservation` 행에 공유 잠금

인기 객실타입 하나에 예약이 몰리면 **모든 예약 트랜잭션이 같은 부모 행의 잠금을 공유**하게 되고, 다른 잠금(재고 행 X 잠금)과 얽히는 조합이 하나 더 생긴다. 데드락은 잠금 종류가 늘수록 조합적으로 늘어난다 — 이 프로젝트는 잠금 순서를 정렬 하나로 통제하고 있는데(3.3절), 외래키 잠금은 그 통제 밖에서 암묵적으로 걸린다.

**관리 부담도 실재한다.** 시드·마이그레이션·테스트 데이터를 넣는 순서가 부모→자식으로 강제되고, 뺄 때는 역순이 강제된다. 신경 쓸 목록이 하나 더 있는 셈이다.

**애플리케이션 검증은 이미 있다.** 예약 생성은 객실타입을 먼저 조회해 없으면 404를 낸다. 이력은 방금 만든 예약의 id로만 쓴다. 외래키가 실제로 막아주던 운영 경로가 없다.

## 사실 확인 — 연쇄 삭제에 대하여

검토 중에 "부모를 지우면 자식도 지워지는 문제"가 우려로 나왔다. **외래키의 기본 동작은 그 반대다** — `ON DELETE`를 지정하지 않으면 RESTRICT라서 자식이 있는 부모의 삭제가 **거부**된다. 연쇄 삭제는 `ON DELETE CASCADE`를 명시했을 때만 일어나고, 이 스키마의 외래키 4개에는 없었다. 결정의 근거는 위의 잠금·관리 부담이고, 이 항목은 사실 관계를 기록으로 남긴다.

## 어떻게 제거했나

- 마이그레이션 `055_drop_foreign_keys` — 제약 4개 DROP. `downgrade()`가 역순으로 되살린다
- 모델(SQLModel)에서 `ForeignKey` 선언 4개 제거 — 모델-스키마 대조(T28)가 일치를 검증한다
- **인덱스는 남긴다.** 자식→부모 조회가 타는 경로다 — `idx_reservation_room_type`, `idx_history_reservation`은 명시 인덱스라 그대로 있고, `room_type.hotel_id`와 재고 PK는 기존 인덱스의 선두 컬럼이라 애초에 별도 인덱스가 없었다

## 대가

- **DB가 참조 무결성을 지켜주지 않는다.** 버그로 없는 객실타입 id가 예약에 들어가도 DB는 침묵한다. 마지막 방어선 하나를 코드 검증과 맞바꾼 것이다.
- 부하 실측(22만 건)에서 외래키가 병목으로 **관측되지는 않았다.** 이 결정은 측정된 병목의 제거가 아니라 잠금 조합을 줄이는 설계 방침이다 — 그 구분을 숨기지 않는다.
- 초과 판매를 막는 제약(CHECK 11 · UNIQUE 4)은 그대로다. 이 결정은 3층 방어를 건드리지 않는다.

## 되돌리는 비용

**싸다.** `055`의 `downgrade()` 한 번이면 복원된다. 고아 행이 이미 생겼다면 복원 전에 정리해야 한다는 것이 유일한 조건이다.
