# ADR-0003. 상태 전이를 전이 테이블로 구현

- 날짜: 2026-08-14
- 상태: 채택 (결론 유효)
- 관련 feature: 예약 코어

> **결론(전이 테이블)은 그대로다.** 아래 기각한 대안 중 C·D는 Java·Spring 것이라 지금은 존재하지 않는
> 선택지다. 지운 게 아니라 남겨둔 이유는, **당시 무엇과 비교해서 골랐는지가 결정의 절반**이기 때문이다.
> 스택이 바뀌어도 기각 사유("상태별 부가 데이터는 nullable 컬럼으로 감당 가능", "라이브러리를 쓰면
> 전이 표가 코드 밖으로 나간다")는 그대로 성립한다.

## 문제

예약은 상태(대기, 확정, 체크인, 취소 등)를 가지며 정해진 규칙으로만 전이해야 한다. 요구사항에 "상태 머신 (not if-else)"이 명시되어 있어 if-else 분기는 배제하고, 남은 방식 중에서 골라야 했다.

if-else의 문제는 전이 규칙이 코드 흐름 속에 흩어진다는 것이다. 상태 5개면 조합이 20개인데 어떤 걸 다뤘는지 코드만으로 알 수 없고, 상태 추가 시 모든 분기를 다시 훑어야 하며, 규칙을 문서로 뽑을 수 없다.

## 산출물

`ReservationStateMachine` 클래스. `(현재 상태, 이벤트) -> 다음 상태` 맵 하나가 유일한 판단 근거다. 스펙 문서의 전이 표와 1:1 대응한다.

## 검토한 대안

### 대안 A. enum이 허용 전이 집합을 보유

- 장점: 가장 간단하다. `PENDING.canTransitTo(CONFIRMED)` 형태로 읽기 쉽다.
- 단점: 전이 사유(이벤트)가 없다. 사용자 취소와 결제 실패 취소를 구분할 수 없다.
- 채택하지 않은 이유: 멱등성 처리("같은 이벤트 재수신")와 이력 기록에 이벤트가 필요하다.

### 대안 B. State 패턴 (상태별 클래스)

- 장점: 상태별 로직이 많을 때 응집도가 높다.
- 채택하지 않은 이유: 예약 도메인은 상태별 로직이 얇다. 클래스 수만 늘어난다.

### 대안 C. sealed interface + pattern matching (Java 21)

- 장점: 상태별로 다른 데이터를 타입으로 강제할 수 있다. `Cancelled(reason, cancelledAt)`.
- 채택하지 않은 이유: ADR-0002에서 도메인과 JPA를 통합했는데, sealed 계층의 JPA 매핑이 지저분하다. 상태별 부가 데이터는 nullable 컬럼으로 감당 가능한 수준이다.

### 대안 D. Spring Statemachine 라이브러리

- 채택하지 않은 이유: 상태 6개 수준에는 과하다. 학습·설정 비용이 이득을 넘는다.

## 결정

전이 테이블 방식. `(상태, 이벤트)` 쌍을 키로 하는 맵을 두고, 전이 판단은 이 표로만 한다. `setStatus`는 만들지 않고 외부는 이벤트만 던진다.

## 근거

세 가지가 결정적이었다.

1. 규칙이 완전히 데이터라서 스펙 문서의 표와 코드가 1:1로 대응하고, 테스트에서 전 조합을 순회해 전수 검증할 수 있다.
2. 이벤트가 명시적이라 멱등성 처리(같은 이벤트 재수신 시 조용히 성공)와 취소 사유 구분이 자연스럽다.
3. 조건부 UPDATE(`SET status=? WHERE id=? AND status=?`)의 WHERE 조건이 표에서 그대로 유도된다. 동시성 제어와 직결된다.

## 대가

- 전이 시 부가 로직(취소 시각 기록 등)은 표 밖에서 처리해야 한다. 표는 "갈 수 있는가"만 답한다.
- 상태별로 크게 다른 데이터를 들게 되면 대안 C보다 타입 안전성이 떨어진다.

## 되돌리는 비용

낮다. 전이 판단이 한 클래스에 모여 있어서, 다른 방식으로 바꿔도 호출부는 `handle(event)` 그대로다.
