# ADR-0005. 다이어그램 표기는 Mermaid 표준형

- 날짜: 2026-08-14
- 상태: 채택
- 관련 feature: 전체 (문서 규칙)

## 문제

시퀀스·도메인 모델·ERD를 글과 표로만 쓰니 관리자 검토 때 이해 비용이 컸다. 문서에 그림을 넣는 표준을 정해야 했고, 제출물이 GitHub repo라서 GitHub 웹에서 렌더링되는지가 제약이었다.

## 산출물

`docs/architecture/diagram-rules.md`. 스펙 템플릿의 다이어그램 필수 조항.

## 검토한 대안

시안 4종을 실제로 만들어 관리자가 직접 비교했다.

- **A. Mermaid 표준형**: 목적별 정식 다이어그램(sequence·class·er·state), 장식 없음.
- **B. Mermaid 그룹·색상형**: subgraph·색으로 방어선·구역 강조. 작성자 추천안이었으나 관리자 가독성 판단에서 밀렸다.
- **C. 커스텀 HTML 카드형**: 표현 자유도 최고. GitHub·Bear에서 렌더링되지 않아 기각.
- **D. Mermaid 최소 + 표 병기**: 그림은 뼈대만. 단독 채택은 안 됐지만 "세부는 표 담당" 원칙은 규칙에 흡수했다.

## 결정

시안 A(Mermaid 표준형)를 채택한다. 세부 정보는 표가 담당한다는 D의 원칙을 병용한다.

## 근거

관리자가 직접 읽어보고 A가 가장 잘 읽힌다고 판단했다. 검토 주체의 가독성이 이 규칙의 존재 이유이므로 그 판단이 결정 기준이다. GitHub 렌더링 제약도 충족한다.

## 대가

- 색·그룹 강조가 없어 방어 계층 같은 설계 의도는 그림이 아니라 본문·표로 전달해야 한다.
- Bear에서는 코드로 보이므로 검토 시 세션 패널이나 GitHub 링크가 필요하다.

## 되돌리는 비용

낮다. 표기 규칙이라 문서를 고치면 된다. 단 문서가 쌓일수록 전환 비용이 커지므로 바꾸려면 빨리 바꾸는 게 낫다.
