# ADR-0060. 프론트엔드 스택 — Next.js + TypeScript, 런타임 라이브러리 0

- 날짜: 2026-08-15 (승인) / 2026-08-16 (구현 완료 후 기록)
- 상태: 채택
- 관련 feature: F05

## 문제

화면 세 개(검색·주문서·예약 상세)를 마감 이틀 전 상황에서 만들어야 했다. 제약: ① F05는 절단 1순위라 잘려도 남는 것이 커야 한다 ② 백엔드(F01)가 아직 없어 가짜 응답으로 끝까지 만들 수 있어야 한다 ③ 교육 노트가 산출물의 절반이라, 도구 뒤에 숨지 않은 코드가 필요하다. 프레임워크는 브리핑에서 Next.js로 확정됐고 나머지(언어·스타일링·페칭·상태 관리)를 정해야 했다.

## 산출물

`frontend/` 전체. 런타임 의존성 next·react·react-dom 셋. `lib/`(contracts·api·mock-backend·booking-flow·error-messages·dates·countdown·reservation-view 등 + 테스트 115건), `app/`(화면 3개), `components/`(2개). First Load JS 103kB(프레임워크 기준선), 화면 코드 경로당 1kB 미만.

## 검토한 대안

### 대안 A. TanStack Query + zod + Tailwind (통상 조합)

- 장점: 캐시·재검증·선언적 검증·유틸리티 클래스 — 큰 앱에서 검증된 조합.
- 단점: 번들 증가, 학습 대상 3개 추가, 교육 노트가 도구 사용법 설명이 됨.
- 채택하지 않은 이유: 호출 4종·화면 3개에 캐시 계층이 할 일이 없고, 재시도 정책(409 2회·REQUEST_IN_PROGRESS 3회)은 이 화면 고유 규칙이라 어차피 직접 쓴다.

### 대안 B. 상태 관리 라이브러리 (Zustand 등)

- 장점: 화면 간 공유 상태가 많아지면 표준적 해법.
- 단점: 지금은 보관할 상태가 없다 — 화면 간 공유는 검색 조건·확인번호뿐이고 둘 다 URL에 실린다.
- 채택하지 않은 이유: "왜 있는지 모르는 의존성"이 된다. 이 판단 자체가 교육 노트(프론트엔드-상태)의 본문이 됐다.

## 결정

TypeScript + 전역 CSS(토큰 변수) + fetch 직접(`lib/api.ts` 한 곳) + 손수 쓴 경계 검증(`lib/contracts.ts`) + 상태 관리 없음(URL + useState).

## 근거

선택 기준은 브리핑의 한 줄 — "화면 세 개에 그게 정말 필요한가." 프론트 의존성의 비용은 서버와 달리 모든 사용자의 로딩 시간이 진다(교육 노트 「번들」). 계약 사본과 검증을 `contracts.ts` 한 곳에 모으면 Swagger 대조가 "한 파일 고치고 타입 오류를 따라간다"로 끝난다 — 라이브러리 스키마보다 이 요구에 직접적이다.

## 대가

- 검증 함수·재시도 로직을 손으로 유지한다. 계약 변경 시 자동 생성이 없다.
- 화면·상태가 늘면(목록·필터·장바구니류) 이 결정의 전제가 무너진다 — 그때는 도입 비용을 다시 치러야 한다.

## 되돌리는 비용

낮다. 페칭 라이브러리는 `lib/api.ts` 뒤에, 검증은 `lib/contracts.ts` 뒤에 있어 화면 코드 변경 없이 교체 가능. 상태 관리는 필요해지는 시점에 그 상태만 옮기면 된다.
