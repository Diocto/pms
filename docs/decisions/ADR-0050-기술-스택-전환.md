# ADR-0050. 기술 스택을 FastAPI + SQLModel + Dependency Injector로 전환

- 날짜: 2026-08-15
- 상태: 채택
- 관련 feature: 전체
- 대체하는 결정: [ADR-0001 기술 스택 선정](ADR-0001-기술-스택-선정.md)의 언어·프레임워크 항목

## 문제

마감이 2026-08-17 23:59이고, 이 결정 시점(8/15 11시)에 남은 시간은 약 61시간이다. 스펙 4벌과 부하테스트 자산은 완성됐지만 **구현 코드는 0줄**이다.

관리자가 상황을 이렇게 정리했다.

> 하다 보니 코드 검토를 전반적으로 해야 할 것 같은데 2일은 시간이 부족한 듯. 익숙한 FastAPI + SQLModel + Dependency Injector 이렇게 가야 할 것 같다.

핵심은 **구현만 끝내면 되는 것이 아니라는 점**이다. 이 과제는 동시성·멱등성·상태 전이를 수치로 증명하는 것이 목표이고, 그러려면 짜고 나서 **읽고 고칠 시간**이 있어야 한다. 손에 익지 않은 스택에서는 구현에 시간을 다 쓰고 검토할 여력이 남지 않는다.

## 결정

| 항목 | 전 (ADR-0001) | 후 |
|---|---|---|
| 언어 | Java 21 | **Python** |
| 프레임워크 | Spring Boot 4.0.7 (MVC) | **FastAPI** |
| ORM | Spring Data JPA / Hibernate | **SQLModel (SQLAlchemy)** |
| 조립 | Spring DI 컨테이너 | **Dependency Injector** |
| 마이그레이션 | Flyway | **Alembic** |
| 빌드 | Gradle | Python 패키지 관리자 |
| 테스트 | JUnit 5 | **pytest** |

**바뀌지 않는 것.** MySQL 8.4, Redis 7.4, Testcontainers(파이썬 구현체), k6, `X-User-Id` 헤더 인증, `ddl-auto` 없이 마이그레이션이 스키마의 진실이라는 원칙.

## 왜 지금이 가장 싼 시점인가

**전환 비용은 이미 만든 코드의 양에 비례하는데, 그 양이 0이다.**

승인 게이트를 지킨 결과다. "스펙 승인 전에는 코드를 쓰지 않는다"는 규칙 때문에 8시간 동안 `src/` 변경이 한 건도 없었고, 그래서 버릴 코드가 없다. 승인이 늦어진 것이 여기서는 이득이 됐다.

## 무엇이 살아남는가

문서 작업의 대부분이 언어와 무관하다.

**그대로 유지**

- `docs/spec/00-problem-and-scope.md` — 승인된 문제 정의와 범위 전체
- 도메인 설계: 상태 전이 표 36칸, 객실타입 × 날짜 재고 모델, 자연키 복합 PK, CHECK 제약
- 시드 데이터 계약: 날짜 범위 2026-08-01~10-29, 호텔 2·객실타입 5, 경합 실험용 타입 지정
- API 계약: 경로, 상태 코드, 멱등 재요청 200, 결제 거절 200 + CANCELLED, 확인번호 형식

**다시 쓴다**

## 검토한 대안

### 대안 A. Java·Spring 유지

- **장점:** 전환 비용 0. 하네스와 스펙이 이미 그 전제로 완성돼 있다. 빌드·Testcontainers 검증도 통과했다.
- **채택하지 않은 이유:** 관리자가 검토 시간을 확보할 수 없다고 판단했다. 이 과제의 평가 대상은 코드량이 아니라 **설계 판단과 그 증명**인데, 검토 없이 구현만 밀어내면 그 판단을 보여줄 수 없다. 익숙하지 않은 스택에서 리뷰어 지적을 받아 고치는 왕복은 특히 느리다.

### 대안 B. 절충 — 코어만 Java, 나머지 축소

- **채택하지 않은 이유:** 이 프로젝트의 어려운 부분이 전부 코어에 있다. 코어를 익숙하지 않은 스택에 두면 문제가 그대로 남는다.

### 대안 C. FastAPI를 async로 사용

- **채택하지 않은 이유:** 별도 판단으로 미룬다. 동기 + 스레드풀이면 현재 설계가 거의 그대로 옮겨지고 동시성 테스트 방식도 유지된다. 부하는 k6가 프로세스 밖에서 걸므로 이 규모에서 async의 처리량 이득이 없고, async SQLAlchemy의 세션 스코프 함정을 새로 떠안는다. **F01 스펙의 결정 항목으로 올려 관리자 확인을 받는다.**

## 트레이드오프

- **하네스를 다시 써야 한다.** 규칙 4종 + 리뷰어 3종 + 소유 표현으로 약 54KB다. PM 작업이며 1~2시간으로 본다.
- **스펙 재승인이 필요하다.** 도메인 판단은 유효하지만 구현 계약 절이 바뀌므로 승인 요청을 다시 올린다. 다만 관리자 판단 6건은 그대로 유효해 재검토 범위가 좁다.
- **Spring Boot 4.x 레퍼런스 부족이라는 리스크가 사라진다.** `00-problem-and-scope.md` 리스크 표의 한 항목이 해소된다.
- **`@Transactional` 프록시 자기 호출 함정이 사라진다.** SQLAlchemy는 세션이 명시적이라 이 버그 종류가 존재하지 않는다. 리뷰 항목이 하나 줄어든다.
- **actuator가 없다.** F04의 락 스위치 검증이 `/actuator/info`에 걸려 있었으므로 대체 엔드포인트 계약이 필요하다. 응답 형식은 그대로 유지한다.
- **Alembic은 기본이 해시 리비전이다.** `--rev-id`로 번호를 명시해 기존 대역 체계(F01 001~099, F02 201~299, F03 301~399)를 그대로 유지한다.

## 결론

전환한다. 근거는 **남은 시간에 구현과 검토를 모두 하려면 익숙한 도구가 필요하다**는 것이고, 지금이 전환 비용이 최소인 시점이다.

`ADR-0001`은 폐기하지 않는다. MySQL·Redis·Testcontainers·k6 선택과 그 근거는 그대로 유효하며, 언어·프레임워크·ORM·마이그레이션 항목만 이 문서가 대체한다.
