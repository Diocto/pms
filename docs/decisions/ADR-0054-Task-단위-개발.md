# ADR-0054. 코드를 쓰기 전에 Task 목록을 먼저 만든다

- 날짜: 2026-08-15
- 상태: 채택
- 관련 feature: 전체 (하네스)
- **결정자: 관리자**

## 문제

스펙이 승인되면 세션이 바로 구현에 들어가는 구조였다. 스펙은 "무엇을 만드는가"를 정하지만 **"어떤 순서로 끝내는가"는 아무 데도 없었다.**

이게 두 가지를 못 하게 했다.

- **진행 상황을 물을 수 없다.** "재고 도메인 구현 중"이라는 답은 30% 됐는지 90% 됐는지 알려주지 않는다.
- **잘렸을 때 뭐가 남는지 모른다.** 이 프로젝트는 절단 순서가 정해져 있는데, 한 덩어리로 만들면 잘리는 순간 전부 사라진다.

관리자 지시 원문:

> "피쳐 개발시 Task 단위로 업무를 나눠서 먼저 만들고, 거기에 맞춰서 개발해야한다"
> "현황페이지는 FXX 단위로 리스트뷰 세션/현재 작업 Task/상태(문서/작업/대기 등) 이렇게 보이게해주고, 해당 리스트 누르면 각 세션의 상세가 보이게해줘"

## 결정

**`dev-cycle`의 0단계로 Task 목록 작성을 넣는다.** 코드를 쓰기 전에 `docs/tasks/FXX.md`를 만든다.

형식을 고정했다. 사람과 현황판이 같은 파일을 읽는다.

```
| ID | Task | 상태 | 완료 기준 |
```

- 상태는 **대기 · 진행 · 완료 · 보류** 넷
- **`진행`은 한 번에 하나만.** 둘이면 둘 다 안 끝나고 있는 것이다
- 완료 기준은 관찰 가능한 문장 ("잘 동작한다" 금지, "K3·K4가 초록"처럼)
- 상태 변경을 커밋에 함께 담는다

## 검토한 대안

### 대안 A. 세션이 알아서 진행 보고

- 채택하지 않은 이유: 보고 형식이 제각각이라 비교가 안 된다. 그리고 **보고하려면 작업을 멈춰야 한다.**

### 대안 B. 커밋 로그로 진행을 본다

- 장점: 별도 관리가 필요 없다. 커밋은 일을 해야만 생긴다.
- 채택하지 않은 이유: **끝을 알 수 없다.** 커밋 10개가 쌓여도 남은 게 3개인지 30개인지 모른다. (다만 이 장점은 살려서 현황판이 커밋 타임라인도 함께 보여준다)

## 근거

**먼저 만들게 한 이유가 셋이다.**

1. **끝을 정의하게 된다.** 쪼개면서 완료 기준을 못 쓰는 덩어리가 드러나고, 그건 설계가 덜 됐다는 신호다. 코드를 쓴 뒤에 알면 늦다.
2. **순서의 이유를 묻게 된다.** 앞의 것이 뒤의 것의 전제인지 그냥 나열인지 갈린다.
3. **잘릴 때 무엇이 남는지 알 수 있다.**

**실제로 효과가 바로 나왔다.** 다섯 세션이 한 시간 안에 Task 75개를 등록했고, 그 과정에서 스펙의 빈 곳이 둘 나왔다.

- F01: "설정 노출의 키 충돌을 확인할 테스트가 없다"
- F03: "계약표 대조가 착수 순서에 빠져 있다"

**둘 다 완료 기준을 쓰려고 할 때에야 물어진 것들이다.**

## 대가

- **표를 갱신하지 않으면 거짓 보고가 된다.** 현황판이 이 파일을 읽으므로 낡은 상태는 곧 틀린 정보다.
- **표에 없는 일을 하면 "작업 없음"으로 보인다.** 실제로 F05가 리뷰 회차를 도는 동안 이 문제가 났다. 현황판에 "표 밖 작업 중" 표시를 붙여 완화했지만, 근본적으로는 리뷰 회차도 Task로 올려야 한다.
- Task를 쪼개는 시간이 든다. 세션당 20~30분.

## 되돌리는 비용

**싸다.** 파일을 안 읽으면 그만이다. 다만 현황판이 이 형식에 의존하므로 형식을 바꾸면 파서도 바꿔야 한다.
