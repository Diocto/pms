# ADR-0056. 검토와 승인을 어떻게 운영하는가

- 날짜: 2026-08-15
- 상태: 채택
- 관련 feature: 전체 (하네스)
- **결정자: 관리자**

> 소급 기록이다. 관리자가 여러 시점에 내린 운영 결정을 한 문서에 모았다.
> **전부 "사람이 어디서 무엇을 보고 결정하는가"**에 관한 것이다.

## 문제

세션이 다섯이면 관리자가 봐야 할 것이 다섯 배가 된다. 그런데 관리자의 시간은 그대로다. **무엇을 보고 무엇을 위임할지 정하지 않으면 관리자가 병목이 된다.**

실제로 그렇게 됐다. 승인 대기 항목이 18건 쌓이는 동안 네 세션이 멈춰 있었다.

## 결정 ①. 검토는 아티팩트 페이지로, 코멘트를 달 수 있게

관리자 지시 원문:

> "내가 봐야할것은 - 항상 클로드 아티팩트로 페이지 열어서 검토 페이지 만들어줘 + 모든 검토 페이지는 내가 코멘트를 달수 있어야한다"

**근거:** 마크다운 파일을 터미널이나 GitHub에서 읽으면 **읽은 것과 답한 것이 갈린다.** 답을 대화에 쓰면 그 답이 문서에 안 붙는다. 항목마다 동의·이견·보류를 누르고 메모를 다는 페이지면 **읽기와 답하기가 한 자리에서 끝난다.**

**대가:** 페이지를 만드는 시간이 든다. 그리고 아티팩트는 저장이 안 되므로 브라우저 로컬 저장 + 내보내기로 답을 회수해야 한다.

## 결정 ②. PR 병합 판단을 PM에게 위임

관리자 지시 원문:

> "해당 부분 처리되면 PR 은 너가 판단하고 처리해"

**근거:** 병합은 **되돌리기 쉽고 지연 비용이 크다.** 세션 하나가 PR을 열고 관리자 승인을 기다리면 그 시간 동안 다른 세션이 그 커밋을 못 받는다. 반대로 잘못 병합해도 revert가 한 줄이다.

**대가:** PM이 코드를 안 보고 병합한다. 리뷰 품질은 세션의 리뷰어 3종에 전적으로 의존한다.

**적용 결과:** 15분 주기 작업이 열린 PR을 자동으로 확인해 병합한다. F01의 회차가 병합 지연 없이 쌓였다.

## 결정 ③. 현황판을 만들어 상태를 직접 본다

관리자 지시 원문:

> "현황판은 - 클로드에 기능이 없다면 로컬서버나 아티팩트로 하나 만들어서 실시간 페이지를 만들어줘"
> "15분마다 각 세션의 작업내역을 pms 운영 현황판에 업데이트 하도록해"

**근거:** 보고를 받아야 아는 상태는 **보고가 늦으면 모르는 상태**다. git과 Task 파일을 직접 읽는 페이지가 있으면 세션이 보고할 필요가 없어진다. 이게 나중에 [ADR-0053](ADR-0053-PM-역할-축소.md)에서 진행 보고를 아예 없애는 근거가 됐다.

**대가:** 현황판이 틀리면 아무도 모른다. 실제로 두 번 틀렸다 — 두 점 diff로 모든 세션이 "코드 있음"으로 오표시된 것, Task 표 밖 작업을 "작업 없음"으로 보여준 것. **현황판 자체를 검증할 수단이 없다는 게 이 결정의 약점이다.**

## 결정 ④. 승인은 항목 단위로 받되, 답하지 않은 것은 동의로 본다

**근거:** 결정이 18개인데 전부 개별 답을 요구하면 관리자가 시작을 못 한다. **[필수]·[확인]·[참고]로 등급을 나누고 [확인]·[참고]는 침묵을 동의로** 처리하면, 관리자는 뒤집힐 만한 것에만 시간을 쓴다.

**대가:** **동의하지 않았는데 동의로 처리될 수 있다.** 실제로 PM이 이 규칙을 확대 해석해 F01의 17개를 착수 신호로 통과시켰다가 철회한 일이 있다. 관리자가 그 문서를 직접 검토 중이었다.

**보완:** 되돌리기 비싼 항목을 앞에 세우게 했다. F01의 17개 중 넷(D13·D14·D16·D19·D20)만 뒤집으면 스키마나 계약이 바뀌고 나머지 열둘은 코드 몇 줄이다. **관리자가 다섯 줄만 읽으면 나머지는 나중에 봐도 된다.**

## 되돌리는 비용

넷 다 싸다. 운영 방식이라 코드에 박혀 있지 않다. 다만 ③ 현황판은 도구(`tools/dashboard.py`)가 있어서, 형식을 바꾸면 Task 파일 파서를 함께 고쳐야 한다.
