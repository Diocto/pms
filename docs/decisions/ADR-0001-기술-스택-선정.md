# ADR-0001. 기술 스택 선정

- 날짜: 2026-08-14
- 상태: 채택
- 관련 feature: 전체

## 문제

숙박 예약 시스템 과제의 기술 스택을 정해야 했다. 제약은 세 가지였다.

- 마감이 2026-08-17로 실질 3일 반이다.
- 지원 기업의 스택은 Kotlin + Spring이다. 과제 안내는 "지원자에게 가장 적합한 언어"를 쓰라고 했다.
- 작성자의 경험은 FastAPI가 가장 깊고, Java + Spring은 saga 패턴 구현까지 해본 수준이다. Kotlin은 익숙하지 않다.

과제의 본질이 동시성 제어라서, 스택 선택은 "빨리 만들 수 있는가"보다 "동시성 제어를 설명 가능한 수준으로 구현할 수 있는가"로 판단했다.

## 산출물

`build.gradle`, `docker-compose.yml`, `application.yml`, 프로젝트 전체 구조.

## 검토한 대안

### 대안 A. Kotlin + Spring Boot

- 장점: 지원 기업 스택과 완전히 일치. sealed class로 상태 표현이 깔끔하다.
- 단점: 문법이 낯설어 3일 반 동안 문법에 시간을 뺏길 수 있다. 면접에서 Kotlin 관련 질문에 깊이가 안 나온다.
- 채택하지 않은 이유: 면접에서 물어보는 건 설계 판단이지 문법이 아니다. 그런데 문법 때문에 구현이 늦어지면 설계 깊이까지 얕아진다. 리스크 대비 이득이 작았다.

### 대안 B. Python + FastAPI

- 장점: 작성자가 가장 익숙해 구현이 가장 빠르다.
- 단점: 기업 스택과 다르다는 것을 문서로 변호해야 한다. 동시성 제어를 SQLAlchemy 레벨에서 직접 보여줘야 해서 오히려 설명 부담이 크다.
- 채택하지 않은 이유: JPA 생태계의 락·트랜잭션 도구를 쓰는 편이 "기업 환경에서 일할 수 있다"는 신호로 더 강하다.

## 결정

Java 21 + Spring Boot 4.0.7 (MVC, 동기) + Gradle 9.7.0 + MySQL 8.4 + Redis 7.4 + Flyway + Testcontainers + k6.

WebFlux와 코루틴은 쓰지 않는다. 동시성 제어를 DB 락과 트랜잭션 경계로 정면 돌파하는 그림을 만들기 위해서다. 비동기를 섞으면 3일 안에 설명 가능한 수준이 안 된다.

Spring Boot 버전은 4.0.7이다. 원래 3.x를 계획했지만 Spring Initializr가 3.x 지원을 내렸고(호환 범위 >=4.0.0), 4.1.0은 마이너 GA 직후라 패치가 7번 돈 4.0.x 라인을 골랐다.

## 근거

Java + Spring 경험(saga까지)이 그대로 전이되면서, 생태계는 지원 기업(Kotlin + Spring)과 동일하다. "언어만 다르고 프레임워크·라이브러리·운영 지식은 같다"는 위치가 세 대안 중 가장 방어하기 좋았다.

## 대가

- 지원 기업 스택과 언어가 다르다. "왜 Kotlin이 아닌가"에 답해야 한다. 답은 이 문서다.
- Spring Boot 4.x는 나온 지 얼마 안 된 메이저라 레퍼런스가 3.x보다 적다.

## 되돌리는 비용

언어 변경은 사실상 전체 재작성이라 되돌릴 수 없는 결정이다. Boot 버전 변경은 `build.gradle` 한 줄이라 싸다.
