# ADR-0061. 프론트 데스크(F06)는 스펙으로만 남기고 구현하지 않는다

- 날짜: 2026-08-17
- 상태: 채택
- 관련 feature: F06 (미착수), ADR-0057의 후속
- **결정자: 관리자**

## 문제

지금 시스템은 예약까지만 있다. 손님이 도착했을 때 **몇 호실에 들어가는지**를 다루는 층이 없다. 체크인 API는 상태만 바꾸고, 방은 사람이 수기로 나눠준다고 가정한다 — [ADR-0057](ADR-0057-방-배정은-범위-밖.md)이 대가로 적어둔 항목이다.

2026-08-16에 그 빠진 층의 기획서를 만들었다. 관리자가 화면 시안을 검토하면서 요구를 두 번 더했다.

> "객실별로 어떤 손님이 언제부터 언제까지 묵는 지 타임라인 그래프가 필요해. 그리고 객실 배정시 어떤 호실에 배정할지 선택이 가능해야하고 (…) 선택하면서 해당 호실을 선택할수있는지 없는지를 보여줘야할거같다."

> "선택불가여부는 현재 예약 현황과 이미 묵고있는 사람들을 고려해서, **이곳에 배정하면 다른 손님이 묵지 못한다** — 라는 알고리즘이 들어가야해."

이 두 가지가 규모를 바꿨다. **10~13시간에서 16~22시간(리뷰 포함 ~25시간)으로 올랐다.** 마감이 2026-08-17 밤인데, 남은 확정 작업(제출 문서 마무리, 남은 승인 게이트)과 양립하지 않는 크기다.

## 결정

**F06을 구현하지 않는다. 기획서를 스펙으로 남긴다.**

관리자 판단:

> "스펙으로만 남기고. 마무리하고 시간 남으면 진행하자"

**마감 마무리를 먼저 끝내고, 시간이 남으면 그때 착수한다.** 착수하지 못하고 끝나도 그대로 둔다.

## 근거

**규모를 키운 것이 알고리즘이었고, 그 알고리즘이 곧 가치였다.** "지금 비어 있나"만 보는 판정은 몇 줄이면 되지만, "여기 넣으면 뒤에 오는 손님이 묵지 못하는가"는 구간 배정 문제다. 값이 있어서 늘어난 것이지 군더더기가 아니다. 그래서 **줄여서 만드는 선택**(판정을 1단으로 낮춘다)은 만들 이유 자체를 없앤다.

**그런데 이 과제가 증명해야 하는 것에는 새 패턴을 보태지 않는다.** 동시 체크인 경합의 방어는 F01과 같은 계열이다 — 조건부 갱신 + DB 제약 최후 방어선. ADR-0058이 F02를 뺄 때 쓴 논리와 같다. **같은 증명의 두 번째 표본**이지 새로운 증명이 아니다.

**남은 시간을 어디에 쓰는가의 문제였다.** 부하테스트로 이미 증명한 것을 수치화하고 제출 문서를 다듬는 쪽이, 같은 급의 증명을 한 번 더 만드는 쪽보다 낫다고 봤다.

## 검토한 대안

### 대안 A. 전부 구현 (16~22시간)

- 장점: 시연 가치가 가장 크다. 타임라인과 가상 배정 미리보기는 눈에 보이는 결과물이다.
- 채택하지 않은 이유: 마감까지 남은 시간을 전부 쓴다. **제출 문서 마무리를 포기해야 한다.** 만들다 만 기능은 안 만든 기능보다 나쁘다.

### 대안 B. 백엔드만 구현, 화면 생략 (10~14시간)

- 장점: "동시 배정 경합"과 "구간 배정" 두 사례가 코드와 테스트로 남는다.
- 채택하지 않은 이유: 관리자가 요구한 것의 절반(타임라인·선택·미리보기)이 정확히 화면 쪽이다. **화면 없는 배정 API는 관리자가 보려던 것이 아니다.** 시연 가치가 낮은데 비용은 절반 넘게 든다.

## 대가

- **판정 알고리즘이 코드로 존재하지 않는다.** 문서의 반례로만 남는다.
- **ADR-0057의 한계가 그대로 유지된다** — 방 배정은 여전히 사람이 한다.
- 두 모델의 상호 검산(배정 수 = 투숙 중 객실 수 ≤ 판매 수량)을 실제로 돌려보지 못한다. 등식은 문서에만 있다.

## 버려지지 않는 것

**판정 알고리즘의 반례가 문서에 남는다.** 쓸 수 있는 방이 302호(계속 빔)와 303호(8/18부터 점검) 둘뿐이고 2박 손님과 3박 손님이 온다고 할 때 — 2박 손님에게 302호를 주면 3박 손님이 못 묵고, 303호를 주면 둘 다 된다. **짧게 묵는 손님을 짧게 열린 방에 넣고 길게 열린 방을 아껴둔다**는 해법까지 적혀 있다.

이 반례가 있으면 "문제를 몰라서 안 만든 것이 아니라 알아보고 우선순위로 잘랐다"가 된다. ADR-0058이 F02에서 얻은 것과 같은 값이다.

**화면 시안도 실물로 남는다.** 유스케이스별 HTML 시안이 있어, 착수 시점에 무엇을 만들지 다시 정할 필요가 없다.

## 하위 영향

| 대상 | 영향 |
|---|---|
| **ADR-0057** | **뒤집지 않는다.** 배정을 자동화하지 않으므로 그 문서가 예고한 "결정이 틀린 것이 되는 때"에 도달하지 않았다. 이 ADR을 후속 자료로 연결한다 |
| **범위 문서 D3** | 그대로 유지 (체크인 시점·체크인 날짜 순서 배정). 사람이 지키는 규칙이라는 전제도 그대로다 |
| **F04** | 배정 검산 등식을 부하테스트 검증에 넣는 안(F06 D4)은 무산. F04 검증 스크립트를 건드릴 일이 없다 |
| **F05** | 데스크 화면(`/desk`)을 만들지 않는다 |

## 되돌리는 비용

**싸다.** 기획서와 화면 시안이 다 있고 코드를 하나도 안 썼으므로 되돌릴 것이 없다. 착수하게 되면 규모 표의 위에서부터 내려간다 — 호실·배정 테이블 → 배정 도메인 → 판정 → 조회 API → 테스트. **화면은 맨 뒤다.** 백엔드만 끝나도 「동시 체크인 경합」 테스트라는 결과물이 남기 때문이다.
